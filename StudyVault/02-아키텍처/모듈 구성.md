# 모듈 구성 (★★)

#ddd #architecture #module-structure #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 대원칙 | **패키지 구성 규칙에 정답은 없다** |
| 기본 | 아키텍처의 **각 영역은 별도 패키지**에 위치 |
| 도메인이 크면 | **하위 도메인마다 별도 패키지** |
| 하위 도메인이 크면 | **애그리거트를 기준으로** 다시 패키지 구성 |
| 배치 규칙 | **애그리거트, 모델, 리포지터리는 같은 패키지**에 위치 |
| 세분화 기준 | 정해진 규칙 없음. 저자 개인 기준은 **한 패키지에 10~15개 미만 타입** |

## ① 영역별 패키지 (그림 2.21)

```
com.myshop
   ├── ui              (표현)
   ├── application     (응용)
   ├── domain          (도메인)
   └── infrastructure  (인프라스트럭처)
```

> [!note] `com.myshop`은 예시 패키지이므로 알맞은 패키지로 대체하면 된다.

## ② 하위 도메인별 패키지 (그림 2.22)

도메인이 크면 하위 도메인으로 나누고 **각 하위 도메인마다 별도 패키지**를 구성한다.

```
com.myshop
   ├── catalog
   │      ├── ui
   │      ├── application
   │      ├── domain
   │      └── infrastructure
   ├── order
   │      ├── ui
   │      ├── application
   │      ├── domain
   │      └── infrastructure
   └── member
          ├── ui
          ├── application
          ├── domain
          └── infrastructure
```

## ③ 애그리거트별 패키지 (그림 2.23)

도메인 모듈은 **도메인에 속한 애그리거트를 기준으로** 다시 패키지를 구성한다.
예: 카탈로그 하위 도메인이 **상품 애그리거트**와 **카테고리 애그리거트**로 구성될 경우

```
com.myshop
   └── catalog
          ├── application
          ├── domain
          │      ├── product      ← 상품 애그리거트
          │      └── category     ← 카테고리 애그리거트
          └── infrastructure
```

> [!important] 배치 규칙
> **애그리거트, 모델, 리포지터리는 같은 패키지에 위치시킨다.**
> 예: `Order`, `OrderLine`, `Orderer`, `OrderRepository` 등은
> `com.myshop.order.domain` 패키지에 위치시킨다.

## ④ 도메인이 복잡할 때 — 모델과 서비스 분리

도메인이 복잡하면 도메인 모델과 도메인 서비스를 별도 패키지에 둘 수도 있다.

| 패키지 | 내용 |
|--------|------|
| `com.myshop.order.domain.order` | **애그리거트** 위치 |
| `com.myshop.order.domain.service` | **도메인 서비스** 위치 |

응용 서비스도 도메인별로 패키지를 구분할 수 있다.

| 패키지 |
|--------|
| `com.myshop.catalog.application.product` |
| `com.myshop.catalog.application.category` |

## 얼마나 세분화할 것인가

> [!tip] 저자의 기준 (p.096)
> - 모듈 구조를 얼마나 세분화해야 하는지에 대해 **정해진 규칙은 없다.**
> - 한 패키지에 너무 많은 타입이 몰려서 **코드를 찾을 때 불편한 정도만 아니면 된다.**
> - 개인적으로는 한 패키지에 가능하면 **10~15개 미만**으로 타입 개수를 유지하려고 노력한다.
> - 이 개수가 넘어가면 **패키지를 분리하는 시도**를 해본다.

```
   타입 개수 ≤ 10~15  →  유지
   타입 개수 > 15     →  패키지 분리 검토
```

> [!warning] 규칙에 매몰되지 말 것
> 정답이 없는 영역이므로, **"코드를 찾기 불편한가?"** 라는 실용적 기준으로 판단한다.
