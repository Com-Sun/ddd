# 도메인 영역의 주요 구성요소 (★★★)

#ddd #architecture #domain-model #concept

## Overview Table (표 2.1 — 5대 구성요소)

| 요소 | 설명 |
|------|------|
| **엔티티(Entity)** | 고유의 식별자를 갖는 객체로 **자신의 라이프 사이클**을 갖는다. 주문(Order), 회원(Member), 상품(Product)과 같이 도메인의 고유한 개념을 표현한다. 도메인 모델의 **데이터를 포함하며 해당 데이터와 관련된 기능을 함께 제공**한다 |
| **밸류(Value)** | 고유의 식별자를 갖지 **않는** 객체로 주로 **개념적으로 하나인 값**을 표현할 때 사용된다. `Address`, `Money` 같은 타입. **엔티티의 속성뿐 아니라 다른 밸류 타입의 속성으로도** 사용할 수 있다 |
| **애그리거트(Aggregate)** | 연관된 **엔티티와 밸류 객체를 개념적으로 하나로 묶은 것**. `Order` 엔티티, `OrderLine` 밸류, `Orderer` 밸류를 '주문' 애그리거트로 묶을 수 있다 |
| **리포지터리(Repository)** | 도메인 모델의 **영속성을 처리**한다. DB 테이블에서 엔티티 객체를 로딩하거나 저장하는 기능을 제공한다 |
| **도메인 서비스(Domain Service)** | **특정 엔티티에 속하지 않은 도메인 로직**을 제공한다. '할인 금액 계산'처럼 로직이 **여러 엔티티와 밸류를 필요로 하면** 도메인 서비스에서 구현한다 |

> [!note] 출처
> 이 구성요소들 역시 **에릭 에반스가 소개한 패턴**에 기반하고 있다.

## 엔티티와 밸류 (§2.4.1)

> [!danger] ★ 가장 중요한 구분 — 도메인 모델의 엔티티 ≠ DB 모델의 엔티티
> 저자도 개발 초년 시절 **DB 테이블의 엔티티와 도메인 모델의 엔티티를 구분하지 못해 동일하게 만들곤 했다.**
> 경험이 쌓이고 도메인 모델에 대한 이해가 높아지면서, 실제 **도메인 모델의 엔티티와 DB 관계형 모델의 엔티티는 같은 것이 아님**을 알게 되었다.

### 차이 ① — 도메인 모델의 엔티티는 기능을 함께 제공한다

```java
public class Order {
    // 주문 도메인 모델의 데이터
    private OrderNo number;
    private Orderer orderer;
    private ShippingInfo shippingInfo;

    // ★ 도메인 모델 엔티티는 도메인 기능도 함께 제공
    public void changeShippingInfo(ShippingInfo newShippingInfo) {
        ...
    }
}
```

| 구분 | 성격 |
|------|------|
| **DB 모델의 엔티티** | 데이터만 담는 **데이터 구조** |
| **도메인 모델의 엔티티** | **데이터와 함께 기능을 제공하는 객체** |

> [!tip]
> 도메인 관점에서 기능을 구현하고, **기능 구현을 캡슐화**해서 데이터가 임의로 변경되는 것을 막는다.

### 차이 ② — 도메인 모델의 엔티티는 밸류 타입을 가질 수 있다

두 개 이상의 데이터가 **개념적으로 하나인 경우 밸류 타입**을 이용해서 표현할 수 있다.

```java
public class Orderer {
    private String name;
    private String email;
}
```

**RDBMS는 밸류 타입을 제대로 표현하기 힘들다 (그림 2.15)**

| 방식 | 테이블 | 문제 |
|------|--------|------|
| ① 한 테이블에 주문자 정보 함께 넣기 | `ORDERS(ORDER_NUMBER, ORDERER_NAME, ORDERER_EMAIL, ...)` | **주문자라는 개념이 드러나지 않고** 개별 데이터만 드러난다 |
| ② 별도 테이블로 분리 | `ORDERS`, `ORDERER(ORDER_NUMBER, NAME, EMAIL)` | 이것은 **테이블의 엔티티에 가까우며** 밸류 타입의 의미가 드러나지 않는다 |

```
  RDBMS 표현                          도메인 모델
  ┌──────────────────────┐           ┌─────────────────┐
  │ ORDERS               │           │ Order           │
  │  ORDER_NUMBER        │           │  ├ Orderer      │ ← "주문자"라는
  │  ORDERER_NAME    ────┼── 개념    │  │   ├ name     │    개념이 명확
  │  ORDERER_EMAIL   ────┼── 상실    │  │   └ email    │
  └──────────────────────┘           └─────────────────┘
```

> [!important]
> 도메인 모델의 `Orderer`는 **주문자라는 개념을 잘 반영**하므로 도메인을 더 잘 이해할 수 있도록 돕는다.

### 밸류는 불변으로 — 변경 시 새 객체로 교체

```java
public class Order {
    private ShippingInfo shippingInfo;

    // 도메인 모델 엔티티는 도메인 기능도 함께 제공
    public void changeShippingInfo(ShippingInfo newShippingInfo) {
        checkShippingInfoChangeable();
        setShippingInfo(newShippingInfo);
    }

    private void setShippingInfo(ShippingInfo newShippingInfo) {
        if (newShippingInfo == null) throw new IllegalArgumentException();
        // ★ 밸류 타입의 데이터를 변경할 때는 새로운 객체로 교체한다.
        this.shippingInfo = newShippingInfo;
    }
}
```

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "도메인 영역 5대 구성요소" | 엔티티 / 밸류 / **애그리거트** / 리포지터리 / **도메인 서비스** |
| "고유 식별자 + 라이프 사이클" | **엔티티** |
| "식별자 없음, 개념적으로 하나인 값" | **밸류** |
| "연관 엔티티·밸류를 하나로 묶은 것" | **애그리거트** |
| "도메인 모델의 영속성 처리" | **리포지터리** |
| "특정 엔티티에 속하지 않은 도메인 로직" | **도메인 서비스** |
| "할인 금액 계산(상품·쿠폰·회원등급·구매금액)" | **도메인 서비스** |
| "도메인 모델 엔티티 = DB 엔티티?" | **거짓.** 도메인 엔티티는 **기능도 제공** |
| "밸류는 다른 밸류의 속성이 될 수 있나?" | **가능하다** |
| "밸류 데이터 변경 방법" | **새로운 객체로 교체** |
| "RDBMS로 밸류를 표현하면?" | 개념이 드러나지 않거나 **테이블 엔티티처럼 되어버린다** |
