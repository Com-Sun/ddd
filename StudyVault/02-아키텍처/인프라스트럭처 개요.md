# 인프라스트럭처 개요 (★★)

#ddd #architecture #infrastructure #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 역할 | 표현·응용·도메인 영역을 **지원**하는 보조 기능 |
| 원칙 | 세 영역이 인프라 기능을 **직접 사용하기보다** 인터페이스를 정의하고 인프라가 구현 |

| 예외 없는 규칙 | **표현 영역은 항상 인프라스트럭처 영역과 쌍을 이룬다** |

## 기본 원칙 — 인터페이스를 통해 사용하라

인프라스트럭처는 표현 영역, 응용 영역, 도메인 영역을 **지원**한다. [[DIP]]에서 언급한 것처럼,
도메인 영역과 응용 영역에서 **인프라스트럭처의 기능을 직접 사용하는 것보다**,
이 두 영역에 **정의한 인터페이스를 인프라스트럭처 영역에서 구현**하는 것이 **시스템을 더 유연하고 테스트하기 쉽게** 만들어준다.

## ★ 그러나 — 구현의 편리함도 중요하다

> [!important] 핵심 메시지 (p.092~093)
> **구현의 편리함은 DIP가 주는 다른 장점(변경의 유연함, 테스트가 쉬움)만큼 중요하다.**
> DIP의 장점을 해치지 않는 범위에서 **응용 영역과 도메인 영역에서 구현 기술에 대한 의존을 가져가는 것이 나쁘지 않다.**
>
> 응용 영역과 도메인 영역이 **인프라스트럭처에 대한 의존을 완전히 갖지 않도록 시도하는 것은**
> 자칫 **구현을 더 복잡하고 어렵게 만들 수 있다.**

### 타협 예 ① — 도메인 모델에 JPA 애너테이션

```java
// 구현의 편리함을 위해 인프라스트럭처에 대한 의존을 일부 도메인에 넣은 코드.
// JPA의 @Entity 애너테이션을 이용해서 엔티티를 저장.
// @Table을 사용하면 XML 설정을 사용하는 것보다 편리하게 테이블 이름을 지정할 수 있다.
@Entity
@Table(name = "purchase_order")
public class Order {
    ...
}
```

### 타협 예 ② — `@Transactional`

> [!tip] 좋은 예: 스프링의 `@Transactional`
> `@Transactional`을 사용하면 **한 줄로 트랜잭션을 처리**할 수 있다.
> 코드에서 스프링에 대한 의존을 없애려면 **복잡한 스프링 설정을 사용해야 한다.**
> 의존은 없앴지만 **특별히 테스트를 더 쉽게 할 수 있다거나 유연함이 증가하지 않는다.**

| 선택 | 얻는 것 | 잃는 것 |
|------|---------|---------|
| `@Transactional` 사용 | **한 줄로 처리**, 코드 단순 | 스프링에 대한 의존 |
| 의존 제거 시도 | 이론적 순수성 | **복잡한 설정**, 테스트·유연성 이득 **없음** |

```
   의존 제거의 이득  ⚖️  구현 복잡도 증가
                     │
                     └─▶ 이득이 없다면 의존을 받아들여라
```

## 표현 영역은 항상 인프라스트럭처와 쌍을 이룬다

> [!warning] 이건 타협이 아니라 필연이다
> **표현 영역은 항상 인프라스트럭처 영역과 쌍을 이룬다.**

| 사용 기술 | 표현 영역 구현 방식 |
|-----------|---------------------|
| 스프링 MVC로 웹 요청 처리 | **스프링 MVC 프레임워크에 맞게** 표현 영역을 구현해야 한다 |
| 서블릿(Servlet)으로 REST API 서버 구축 | **서블릿에 맞게** 웹 요청 처리 부분을 구현해야 한다 |

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "인프라스트럭처의 역할" | 표현·응용·도메인 영역을 **지원**하는 보조 기능 |
| "도메인 모델에 `@Entity`를 붙여도 되나?" | **된다.** 구현의 편리함도 중요 |
| "`@Transactional` 의존을 없애야 하나?" | **불필요.** 복잡해지기만 하고 이득이 없다 |
| "의존을 완전히 제거하려 하면?" | 구현이 **더 복잡하고 어려워질 수 있다** |
| "표현 영역과 인프라의 관계" | **항상 쌍을 이룬다** |
| "판단 기준" | **DIP의 장점을 해치지 않는 범위**에서 의존 허용 |
