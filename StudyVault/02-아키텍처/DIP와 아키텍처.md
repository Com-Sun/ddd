# DIP와 아키텍처 (★★★)

#ddd #architecture #dip #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 저수준 모듈 | **인프라스트럭처 영역** |
| 고수준 모듈 | **응용 영역 + 도메인 영역** |
| 구조 변화 | 인프라스트럭처가 **가장 하단**에 있던 계층형 구조 → 인프라스트럭처가 **응용·도메인에 의존(상속)** 하는 구조 |
| 효과 | 도메인·응용에 **영향을 주지 않거나 최소화하면서 구현 기술 변경 가능** |
| ★ 현실적 조언 | **DIP를 항상 적용할 필요는 없다** |

## 구조 변화 (그림 2.12)

```
[ 계층형 구조 ]                    [ DIP 적용 구조 ]

    표현                                 표현
     │                                    │
    응용                                 응용 ◀────┐
     │                                    │        │
   도메인                               도메인 ◀───┤ 의존(상속)
     │                                             │
인프라스트럭처  ◀── 최하단           인프라스트럭처 ─┘
```

> [!important] 역할 배치
> - **인프라스트럭처 영역** = 구현 기술을 다루는 **저수준 모듈**
> - **응용 영역 + 도메인 영역** = **고수준 모듈**
>
> 아키텍처에 DIP를 적용하면 **인프라스트럭처 영역이 응용 영역과 도메인 영역에 의존(상속)하는 구조**가 된다.

인프라스트럭처에 위치한 클래스가 **도메인이나 응용 영역에 정의한 인터페이스를 상속받아 구현**하는 구조가 되므로,
**도메인과 응용 영역에 대한 영향을 주지 않거나 최소화하면서 구현 기술을 변경하는 것이 가능하다.**

## 실제 배치 예 (그림 2.13)

```
[ 응용 영역 ]                                 [ 인프라스트럭처 영역 ]
  OrderService ────▶ «interface» Notifier ◀───── EmailNotifier
                          (응용에 위치)

[ 도메인 영역 ]
  CalculateDiscountService
        │
        ├──────▶ «interface» CustomerRepository ◀──── MyBatisCustomerRepository
        └──────▶ «interface» RuleDiscounter     ◀──── DroolsRuleDiscounter
                          (도메인에 위치)
```

## 확장 시나리오 (그림 2.14)

> [!tip] 요구사항: "이메일뿐 아니라 **SMS로도 통지**해야 한다"
> 응용 영역의 `OrderService`는 **변경할 필요가 없다.**
> 두 통지 방식을 함께 제공하는 `Notifier` 구현 클래스를 **인프라스트럭처 영역에 추가**하면 된다.

```
  OrderService ────▶ «interface» Notifier
                            △
                            ╎
                    EmailSmsNotifier      ← 인프라에 새 구현만 추가
```

> [!tip] 요구사항: "마이바티스(MyBatis) 대신 **JPA를 구현 기술로 사용**하고 싶다"
> JPA를 이용한 `CustomerRepository` 구현 클래스를 **인프라스트럭처 영역에 추가**하면 된다.

| 변경 요청 | 손대야 하는 곳 | 손대지 않아도 되는 곳 |
|-----------|----------------|------------------------|
| 이메일 → 이메일 + SMS | 인프라에 `Notifier` 구현 추가 | **응용 영역 `OrderService`** |
| MyBatis → JPA | 인프라에 `CustomerRepository` 구현 추가 | **도메인·응용 영역** |

## ★ DIP를 항상 적용할 필요는 없다

> [!warning] 현실적인 조언 (p.079)
> DIP를 **항상 적용할 필요는 없다.**
> - 사용하는 구현 기술에 따라 완벽한 DIP를 적용하기보다는, **구현 기술에 의존적인 코드를 도메인에 일부 포함하는 게 효과적일 때도 있다.**
> - 또는 **추상화 대상이 잘 떠오르지 않을 때도 있다.**
>
> 이럴 때는 무조건 DIP를 적용하려고 시도하지 말고, **DIP의 이점을 얻는 수준에서 적용 범위를 검토**해 보자.

```
   완벽한 DIP  ◀──────────────────────▶  실용적 타협
   (이론적 순수)                          (구현 편리함)
              ▲
              └── DIP의 이점(변경 유연함·테스트 용이)을
                  얻는 수준에서 범위를 결정한다
```

> [!note] 이어지는 논의
> 이 "실용적 타협"은 [[인프라스트럭처 개요]]와 [[도메인 구현과 DIP]]에서 구체적인 예(JPA 애너테이션, `@Transactional`)로 다시 다룬다.

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "아키텍처에서 저수준 모듈은?" | **인프라스트럭처 영역** |
| "아키텍처에서 고수준 모듈은?" | **응용 영역 + 도메인 영역** |
| "DIP 적용 후 의존 방향" | 인프라스트럭처 → **응용·도메인** |
| "SMS 통지 추가 시 OrderService를 고쳐야 하나?" | **아니다.** 인프라에 구현만 추가 |
| "MyBatis → JPA 교체 시 도메인 변경?" | **불필요** |
| "DIP는 항상 적용해야 한다?" | **거짓.** 이점을 얻는 수준에서 범위 검토 |
