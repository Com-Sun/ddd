# 계층 구조 아키텍처 (★★★)

#ddd #architecture #layered-architecture #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 의존 방향 | **상위 계층 → 하위 계층** 단방향. 하위는 상위에 의존하지 않는다 |
| 엄격한 적용 | 상위 계층은 **바로 아래 계층에만** 의존 |
| 유연한 적용 | 구현의 편리함을 위해 **더 아래 계층에 바로 의존**하기도 한다 |
| **치명적 문제** | 표현·응용·도메인 계층이 **인프라스트럭처 계층에 종속**된다 |
| 문제 ① | **테스트가 어렵다** |
| 문제 ② | **구현 방식(기능 확장) 변경이 어렵다** |
| 해답 | **DIP** |

## 계층 구조

```
   ┌────────────────────────┐
   │        표현             │
   ├────────────────────────┤
   │        응용             │
   ├────────────────────────┤
   │       도메인            │
   ├────────────────────────┤
   │    인프라스트럭처       │  ◀── 가장 하단
   └────────────────────────┘
          의존 방향: 위 → 아래 (단방향)
```

- 표현 영역과 응용 영역은 도메인 영역을 사용하고, 도메인 영역은 인프라스트럭처 영역을 사용하므로 **계층 구조를 적용하기에 적당해 보인다.**
- 도메인의 복잡도에 따라 **응용과 도메인을 분리하기도 하고 한 계층으로 합치기도** 하지만 전체적인 아키텍처는 계층 구조를 따른다.

> [!important] 계층 구조의 의존 규칙
> 상위 계층에서 하위 계층으로의 **의존만 존재**하고, 하위 계층은 상위 계층에 의존하지 않는다.
> - 표현 → 응용 ⭕ / 응용 → 도메인 ⭕
> - 인프라스트럭처 → 도메인 ❌ / 도메인 → 응용 ❌

### 엄격한 적용 vs 유연한 적용

| 방식 | 내용 |
|------|------|
| 엄격한 적용 | 상위 계층은 **바로 아래 계층에만** 의존해야 한다 |
| 유연한 적용 | 구현의 편리함을 위해 응용 계층이 **도메인을 건너뛰고 인프라스트럭처에 바로 의존**하기도 한다 |

## 문제 — 인프라스트럭처에 종속된다

도메인과 응용 계층은 룰 엔진과 DB 연동을 위해 **인프라스트럭처 모듈에 의존**하게 된다.

```java
// 인프라스트럭처 영역 — Drools 룰 엔진 사용
public class DroolsRuleEngine {
    private KieContainer kContainer;

    public DroolsRuleEngine() {
        KieServices ks = KieServices.Factory.get();
        kContainer = ks.getKieClasspathContainer();
    }

    public void evalute(String sessionName, List<?> facts) {
        KieSession kSession = kContainer.newKieSession(sessionName);
        try {
            facts.forEach(x -> kSession.insert(x));
            kSession.fireAllRules();
        } finally {
            kSession.dispose();
        }
    }
}
```

```java
// 응용 영역 — 인프라스트럭처를 직접 사용
public class CalculateDiscountService {
    private DroolsRuleEngine ruleEngine;

    public CalculateDiscountService() {
        ruleEngine = new DroolsRuleEngine();       // ← 직접 생성
    }

    public Money calculateDiscount(List<OrderLine> orderLines, String customerId) {
        Customer customer = findCustomer(customerId);

        MutableMoney money = new MutableMoney(0);       // ← Drools에 특화된 타입
        List<?> facts = Arrays.asList(customer, money);
        facts.addAll(orderLines);
        ruleEngine.evalute("discountCalculation", facts);   // ← Drools 세션 이름
        return money.toImmutableMoney();
    }
}
```

### 문제 ① — 테스트가 어렵다

> [!danger]
> `CalculateDiscountService`만 테스트하기 어렵다.
> 테스트하려면 `RuleEngine`이 **완벽하게 동작해야** 하고, `RuleEngine` 클래스와 **관련 설정 파일을 모두 만든 이후에야** 비로소 올바르게 동작하는지 확인할 수 있다.

### 문제 ② — 구현 방식 변경이 어렵다 (숨은 의존)

> [!warning] 겉으로는 의존이 없어 보이지만…
> 코드만 보면 Drools가 제공하는 타입을 직접 사용하지 않으므로 Drools 자체에 의존하지 않는다고 생각할 수 있다. **하지만 실제로는 완전히 의존하고 있다.**

| 숨은 의존 | 설명 |
|-----------|------|
| `"discountCalculation"` 문자열 | **Drools의 세션 이름**이다. 세션 이름을 변경하면 `CalculateDiscountService` 코드도 함께 변경해야 한다 |
| `MutableMoney` 타입 | 룰 적용 **결괏값을 보관하기 위해 추가한 타입**. 다른 방식을 사용했다면 필요 없는 타입이다 |

```
   CalculateDiscountService
        │ (겉보기: Drools 타입 미사용 → 독립적으로 보임)
        │
        └── 실제: "discountCalculation" 세션명 + MutableMoney
                 ▼
            ★ Drools에 완전하게 의존 ★
```

> [!danger] 결과
> 이런 상황에서 Drools가 아닌 **다른 구현 기술을 사용하려면 코드의 많은 부분을 고쳐야 한다.**

## 정리

```
   인프라스트럭처에 의존
          │
          ├──▶ ① 테스트 어려움
          └──▶ ② 기능 확장(구현 교체) 어려움
                        │
                        ▼
                    해답: DIP
```

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "계층 구조의 의존 방향" | 상위 → 하위 **단방향** |
| "도메인이 응용에 의존한다?" | **거짓** |
| "응용이 인프라에 바로 의존해도 되나?" | 유연한 적용에서는 **가능** |
| "계층 구조의 근본 문제" | 표현·응용·도메인이 **인프라스트럭처에 종속** |
| "종속되면 생기는 두 문제" | **테스트 어려움 + 구현 변경 어려움** |
| "Drools 타입을 안 쓰면 독립적인가?" | **거짓.** 세션 이름 문자열·전용 타입으로 **여전히 의존** |
| "이 문제의 해답" | **DIP (의존 역전 원칙)** |
