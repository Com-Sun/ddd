## 1. 핵심 용어 한 줄 정의 → [[도메인이란]], [[도메인 모델]], [[애그리거트]], [[바운디드 컨텍스트]]

| 용어 | 한 줄 정의 |
|------|-----------|
| **도메인(Domain)** | 소프트웨어로 **해결하고자 하는 문제 영역** |
| **하위 도메인(Subdomain)** | 한 도메인을 기능 단위로 나눈 영역 |
| **도메인 모델** | 특정 도메인을 **개념적으로 표현**한 것 |
| **엔티티(Entity)** | **식별자를 갖는** 객체. 자신의 라이프 사이클을 갖는다 |
| **밸류(Value)** | 식별자가 **없고**, **개념적으로 완전한 하나**를 표현 |
| **애그리거트(Aggregate)** | **관련 객체를 하나로 묶은 군집** |
| **애그리거트 루트** | 애그리거트 전체를 관리하는 **대표 엔티티** |
| **리포지터리(Repository)** | 도메인 모델의 **영속성을 처리**. 단위는 **애그리거트** |
| **도메인 서비스** | **특정 엔티티에 속하지 않은** 도메인 로직. **상태 없음** |
| **응용 서비스** | 사용자 요청 기능 실행 + **흐름 제어** + **트랜잭션 관리** |
| **바운디드 컨텍스트** | **모델의 경계**. 논리적으로 **한 개의 모델**을 갖는다 |
| **유비쿼터스 언어** | 전문가·관계자·개발자가 쓰는 **공통 언어** |
| **CQRS** | **Command Query Responsibility Segregation** — 명령/조회 모델 분리 |

## 2. 엔티티 vs 밸류 → [[엔티티와 식별자]], [[밸류 타입]]

| 기준 | **엔티티** | **밸류** |
|------|-----------|---------|
| 식별자 | **있음** | 없음 |
| **동등성 판단** | **식별자만** 비교 | **모든 속성** 비교 |
| 가변성 | 상태가 바뀔 수 있음 | **불변 권장** |
| 변경 방법 | 자신의 필드 변경 | **새 객체 생성으로 교체** |
| JPA 매핑 | **`@Entity`** | **`@Embeddable`** |
| 예 | `Order`, `Member`, `Article` | `Money`, `Address`, `Receiver`, `ShippingInfo` |

**식별자 생성 4방식** → [[엔티티와 식별자]], [[식별자 생성 기능]]

| 방식 | 식별자 확보 시점 |
|------|------------------|
| **특정 규칙** (주문번호·운송장번호) | 엔티티 생성 **전** |
| **UUID / Nano ID** | 엔티티 생성 **전** |
| **값 직접 입력** (아이디·이메일) | 엔티티 생성 **전** |
| **DB 일련번호(자동 증가)** | **저장 후** ⚠️ |

## 4. DIP 공식 → [[DIP]], [[DIP와 아키텍처]]

```
   고수준 모듈 = 의미 있는 단일 기능        (도메인 · 응용 영역)
   저수준 모듈 = 하위 기능의 실제 구현       (인프라스트럭처 영역)

   [ DIP 적용 전 ]  고수준 ──▶ 저수준
   [ DIP 적용 후 ]  고수준 ──▶ «interface» ◀╌╌ 저수준
                              (고수준에 위치!)
```

| 체크 | 규칙 |
|------|------|
| ✅ | 인터페이스는 **고수준 모듈 관점에서 도출** |
| ✅ | 인터페이스는 **고수준 모듈에 위치** |
| ❌ | `RuleEngine` — **저수준(룰 엔진) 관점** 이름 → 잘못된 DIP |
| ⭕ | `RuleDiscounter` — **고수준(도메인) 관점** 이름 |
| 💡 | **DIP를 항상 적용할 필요는 없다** — 구현의 편리함도 중요 |

## 5. 애그리거트 핵심 규칙 → [[애그리거트]], [[애그리거트 루트]], [[트랜잭션 범위]]

| 규칙 | 내용 |
|------|------|
| **경계 설정 기준** | **도메인 규칙과 요구사항**. **함께 생성·변경**되는가 |
| **"A가 B를 갖는다"** | **한 애그리거트를 의미하지 않는다** (상품 vs 리뷰) |
| **크기 경험칙** | 대부분 **엔티티 1개**. 2개 이상은 드물다 |
| **접근 규칙** | 루트를 통해 **간접적으로만** 접근 |
| **두 가지 습관** | ① **공개 set 메서드 금지** ② **밸류는 불변** |
| **트랜잭션 범위** | **한 트랜잭션 = 한 애그리거트** |
| **예외 3가지** | **팀 표준 / 기술 제약 / UI 구현의 편리** |
| **애그리거트 간 참조** | **ID 참조** (직접 참조 ❌) |
| **1-N 연관** | **구현에 반영하지 않는다** → 상품 쪽에서 **N-1** |
| **M-N 연관** | **단방향만** + 조인 테이블 + **`member of`** |

**애그리거트 판별 흐름**

```
   고유 식별자를 갖는가? ──아니오──▶ 밸류
        │ 예
   독자적인 라이프 사이클을 갖는가? ──예──▶ 별도 애그리거트
        │ 아니오
   같은 애그리거트에 속한 엔티티
```

## 6. JPA 매핑 치트시트 → [[엔티티와 밸류 기본 매핑]], [[밸류 컬렉션 매핑]], [[밸류를 이용한 ID 매핑과 별도 테이블 매핑]]

| 대상 | 애너테이션 |
|------|-----------|
| 애그리거트 루트 | **`@Entity`** |
| 밸류 | **`@Embeddable`** |
| 밸류 타입 프로퍼티 | **`@Embedded`** |
| 칼럼 이름 재정의 | **`@AttributeOverride(s)`** |
| 밸류 식별자 | **`@EmbeddedId`** (+ `Serializable` + `equals`/`hashCode`) |
| **두 프로퍼티 → 한 칼럼** | **`AttributeConverter`** + **`@Converter`** / **`@Convert`** |
| 밸류 컬렉션(별도 테이블) | **`@ElementCollection`** + **`@CollectionTable`** |
| 리스트 인덱스 | **`@OrderColumn`** |
| 밸류를 별도 테이블에 | **`@SecondaryTable`** (+ `pkJoinColumns`) |
| 밸류에 **상속**이 필요 | **`@Entity`** + `@Inheritance` + `@DiscriminatorColumn` |
| 영속성 전파(`@Entity` 컬렉션) | **`cascade = {PERSIST, REMOVE}`** + **`orphanRemoval = true`** |
| 접근 방식 | **`@Access(AccessType.FIELD)`** |
| 기본 생성자 | **`protected`** (JPA 프로바이더 전용) |

**필수 규칙**

| 항목 | 값 |
|------|-----|
| `@Converter`의 `autoApply` **기본값** | **`false`** |
| `@Embeddable`에 `cascade`가 필요한가 | **불필요** |
| `@OneToOne`/`@OneToMany`의 `cascade` 기본값 | **없음** → 반드시 지정 |
| `@Access` 미지정 시 결정 기준 | **`@Id`/`@EmbeddedId`의 위치** |

**`clear()` 성능 공식** → [[밸류 컬렉션 매핑]]

```
   @Entity + @OneToMany 컬렉션.clear()   →  SELECT 1회 + DELETE N회
   @Embeddable + @ElementCollection.clear() →  DELETE 1회      ⭕
```

**카타시안 조인 공식** → [[애그리거트 로딩 전략]]

```
   결과 행 수 = 컬렉션A 개수 × 컬렉션B 개수
   예) 이미지 20 × 옵션 15 = 300행   (실제 필요: 1+20+15 = 36행)
```

## 7. 조회 기능 치트시트 → [[검색을 위한 스펙]], [[스펙 조합]], [[정렬 지정하기]], [[페이징 처리하기]]

| 기능 | API |
|------|-----|
| 스펙 인터페이스 | `Specification<T>` — **`toPredicate(root, query, cb)`** |
| 스펙은 **함수형 인터페이스** | **람다로 생성 가능** |
| 정적 메타 모델 | **`@StaticMetamodel`** + 클래스명 + **`_`** |
| 스펙 조합 (디폴트) | **`and()`, `or()`** |
| 스펙 조합 (정적) | **`not()`, `where()`** |
| null 안전 시작점 | **`Specification.where(nullable)`** |
| 정렬 | **`OrderBy`** 메서드명 / **`Sort`** 인자 |
| 정렬 결합 | **`Sort.by("a").ascending().and(Sort.by("b").descending())`** |
| 페이징 | **`Pageable`** / **`PageRequest.of(page, size)`** |
| 처음 N개 | **`findFirst3By...`** / `findTop3By...` (숫자 없으면 **1개**) |

**★ COUNT 쿼리 실행 규칙** → [[페이징 처리하기]]

| 메서드 | 리턴 | COUNT |
|--------|------|-------|
| `findByXxx(..., Pageable)` | `Page` | **⭕ 실행** |
| `findByXxx(..., Pageable)` | `List` | **❌ 안 함** |
| **`findAll(Specification, Pageable)`** | **`List`여도** | **⭕ 실행** ⚠️ |

**★ 페이지 번호는 0부터** — `PageRequest.of(1, 10)` = **11~20번째**

**조회 전용 모델 3기법**

| 기법 | 핵심 |
|------|------|
| **조회 전용 DAO + 조인** → [[ID 참조와 조회 성능]] | N+1 해결 |
| **동적 인스턴스** → [[동적 인스턴스를 이용한 조회]] | JPQL **`new`** + 완전한 클래스 이름 |
| **`@Subselect`** → [[하이버네이트 Subselect 사용]] | **`@Subselect` + `@Immutable` + `@Synchronize`** |

## 8. 응용 서비스·표현 영역 원칙 → [[응용 서비스의 역할]], [[메서드 파라미터와 값 리턴]], [[표현 영역에 의존하지 않기와 트랜잭션 처리]]

| 원칙 | 내용 |
|------|------|
| 응용 서비스가 복잡하다 | **도메인 로직이 새어 들어온 신호** |
| 도메인 로직 분산의 폐해 | **응집도 ↓ + 코드 중복 ↑ → 변경 어려움 → 소프트웨어 가치 ↓** |
| 파라미터 2개 이상 | **별도 데이터 클래스** |
| **리턴** | **표현 영역에서 필요한 데이터만** (애그리거트 ❌) |
| **파라미터 금지 타입** | `HttpServletRequest`, `HttpSession` 등 **표현 영역 기술** |
| 가장 심각한 위반 | 응용 서비스가 **세션·쿠키를 조작** |
| 인터페이스 | **명확히 필요하기 전까지 만들지 않는다** (Mockito가 클래스도 대역 생성) |
| 트랜잭션 롤백 조건 | **`RuntimeException`** |
| 조회만 하는 서비스 | **생략 가능** |

**값 검증** → [[값 검증]]

| 항목 | 내용 |
|------|------|
| 원칙 | **모든 값 검증은 응용 서비스에서** |
| 익셉션 즉시 발생의 문제 | **첫 오류만 알려줌 → 나쁜 UX** |
| 해법 A | 에러를 모아 **하나의 익셉션**(`ValidationErrorException`) |
| 해법 B | **표현 영역에서 형식 검증** + 응용 서비스는 논리적 오류 |
| 저자의 현재 입장 | **응용 서비스에서 필수 값 + 논리적 오류 모두** |

**권한 검사 3위치** → [[권한 검사]]

| 위치 | 수단 |
|------|------|
| **표현 영역** (URL) | **서블릿 필터** |
| **응용 서비스** (메서드) | **AOP 애너테이션** (`@PreAuthorize`) |
| **도메인** (개별 객체) | **직접 권한 검사 로직** (애그리거트 로딩 필요) |

## 9. 도메인 서비스 판별 공식 → [[도메인 서비스]]

```
   애그리거트의 상태를 변경하는가?  또는  상태 값을 계산하는가?
        │ 예                                    │ 아니오
        ▼                                       ▼
   도메인 로직                              응용 로직 → 응용 서비스
        │
        ├─ 한 애그리거트에 적합? ──▶ 애그리거트에 구현
        └─ 넣기에 부적합       ──▶ 도메인 서비스
```

| 항목 | 내용 |
|------|------|
| 도메인 서비스의 특징 | **상태 없이 로직만** |
| 필요한 상태 | **파라미터로 전달** |
| 사용 상황 2가지 | **계산 로직 / 외부 시스템 연동** |
| 애그리거트에 전달하는 주체 | **응용 서비스** |
| **DI 주입** | ❌ 데이터 아님 · 저장 대상 아님 · 일부 기능만 사용 |
| 인터페이스가 필요한 때 | **로직이 고정되지 않음** / **외부 시스템·별도 엔진** 사용 |

## 10. 트랜잭션 잠금 비교 → [[선점 잠금]], [[비선점 잠금]], [[오프라인 선점 잠금]]

| 관점 | **선점 잠금** | **비선점 잠금** | **오프라인 선점 잠금** |
|------|--------------|----------------|----------------------|
| 다른 이름 | 비관적 잠금 | 낙관적 잠금 | — |
| 적용 범위 | **한 트랜잭션** | 여러 트랜잭션 가능 | **여러 트랜잭션에 걸쳐** |
| 처리 시점 | **진입 시 대기(블로킹)** | **커밋 시 감지(사후 실패)** | **진입 시 차단(사전 방지)** |
| 구현 | **`for update`** / `PESSIMISTIC_WRITE` | **`@Version`** | **별도 잠금 저장소 + 유효 시간** |
| 스프링 | **`@Lock`** | (자동) | `LockManager` 직접 구현 |
| 위험 | **교착 상태** | 사용자가 작업을 잃음 | 유효 시간 만료로 정상 사용자 실패 |
| 대비책 | **`javax.persistence.lock.timeout`** + `@QueryHints` | 버전을 화면에 왕복 | **주기적 AJAX로 유효 시간 연장** |

**잠금 모드 3종**

| `LockModeType` | 용도 |
|----------------|------|
| **`PESSIMISTIC_WRITE`** | 선점 잠금 |
| `OPTIMISTIC` | 비선점 잠금 |
| **`OPTIMISTIC_FORCE_INCREMENT`** | **비선점 + 강제 버전 증가** → [[강제 버전 증가]] |

**비선점 잠금 쿼리 공식**

```sql
UPDATE aggtable SET version = version + 1, ...
WHERE aggid = ? AND version = 현재버전
```
→ **수정된 행이 0이면 충돌** → `OptimisticLockingFailureException`

**두 익셉션의 의미**

| 익셉션 | 의미 |
|--------|------|
| `VersionConflictException` (응용 서비스) | **이미 누군가가 수정했다** |
| `OptimisticLockingFailureException` (프레임워크) | **거의 동시에 수정했다** |

## 12. 이벤트 치트시트 → [[이벤트 개요]], [[이벤트 핸들러와 디스패처 구현]], [[비동기 이벤트 처리]]

| 항목 | 내용 |
|------|------|
| 이벤트 = | **과거에 벌어진 것** → 이름은 **과거 시제** |
| 상위 타입 | **없다** — 원하는 클래스를 사용 |
| 4대 구성요소 | **이벤트 / 생성 주체 / 디스패처(퍼블리셔) / 핸들러(구독자)** |

**비동기 4방식 비교** → [[비동기 이벤트 처리]], [[이벤트 저장소를 이용한 비동기 처리]]

| 방식 | 이벤트 손실 | 순서 보장 | 복잡도 |
|------|-------------|-----------|--------|
| **로컬 핸들러(`@Async`)** | **유실 가능** | — | **가장 단순** |
| **메시지 큐** | 글로벌 트랜잭션 시 안전 | **기술에 따라 다름** | 중간 |
| **이벤트 저장소 + 포워더** | **없음** | **보장** | 높음 |

## 13. CQRS 판단 매트릭스 → [[CQRS]], [[CQRS 장단점]]

```
                  트래픽 높음
                       │
      단일 모델 고집    │    CQRS 도입 ⭕
      → 유지 비용 ↑     │
   도메인 ──────────────┼────────────── 도메인
   단순                 │              복잡
      CQRS 불필요 ❌     │    CQRS 도입 ⭕
                  트래픽 낮음
```

| 항목 | 명령 모델 | 조회 모델 |
|------|-----------|-----------|
| 데이터 범위 | **한 애그리거트** | **두 개 이상** |
| 적합 기술 | **JPA** | **마이바티스** |
| 응용 서비스 | 필요 | **없어도 된다** |
| 저장소 | RDBMS | RDBMS / NoSQL |

| 장점 | 단점 |
|------|------|
| **도메인 모델 단순 유지** | **코드가 더 많다** |
| **조회 성능 향상 유리** | **더 많은 구현 기술 필요** |

**저장소 동기화**: **이벤트** (실시간 필요 시 **동기 이벤트 + 글로벌 트랜잭션** → **성능 저하**)
