## Q12. 책에 "왜 나뉘는지"가 없는 게 아쉽다. DDD의 best practice·convention을 명확히 하고 싶다

> **한 줄 답: 앵간하면 `@Embeddable`로 한 테이블에서 관리하는 게 맞고, 1:1인데 별도 테이블로 빠지는 건 이득 조건(레거시 스키마 / 데이터가 크다)이 이미 충족된 케이스만이다.**
> **그리고 "왜 나뉘는지"가 책에 없는 것은 누락이 아니라 경계다 — 그건 DDD가 아니라 DB 물리 설계의 질문이다.**

### 왜 책에 없나 — 두 개의 다른 분야

| | 질문 | 다루는 분야 |
|---|---|---|
| **왜 나누나** | 이 컬럼들을 어느 테이블에 둘까 | **DB 물리 설계** (vertical partitioning) |
| **나뉘었을 때 뭐라 부르나** | `ArticleContent`는 엔티티인가 밸류인가 | **DDD / O-R 매핑** |

최범균 책은 두 번째만 다룬다. DDD 문헌 전반이 그렇다 — **"DB가 도메인 모델을 결정하게 두지 말라"가 DDD의 핵심 주장**이기 때문이다.

> ⚠️ **C등급**: Vaughn Vernon(『Implementing DDD』)의 입장으로 검색 결과가 요약하기를, "영속성 표현이 그렇다는 이유로 어떤 개념을 엔티티로 모델링해서는 안 되며, 이는 DDD 원칙이 아니라 **객체-관계 임피던스 불일치** 문제"라고 한다. **검색엔진 요약이고 원문 대조를 못 했다. 인용으로 쓰지 말 것.**

---

### ★ 업계 표준 용어 (convention) — Martin Fowler, PoEAA

찾던 "명확한 개념"에는 이미 이름이 붙어 있다. 아래는 **카탈로그 원문 직접 인용 (A등급)**.

| Fowler 패턴명 | 원문 정의 | `ddd-start2` 대응 |
|---|---|---|
| **Embedded Value** | *"Maps an object into several fields of another object's table."* | **① `@Embedded`** — 정확히 일치 |
| **Serialized LOB** | *"Saves a graph of objects by serializing them into a single large object (LOB), which it stores in a database field."* | ② `EmailSet`→콤마 문자열 (**어시스턴트의 대응 판단**) |
| **Dependent Mapping** | *"Has one class perform the database mapping for a child class."* | ④ `@ElementCollection` (**어시스턴트의 대응 판단**) |
| **Single Table Inheritance** | *"Represents an inheritance hierarchy of classes as a single table that has columns for all the fields of the various classes."* | (예외) `Image`의 `@Inheritance(SINGLE_TABLE)` — 일치 |
| **Identity Field** | *"Saves a database ID field in an object to maintain identity between an in-memory object and a database row."* | 엔티티에만 해당 |

> ⚠️ **③ `@SecondaryTable`에 대응하는 Fowler 패턴은 카탈로그에 없다.** 억지로 이름 붙이지 않는다.

**★ Embedded Value가 기본값인 이유 — 원문**

> *"Many small objects make sense in an OO system that don't make sense as tables in a database. Examples include **currency-aware money objects and date ranges**."*
>
> *"Although the default thinking is to save an object as a table, **no sane person would want a table of money values**."*

Fowler가 든 예시 두 개가 `Money`와 `DateRange`인데, **`Money`는 실제로 `ddd-start2`에 있고 `DateRange`는 [[#Q4]]의 호텔 시나리오에 나왔던 그것**이다.

### ★★ 결정적 — .NET/EF Core가 같은 문제에 같은 답을 냈다

완전히 다른 생태계가 같은 결론에 도달한 것이 "convention"의 증거다. **Microsoft 공식 문서 원문 인용 (A등급)**.

**(1) 저장 위치는 선택 사항이고, 밸류라는 사실은 안 바뀐다** ← [[#Q11]]에 대한 직답

> *"**Table splitting is set up by convention, but you can opt out by mapping the owned type to a different table using ToTable.**"*
>
> *"Table splitting is optional, that is, they can **optionally be mapped to a separate table and still be owned types**."*

**같은 테이블이든 별도 테이블이든 여전히 owned type(=밸류)이다.**

**(2) EF Core 1.x는 JPA와 똑같은 고통을 겪었다**

> *"if using EF Core 1.0 or 1.1, you needed to **store your value object as an EF entity with an ID field**. Then, so it looked more like a value object with no identity, you could **hide its ID**..."*

→ `Image`가 상속 때문에 `@Entity`가 되어 `image_id`를 얻은 것과 **같은 구조의 타협**이다. JPA만의 문제가 아니다.

**(3) ★★★ 밸류에도 "식별"은 있다. 단, 자기 것이 아니다**

> *"under the covers, **owned types do have the identity, but the owner navigation property is part of this identity**. The identity of instances of owned types **is not completely their own**. It consists of three components: The identity of the owner / The navigation property pointing to them / In the case of collections of owned types, an independent component."*

`order_line` DDL에 그대로 겹쳐 보면:

```sql
create index order_line_idx ON order_line (order_number, line_idx);
                                            ▲              ▲
                                 부모의 식별자      컬렉션 인덱스
                                 (component 1)     (component 3)
```

**MS 문서가 말한 3요소 중 1번과 3번이 그대로 나와 있다.**

---

### ★ 이게 왜 더 나은 프레임인가 — 예외가 사라진다

지금까지 쓰던 표현은 **"밸류는 식별자가 없다"** 였다. 그러면 `image_id`나 `article_content.id`가 보일 때마다 예외 설명이 필요하다. 바꿔 쓰면:

> **저장 계층은 반드시 행을 특정할 방법이 필요하다.**
> **그 방법이 부모에서 파생되면 밸류, 자기 자신에서 나오면 엔티티.**

| 대상 | 행을 특정하는 것 | 출처 | 판정 |
|---|---|---|---|
| `Orderer`, `ShippingInfo`, `Password` | 부모 행 자체 | **부모** | 밸류 |
| `ArticleContent` | `article_content.id` = 부모 PK | **부모** | 밸류 |
| `OrderLine` | `(order_number, line_idx)` | **부모 + 인덱스** | 밸류 |
| `CategoryId` (Set) | `(product_id, category_id)` | **부모 + 값 자체** | 밸류 |
| `Image` | `image_id` auto_increment | ⚠️ **자기 자신** | **밸류** (기술 타협) |

`Image`만 어긋나고 그 이유가 코드에 남아 있다 — `@Inheritance(SINGLE_TABLE)` 때문이고, 그 대가로 **상태 변경 메서드를 0개로 유지**해 밸류처럼 다룬다.

### "왜 나누나" — DB 설계 쪽의 답

> ⚠️ **B/C등급**: 아래는 **DB 설계 아티클들의 통용 기준**이다. Fowler·MS 문서 같은 1차 출처가 아니고, DDD 문헌 근거도 아니다.

**나누는 이유**: 행마다 데이터가 너무 커서 스캔이 느림(행 **수**가 아니라 행 **크기**가 문제) / 자주 안 쓰는 큰 컬럼(BLOB·TEXT·JSON)을 분리해 빠른 스토리지·캐시 공간 절약 / 핫·콜드 컬럼의 접근 패턴이 다름

**나누는 게 이득인 조건 (대략적 기준)**
- 핫 컬럼이 평균 행 크기의 **10~20%** 정도로 작을 때
- 콜드 컬럼이 **KB 단위**로 클 때
- 읽기의 **5~10% 미만**만 콜드 컬럼을 필요로 할 때

★ **이 기준을 `ddd-start2`에 대보면 `article_content` 분리는 정당화되지 않는다.** `content`가 `varchar(255)`라 "KB 단위로 크다"에 해당하지 않는다. → [[#Q11]]의 "`product.detail`은 `text`인데 안 나눴다"와 합쳐 보면 **교육용 예시**임이 확실하다.

**실무에서 가장 흔한 이유는 크기가 아니라 레거시다.** Thorben Janssen(JPA 전문 저자)이 `@SecondaryTable`을 쓰는 동기는 단 하나였다:

> *"I'm working with a **legacy database**, and I need to map an entity to 2 database tables."*

그 글은 **단점을 아예 언급하지 않는다.** 최범균 책이 "항상 조인" 한계를 짚은 것이 오히려 더 친절한 셈이다. → [[#Q9]]

---

### ★ 결론 — best practice 4줄

```
1. 도메인 판정이 먼저다.       "지목해서 조회·변경·추적할 요구사항이 있는가"
                                ← DB를 보지 않고 결정한다
2. 기본 저장 방식은 ① Embedded Value.
                                "no sane person would want a table of money values"
3. ③ 별도 테이블은 이유가 이미 있을 때만.
                                레거시 스키마(가장 흔함) / vertical partitioning 기준 충족
                                → DB 설계 결정이지 DDD 결정이 아니다
4. 저장 방식이 무엇이든 도메인 판정은 안 바뀐다.
                                "optionally be mapped to a separate table
                                 and still be owned types"
```

## Q11. 밸류는 객체에서 PK가 없으니 결국 1:1인데, 왜 굳이 다른 테이블로 빼? `@Embeddable`로 같은 테이블에 두는 거와 같지 않아?

> **한 줄 답: 도메인 관점에서는 완전히 같다. 직관이 맞다. 다른 건 SQL이 테이블을 몇 개 건드리냐뿐이고, 그걸 정하는 건 도메인이 아니라 이미 주어진 스키마다.**

### 먼저 — 정말 같다는 증거

```java
@Embeddable                          @Embeddable
public class Address {               public class ArticleContent {
    private String zipCode;              private String content;
    private String address1;             private String contentType;
    private String address2;             // 식별자 필드 없음
}   // 식별자 필드 없음               }
```

| | `Address` (①) | `ArticleContent` (③) |
|---|---|---|
| 클래스 애너테이션 | `@Embeddable` | `@Embeddable` |
| 식별자 필드 | 없음 | 없음 |
| 변경 방식 | 통째 교체 | 통째 교체 |
| **도메인 판정** | **밸류** | **밸류** |
| 저장 테이블 | `purchase_order` | `article_content` |

**다른 줄은 마지막 하나뿐이다.**

### 그럼 왜 나누나 — 세 겹

**겹 1 — 책은 나눈 이유를 정당화하지 않는다**

노트 §4.3.8 원문: *"게시글 데이터를 `ARTICLE` 테이블과 `ARTICLE_CONTENT` 테이블로 **나눠 저장한다고 하자**"*
→ **"~라고 하자"**. 나뉜 스키마는 **주어진 전제**다. 책의 질문은 "왜 나누나"가 아니라 **"이미 나뉘어 있을 때 `ArticleContent`를 엔티티로 볼 것인가"**이고, 답은 **"아니다, 밸류다"**. `@SecondaryTable`은 그 답을 매핑으로 옮기는 수단일 뿐.

**겹 2 — ★ 이 스키마는 "본문이 커서 나눴다"를 오히려 반박한다**

```sql
create table shop.article_content ( id int not null primary key,
  content varchar(255), content_type varchar(255) );   -- varchar(255) → 별도 테이블
create table shop.product ( product_id varchar(50) not null primary key,
  name varchar(100), price int, detail text );          -- text        → 같은 테이블
```

| 컬럼 | 타입 | 처리 |
|---|---|---|
| `article_content.content` | `varchar(255)` | **별도 테이블** |
| `product.detail` | **`text`** | **같은 테이블** |

**큰 쪽이 안 나뉘고 작은 쪽이 나뉘었다.** 크기가 이유라면 정반대여야 한다. → [[#Q9]]의 "본문이 커서" 서술이 틀렸음이 스키마로 재확인된다.

**겹 3 — 책은 이 매핑을 사실상 권장하지 않는다**

```
@SecondaryTable → 목록 조회에서도 항상 조인   ← 한계
        ├── ArticleContent를 @Entity + 지연로딩  ❌ "밸류인 모델을 엔티티로 만드는 것"
        └── 조회 전용 기능 구현                   ⭕ 권장 (5장·11장)
```

### 현실에서 테이블을 나누는 진짜 이유

> ⚠️ **어시스턴트의 일반 지식이다. 책에도 `ddd-start2`에도 근거가 없다.**
> 레거시 스키마가 이미 그렇다(가장 흔함) / BLOB·TEXT 분리로 메인 테이블 행 크기 축소 / 테이블 단위 접근 권한·암호화 / 아카이빙·파티셔닝 주기가 다름
> → 전부 **운영 사정**이고 도메인 사정이 아니므로 **판정은 안 바뀐다.**

### 4패턴 전수 — 실제 코드·DDL로만 확인

| | ① `@Embedded` | ② Converter | ③ `@SecondaryTable` | ④ `@ElementCollection` | (예외) `@Entity` |
|---|---|---|---|---|---|
| 실제 예 | `Orderer`, `ShippingInfo`, `Address`, `Receiver`, `Password` | `Money`, `EmailSet` | `ArticleContent` | `OrderLine`, `CategoryId` | `Image` |
| 원소 수 | 1 | 1 또는 N | 1 | N | N |
| 테이블 | 부모와 같음 | 부모와 같음 | **다름** | **다름** | **다름** |
| 칼럼 수 | 필드 수만큼 | **1개** | 필드 수만큼 | 필드 수만큼 | 필드 수만큼 |
| 그 테이블 PK | (부모 PK) | (부모 PK) | 부모 PK 공유 | `order_line` **없음** / `product_category` **복합 PK** | **고유 auto_increment** |
| 클래스 애너테이션 | `@Embeddable` | **없음** (순수 클래스) | `@Embeddable` | `@Embeddable` | `@Entity` |
| 조회 | SELECT 1번 | SELECT 1번 | **항상 조인** (책이 명시한 한계) | LAZY 별도 SELECT | LAZY 별도 SELECT |

**② 가장 헷갈리는 사례 — 컬렉션인데 칼럼 1개**
```java
@Column(name = "emails") @Convert(converter = EmailSetConverter.class)
private EmailSet emails;                       // 객체는 Set<Email>
```
```java
// EmailSetConverter — 실제 구현
return attribute.getEmails().stream().map(Email::getAddress)
        .collect(Collectors.joining(","));     // "a@x.com,b@y.com"
```
`OrderLine`도 컬렉션인데 ④(별도 테이블)다. → **"컬렉션이니까 별도 테이블"이 아니다.**
⚠️ 대가(일반 지식): 콤마 문자열이면 **이메일로 검색·인덱싱이 불가능**하다.

**④ 같은 애너테이션인데 PK가 갈린다**
```sql
order_line       ( order_number, line_idx, product_id, price, quantity, amounts );
create index order_line_idx ON order_line (order_number, line_idx);  -- PK 없음, 인덱스만
product_category ( product_id, category_id, constraint primary key (product_id, category_id) );  -- 복합 PK
```
`List`는 순서가 필요해 `@OrderColumn(line_idx)`, `Set`은 순서가 없어 없다.

**(예외) `Image` — `@Entity`인데 밸류인 근거가 코드에 있다**
```java
@Entity @Inheritance(strategy = InheritanceType.SINGLE_TABLE)   // ★ 상속 때문에 @Entity
@DiscriminatorColumn(name = "image_type")
public abstract class Image {
    // 상태 변경 메서드가 하나도 없다 — getter와 abstract 조회 메서드뿐
}
```
```java
@OneToMany(cascade = {PERSIST, REMOVE}, orphanRemoval = true, fetch = LAZY)
private List<Image> images;
public void changeImages(List<Image> newImages) { images.clear(); images.addAll(newImages); }
```

### ★ 무엇이 패턴을 결정하나 — 정정된 결정 로직

```
0. 기본값은 ① @Embedded. 아래에 걸리는 게 없으면 ①.

1. 밸류인데 상속이 필요한가?
      YES → (예외) @Entity + @OneToMany       [Image]  ← JPA가 @Embeddable 상속 미지원
2. 원소가 여러 개인가?
      YES ─┬─ 칼럼 1개에 뭉쳐도 되나(검색 불필요)? → ② Converter          [EmailSet]
           └─ 아니면                              → ④ @ElementCollection  [OrderLine, CategoryId]
3. 여러 필드를 칼럼 1개에 뭉쳐야 하나? (레거시 등)
      YES → ② Converter                        [Length{value,unit} → "1000mm"]
4. 스키마가 이미 다른 테이블로 나뉘어 있나?
      YES → ③ @SecondaryTable                  [ArticleContent]
      NO  → ① @Embedded                        ← 기본
```

**4번이 이 질문의 답이다.** ③은 골라잡는 옵션이 아니라 **스키마가 이미 나뉘어 있을 때 쓰는 것**이고, 책은 그 대가(항상 조인)까지 함께 명시한다.

### ★ 착시 정리 — 관찰은 전부 근거가 안 된다

| 관찰 | 진실 | 반례 |
|---|---|---|
| "같은 테이블 컬럼이니까 밸류" | ❌ ①일 뿐 | — |
| "별도 테이블이니까 엔티티" | ❌ ③④일 뿐 | `ArticleContent`, `OrderLine` |
| "PK 있으니까 엔티티" | ❌ | `article_content.id`(부모 것) · `product_category`(복합) · `image.image_id`(상속 때문) |
| "PK 없으니까 밸류" | ❌ 이것도 근거 아님 | `order_line`에 PK가 없지만 그게 이유는 아니다 |
| "1:N이니까 별도 테이블" | ❌ | `EmailSet` — 컬렉션인데 칼럼 1개 |
| "1:1이니까 같은 테이블" | ❌ | `ArticleContent` — 1:1인데 별도 테이블 |
| "크니까 나눈다" | ❌ **이 스키마가 반박** | `product.detail`은 `text`인데 안 나눔 |

**판정은 오직 "지목해서 조회·변경·추적할 요구사항이 있는가" 한 줄로만 한다.**

## Q10. `@AttributeOverride`는 왜 필요해? 그리고 `Password`는 밸류인데 왜 컬럼이 하나야?

> **한 줄 답 ①: 컬럼 이름은 밸류 클래스가 자기 안에 선언하는데, 밸류는 자기가 어느 부모 테이블에 펼쳐질지 모른다. 그래서 부모 쪽에서 덮어쓴다.**
> **한 줄 답 ②: `@Embeddable`은 "필드 하나당 컬럼 하나"로 펼친다. `Password`는 필드가 하나라서 컬럼도 하나다. 컬럼 개수 = 필드 개수이지, 밸류라서 몇 개인 게 아니다.**

### 결정적 증거 — `MemberId` **한 클래스**가 두 테이블에서 **다른 컬럼 이름**

```java
// member/command/domain/MemberId.java — 자기가 정한 기본 이름
@Embeddable
public class MemberId implements Serializable {
    @Column(name = "member_id")
    private String id;
```
```java
// 부모 A — Member.java : 오버라이드 없음
@EmbeddedId
private MemberId id;                        // → member.member_id

// 부모 B — Orderer.java : 오버라이드 있음
@AttributeOverrides(
        @AttributeOverride(name = "id", column = @Column(name = "orderer_id"))
)
private MemberId memberId;                  // → purchase_order.orderer_id
```
```sql
create table shop.member         ( member_id varchar(50) not null primary key, ... );
create table shop.purchase_order ( ..., orderer_id varchar(50), ... );
```

`purchase_order`에 `member_id`가 있으면 무슨 회원인지 애매하다. `orderer_id`라야 **주문자**임이 드러난다.

### ★ 대조가 핵심 — 바로 옆 `Receiver`는 오버라이드가 **없다**

같은 `ShippingInfo` 안에서 `Address`는 덮어쓰고 `Receiver`는 안 덮어쓴다.

```java
// ShippingInfo.java
@Embedded
@AttributeOverrides({
    @AttributeOverride(name = "zipCode",  column = @Column(name = "shipping_zip_code")),
    @AttributeOverride(name = "address1", column = @Column(name = "shipping_addr1")),
    @AttributeOverride(name = "address2", column = @Column(name = "shipping_addr2"))
})
private Address address;

@Embedded
private Receiver receiver;          // ← 오버라이드 없음
```

`Receiver`가 **이미 맞는 이름을 갖고 있어서**다:
```java
// order/command/domain/Receiver.java
@Column(name = "receiver_name")   private String name;
@Column(name = "receiver_phone")  private String phone;
```

| | `Address` | `Receiver` |
|---|---|---|
| 위치 | `common/model/` | `order/command/domain/` |
| 자기 컬럼 이름 | `zip_code`, `address1`, `address2` (중립적) | `receiver_name`, `receiver_phone` (구체적) |
| 오버라이드 | **필요** | **불필요** |

> ⚠️ 위 표의 경로·이름은 **코드에서 직접 확인한 사실**이다. 다만 "`Address`가 범용이라서 이름이 중립적이다"라는 **인과 설명은 어시스턴트의 추론**이다. `Address`는 `common/model/`에 있지만 실사용처는 `ShippingInfo` 하나뿐이라, 재사용이 관찰된 것은 아니다.

### 세 번째 사례 — `Article`: 이름이 아니라 **테이블**을 바꾼다

```java
@AttributeOverrides({
    @AttributeOverride(name = "content",
        column = @Column(table = "article_content", name = "content")),
    @AttributeOverride(name = "contentType",
        column = @Column(table = "article_content", name = "content_type"))
})
@Embedded
private ArticleContent content;
```

`@Column`에 **`table =`** 속성이 있다. `ArticleContent` 클래스에는 `@Column`이 **하나도 없고**(필드 2개뿐), 매핑 정보가 **전부 `Article` 쪽**에 있다.

### 오버라이드가 하는 일 3층

| 층 | 사례 | 바꾸는 것 |
|---|---|---|
| 이름 모호 해소 | `MemberId` → `orderer_id` | 컬럼 이름 |
| 맥락 표시 | `Address` → `shipping_zip_code` | 컬럼 이름 |
| **대상 테이블 지정** | `ArticleContent` → `article_content` | 컬럼 이름 **+ 테이블** |

> ⚠️ 일반론(**이 코드베이스에 사례 없음**): 한 부모에 같은 밸류를 두 번 넣으면(청구지 주소 + 배송지 주소) 컬럼 이름이 반드시 충돌하므로 오버라이드가 **필수**가 된다.

### `Password`가 컬럼 하나인 이유

```java
@Embeddable
public class Password {
    @Column(name = "password")
    private String value;                    // ★ 필드가 하나뿐
    protected Password() {}
    public Password(String value) { this.value = value; }
    public boolean match(String password) { return this.value.equals(password); }
}
```
```sql
create table shop.member ( ..., password varchar(255), ... );
```

**컬럼 개수 = 밸류의 필드 개수.**

| 밸류 | 필드 수 | 컬럼 수 |
|---|---|---|
| `Address` | 3 | 3 |
| `Receiver` | 2 | 2 |
| `Orderer` | 2 (`MemberId` + `name`) | 2 |
| **`Password`** | **1** | **1** |

`Address`·`Receiver`·`Orderer`만 보면 "밸류 = 컬럼 여러 개"라는 착시가 생긴다.

**필드 1개인데 왜 굳이 밸류로 뺐나** — `밸류 타입.md`(§1.6.3 p.046~052): **"데이터 개수는 꼭 2개 이상일 필요 없다. 1개여도 의미 명확화를 위해 사용"**. 그리고 실제 이득이 코드에 남아 있다:

```java
// Member.changePassword() — 실제 코드
public void changePassword(String oldPw, String newPw) {
    if (!password.match(oldPw)) {              // ★ 비교 로직이 Password 안에
        throw new IdPasswordNotMatchingException();
    }
    this.password = new Password(newPw);       // ★ 통째 교체 (불변)
}
```

`String`이면 `password.equals(oldPw)`가 되고, 해시 비교로 바뀌는 순간 **호출한 모든 곳**을 고쳐야 한다. `Password.match()`면 그 안만 고친다.

> ★ `Password`에는 `equals()`가 **없다.** 대신 `match()` — "암호가 일치하는가"는 객체 동등성이 아니라 **도메인 행위**이기 때문. → [[#Q6]]

### ⚠️ 이 과정에서 발견한 Q9 노트의 오류 2건

**오류 1 — 결정 트리와 패턴 표가 모순**

Q9 결정 트리는 `필드가 1개 → ② AttributeConverter`라고 했는데, 같은 Q9의 패턴 표는 `Password`를 **①(부모 컬럼)** 에 넣었다. `Password`는 필드 1개인데 ①이다.

| | `Money` | `Password` |
|---|---|---|
| 필드 수 | **1** (`int value`) | **1** (`String value`) |
| JPA 애너테이션 | **하나도 없음** (순수 자바 클래스) | `@Embeddable` + `@Column` |
| 매핑 | `MoneyConverter` (②) | `@Embedded` (①) |

**필드 개수는 ①/②를 가르지 않는다.** 노트 `AttributeConverter를 이용한 밸류 매핑.md`(§4.3.4 p.145~147)가 대는 컨버터의 사유는 **"두 개 이상의 프로퍼티를 가진 밸류를 한 개 칼럼에 매핑"**(예: `Length{value,unit}` → `"1000mm"`)이고, `Money`는 필드 1개라 **이 사유에 해당하지 않는다.** 관찰되는 실제 차이는 `Money`가 **JPA 애너테이션을 전혀 달지 않은 순수 도메인 클래스로 남았다**는 점이다.
→ 책이 "왜 Money를 컨버터로 했는가"에 명시적 이유를 대는지는 **확인 불가** (PDF가 스캔 이미지).

**오류 2 — 노트의 리스트 4.5와 실제 코드가 다름**

```java
@Converter(autoApply = true)     // ← 노트(책 리스트 4.5)
public class MoneyConverter ...

public class MoneyConverter ...  // ← 실제 ddd-start2: @Converter 없음
```
**저장소 전체에 `@Converter` 애너테이션이 0개**이고, 사용처마다 `@Convert(converter = MoneyConverter.class)`를 명시한다 (`Order:29`, `OrderLine:17,24`, `Product:26`, `ProductData:28`). → 책이 설명하는 **`autoApply = false`(기본값) 경로**를 예제 코드가 택했다.

<a id="q9"></a>
## Q9. 엔티티 내부의 밸류를 한 테이블에서 관리한다거나, 밸류로 빼서 다른 테이블로 관리되는 개념이 헷갈린다

> **한 줄 답: 테이블은 "어떻게 저장할까"의 답이고, 엔티티/밸류는 "이게 무엇인가"의 답이다. 저장 방식을 바꿔도 그게 무엇인지는 바뀌지 않는다.**

### 근본 원인 — RDB에는 "밸류"라는 개념이 없다

| | **객체 모델** | **관계형 모델** |
|---|---|---|
| **중첩** | 무한히 가능 (`Order → ShippingInfo → Address → zipCode`) | **불가능. 평평하다** |
| **식별** | **엔티티만** 식별자를 갖는다 | **모든 행이 식별된다** (PK) |
| **소유** | 포함(내 것) / 참조(남의 것) 구분 | **FK 하나뿐.** 구분 안 됨 |
| **행동** | 데이터 **+ 기능** | 데이터만 |

RDB에는 "식별자가 없는 것"을 담을 자리가 없다. 그래서 밸류를 저장하려면:

```
   ① 부모 행에 컬럼으로 펼친다  →  개념이 드러나지 않는다 (그냥 컬럼 나열)
   ② 별도 테이블로 뺀다         →  PK가 생겨서 엔티티처럼 보인다
```

> 책 원문: RDBMS는 밸류를 제대로 표현하지 못해, **한 테이블에 넣으면 개념이 드러나지 않고, 별도 테이블로 빼면 테이블 엔티티처럼** 되어버린다.

**둘 다 손해다. 헷갈리는 게 정상 — 모델 자체가 안 맞는다.**

### 실물 ① — 테이블 1행 = 객체 **8개** (`purchase_order`)

```sql
create table shop.purchase_order (
  order_number varchar(50) not null primary key,
  version bigint,
  orderer_id varchar(50), orderer_name varchar(50),
  total_amounts int,
  shipping_zip_code varchar(6), shipping_addr1 varchar(100), shipping_addr2 varchar(100),
  shipping_message varchar(200),
  receiver_name varchar(50), receiver_phone varchar(50),
  state varchar(20), order_date datetime
);
```

```
Order (엔티티)
├── number         : OrderNo       ← 밸류
├── orderer        : Orderer       ← 밸류
│     └── memberId : MemberId      ← 밸류 안의 밸류
├── totalAmounts   : Money         ← 밸류 (converter로 int 칼럼 1개)
└── shippingInfo   : ShippingInfo  ← 밸류
      ├── address  : Address       ← 밸류 안의 밸류
      └── receiver : Receiver      ← 밸류 안의 밸류
```

**객체는 3단계 중첩 + 8개. 테이블은 평평한 컬럼 13개 1행.**

`@Embeddable`이 핵심 신호: **"이 클래스는 자기 테이블을 갖지 않는다. 부모 테이블에 컬럼으로 녹아든다."**

⚠️ 여기서 착시: 테이블만 보면 "주소는 그냥 컬럼이네" 싶지만, 객체 쪽에서 `Address`는 **독립된 클래스**이고 `ShippingInfo` 안에 중첩되어 있다. **테이블에서 보면 컬럼, 객체에서 보면 개념.**

> ⚠️ **정정**: 실제 `common/model/Address.java`에는 **검증 로직도 도메인 메서드도 없다.** 필드 3개 + `public` 기본 생성자 + getter 3개뿐이고, 검증은 응용 계층 `OrderRequestValidator`가 한다.
> "밸류에 로직을 붙일 수 있다"는 **가능성**이지 이 코드가 실제로 그렇다는 뜻이 아니다.
> 이 코드베이스에서 실제로 로직을 가진 밸류는 **`Money.multiply()`**, **`Password.match()`** 다.

### 실물 ② — 엔티티 1개 = 테이블 **2개** (`Article`)

```sql
create table shop.article ( id int auto_increment primary key, title varchar(255) );
create table shop.article_content ( id int not null primary key, content varchar(255), content_type varchar(255) );
```

```java
@Entity
@Table(name = "article")
@SecondaryTable(name = "article_content",
                pkJoinColumns = @PrimaryKeyJoinColumn(name = "id"))   // PK 공유
public class Article {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String title;

    @Embedded                                    // ★ 여전히 밸류
    @AttributeOverrides({
        @AttributeOverride(name = "content",
            column = @Column(table = "article_content", name = "content")),
        @AttributeOverride(name = "contentType",
            column = @Column(table = "article_content", name = "content_type"))
    })
    private ArticleContent content;
}

@Embeddable                       // ← @Entity가 아니다. 식별자 필드도 없다
public class ArticleContent {
    private String content;
    private String contentType;
}
```

**왜 나눴나**: 본문은 크고 목록 조회 때는 필요 없다.

> ❌ **2026-08-14 정정 — 여기 있던 "목록 = `article`만 읽고, 상세 = 조인"은 틀렸다.**
> 원본 노트 `밸류를 이용한 ID 매핑과 별도 테이블 매핑.md`(§4.3.8)는 **정반대**를 말한다:
> **"`@SecondaryTable`을 사용하면 목록 화면에 보여줄 `Article`을 조회할 때 `article_content` 테이블까지 조인해서 데이터를 읽어오는데 이것은 원하는 결과가 아니다."**
> 즉 별도 테이블로 뺀 것이 목록 성능을 **해결하는 게 아니라**, 조인이 딸려오는 것이 **`@SecondaryTable`의 알려진 한계**다.
> 책의 해법: ① `ArticleContent`를 `@Entity`+지연로딩 → ❌ "밸류인 모델을 엔티티로 만드는 것이라 좋은 방법이 아니다" / ② **조회 전용 기능 구현 ⭕**(5장 조회 전용 쿼리, 11장 CQRS)

**⚠️ `article_content.id`의 정체**: `ArticleContent` 자신의 식별자가 ❌ / **`article`과 연결하기 위한 것** ⭕ (부모 id를 그대로 씀). 클래스에는 식별자 필드가 아예 없다.

> **매핑되는 테이블의 식별자를 구성요소의 식별자와 동일시하면 안 된다.**

### 밸류 저장 4가지 패턴 — 전체 지도

> ⚠️ **"하나의 밸류가 4번 저장된다"는 뜻이 아니다.** 저장 방법이 4가지 있고, **밸류마다 그중 하나를 고른다.**

| 패턴 | 애너테이션 | 저장 형태 | 실제 예 |
|---|---|---|---|
| **① 부모 테이블에 컬럼으로 펼치기** | `@Embeddable` + `@Embedded` | 부모 행에 컬럼 추가 | `Orderer`, `ShippingInfo`, `Address`, `Receiver`, `Password` |
| **② 한 칼럼에 몰아넣기** | `AttributeConverter` + `@Convert` | 값 → 칼럼 1개 | `Money`→`int`, `EmailSet`→콤마 문자열 |
| **③ 별도 테이블 1:1** | `@SecondaryTable` | **부모 PK 공유** | `ArticleContent` |
| **④ 별도 테이블 1:N** | `@ElementCollection` + `@CollectionTable` | FK + 인덱스 칼럼 | `OrderLine` |
| (예외) 상속 필요 | `@Entity` + `@OneToMany` | **고유 PK 생김** | `Image` |

### 무엇이 패턴을 결정하나 — 결정 트리

```
밸류를 저장해야 한다
│
├── 컬렉션인가? (원소가 여러 개)
│     ├── YES ─┬─ ④ @ElementCollection + @CollectionTable   [OrderLine → order_line]
│     │        └─ ② AttributeConverter (한 칼럼 문자열)      [EmailSet → member.emails]
│     │
│     └── NO (단일 값)
│           ├── 필드 여러 개를 칼럼 1개에 넣어야 하나?
│           │        └── YES ── ② AttributeConverter        [Length{value,unit} → "1000mm"]
│           └── 필드마다 칼럼 1개씩 (기본)
│                 ├── 부모 테이블에 함께 ── ① @Embedded       [Orderer, Address, Receiver, Password]
│                 └── 별도 테이블로 ─────── ③ @SecondaryTable [ArticleContent]
```

> ⚠️ **2026-08-14 정정**: 이전 버전은 `필드가 1개 → ② AttributeConverter`라고 적어 아래 패턴 표(`Password`를 ①에 배치)와 **모순**이었다. **필드 개수는 ①/②를 가르지 않는다.**
> - `Password` — 필드 1개인데 **①** (`@Embeddable` + `@Column(name="password")` → `member.password`)
> - `Money` — 필드 1개인데 **②** (`MoneyConverter`)
> - 노트 `AttributeConverter를 이용한 밸류 매핑.md`(§4.3.4 p.145~147)의 컨버터 사유는 **"두 개 이상의 프로퍼티를 한 개 칼럼에"** 이고, `Money`는 여기 해당하지 않는다. 관찰되는 실제 차이는 **`Money`가 JPA 애너테이션을 전혀 안 단 순수 도메인 클래스**라는 점. 책의 명시적 이유는 확인 불가(PDF가 스캔 이미지).
> - 상세 → [[#Q10]]

**컬렉션인가 / 칼럼 1개로 뭉쳐야 하나 / 같은 테이블인가 — 이 갈림길이 패턴을 정한다. 도메인 판정과는 무관하다.**

### 실증 A — 하나의 밸류가 3개 테이블에 흩어져 저장된다

`Money`가 실제 매핑된 곳 전부:

```
                        Money (클래스 1개)
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   purchase_order          order_line             product
   total_amounts           price, amounts          price
```

테이블 3개·칼럼 4개에 흩어져 있는데 **도메인에는 `Money` 클래스 하나뿐**이다.
DB에서는 서로 다른 `int` 칼럼 4개지만 도메인에서는 전부 같은 `Money`.

### 실증 B — 같은 모양의 밸류가 다른 패턴으로 갈린다 ★

필드 2개짜리 `@Embeddable` 밸류 두 개 비교:

| | `Orderer` | `ArticleContent` |
|---|---|---|
| 클래스 애너테이션 | `@Embeddable` | `@Embeddable` |
| 필드 수 | 2개 | 2개 |
| 식별자 필드 | ❌ 없음 | ❌ 없음 |
| **도메인 개념** | **밸류** | **밸류** |
| 저장 패턴 | ① 부모 컬럼 (`purchase_order.orderer_id/orderer_name`) | ③ 별도 테이블 (`article_content`) |
| **테이블 PK** | **없음** | **있음** |

**도메인에서는 완전히 같은 종류인데, 테이블에서는 하나는 컬럼이고 하나는 PK 가진 테이블이다.**

**왜 갈렸나 — 순전히 기술적 이유:**
```
Orderer         →  작다. 주문 조회할 때 항상 같이 필요   →  ① 같은 테이블
ArticleContent  →  본문이 크다. 목록 조회 땐 불필요      →  ③ 별도 테이블
```

> ❌ **2026-08-14 정정.** 여기 있던 SQL 예시(`SELECT id, title FROM article; -- 무거운 본문을 안 읽는다 ✅`)는 **틀려서 삭제했다.**
> `@SecondaryTable`은 **목록 조회에서도 항상 조인한다.** `entityManager.find(Article.class, 1L)`이 `article_content`까지 읽는다.
> 원본 노트 §4.3.8이 이것을 **`@SecondaryTable`의 한계**로 명시하며, 해법은 **조회 전용 기능**(5장·11장)이다.
> → **별도 테이블로 나눈 것과 목록 조회 성능이 해결되는 것은 별개다.** 나눠도 조인은 따라온다.

**저장 위치의 차이는 기술 결정이지 도메인 결정이 아니다** — 어느 쪽이든 `Orderer`도 `ArticleContent`도 **밸류**다.

### `article_content.id`의 정체 — 테이블로 빼는 순간 생기는 부작용

RDB에서 두 테이블을 잇는 방법은 키밖에 없다. 그래서 별도 테이블로 빼면 **연결용 칼럼이 반드시 필요**해진다.

```
   article           article_content
   ─────────         ───────────────
   id=1  ◀─────────  id=1              ← 같은 값. 새로 만든 식별자가 아니다
   title             content
                     content_type
```
```java
@SecondaryTable(name = "article_content",
                pkJoinColumns = @PrimaryKeyJoinColumn(name = "id"))   // "부모 PK를 조인 키로 써라"
```

**`article_content.id`는 `ArticleContent`의 정체성이 아니라 `article`을 가리키는 손가락이다.**
증거: `ArticleContent` 클래스에 `id` 필드가 **없다**.

> **매핑되는 테이블의 식별자를 구성요소의 식별자와 동일시하면 안 된다.**

②의 극단적 예 — 컬렉션인데 칼럼 하나:
```sql
create table shop.member ( ..., emails varchar(200) );   -- "a@x.com,b@y.com"
```
```java
@Column(name = "emails")
@Convert(converter = EmailSetConverter.class)
private EmailSet emails;        // 객체는 Set<Email>, DB는 문자열 하나
```

### ★ 결론

| 테이블에서 본 관찰 | 진실 |
|---|---|
| "테이블 컬럼이니까 밸류" | ❌ 저장 방식 ①일 뿐 |
| "자기 테이블 + PK 있으니까 엔티티" | ❌ 저장 방식 ③④일 뿐 |
| "1:N으로 저장되니까 엔티티" | ❌ 저장 방식 ④일 뿐 |

**판별은 항상 객체 쪽에서 한다. 테이블 모양은 저장 사정이 만든 결과이기 때문이다.**

```
① 밸류의 "모양"이 저장 패턴을 좁힌다      컬렉션? 필드 몇 개?
② 기술적 사정이 최종 패턴을 고른다        본문이 커서 목록 조회 성능 걱정 → 별도 테이블
                                        기존 스키마가 콤마 문자열 → 컨버터
③ 어느 패턴을 골라도 도메인 판정은 안 바뀐다
   Orderer(컬럼)도 밸류, ArticleContent(PK 가진 테이블)도 밸류
```

**PK가 생기는 건 "별도 테이블로 뺐다"의 부작용이다.** RDB에서 테이블을 나누면 이을 키가 필요해서지, 도메인이 그 밸류에 정체성을 부여해서가 아니다.

판정 순서:
```
1) 도메인 요구사항으로 판정          ← ★ 여기서 결정 (Q8의 판별 질문 3개)
2) 그 결과를 객체 모델로 쓴다        밸류 → 식별자 필드 없음 / 엔티티 → 있음
3) 저장 방식은 기술 사정으로 고른다   ← 도메인과 무관. PK가 생기든 말든 상관없다
```

`ShippingInfo`가 오늘은 `purchase_order` 컬럼이고 내일 `shipping_info` 테이블로 빠져도, **어제도 오늘도 내일도 밸류**다.

## Q8. 밸류도 "추적해야 할 요구사항"이 있을 때 컬럼에서 빠지는 거잖아? 그럼 1:N으로 관리되는 밸류랑 뭐가 달라?

> **한 줄 답: "추출"과 "추적"은 방향이 정반대다. 밸류 추출은 흩어진 필드를 합치는 것이고, 엔티티 판정은 한 덩어리를 개별로 나누는 것이다.**

```
밸류 추출     zipCode, address1, address2   →   Address       ← 합친다
              흩어진 필드 여러 개                하나의 개념

엔티티 판정   Lecture 목록 [A, B, C, ...]   →   A? B? C?      ← 나눈다
              한 덩어리                          개별 지목
```

> 📐 **출처 표시 (2026-08-14 검증)**: "3신호"는 **어시스턴트가 만든 프레임**이다. ②·③은 `01-도메인모델/밸류 타입.md`(§1.6.3 p.046~052)의 **"개념적으로 완전한 하나"**·**"기능(계산 로직)을 추가할 수 있다"**에 근거가 있으나, **①"함께 변한다"는 대응 서술이 없다.** 원서 PDF는 스캔 이미지라 직접 대조는 불가능했다.

**밸류 추출 3신호에 "추적"은 없다.** ① 함께 변한다 ② 이름이 붙는다 ③ 로직이 붙는다 — **셋 다 "묶는" 이유**다.
`Address`를 뺀 건 "주소를 추적하려고"가 아니라 **"세 필드가 흩어져 있으면 검증과 로직이 갈 자리가 없어서"**다.

### `OrderLine`(밸류) vs `Lecture`(엔티티) — 둘 다 1:N인데 왜 다른가

| | `OrderLine` (밸류) | `Lecture` (엔티티) |
|---|---|---|
| 목록에 여러 개 있나 | ⭕ 3줄 | ⭕ 10회차 |
| **개별 원소가 서로 다른 상태를 갖나** | ❌ 전부 그냥 데이터 | ⭕ **3회차만 `hidden=true`** |
| **개별 원소를 지목해 상태를 바꾸나** | ❌ | ⭕ **"3회차만 비공개"** |
| **다른 곳에서 이 하나를 참조하나** | ❌ | ⭕ **수강 진도가 `lectureId` 저장** |
| **목록을 통째로 교체해도 되나** | ⭕ `clear()` + `addAll()` | ❌ **하면 안 된다** |
| 테이블 PK | **없음** | **필요** |

### 결정타 ① — 통째로 교체할 수 있는가

```java
// OrderLine: 아무 문제 없다. 아무도 예전 줄을 기억하지 않는다
public void changeOrderLines(List<OrderLine> newLines) {
    this.orderLines = newLines;
    calculateTotalAmounts();
}
```

```
// Lecture에 같은 짓을 하면:
   기존 회차: [id=101, id=102, id=103]
   수강 진도: (수강생A, lecture_id=101, 완료) (수강생A, 102, 완료) (수강생B, 101, 완료)

   통째로 교체 → 새 회차 [id=201, 202, 203]
               → 진도 기록이 전부 고아  ❌  학습 이력 증발
```

**통째로 교체하면 안 되는 것 = 개별 원소가 정체성을 가져야 하는 것 = 엔티티.**

### 결정타 ② — 다른 곳에서 참조되는가 (가장 기계적인 판별법)

```java
public class LectureProgress {
    private StudentId studentId;
    private Long lectureId;          // ★ 회차를 가리켜야 한다
    private LocalDateTime completedAt;
}
```

가리키려면 **안정적인 이름표(식별자)**가 있어야 하고, 식별자가 있으면 엔티티다.

반대로 `OrderLine`은 **아무도 가리키지 않는다.** 그래서 `order_line` 테이블에 **PK가 아예 없다** — 참조당할 일이 없으니 PK가 필요 없다. 이게 밸류 컬렉션의 표식.

### 결정타 ③ — 원소마다 서로 다른 상태를 갖는가

```
   주문의 3줄:   [상품A 2개] [상품B 1개] [상품C 5개]     ← 전부 "그냥 데이터"
   강의의 3회차: [1회차 공개] [2회차 공개] [3회차 비공개 ★]  ← 그것만 다르고 그것만 바뀐다
```

### `Image`는 PK가 있는데도 왜 밸류인가

- 개별 이미지를 지목해 상태를 바꾸나? ❌ **`Image`에는 상태 변경 메서드가 아예 없다**
- 다른 곳에서 `image_id`를 참조하나? ❌
- 통째로 교체해도 되나? ⭕ `changeImages()`가 `clear()` + `addAll()`

**세 테스트 전부 밸류.** PK는 상속 매핑 때문에 JPA가 요구한 것뿐이다.

### ★ 판별 질문 3개 (헷갈릴 때 이것만)

> 📐 **출처 표시 (2026-08-14 검증)**: 아래 3개는 **어시스턴트가 만든 조작적 정의**다. 책의 기준은 `01-도메인모델/엔티티와 식별자.md`의 **"식별자를 가진다"** 하나뿐이다.
> **시험 답 = "식별자가 필요한가"**, 아래 3개는 그 판단을 실제 코드에 내릴 때 쓰는 도구로만 쓴다.
> 단, 3개 안의 관찰 사실(`order_line`에 PK 없음, `changeImages()`의 `clear()`+`addAll()`)은 실제 코드에서 확인된 것이다.

> **① 이 목록을 통째로 갈아끼워도 아무 문제 없는가?** → 문제없으면 **밸류**
> **② 다른 데이터가 이것 하나를 가리켜서 저장하는가?** → 가리키면 **엔티티**
> **③ 원소마다 서로 다른 상태를 갖고 개별적으로 변하는가?** → 그러면 **엔티티**

| | ① 통째 교체 | ② 참조됨 | ③ 개별 상태 | 판정 |
|---|---|---|---|---|
| `Lecture` | ❌ | ⭕ | ⭕ | **엔티티** |
| `OrderLine` | ⭕ | ❌ | ❌ | **밸류** |
| `Image` | ⭕ | ❌ | ❌ | **밸류** (PK 있어도) |

## Q7. 밸류인데 저장만 1:N으로 고유한 PK를 갖고 관리되는 건가?

> **한 줄 답: 그렇다. 그리고 PK가 아예 없을 수도 있다. PK와 엔티티/밸류의 상관관계는 0이다.**

### 실제 DDL 3개 — **셋 다 도메인상 밸류**

```sql
-- ① order_line : PK가 아예 없다
create table shop.order_line (
  order_number varchar(50) not null,      -- FK
  line_idx     int not null,              -- 리스트 인덱스
  product_id   varchar(50) not null,
  price int, quantity int, amounts int
);
create index order_line_idx ON order_line (order_number, line_idx);   -- 인덱스만!

-- ② article_content : PK 있음 (부모 article의 id 공유)
create table shop.article_content ( id int not null primary key, ... );

-- ③ image : 자기만의 auto_increment PK가 있다
create table shop.image ( image_id int not null auto_increment primary key, ... );
```

| 테이블 | PK | JPA 매핑 | 도메인 개념 |
|---|---|---|---|
| `order_line` | **없음** | `@ElementCollection` | **밸류** |
| `article_content` | 부모와 공유 | `@SecondaryTable` | **밸류** |
| `image` | **고유 auto_increment** | `@Entity` + `@OneToMany` | **밸류** ⚠️ |

### 밸류 컬렉션이 1:N으로 저장되는 방식

```java
@ElementCollection(fetch = FetchType.LAZY)
@CollectionTable(name = "order_line", joinColumns = @JoinColumn(name = "order_number"))
@OrderColumn(name = "line_idx")
private List<OrderLine> orderLines;

@Embeddable                        // ← @Entity가 아니다
public class OrderLine {
    @Embedded private ProductId productId;
    private Money price; private int quantity; private Money amounts;
    // ★ 식별자 필드가 없다
}
```

- `@ElementCollection` — 밸류 컬렉션 지정
- `@CollectionTable` — 저장 테이블 + FK 칼럼
- `@OrderColumn` — 리스트 인덱스를 저장할 칼럼
- `OrderLine`에 인덱스 필드가 없는 이유: **`List` 타입 자체가 인덱스를 갖기 때문**

행을 특정하는 건 `(order_number, line_idx)` = **"몇 번 주문의 몇 번째 줄"**이지, `OrderLine` 자신의 정체성이 아니다.

### ★ `Image`는 왜 고유 PK를 갖나 — 여기가 핵심

**개념은 밸류인데 기술 한계로 `@Entity` 매핑**한 것.

> **JPA는 `@Embeddable` 타입의 클래스 상속 매핑을 지원하지 않는다.**
> `Image`는 `InternalImage`/`ExternalImage` 상속이 필요해 `@Entity` + discriminator로 갈 수밖에 없었다.

책이 못 박는다: **"`Image`를 `@Entity`로 매핑했지만 모델에서 `Image`는 밸류이므로 상태를 변경하는 기능은 추가하지 않는다."**

행동으로 확인 — `product.changeImages()`는 `clear()` 후 `addAll()`:
**"image #17을 수정"이 아니라 "목록을 통째로 교체"**. 이게 밸류의 행동 방식이다.

⚠️ 대가: `@Entity` 컬렉션의 `clear()`는 **SELECT 1 + DELETE N**, `@Embeddable`은 **DELETE 1**. 변경 빈도가 높으면 상속을 포기하고 `@Embeddable` 단일 클래스 + if-else로 가는 게 낫다.

### 결론 — 판정의 3단계

```
1) 도메인 요구사항:  식별자로 지목해서 추적·변경하는가?      ← ★ 진짜 기준
                        ↓
2) 도메인 모델:      그 결과로 식별자 필드를 둔다 (또는 안 둔다)
                        ↓
3) JPA 매핑:         기술 제약(상속·성능)에 따라 별개로 결정
                     PK 유무는 여기서 정해진다 ← 도메인과 무관
```

`Image`가 3단계에서 PK를 얻었다고 1단계 판정이 바뀌지 않는다. **PK는 저장 계층의 사정이다.**

## Q6. DDD에서 equals/hashCode를 반드시 오버라이드해야 해? IntelliJ 자동 생성 말고 도메인 정의에 따라? 객체 비교할 상황이 많나?

> **한 줄 답: 아니다. 필요할 때만 만든다. 실무 감각이 맞았다.**

**실증 조사 (`ddd-start2/` 도메인 클래스 24개 전수)**

- `equals()` 구현은 **7개뿐**
- 애그리거트 루트 5개(`Order`, `Member`, `Product`, `Article`, `Category`) **전부 없음**
- 밸류인 `Address`, `Receiver`, `ShippingInfo`, `OrderLine`, `Image`, `Option`도 **없음**

**구현한 7개의 이유가 각각 다르다**

| 클래스 | 이유 |
|---|---|
| `OrderNo`, `MemberId`, `ProductId`, `CategoryId` | **JPA 강제.** `@EmbeddedId`로 쓰이므로 스펙이 `Serializable` + `equals()` + `hashCode()` 요구 |
| `Money`, `Email` | **값 비교를 실제로 한다.** `Money`는 불변이라 `multiply()`마다 새 인스턴스 → `new Money(2000) == new Money(2000)`이 false |
| `Orderer` | 내부에 `MemberId`(equals 구현체)를 품어서 **일관성상** 필요 |

> ★ **반전**: `equals()`가 필요해지는 건 엔티티가 아니라 **식별자 밸류 타입** 쪽이다.
> PK를 `OrderNo` 밸류로 만들었기 때문에 생긴 요구다. `Article`처럼 `private Long id`면 `Long`에 이미 있으니 불필요.

**"비교할 상황이 많나?" → 엔티티는 거의 없다**

실제 코드의 도메인 비교 지점은 딱 2곳이고, 둘 다 **엔티티끼리가 아니라 ID(String) 비교**(권한 검사):
- `order/ui/MyOrderController.java:38`
- `order/infra/domain/SecurityCancelPolicy.java:23`

**IntelliJ 자동 생성은?**

실제 코드가 **IDE 템플릿 그대로**다 (`Objects.equals`, `Objects.hash`, `getClass() != o.getClass()`).
→ **도구는 IDE, 판단만 도메인 정의로.** IntelliJ가 "어떤 필드를 포함할까요?" 물을 때:

- 엔티티 → **식별자만** 체크
- 밸류 → **전부** 체크

⚠️ 엔티티에 모든 필드를 체크하면 **배송지만 바꿔도 다른 주문**이 되는 버그.

**만드는/안 만드는 기준**

| 대상 | 판정 |
|---|---|
| `@EmbeddedId` 식별자 밸류 | **필수** (JPA 스펙) |
| 연산으로 새 인스턴스가 생기는 밸류 (`Money`) | **필수** |
| 테스트에서 값 비교 / `Set`·`Map` 키 | 필요 |
| 저장·조회만 되는 밸류 (`Address`) | 불필요 |
| 애그리거트 루트 | **대개 불필요** |
| 도메인 의미가 "일치 검사"인 것 | `equals()` 대신 **`match()`** ← `Password`가 실제로 이렇게 함 |

> 1장의 `Order.equals()` 예제는 **"엔티티의 동등성은 식별자로 판단한다"는 개념 교육용 코드**다. 시험엔 나오지만 실무에선 대개 안 만든다.

## Q5. JPA 쓰면 PK가 UUID나 auto increment잖아. 그 PK로 바로 비교하면 되는 거 아냐? 왜 equals()를 따로 오버라이드해?

> **한 줄 답: 같은 트랜잭션 안에서는 네 말이 맞다. 그 밖에서 깨진다.**

**맞는 부분** — JPA는 **1차 캐시(identity map)** 를 유지한다. 같은 영속성 컨텍스트에서 같은 PK를 조회하면 **같은 인스턴스**를 준다.

```java
@Transactional
void test() {
    Reservation a = repo.findById(no);
    Reservation b = repo.findById(no);
    a == b;   // true ★ JPA가 같은 인스턴스를 준다
}
```

**깨지는 경우 3가지**

1. **트랜잭션 경계를 넘을 때** — 다른 트랜잭션/요청에서 읽은 두 객체는 다른 인스턴스 → `==` false
2. **`Set`/`Map`에 담을 때** — `hashCode()`도 없으면 버킷이 달라 비교조차 안 된다. **둘은 항상 쌍으로 구현**
3. **auto_increment 저장 전** — `id`가 `null`인 구간이 존재한다

> auto_increment는 **INSERT해야 값을 알 수 있어** 객체 생성 시 식별자를 전달할 수 없다.
> 그래서 이 책은 **규칙 기반/UUID 식별자를 선호**한다:
> ```java
> String orderNumber = orderRepository.generateOrderNumber();  // 생성 전에 확보
> Order order = new Order(orderNumber, ...);
> ```

**전제**: Java 기본 `equals()`는 `==`, 즉 **메모리 주소 비교**다. 오버라이드하지 않으면 같은 예약번호여도 `false`.

<a id="q4"></a>
## Q4. 예약=엔티티, 기간·투숙객=밸류인 건 감으로 알겠는데 "왜"인지 설명을 못 하겠어

> **한 줄 답: 기준은 "이걸 지목해서 조회/변경/삭제/추적할 일이 있는가?" 하나다.**

**3단계 판단 절차**

```
1) 지목해서 조회/변경/삭제/추적할 요구사항이 있는가?
     있다 → 엔티티 (식별자 필요)
2) 속성이 전부 같은 두 개를 서로 다른 것으로 구분해야 하는가?
     구분 필요 → 엔티티 / 같은 것으로 취급 → 밸류
3) (밸류면) 관련 규칙·계산 로직을 이 안에 모을 수 있는가?
```

**적용**

| | 판정 | 결정적 근거 |
|---|---|---|
| `Reservation` | 엔티티 | 홍길동이 같은 날짜·같은 금액으로 방 2개 예약 → 속성이 전부 같아도 **다른 예약**. A만 취소 가능해야 한다 |
| `DateRange` | 밸류 | `8/10~8/12` 두 개는 **완전히 같음**. "기간 ID 42번 조회"라는 요구가 없다 |
| `Guest` | 밸류 (조건부) | 예약서에 적힌 정보일 뿐. `Orderer`와 같은 구조 |

**밸류로 만들면 얻는 것** — 규칙이 그 안에 모인다:

```java
public class DateRange {
    public long nights() { ... }
    public boolean overlaps(DateRange other) { ... }   // ★ "예약 기간이 겹치면 안 된다"
    // 생성자에서 "종료일 < 시작일" 검증
}
```

필드 2개로 흩어두면 이 규칙이 서비스 코드로 흩어진다.

### ⚠️ 내가 썼던 틀린 근거: "테이블 컬럼이면 밸류, 테이블이면 엔티티"

**반례 2개 (둘 다 테이블 + PK가 있는데 밸류):**

- **`OrderLine`** — `order_line` 테이블 + PK 있음 → **밸류**
- **`ArticleContent`** — `article_content` 테이블 + `id` 칼럼 있음 → **밸류**

> **매핑되는 테이블의 식별자를 구성요소의 식별자와 동일시하면 안 된다.**
> 그 PK는 부모 테이블과 **연결하기 위한 것**이고, RDB가 밸류를 표현하지 못해 생긴 **기술적 부산물**이다.

**테이블 구조 = 저장 방식 / 엔티티·밸류 = 도메인 모델 개념.** `Address`가 컬럼으로 들어가든 별도 테이블로 빠지든 **양쪽 다 밸류**다.

> 저자도 초년 시절 "도메인 모델의 엔티티 = DB 모델의 엔티티"로 동일시했다고 책에 적혀 있는 흔한 함정.

### ⚠️ 또 하나: 요구사항이 바뀌면 판정도 바뀐다

| 요구사항 | `Guest`는 |
|---|---|
| "예약서에 이름·연락처를 적는다" | **밸류** |
| "투숙객이 로그인하고, 등급과 누적 숙박일이 쌓인다" | **엔티티** → `GuestId`로 ID 참조 |

**필드 개수는 기준이 아니다.** `Money`는 필드 1개인데 밸류.

## Q3. 포워더(Forwarder)가 뭐야?

> **한 줄 답: 이벤트를 DB에 저장해 두고, 주기적으로 읽어서 외부로 push하는 별도 컴포넌트.**

**선행 개념 (여기서 오해가 자주 생긴다)**

> **이벤트는 "강결합 문제"를 해결할 뿐, 성능·트랜잭션 문제를 해결하지 않는다.**
> 스프링 기본 `@EventListener`는 **동기 = 같은 스레드·같은 트랜잭션**이다.
> 외부 환불이 10초 걸리면 `cancel()`도 10초 걸리고, 환불이 실패해 롤백하면 **주문 취소 자체가 실패**한다.
> → 성능·트랜잭션 문제는 **비동기 처리**로 푼다.

```
   [ 한 트랜잭션 ]
   도메인 → Events.raise() → 디스패처 → 로컬 핸들러
                                            │
                                    ┌───────▼────────┐
                                    │  이벤트 저장소  │ (DB)
                                    └───────┬────────┘
                                            │ @Scheduled 로 주기적으로 읽음
                                    ┌───────▼────────┐
                                    │    포워더       │ ← 이것
                                    └───────┬────────┘
                                            ▼
                                    외부 핸들러 / 메시징 시스템
```

**최대 강점 2개**
1. **이벤트 유실 없음** — 발생과 저장을 **한 트랜잭션**으로
2. **재처리 가능** — 실패한 이벤트부터 다시 읽어 재시도

**포워더 vs API 방식**

| | 포워더 | API |
|---|---|---|
| 전달 방향 | **push** | **pull** |
| offset 추적 주체 | **포워더** | **외부 핸들러** |

**offset 로직의 핵심**
순서대로 보내다 익셉션이 나면 **멈추고 성공 개수만 리턴** → offset은 **성공한 만큼만** 전진 → 다음 주기에 실패한 이벤트부터 재시도. offset 저장 이유는 **중복 처리 방지**.

**함께 알아둘 함정 2개**
- **재전송 횟수 제한이 없으면** 실패 이벤트에 막혀 **뒤의 모든 이벤트가 정체** → 3회 실패 시 생략 + 별도 실패용 DB/큐 보관
- **롤백됐는데 핸들러가 실행되는 것** 방지 → `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`

<a id="q2"></a>
## Q2. spec(Specification)가 뭐야?

> **한 줄 답: 검색 조건을 객체로 만들어서 `find` 메서드 조합 폭발을 막는 것.**

**해결하려는 문제**

```java
findByOrderer(...)
findByOrdererAndDate(...)
findByOrdererAndState(...)
findByDateAndState(...)
findByOrdererAndDateAndState(...)
// 조건 A/B/C만 있어도 7개. 조건 하나 늘면 2배로 폭발
```

**해법** — 조건 자체를 객체로:

```java
public interface Specification<T> {
    boolean isSatisfiedBy(T agg);
}

Specification<Order> spec = new OrdererSpec("madvirus");
List<Order> orders = orderRepository.findAll(spec);   // 메서드는 이거 하나면 끝
```

조합은 `spec.and(otherSpec)`으로.

**`agg` 파라미터의 정체**
- 리포지터리에 쓰면 → **애그리거트 루트**
- DAO에 쓰면 → **검색 결과로 리턴할 데이터 객체**

### ★ 반드시 알아야 할 함정

> 책의 `isSatisfiedBy()` **메모리 필터링 코드는 개념 설명용이고 실제 구현이 아니다.**
> 모든 애그리거트를 메모리에 올릴 수 없고 **조회 성능이 붕괴**한다.
> **실제로는 `toPredicate()`로 DB 쿼리의 `WHERE` 절로 변환**되어 DB가 필터링한다.

<a id="q1"></a>
## Q1. "같은 라이프 사이클"이 무슨 뜻이야?

> **한 줄 답: 생성 → 변경 → 삭제의 타이밍. 한 애그리거트 객체들은 함께 태어나고 함께 죽는다.**

```
   주문 애그리거트를 생성하는 순간
   ├─ Order         ┐
   ├─ OrderLine     ├─ 전부 동시에 태어난다
   ├─ Orderer       │
   └─ ShippingInfo  ┘

   주문을 삭제하는 순간 → 전부 동시에 사라진다
```

`Order`는 만들었는데 `Orderer`(주문자)를 안 만드는 경우? **없다.** 주문자 없는 주문은 성립하지 않는다.

**`Product` / `Review`에 적용하면**

- 상품 등록 → 리뷰는 **0개** (같이 안 태어남)
- 리뷰 작성 → 상품은 **이미 오래전에 존재** (태어나는 시점이 완전히 다름)
- 리뷰 삭제 → 상품은 **멀쩡히 살아있음** (같이 안 죽음)

→ 라이프 사이클이 완전히 다르다 = **다른 애그리거트**

**함께 쓰는 판단 체크리스트 4개**

| # | 질문 | Product/Review |
|---|---|---|
| 1 | 함께 **생성**되는가? | ❌ |
| 2 | 함께 **변경**되는가? | ❌ |
| 3 | **변경 주체**가 같은가? | ❌ 상품=담당자, 리뷰=고객 |
| 4 | 한쪽 변경이 **다른 쪽에 영향**을 주는가? | ❌ |

> ★ **3번이 가장 강력한 근거**다. 애그리거트의 존재 이유가 **일관성 관리 단위**이므로, 바꾸는 사람이 다르면 지켜야 할 정합성이 없다 = 한 트랜잭션에 묶을 이유가 없다.

**⚠️ 1-N 관계(개수)는 판단 기준이 아니다.** `Order`-`OrderLine`도 1-N인데 **같은** 애그리거트다.
