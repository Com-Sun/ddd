## 1장 도메인 모델

> [!danger]- Trap: "A가 B를 갖는다" → 한 애그리거트일까?
> - **함정**: 요구사항이 "상품 상세 페이지에 **상품 정보와 리뷰**를 함께 보여준다"이면 `Product`가 `Review`를 갖는 것처럼 보인다.
> - **왜 헷갈리나**: 화면에 함께 보이는 것과 모델의 경계를 혼동한다.
> - **정답**: **서로 다른 애그리거트다.** ① **함께 생성되지 않고** ② **함께 변경되지 않으며** ③ **변경 주체가 다르다**(상품=담당자, 리뷰=고객) ④ 한쪽 변경이 다른 쪽에 영향을 주지 않는다.
> - → [[애그리거트]], [[도메인 모델]]

> [!danger]- Trap: 개념 모델을 처음부터 완벽하게 만들어야 한다?
> - **함정**: "설계를 잘하려면 초기에 완벽한 모델을 만들어야 한다"는 통념.
> - **정답**: **불가능하다.** 개발하는 동안 도메인 이해도가 계속 높아지고, 초기 지식이 **완전히 다른 의미로 해석**되기도 한다. 처음에는 **개요 수준**으로 전체 윤곽을 잡고 **점진적으로 구현 모델로 발전**시킨다.
> - → [[도메인 모델]]

> [!danger]- Trap: 밸류 타입은 데이터가 2개 이상이어야 한다?
> - **함정**: "여러 데이터를 하나로 묶는 것"이라는 정의만 기억하면 그렇게 오해한다.
> - **정답**: **거짓.** `Money`처럼 **데이터가 1개여도** 의미를 명확히 하기 위해 밸류 타입을 쓴다. 게다가 **밸류 타입을 위한 기능(계산 로직)을 추가**할 수 있다는 이점도 있다.
> - → [[밸류 타입]]

> [!danger]- Trap: 밸류의 `equals()`도 식별자 하나만 비교한다?
> - **함정**: 엔티티의 `equals()` 규칙과 혼동한다.
> - **정답**: **엔티티는 식별자만**, **밸류는 모든 속성**을 비교한다.
> - → [[엔티티와 식별자]], [[밸류 타입]]

> [!danger]- Trap: `private` set 메서드도 안티패턴인가?
> - **함정**: "도메인 모델에 set 메서드를 넣지 말라"를 **모든 set 금지**로 오해한다.
> - **정답**: 금지 대상은 **공개(public) set 메서드**다. 코드의 `setOrderer()` 등은 **접근 범위가 `private`** 이며, **생성자/도메인 메서드 안에서 검증 로직을 모으기 위해** 쓰인다.
> - → [[도메인 모델에 set 메서드 넣지 않기]], [[애그리거트 루트]]

## 2장 아키텍처

> [!danger]- Trap: Drools 타입을 안 쓰면 Drools에 의존하지 않는 것인가?
> - **함정**: import 문에 외부 라이브러리가 없으면 독립적이라고 착각한다.
> - **정답**: **완전히 의존하고 있다.** ① `"discountCalculation"` 문자열은 **Drools의 세션 이름** ② `MutableMoney`는 **룰 적용 결과 보관용 타입**. 둘 다 기술을 바꾸면 함께 바뀐다.
> - → [[계층 구조 아키텍처]]

> [!danger]- Trap: DIP = 인터페이스와 구현 클래스를 분리하는 것?
> - **함정**: 인터페이스만 뽑으면 DIP를 지켰다고 생각한다.
> - **왜 헷갈리나**: 구조만 보면 둘 다 "인터페이스 + 구현"이다.
> - **정답**: DIP의 핵심은 **고수준이 저수준에 의존하지 않게** 하는 것이다. **인터페이스를 저수준 관점에서 도출해 인프라에 두면 여전히 도메인이 인프라에 의존**한다.
>   - ❌ `RuleEngine` (룰 엔진 = 저수준 관점) — 인프라에 위치
>   - ⭕ `RuleDiscounter` (할인 계산 = 고수준 관점) — **도메인에 위치**
> - → [[DIP]]

> [!danger]- Trap: 도메인 모델에 `@Entity`를 붙이면 DIP 위반이니 없애야 한다?
> - **함정**: 원칙을 기계적으로 적용한다.
> - **정답**: 형식적으로는 위반이지만 **저자는 받아들인다.** **구현의 편리함은 DIP의 다른 장점만큼 중요**하고, `@Transactional` 의존을 없애려면 복잡한 설정이 필요한데 **테스트가 더 쉬워지지도 유연해지지도 않는다.** 판단 기준은 **"복잡도를 높이지 않으면서 구현 제약이 낮은가"**.
> - → [[인프라스트럭처 개요]], [[DIP와 아키텍처]], [[도메인 구현과 DIP]]

> [!danger]- Trap: 도메인 모델의 엔티티 = DB 모델의 엔티티?
> - **함정**: JPA `@Entity`를 쓰다 보면 둘을 동일시하게 된다. (저자도 초년 시절 그랬다)
> - **정답**: **다르다.** ① 도메인 엔티티는 **데이터와 함께 기능을 제공**하고 **캡슐화**한다 ② **밸류 타입**을 가질 수 있다. RDBMS는 밸류를 제대로 표현하지 못해, 한 테이블에 넣으면 **개념이 드러나지 않고** 별도 테이블로 빼면 **테이블 엔티티처럼** 되어버린다.
> - → [[도메인 영역의 주요 구성요소]]

## 3장 애그리거트

> [!danger]- Trap: 한 트랜잭션에서 두 애그리거트를 수정하면 무조건 안 되나?
> - **함정**: "1 트랜잭션 = 1 애그리거트"를 절대 규칙으로 외운다.
> - **정답**: 권장 원칙이지만 **3가지 예외**가 있다 — **① 팀 표준 ② 기술 제약(이벤트 도입 불가) ③ UI 구현의 편리**(운영자가 여러 주문 상태를 한 번에 변경).
> - 단, **애그리거트가 다른 애그리거트를 직접 수정하는 것**은 여전히 안 된다. 부득이하면 **응용 서비스**에서 각각 변경한다.
> - → [[트랜잭션 범위]]

> [!danger]- Trap: ID 참조로 바꾸면 모든 문제가 해결된다?
> - **함정**: ID 참조의 세 가지 이점만 기억한다.
> - **정답**: **새로운 문제가 생긴다.** ID 참조는 **지연 로딩과 같은 효과**를 내므로 **N+1 조회 문제**가 발생한다.
>   - 해법은 **조회 전용 쿼리**(별도 DAO + 조인 1회)다.
>   - **객체 참조 + 즉시 로딩으로 되돌리는 것은 ID 참조의 이점을 버리는 셈**이라 권장하지 않는다.
> - → [[ID를 이용한 애그리거트 참조]], [[ID 참조와 조회 성능]]

> [!danger]- Trap: 개념적으로 1-N이면 코드에도 컬렉션을 둔다?
> - **함정**: "카테고리는 여러 상품을 갖는다" → `Set<Product> products`.
> - **정답**: **반영하지 않는다.** 페이징을 위해 `getProducts(page, size)`를 호출하면 **카테고리의 모든 상품을 조회**하게 되어, 상품이 수만 개면 **성능에 심각한 문제**가 생긴다.
>   - 대안: **상품 쪽에서 N-1**(`Product.categoryId`) + 리포지터리에서 **DB가 페이징**하게 한다.
> - → [[애그리거트 간 집합 연관]]

> [!danger]- Trap: `OrderLines`를 그대로 리턴해도 되나?
> - **함정**: getter니까 안전하다고 생각한다.
> - **정답**: **외부에서 내부 상태를 변경**할 수 있게 되어, **`OrderLine` 목록은 바뀌는데 `totalAmounts`는 그대로인 버그**가 생긴다.
>   - 방어: ① **불변으로 구현** ② 불가능하면 변경 기능을 **패키지/`protected` 범위로 제한**.
> - → [[애그리거트 루트]]

## 4장 리포지터리와 모델 구현

> [!danger]- Trap: 별도 테이블에 저장하면 엔티티인가?
> - **함정**: `ARTICLE_CONTENT` 테이블에 `ID` 칼럼이 있으니 `ArticleContent`는 엔티티처럼 보인다.
> - **정답**: **밸류다.** 그 `ID`는 **`ARTICLE` 테이블과 연결하기 위한 것**이지 `ArticleContent`를 위한 **별도 식별자가 필요해서가 아니다.** **`OrderLine`도 별도 테이블에 저장하지만 밸류**다.
>   - 원칙: **매핑되는 테이블의 식별자를 구성요소의 식별자와 동일시하면 안 된다.**
> - → [[밸류를 이용한 ID 매핑과 별도 테이블 매핑]]

> [!danger]- Trap: 즉시 로딩으로 설정하면 조회가 빨라진다?
> - **함정**: "한 번에 가져오니까 빠르다"고 생각한다.
> - **정답**: **컬렉션 두 개에 EAGER를 걸면 카타시안 조인**이 발생한다. 이미지 20개 + 옵션 15개면 **300행**을 리턴한다(실제 필요: **36행**). 하이버네이트가 중복을 제거해 주지만 **애그리거트가 커지면 문제**가 된다.
>   - **지연 로딩은 동작 방식이 항상 동일**해 경우의 수를 따질 필요가 없다는 장점이 있다.
> - → [[애그리거트 로딩 전략]]

> [!danger]- Trap: `@Embeddable`과 `@Entity` 컬렉션은 `clear()` 성능이 같다?
> - **함정**: 둘 다 컬렉션이니 같을 것이라 생각한다.
> - **정답**: **다르다.**
>   - `@Entity` + `@OneToMany` → **SELECT 1회 + DELETE N회**
>   - `@Embeddable` + `@ElementCollection` → **DELETE 1회**
>   - 상속이 필요해 `@Entity`로 매핑했는데 변경 빈도가 높다면, **상속을 포기하고 `@Embeddable` 단일 클래스 + if-else**로 가는 것이 성능상 유리하다.
> - → [[밸류 컬렉션 매핑]]

> [!danger]- Trap: `@Embeddable`에도 `cascade`를 지정해야 하나?
> - **함정**: 영속성 전파는 다 설정해야 한다고 생각한다.
> - **정답**: **`@Embeddable`은 불필요**하다(자동으로 함께 저장·삭제). **`@Entity` 매핑(`@OneToOne`, `@OneToMany`)은 `cascade` 기본값이 없으므로** `PERSIST`, `REMOVE`를 직접 지정하고 `orphanRemoval = true`도 설정해야 한다.
> - → [[애그리거트의 영속성 전파]]

> [!danger]- Trap: 불변 밸류인데 왜 기본 생성자가 필요한가?
> - **함정**: 불변이면 생성자로 모든 값을 받으니 기본 생성자가 불필요하다고 생각한다.
> - **정답**: **JPA가 DB에서 데이터를 읽어와 객체를 생성할 때 기본 생성자를 사용**하기 때문이다. 다만 다른 코드가 쓰면 **온전하지 못한 객체**가 만들어지므로 **`protected`** 로 선언한다.
> - → [[엔티티와 밸류 기본 매핑]]

## 5장 조회 기능

> [!danger]- Trap: `List`로 리턴하면 COUNT 쿼리가 실행되지 않는다?
> - **함정**: "`Page`면 COUNT, `List`면 안 함"만 외운다.
> - **정답**: **스펙을 사용하는 `findAll(Specification, Pageable)`은 리턴 타입이 `List`여도 COUNT 쿼리를 실행한다.**
>   - `findByXxx(..., Pageable)` + `List` → COUNT 안 함 ⭕
>   - **`findAll(Spec, Pageable)` + `List` → COUNT 실행** ⚠️
>   - 회피하려면 **커스텀 리포지터리 기능**으로 직접 구현해야 한다.
> - → [[페이징 처리하기]]

> [!danger]- Trap: `PageRequest.of(1, 10)`은 1~10번째를 조회한다?
> - **함정**: 1페이지라고 생각한다.
> - **정답**: **페이지 번호는 0부터** 시작하므로 **두 번째 페이지 = 11~20번째**를 조회한다.
> - → [[페이징 처리하기]]

> [!danger]- Trap: 스펙은 메모리에서 필터링하는 것이다?
> - **함정**: 5.2절의 `isSatisfiedBy()` 예제 코드를 실제 구현으로 오해한다.
> - **정답**: **실제 스펙은 그렇게 구현하지 않는다.** 모든 애그리거트를 메모리에 보관할 수 없고 **조회 성능에 심각한 문제**가 생긴다. 실제로는 **사용 기술에 맞춰**(스프링 데이터 JPA의 `toPredicate`) **DB 쿼리의 WHERE 절로 변환**된다.
> - → [[검색을 위한 스펙]]

> [!danger]- Trap: `@Subselect`만 붙이면 되나?
> - **함정**: 세 애너테이션의 역할을 구분하지 못한다.
> - **정답**: 셋 다 필요하다.
>   - **`@Subselect`** — 쿼리 결과를 매핑할 테이블처럼 사용
>   - **`@Immutable`** — 수정 시 UPDATE로 **에러 나는 것을 방지**
>   - **`@Synchronize`** — 로딩 전에 **관련 테이블 변경을 먼저 플러시**. 없으면 **이전 값(stale)** 이 조회된다.
>   - 또한 `@Subselect` 쿼리는 **`from` 절의 서브 쿼리**로 들어간다.
> - → [[하이버네이트 Subselect 사용]]

## 6장 응용 서비스와 표현 영역

> [!danger]- Trap: 응용 서비스가 애그리거트를 리턴하면 편하지 않나?
> - **함정**: 컨트롤러에서 바로 쓰면 코드가 짧아진다.
> - **정답**: **도메인 로직 실행을 응용 서비스와 표현 영역 두 곳에서 할 수 있게 되어** 기능 실행 로직이 분산되고 **응집도가 낮아진다.**
>   - "뷰에서 애그리거트 기능을 쓰지 말자"는 **규칙보다, 필요한 데이터만 리턴하는 것이 확실한 방법**이다.
> - → [[메서드 파라미터와 값 리턴]]

> [!danger]- Trap: 응용 서비스는 인터페이스를 만드는 게 좋은 설계다?
> - **함정**: "인터페이스 = 좋은 설계"라는 통념.
> - **정답**: **명확하게 필요하기 전까지는 좋은 선택이 아니다.** 응용 서비스는 **런타임 교체가 거의 없고 구현 클래스가 두 개인 경우도 드물다.** 만들면 **파일 수와 간접 참조만 증가**한다. **Mockito는 클래스에 대해서도 대역 객체를 만들 수 있어** 테스트용 인터페이스도 불필요하다.
> - → [[응용 서비스의 인터페이스와 클래스]]

> [!danger]- Trap: 응용 서비스에 `HttpServletRequest`를 넘기면 무엇이 가장 심각한가?
> - **함정**: "테스트가 어려워진다" 정도로만 답한다.
> - **정답**: 가장 심각한 것은 **응용 서비스가 표현 영역의 역할까지 대신하는 것**이다. `HttpSession`·쿠키는 **표현 영역의 상태**인데 응용 서비스가 이를 조작하면 **표현 영역 코드만으로 상태 변화를 추적할 수 없어 표현 영역의 응집도가 깨진다.**
> - → [[표현 영역에 의존하지 않기와 트랜잭션 처리]]

> [!danger]- Trap: 값 검증은 응용 서비스에서만 하면 되나?
> - **함정**: "원칙적으로 응용 서비스"만 외운다.
> - **정답**: 원칙은 맞지만 **잘못된 값을 만나는 즉시 익셉션을 던지면 첫 오류만 알려주게 되어 나쁜 UX**가 된다.
>   - 해법 A: 에러를 **모아 하나의 익셉션**으로 발생
>   - 해법 B: **표현 영역에서 형식 검증**(`Errors`/`Validator`) + 응용 서비스는 **논리적 오류**
> - → [[값 검증]]

> [!danger]- Trap: 조회만 하는 응용 서비스도 반드시 만들어야 하나?
> - **함정**: "컨트롤러가 DAO를 직접 쓰면 안 된다"는 통념.
> - **정답**: **생략해도 된다.** ① **추가 로직이 없고** ② **단일 쿼리라 트랜잭션도 불필요**하기 때문이다. 판단 기준은 **"응용 서비스가 별다른 기여를 하는가"**.
> - → [[조회 전용 기능과 응용 서비스]]

## 7장 도메인 서비스

> [!danger]- Trap: 도메인 서비스를 애그리거트에 `@Autowired`로 주입하면?
> - **함정**: 스프링 DI에 익숙하면 "기술적으로 더 나은 방법"처럼 느껴진다.
> - **정답**: **좋은 방법이 아니다.** ① **데이터가 아니다**(모델의 필드는 데이터를 담아야 한다) ② **저장 대상이 아니다** ③ **일부 기능만 필요로 한다.**
>   - 대안: **필요한 메서드의 파라미터로 전달**하고, 전달은 **응용 서비스**가 한다.
> - → [[도메인 서비스]]

> [!danger]- Trap: 응용 서비스인가 도메인 서비스인가?
> - **함정**: "여러 애그리거트를 쓰면 도메인 서비스"로만 판단한다.
> - **정답**: 판별 기준은 **"애그리거트의 상태를 변경하거나 상태 값을 계산하는가"** 다.
>   - 계좌 이체 → 계좌 애그리거트의 **상태 변경** → **도메인 서비스**
>   - 결제 금액 계산 → 주문 애그리거트의 **금액 계산** → **도메인 서비스**
>   - 트랜잭션 처리 → **응용 로직** → **응용 서비스**
> - → [[도메인 서비스]]

## 8장 트랜잭션 관리

> [!danger]- Trap: 선점 잠금이면 무조건 안전한가?
> - **함정**: 잠금을 걸면 문제가 없다고 생각한다.
> - **정답**: **교착 상태(deadlock)** 위험이 있다. 스레드1이 A→B, 스레드2가 B→A 순으로 잠그면 둘 다 진행 불가다. **사용자 수가 많을수록 발생 가능성이 높고**, 교착에 빠지는 스레드가 늘면 **시스템이 아무것도 못 하게 된다.**
>   - 대비: **`javax.persistence.lock.timeout`** 힌트 (스프링은 `@QueryHints`)
>   - ⚠️ **DBMS에 따라 힌트가 적용되지 않을 수 있다.** 쿼리별 지정이 되는 DBMS와 **커넥션 단위로만** 되는 DBMS가 있다.
> - → [[선점 잠금]]

> [!danger]- Trap: 선점 잠금으로 모든 동시성 문제를 풀 수 있나?
> - **함정**: 잠금이 강력하니 다 될 것 같다.
> - **정답**: **조회와 수정이 서로 다른 트랜잭션이면 선점 잠금으로 해결할 수 없다.** 운영자가 주문을 조회한 뒤 **별도 요청으로** 배송 상태를 변경하는 사이에 고객이 배송지를 바꾸는 문제가 그것이다. → **비선점 잠금**이 필요하다.
> - → [[비선점 잠금]]

> [!danger]- Trap: `@Version`만 붙이면 비선점 잠금이 완벽한가?
> - **함정**: 버전 필드만 있으면 된다고 생각한다.
> - **정답**: **루트가 아닌 엔티티만 변경되면 JPA는 루트의 버전을 증가시키지 않는다**(루트 자체 값이 안 바뀌었으므로). 하지만 **애그리거트 관점에서는 구성요소가 바뀌면 애그리거트가 바뀐 것**이다.
>   - 해법: **`LockModeType.OPTIMISTIC_FORCE_INCREMENT`** — 상태 변경 여부와 무관하게 트랜잭션 종료 시점에 **버전을 강제 증가**시킨다.
> - → [[강제 버전 증가]]

> [!danger]- Trap: 오프라인 선점 잠금에 유효 시간만 두면 되나?
> - **함정**: 유효 시간을 두면 해결됐다고 생각한다.
> - **정답**: **새로운 문제가 생긴다.** 유효 시간이 지난 뒤 정상 사용자가 수정하면 **잠금이 해제되어 수정에 실패**한다.
>   - 해법: **일정 주기로 유효 시간을 증가**시킨다(예: 수정 폼에서 1분마다 AJAX로 `extendLockExpiration`).
>   - 그리고 기능 실행 전에 **반드시 `checkLock()`** 을 호출해야 한다 — ① 유효 시간이 지나 타인이 선점했을 수 있고 ② 잠금을 선점하지 않은 사용자를 막아야 한다.
> - → [[오프라인 선점 잠금]], [[LockManager 구현]]

## 9장 바운디드 컨텍스트

> [!danger]- Trap: 하위 도메인과 바운디드 컨텍스트는 1:1인가?
> - **함정**: 이상적인 그림만 기억한다.
> - **정답**: **이상적으로는 그렇지만 현실은 다르다.** **기업의 팀 조직 구조**에 따라 결정되기도 한다(주문 팀 + 결제 금액 계산 팀 → 컨텍스트 2개). 반대로 **용어 구분이 명확하지 않아** 카탈로그와 재고를 한 컨텍스트에서 구현하기도 한다.
> - → [[바운디드 컨텍스트]]

> [!danger]- Trap: 한 컨텍스트에 여러 하위 도메인이 있으면 단일 모델을 만들어도 되나?
> - **함정**: 어차피 한 프로젝트니까 하나로 묶고 싶어진다.
> - **정답**: **가장 빠지기 쉬운 유혹**이다. 그러면 도메인 모델이 **개별 하위 도메인을 제대로 반영하지 못해 하위 도메인별 기능 확장이 어려워지고 서비스 경쟁력이 떨어진다.**
>   - 해법: **하위 도메인마다 구분되는 패키지**를 두어 **논리적 바운디드 컨텍스트** 효과를 낸다.
> - → [[바운디드 컨텍스트]]

> [!danger]- Trap: 모든 바운디드 컨텍스트를 DDD로 구현해야 하나?
> - **함정**: DDD 책이니 전부 도메인 모델로 만들어야 할 것 같다.
> - **정답**: **아니다.** **상품 리뷰처럼 복잡한 도메인 로직이 없으면 CRUD(서비스-DAO)로 구현해도 된다.** 한 컨텍스트에서 **두 방식을 혼합**할 수도 있다(대표 예: **CQRS**).
> - → [[바운디드 컨텍스트 구현]]

> [!danger]- Trap: 공유 커널은 중복을 줄이니 항상 좋은가?
> - **함정**: "중복 제거 = 선"이라는 통념.
> - **정답**: **조건이 있다.** 한 팀이 **임의로 모델을 변경하면 안 되고 두 팀이 밀접한 관계를 유지**해야 한다. 그렇지 못하면 **공유 커널의 장점보다 개발이 지연되고 정체되는 문제가 더 커진다.**
> - → [[바운디드 컨텍스트 간 관계]]

> [!danger]- Trap: 메시지 큐로 통합하면 데이터 구조는 누가 정하나?
> - **함정**: 보내는 쪽이 정한다고 생각한다.
> - **정답**: **큐를 제공(소유)하는 쪽의 도메인**을 따른다. 카탈로그가 큐를 제공하면 카탈로그 도메인 구조로 담기고 **추천 시스템이 변환**한다. 이는 **출판/구독 모델**이다.
> - → [[바운디드 컨텍스트 간 통합]]

## 10장 이벤트

> [!danger]- Trap: 이벤트를 도입하면 성능·트랜잭션 문제가 해결되나?
> - **함정**: "이벤트 = 비동기"라고 생각한다.
> - **정답**: **이벤트는 강결합 문제를 해결할 뿐이다.** 스프링의 기본 `@EventListener`는 **동기**로, **같은 스레드·같은 트랜잭션**에서 실행된다. 따라서 **외부 환불이 느려지면 `cancel()`도 느려지고**, 실패 시 롤백하면 **구매 취소 자체가 실패**한다.
>   - 성능·트랜잭션 문제는 **비동기 처리** 또는 **트랜잭션 연계**로 푼다.
> - → [[동기 이벤트 처리 문제]]

> [!danger]- Trap: 이벤트에 데이터를 많이 담을수록 좋은가?
> - **함정**: 핸들러가 편하도록 다 담으려 한다.
> - **정답**: **양쪽 다 문제다.**
>   - **부족하면** 핸들러가 **리포지터리·API·DB 직접 조회**를 해야 한다.
>   - **과하면** — 배송지 변경 이벤트에 **주문 상품 번호와 개수를 담을 필요는 없다.**
> - → [[이벤트 개요]]

> [!danger]- Trap: 포워더에 재전송 제한이 없으면?
> - **함정**: "실패하면 계속 재시도하면 되지"라고 생각한다.
> - **정답**: 포워더는 **실패한 이벤트부터 다시 읽어오므로**, 특정 이벤트가 계속 실패하면 **그 이벤트 때문에 나머지 이벤트를 전송할 수 없게 된다**(전체 정체).
>   - 해법: **3회 실패 시 생략** 등 **재전송 횟수 제한** 정책. 생략한 이벤트는 **별도 실패용 DB/큐에 저장**해 두면 분석·후처리에 도움이 된다.
> - → [[이벤트 적용 시 고려사항]]

> [!danger]- Trap: 자동 증가 칼럼을 offset으로 쓰면 안전한가?
> - **함정**: ID가 순차 증가하니 안전해 보인다.
> - **정답**: **누락이 발생할 수 있다.** 자동 증가 칼럼은 **`INSERT` 시점에 증가하지만 데이터는 커밋 시점에 반영**된다. A가 11, B가 12를 획득한 상태에서 **B가 먼저 커밋되면 그 사이 조회 시 11이 빠지고 12만 조회**된다 → offset이 12를 넘어가 **11번 이벤트가 영원히 누락**된다.
>   - 해법: **ID 기준 지연 조회**
> - → [[이벤트 저장소를 이용한 비동기 처리]]

> [!danger]- Trap: 트랜잭션이 롤백됐는데 이벤트 핸들러가 실행되면?
> - **함정**: 이벤트는 트랜잭션과 무관하다고 생각한다.
> - **정답**: **경우의 수를 줄여야 한다.** 트랜잭션 실패와 이벤트 처리 실패를 모두 고려하면 복잡하므로, **트랜잭션이 성공할 때만 핸들러를 실행**한다.
>   - **`@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`**
>   - 또는 **이벤트 발생과 저장을 한 트랜잭션**으로 처리(DB 이벤트 저장소)
> - → [[이벤트 적용 시 고려사항]]

## 11장 CQRS

> [!danger]- Trap: CQRS는 항상 도입하는 것이 좋은가?
> - **함정**: 좋은 패턴이니 적용하고 싶어진다.
> - **정답**: **도메인이 복잡하지 않은데 도입하면 두 모델을 유지하는 비용만 높아지고 얻을 이점은 없다.** 반대로 **트래픽이 높은데 단일 모델을 고집하면 유지 보수 비용이 오히려 높아진다.**
>   - 판단 축: **도메인 복잡도 × 트래픽 규모**
> - → [[CQRS 장단점]]

> [!danger]- Trap: CQRS를 하려면 특별한 프레임워크가 필요한가?
> - **함정**: 이벤트 소싱·전용 라이브러리가 필수라고 생각한다.
> - **정답**: **필수 기술은 따로 존재하지 않는다.** **JPA만으로도** 명령 모델과 조회 모델을 구현할 수 있다. 5장의 **동적 인스턴스**와 **`@Subselect`** 가 바로 조회 모델이다.
> - → [[CQRS]], [[동적 인스턴스를 이용한 조회]], [[하이버네이트 Subselect 사용]]

> [!danger]- Trap: 우리는 CQRS를 안 쓴다?
> - **함정**: 명시적으로 도입하지 않았으니 무관하다고 생각한다.
> - **정답**: **대규모 트래픽 웹 서비스는 알게 모르게 CQRS를 적용하고 있다.** **화면에 맞게 변환한 데이터를 캐싱**하는 것은 **조회 전용 모델을 캐시하는 것**이고, **쿼리 최적화**도 조회 화면용 데이터를 빠르게 읽는 것이다. 단지 **명시적으로 구분하지 않을 뿐**이다.
> - → [[CQRS]]
