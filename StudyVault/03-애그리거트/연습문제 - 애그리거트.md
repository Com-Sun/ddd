## Question 1 - 애그리거트의 두 효용 [recall]
> 애그리거트가 제공하는 두 가지 효용은 무엇인가?

> [!answer]- 정답 보기
> ① **모델 이해** — 수많은 객체를 묶어서 **상위 수준에서 도메인 모델 간의 관계**를 파악할 수 있다.
> ② **일관성 관리 기준** — 애그리거트 **단위로 일관성을 관리**한다.
> 결과적으로 복잡한 도메인을 단순한 구조로 만들어 **개발 시간을 줄여준다.**

---

## Question 2 - 애그리거트의 경계 [recall]
> 애그리거트의 경계와 관련해, 주문 애그리거트가 할 수 있는 일과 할 수 없는 일을 예로 설명하라.

> [!answer]- 정답 보기
> 각 애그리거트는 **자기 자신을 관리할 뿐 다른 애그리거트를 관리하지 않는다.**
> - 할 수 있음: **배송지 변경**, **주문 상품 개수 변경**
> - 할 수 없음: **회원의 비밀번호 변경**, **상품의 가격 변경**

## Question 3 - 경계 설정 기준 [recall]
> 애그리거트 경계를 설정할 때 기본이 되는 것은 무엇이며, 한 애그리거트에 속할 가능성이 높은 두 가지 신호는?

> [!answer]- 정답 보기
> 기본이 되는 것은 **도메인 규칙과 요구사항**이다.
> 신호: ① 도메인 규칙에 따라 **함께 생성**되는 구성요소 ② **함께 변경되는 빈도가 높은** 객체

## Question 4 - 애그리거트 루트의 역할 [recall]
> 애그리거트 루트의 핵심 역할은 무엇이며, 이를 위해 무엇을 하는가?

> [!answer]- 정답 보기
> 핵심 역할은 **애그리거트의 일관성이 깨지지 않도록 하는 것**이다.
> 이를 위해 애그리거트 루트는 **애그리거트가 제공해야 할 도메인 기능을 구현**하며, 그 메서드는 도메인 규칙에 따라 **속한 객체의 일관성이 깨지지 않도록** 구현해야 한다.

## Question 5 - 일관성을 지키는 두 습관 [recall]
> 애그리거트 루트를 통해서만 도메인 로직을 구현하게 만들려면 도메인 모델에 습관적으로 적용해야 할 두 가지는?

> [!answer]- 정답 보기
> ① **단순히 필드를 변경하는 set 메서드를 공개(public) 범위로 만들지 않는다.**
> ② **밸류 타입은 불변으로 구현한다.**
> 밸류가 불변이면 값을 변경하는 방법은 **새로운 밸류 객체를 할당하는 것뿐**이므로, 루트가 제공하는 메서드를 거칠 수밖에 없다.

## Question 6 - 트랜잭션 범위 원칙 [recall]
> 트랜잭션 범위에 관한 대원칙과, 한 트랜잭션에서 두 개 이상의 애그리거트를 수정하면 생기는 두 가지 문제는?

> [!answer]- 정답 보기
> 대원칙: **트랜잭션 범위는 작을수록 좋다** → **한 트랜잭션에서는 한 애그리거트만 수정한다.**
> 문제 ①: 잠금 대상이 늘어 **동시 처리 트랜잭션 수가 줄고 전체 처리량이 떨어진다.**
> 문제 ②: 애그리거트 간 **결합도가 높아져 향후 수정 비용이 증가한다.**

## Question 7 - 리포지터리의 단위와 완전성 [recall]
> `Order`와 `OrderLine`을 별도 테이블에 저장한다면 리포지터리를 각각 만들어야 하는가? 그리고 조회 시 지켜야 할 규칙은?

> [!answer]- 정답 보기
> **각각 만들지 않는다.** `Order`가 애그리거트 루트이므로 **`OrderRepository`만 존재**한다.
> 조회 규칙: 리포지터리는 **완전한 애그리거트를 제공**해야 한다. 그렇지 않으면 기능 실행 도중 **`NullPointerException`** 같은 문제가 발생한다.
> 저장 규칙: **애그리거트 전체**를 영속화해야 한다(관련 테이블이 3개면 3개 모두).

## Question 8 - 직접 참조의 세 문제 [recall]
> 필드(객체)로 다른 애그리거트를 직접 참조할 때 발생하는 세 가지 문제를 나열하라.

> [!answer]- 정답 보기
> ① **편한 탐색 오용** — 다른 애그리거트의 상태를 쉽게 변경하는 유혹에 빠진다 (가장 큰 문제)
> ② **성능에 대한 고민** — 지연/즉시 로딩 전략을 매번 결정해야 한다
> ③ **확장의 어려움** — 하위 도메인마다 다른 저장소를 쓰면 JPA 같은 단일 기술로 참조할 수 없다

## Question 9 - 1-N 연관 [recall]
> 카테고리-상품처럼 개념적으로 1-N 연관이 존재할 때, 이를 실제 구현에 반영해야 하는가? 이유와 대안은?

> [!answer]- 정답 보기
> **반영하지 않는다.**
> 이유: 페이징을 위해 `category.getProducts(page, size)`를 호출하면 **카테고리에 속한 모든 상품을 조회**하게 되어, 상품이 수만 개면 **실행 속도가 급격히 느려진다.**
> 대안: **상품 입장에서 자신이 속한 카테고리를 N-1로 연관** 짓고(`Product.categoryId`), 리포지터리에서 `findByCategoryId(id, page, size)`로 **DB가 페이징을 처리**하게 한다.

## Question 10 - 애그리거트 경계 판단 [application]
> "상품 상세 페이지에 상품 정보와 리뷰를 함께 보여줘야 한다"는 요구사항이 있다. `Product`와 `Review`를 한 애그리거트로 묶어야 하는가? 판단 근거를 제시하라.

> [!answer]- 정답 보기
> **묶으면 안 된다. 서로 다른 애그리거트다.**
> 근거: ① **함께 생성되지 않는다** ② **함께 변경되지 않는다** ③ **변경 주체가 다르다**(상품=상품 담당자, 리뷰=고객) ④ 한쪽의 변경이 **다른 쪽에 영향을 주지 않는다.**
> 교훈: "**A가 B를 갖는다**"로 해석되는 요구사항이 있어도, 그것이 **한 애그리거트를 의미하지는 않는다.**

## Question 11 - 일관성 위반 코드 수정 [application]
> 아래 코드의 문제를 지적하고 올바르게 고쳐라.
> ```java
> ShippingInfo si = order.getShippingInfo();
> si.setAddress(newAddress);
> ```

> [!answer]- 정답 보기
> **문제**: 애그리거트 루트를 우회해 내부 객체를 직접 변경한다. 주문 **상태에 상관없이** 주소가 바뀌므로 **업무 규칙을 무시하고 DB를 직접 수정하는 것과 같은 결과**가 되어 논리적 일관성이 깨진다.
> **응용 서비스에서 상태를 검사하는 것도 답이 아니다** — 동일한 검사 로직이 여러 응용 서비스에 **중복**된다.
> **고침**: `ShippingInfo`를 **불변**으로 만들고, 루트에 도메인 메서드를 둔다.
> ```java
> order.changeShippingInfo(newShippingInfo);  // 내부에서 verifyNotYetShipped() 수행
> ```

## Question 12 - 트랜잭션 범위 위반 수정 [application]
> 아래 코드의 문제와 두 가지 개선 방법을 제시하라.
> ```java
> public void shipTo(ShippingInfo info, boolean useAsMemberAddr) {
>     setShippingInfo(info);
>     if (useAsMemberAddr) {
>         orderer.getMember().changeAddress(info.getAddress());
>     }
> }
> ```

> [!answer]- 정답 보기
> **문제**: `Order` 애그리거트가 **다른 애그리거트(`Member`)의 상태를 변경**한다. 자신의 책임 범위를 넘어서며 **애그리거트 간 결합도**를 높이고, 한 트랜잭션에서 두 애그리거트를 수정하게 된다.
> **개선 ①** — **응용 서비스**에서 각 애그리거트를 각각 변경한다.
> ```java
> order.shipTo(newShippingInfo);
> Member member = findMember(order.getOrderer());
> member.changeAddress(newShippingInfo.getAddress());
> ```
> **개선 ②** — **도메인 이벤트**를 사용해 한 트랜잭션에서 한 애그리거트만 수정하면서 동기/비동기로 다른 애그리거트를 변경한다(10장).

## Question 13 - N+1 해결 [application]
> 주문 10건의 목록 화면에서 쿼리가 11번 실행된다. 문제의 이름과, ID 참조를 유지하면서 해결하는 방법을 제시하라.

> [!answer]- 정답 보기
> **N+1 조회 문제**다(N개를 읽는 1번의 쿼리 + 연관 데이터를 읽는 N번의 쿼리).
> **해법**: **조회 전용 쿼리**를 사용한다. 데이터 조회를 위한 **별도 DAO**를 만들고 **한 번의 쿼리로 조인**해서 필요한 데이터를 로딩한다.
> ```java
> "select new OrderView(o, m, p) from Order o join o.orderLines ol, Member m, Product p " +
> "where o.orderer.memberId.id = :ordererId and ... and index(ol) = 0 ..."
> ```
> SQL 특화 기능이 필요하면 조회 부분만 **마이바티스** 등으로 구현해도 된다. (객체 참조+즉시 로딩으로 되돌리는 것은 ID 참조의 이점을 버리는 셈이라 권장하지 않는다.)

## Question 14 - 팩토리 메서드 판단 [analysis]
> 아래 응용 서비스 코드의 설계적 문제를 지적하고, 리팩터링 방향과 그 판단 기준을 설명하라.
> ```java
> Store store = storeRepository.findById(req.getStoreId());
> if (store.isBlocked()) throw new StoreBlockedException();
> Product product = new Product(id, store.getId(), ...);
> ```

> [!answer]- 정답 보기
> **문제**: **중요한 도메인 로직이 응용 서비스에 노출**되었다. "`Store`가 `Product`를 생성할 수 있는지 판단하고 생성하는 것"은 **논리적으로 하나의 도메인 기능**인데 응용 서비스에 흩어져 있다.
> **리팩터링**: `Store` 애그리거트에 **팩토리 메서드**를 둔다.
> ```java
> public Product createProduct(ProductId newProductId, ...) {
>     if (isBlocked()) throw new StoreBlockedException();
>     return new Product(newProductId, getId(), ...);
> }
> ```
> **판단 기준**: ① 애그리거트가 갖고 있는 **데이터를 이용해 다른 애그리거트를 생성**하는가(`Store`의 식별자 필요) ② 생성 **조건 판단에 그 애그리거트의 상태**를 쓰는가(`isBlocked()`). 둘 다 참이면 팩토리 메서드를 고려한다.
> **효과**: 생성 조건 로직이 바뀌어도 **도메인의 `Store`만 변경**하면 되고 응용 서비스는 영향받지 않는다.

## Question 15 - ID 참조의 트레이드오프 [analysis]
> ID 참조는 직접 참조의 세 문제를 해결하지만 새로운 문제를 만든다. 무엇을 얻고 무엇을 잃는지 종합적으로 평가하고, 언제 어떤 대응이 필요한지 서술하라.

> [!answer]- 정답 보기
> **얻는 것**
> - 애그리거트 **경계가 명확**해지고 물리적 연결이 제거되어 **모델 복잡도 ↓**
> - 애그리거트 간 **의존 제거 → 응집도 ↑, 결합도 ↓**
> - 다른 애그리거트의 상태 변경이 **근원적으로 불가능**
> - 지연/즉시 로딩 고민 **불필요**
> - **애그리거트별로 다른 저장 기술** 사용 가능(주문=RDBMS, 상품=NoSQL), 별도 프로세스 서비스화도 가능
>
> **잃는 것 / 대응**
> - ID 참조는 **지연 로딩과 같은 효과** → **N+1 조회 문제** 발생
> - 같은 DB 안이면 → **조회 전용 쿼리(별도 DAO, 조인 1회)** 로 해결
> - 애그리거트마다 **저장소가 다르면** 한 번의 쿼리로 조회할 수 없음 → **캐시** 또는 **조회 전용 저장소**. 코드는 복잡해지지만 처리량을 높일 수 있고, **한 대의 DB로 감당 못 하는 트래픽에서는 필수**다.
>
> **결론**: ID 참조의 이점이 크므로 기본 선택으로 삼되, **조회 성능은 조회 전용 모델/쿼리로 별도 해결**한다. 이것이 11장 [[CQRS]]로 이어지는 문제의식이다.
