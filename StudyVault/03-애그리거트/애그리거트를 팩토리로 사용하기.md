# 애그리거트를 팩토리로 사용하기 (★★★)

#ddd #aggregate #aggregate-factory #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 문제 | **생성 가능 판단**과 **생성**이 논리적으로 하나인데 **응용 서비스에 노출**됨 |
| 해법 | 애그리거트에 **팩토리 메서드**를 구현한다 |
| 적용 신호 | 애그리거트가 갖고 있는 **데이터를 이용해서 다른 애그리거트를 생성**해야 할 때 |
| 추가 신호 | 생성 **조건 판단에 그 애그리거트의 상태**를 이용할 때 |
| 효과 | 도메인 로직이 **도메인 영역에 모이고**, 응용 서비스는 **영향을 받지 않는다** |
| 확장 | 알아야 할 정보가 많으면 **다른 팩토리에 위임**해도 된다 |

## ❌ 문제 — 도메인 로직이 응용 서비스에 노출

```java
public class RegisterProductService {

    public ProductId registerNewProduct(NewProductRequest req) {
        Store store = storeRepository.findById(req.getStoreId());
        checkNull(store);
        if (store.isBlocked()) {                  // ① 생성 가능한지 판단
            throw new StoreBlockedException();
        }
        ProductId id = productRepository.nextId();
        Product product = new Product(id, store.getId(), ...생략);  // ② 생성
        productRepository.save(product);
        return id;
    }
}
```

> [!warning] 무엇이 문제인가
> 코드가 나빠 보이지는 않지만 **중요한 도메인 로직 처리가 응용 서비스에 노출**되었다.
>
> **`Store`가 `Product`를 생성할 수 있는지를 판단하고 `Product`를 생성하는 것은 논리적으로 하나의 도메인 기능**인데,
> 이 도메인 기능을 **응용 서비스에서 구현**하고 있는 것이다.

```
   [ 논리적으로 하나의 도메인 기능 ]
   ┌────────────────────────────────┐
   │ ① 차단된 상점인가 판단          │  ← 응용 서비스에 흩어져 있다 ❌
   │ ② Product 생성                  │
   └────────────────────────────────┘
```

## ⭕ 해법 — 애그리거트에 팩토리 메서드

이 도메인 기능을 넣기 위해 **별도의 도메인 서비스나 팩토리 클래스를 만들 수도 있지만**, 이 기능을 **`Store` 애그리거트에 구현할 수도 있다.**

```java
public class Store {

    public Product createProduct(ProductId newProductId, ...생략) {
        if (isBlocked()) throw new StoreBlockedException();
        return new Product(newProductId, getId(), ...생략);
    }
}
```

> [!important]
> `Store` 애그리거트의 `createProduct()`는 **`Product` 애그리거트를 생성하는 팩토리 역할**을 한다.
> **팩토리 역할을 하면서도 중요한 도메인 로직을 구현**하고 있다.

```java
public class RegisterProductService {

    public ProductId registerNewProduct(NewProductRequest req) {
        Store store = storeRepository.findById(req.getStoreId());
        checkNull(store);
        ProductId id = productRepository.nextId();
        Product product = store.createProduct(id, ...생략);   // 팩토리 기능 사용
        productRepository.save(product);
        return id;
    }
}
```

> [!tip] 무엇이 좋아졌나
> - 앞선 코드와 차이점은 **응용 서비스에서 더 이상 `Store`의 상태를 확인하지 않는다**는 것이다.
> - `Store`가 `Product`를 생성할 수 있는지를 확인하는 **도메인 로직은 `Store`에서 구현**하고 있다.
> - 이제 `Product` 생성 가능 여부를 확인하는 **도메인 로직을 변경해도 도메인 영역의 `Store`만 변경하면 되고, 응용 서비스는 영향을 받지 않는다.**

```
   [ Before ]  응용 서비스: 판단 + 생성 지시   ← 도메인 로직 유출
   [ After  ]  응용 서비스: store.createProduct() 한 줄
               도메인(Store): 판단 + 생성      ← 도메인 로직 응집
```

## 언제 적용하는가

> [!important] 판단 기준 (p.127)
> **애그리거트가 갖고 있는 데이터를 이용해서 다른 애그리거트를 생성해야 한다면 애그리거트에 팩토리 메서드를 구현하는 것을 고려**해 보자.

`Product`의 경우:

| 근거 | 설명 |
|------|------|
| **데이터 제공** | 제품을 생성한 **`Store`의 식별자**를 필요로 한다. 즉 `Store`의 데이터를 이용해서 `Product`를 생성한다 |
| **상태 기반 판단** | `Product`를 생성할 수 있는 **조건을 판단할 때 `Store`의 상태**(`isBlocked()`)를 이용한다 |

> [!tip]
> 따라서 `Store`에 `Product`를 생성하는 팩토리 메서드를 추가하면
> **생성에 필요한 데이터의 일부를 직접 제공하면서 동시에 중요한 도메인 로직을 함께 구현**할 수 있게 된다.

## 확장 — 다른 팩토리에 위임

`Store` 애그리거트가 `Product` 애그리거트를 생성할 때 **많은 정보를 알아야 한다면**, 직접 생성하지 않고 **다른 팩토리에 위임**하는 방법도 있다.

```java
public class Store {

    public Product createProduct(ProductId newProductId, ProductInfo pi) {
        if (isBlocked()) throw new StoreBlockedException();
        return ProductFactory.create(newProductId, getId(), pi);
    }
}
```

> [!important]
> 다른 팩토리에 위임하더라도 **"차단 상태의 상점은 상품을 만들 수 없다"는 도메인 로직은 한곳(`Store`)에 계속 위치한다.**

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "응용 서비스에서 `store.isBlocked()` 검사 후 `new Product()`" | **도메인 로직이 응용 서비스에 노출**된 문제 |
| "판단 + 생성은 논리적으로?" | **하나의 도메인 기능** |
| "해법" | 애그리거트(`Store`)에 **팩토리 메서드** 구현 |
| "팩토리 메서드 적용 신호 2가지" | ① 애그리거트 **데이터로 다른 애그리거트 생성** ② 생성 조건 판단에 **그 애그리거트의 상태** 사용 |
| "적용 후 로직 변경 시 어디를 고치나?" | **도메인 영역의 `Store`만** — 응용 서비스는 무영향 |
| "정보가 너무 많으면?" | **다른 팩토리에 위임** (단, 판단 로직은 애그리거트에 유지) |
