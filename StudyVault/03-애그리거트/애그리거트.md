# 애그리거트 (★★★)

#ddd #aggregate #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 목적 | **상위 수준에서 모델을 조망**할 수 있게 해준다 |
| 부가 효과 | **일관성을 관리하는 기준**이 된다 |
| 라이프 사이클 | 한 애그리거트에 속한 객체는 **유사하거나 동일한 라이프 사이클**을 갖는다 |
| 경계 | 애그리거트는 **경계를 갖는다.** 한 애그리거트에 속한 객체는 **다른 애그리거트에 속하지 않는다** |
| 자기 관리 | 각 애그리거트는 **자기 자신만 관리**하고 다른 애그리거트를 관리하지 않는다 |
| 경계 설정 기준 | **도메인 규칙과 요구사항** |
| ★ 흔한 착각 | "**A가 B를 갖는다**"가 곧 한 애그리거트를 의미하지는 **않는다** |
| 실제 크기 | 경험이 쌓일수록 **줄어든다.** 다수가 **엔티티 1개**만 갖는다 |

## 왜 애그리거트인가

> [!warning] 개별 객체 수준으로만 보면 생기는 문제
> 수십 개의 테이블을 한 장의 ERD에 모두 표시하면 개별 테이블 간의 관계를 파악하느라 **큰 틀에서 데이터 구조를 이해하기 어려운 것**처럼,
> 도메인 객체 모델이 복잡해지면 **개별 구성요소 위주로 모델을 이해**하게 되고
> **전반적인 구조나 큰 수준에서 도메인 간의 관계를 파악하기 어려워진다.**

```
   관계 파악이 어렵다
          ▼
   코드 변경/확장이 어렵다
          ▼
   코드 수정이 꺼려진다
          ▼
   코드 변경을 최대한 회피하는 쪽으로 요구사항을 협의하게 된다
          ▼
   꼼수로 당장 돌아가는 코드 추가 → 장기적으로 더 수정하기 어려워진다
```

> [!important] 해법
> 도메인을 이해하고 관리하기 쉬운 단위로 만들려면 **상위 수준에서 모델을 조망할 수 있는 방법**이 필요한데, 그 방법이 바로 **애그리거트**다.

## 애그리거트의 두 가지 효용

| 효용 | 설명 |
|------|------|
| ① **모델 이해** | 수많은 객체를 애그리거트로 묶어서 보면 **상위 수준에서 도메인 모델 간의 관계**를 파악할 수 있다 |
| ② **일관성 관리 기준** | 애그리거트 **단위로 일관성을 관리**한다 |

> [!tip]
> 애그리거트는 복잡한 도메인을 **단순한 구조**로 만들어준다.
> 복잡도가 낮아지는 만큼 도메인 기능을 확장·변경하는 데 필요한 **노력(개발 시간)도 줄어든다.**

## 라이프 사이클

애그리거트는 관련된 모델을 하나로 모았기 때문에, 한 애그리거트에 속한 객체는 **유사하거나 동일한 라이프 사이클**을 갖는다.

```
   주문 애그리거트 생성
   ├─ Order        ┐
   ├─ OrderLine    ├─ 함께 생성
   └─ Orderer      ┘
```

- `Order`는 생성했는데 `ShippingInfo`는 만들지 않거나, `ShippingInfo`를 생성하면서 `Orderer`를 생성하지 않는 경우는 **없다.**
- 도메인 규칙에 따라 최초 주문 시점에 일부 객체를 만들 필요가 없는 경우도 있지만, **대부분 함께 생성하고 함께 제거한다.**

## 경계 — 애그리거트는 자기 자신만 관리한다

> [!important]
> 애그리거트는 **경계를 갖는다.** 한 애그리거트에 속한 객체는 **다른 애그리거트에 속하지 않는다.**
> 애그리거트는 **독립된 객체 군**이며, 각 애그리거트는 **자기 자신을 관리할 뿐 다른 애그리거트를 관리하지 않는다.**

| 주문 애그리거트가 할 수 있는 것 | 할 수 없는 것 |
|--------------------------------|---------------|
| 배송지를 변경한다 | **회원의 비밀번호를 변경**한다 |
| 주문 상품 개수를 변경한다 | **상품의 가격을 변경**한다 |

## 경계 설정 기준 — 도메인 규칙과 요구사항

| 신호 | 판단 |
|------|------|
| 도메인 규칙에 따라 **함께 생성**되는 구성요소 | 한 애그리거트에 속할 가능성이 **높다** |
| 함께 **변경되는 빈도가 높은** 객체 | 한 애그리거트에 속할 가능성이 **높다** |

- 주문할 상품 개수, 배송지 정보, 주문자 정보는 **주문 시점에 함께 생성**되므로 한 애그리거트에 속한다.
- `OrderLine`의 주문 상품 개수를 변경하면 도메인 규칙에 따라 `Order`의 **총 주문 금액을 새로 계산**해야 한다.

## ★ "A가 B를 갖는다" ≠ 한 애그리거트

> [!danger] 가장 흔한 함정
> 흔히 "**A가 B를 갖는다**"로 설계할 수 있는 요구사항이 있으면 A와 B를 한 애그리거트로 묶어서 생각하기 쉽다.
> 하지만 **이것이 반드시 A와 B가 한 애그리거트에 속한다는 것을 의미하지는 않는다.**

### 좋은 예 — 상품(Product)과 리뷰(Review)

> 요구사항: "상품 상세 페이지에 들어가면 **상품 상세 정보와 함께 리뷰 내용**을 보여줘야 한다."

이 요구사항만 보면 `Product`와 `Review`가 한 애그리거트라고 생각하기 쉽다. **하지만 아니다.**

| 판단 기준 | Product | Review |
|-----------|---------|--------|
| 함께 생성되는가 | ❌ **함께 생성되지 않는다** |
| 함께 변경되는가 | ❌ **함께 변경되지 않는다** |
| **변경 주체** | **상품 담당자** | **고객** |
| 서로에게 영향 | `Review` 변경이 `Product`에 영향 ❌ / `Product` 변경이 `Review`에 영향 ❌ |

```
   ❌ [ Product ─── Review ]        한 애그리거트로 착각
   ⭕ [ Product ]   [ Review ]      서로 다른 애그리거트
```

> [!tip] 판단 체크리스트
> 1. **함께 생성**되는가?
> 2. **함께 변경**되는가?
> 3. **변경 주체**가 같은가?
> 4. 한쪽의 변경이 **다른 쪽에 영향**을 주는가?
>
> 모두 아니라면 **서로 다른 애그리거트**다.

## 애그리거트의 실제 크기

> [!important] 경험칙 (p.102)
> 처음 도메인 모델을 만들기 시작하면 **큰 애그리거트로 보이는 것들이 많지만**,
> 도메인에 대한 경험이 생기고 도메인 규칙을 제대로 이해할수록 **애그리거트의 실제 크기는 줄어든다.**
>
> 저자의 경험상:
> - **다수의 애그리거트가 한 개의 엔티티 객체만 갖는 경우가 많았다.**
> - **두 개 이상의 엔티티로 구성되는 애그리거트는 드물었다.**

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "애그리거트의 두 가지 효용" | **모델 이해(상위 조망) + 일관성 관리 기준** |
| "한 애그리거트 객체들의 라이프 사이클" | **유사하거나 동일** — 함께 생성/제거 |
| "주문 애그리거트가 회원 비밀번호를 바꿔도 되나?" | **안 된다.** 자기 자신만 관리 |
| "경계 설정의 기본 기준" | **도메인 규칙과 요구사항** |
| "함께 변경되는 빈도가 높으면?" | 한 애그리거트일 가능성 **높다** |
| "'상품이 리뷰를 갖는다' → 한 애그리거트?" | **거짓.** 생성·변경 시점과 **변경 주체가 다르다** |
| "애그리거트 크기의 경험칙" | 대부분 **엔티티 1개**, 2개 이상은 드물다 |
