# 애그리거트 간 집합 연관 (★★★)

#ddd #aggregate #aggregate-reference #jpa-mapping #concept

## Overview Table (한눈에 비교)

| 연관 | 개념적 존재 | **실제 구현 반영** | 대안 |
|------|-------------|--------------------|------|
| **1-N** (카테고리 → 상품) | 있음 | ❌ **반영하지 않는다** | 상품 쪽에서 **N-1** 연관 |
| **M-N 양방향** (상품 ↔ 카테고리) | 있음 | ❌ 양방향은 반영하지 않는다 | **상품 → 카테고리 단방향 M-N**만 |
| M-N 구현 기술 | — | **조인 테이블** + `@ElementCollection` |

## 1-N 연관 — 구현에 반영하면 안 된다

카테고리 입장에서 한 카테고리에 한 개 이상의 상품이 속할 수 있으니 **카테고리와 상품은 1-N 관계**다.

```java
public class Category {
    private Set<Product> products;    // 다른 애그리거트에 대한 1-N 연관
}
```

### 왜 문제인가 — 페이징

> 보통 목록 관련 요구사항은 한 번에 전체 상품을 보여주기보다는 **페이징을 이용해 나눠서 보여준다.**

```java
public class Category {
    private Set<Product> products;

    public List<Product> getProducts(int page, int size) {
        List<Product> sortedProducts = sortById(products);
        return sortedProducts.subList((page - 1) * size, page * size);
    }
}
```

> [!danger]
> 이 코드를 실제 RDBMS와 연동해서 구현하면 **`Category`에 속한 모든 `Product`를 조회하게 된다.**
> `Product` 개수가 **수만 개 정도로 많다면** 이 코드를 실행할 때마다 **실행 속도가 급격히 느려져 성능에 심각한 문제**를 일으킨다.

```
   category.getProducts(1, 20)
        ▼
   SELECT * FROM product WHERE category_id = ?   ← 수만 건 전부 로딩!
        ▼
   메모리에서 정렬 후 20건만 잘라냄               ← 낭비
```

> [!important] 결론
> 개념적으로는 애그리거트 간에 1-N 연관이 있더라도, **이런 성능 문제 때문에 애그리거트 간의 1-N 연관을 실제 구현에 반영하지 않는다.**

### ⭕ 해법 — 상품 쪽에서 N-1로 뒤집는다

```java
public class Product {
    private CategoryId categoryId;      // 상품 → 카테고리 N-1 연관
}
```

```java
public class ProductListService {

    public Page<Product> getProductOfCategory(Long categoryId, int page, int size) {
        Category category = categoryRepository.findById(categoryId);
        checkCategory(category);
        List<Product> products =
                productRepository.findByCategoryId(category.getId(), page, size);
        int totalCount = productRepository.countsByCategoryId(category.getId());
        return new Page(page, size, totalCount, products);
    }
}
```

> [!tip]
> 카테고리에 속한 상품을 구할 필요가 있다면, **상품 입장에서 자신이 속한 카테고리를 N-1로 연관 지어 구하면 된다.**
> 리포지터리에 `findByCategoryId(categoryId, page, size)`를 두면 **DB가 페이징을 처리**한다.

## M-N 연관 — 단방향만 구현한다

> [!important] 요구사항을 고려하라 (p.123)
> 보통 **특정 카테고리에 속한 상품 목록을 보여줄 때, 목록 화면에서 각 상품이 속한 모든 카테고리를 표시하지는 않는다.**
> 제품이 속한 모든 카테고리가 필요한 화면은 **상품 상세 화면**이다.
>
> → 이 요구사항을 고려하면 **카테고리에서 상품으로의 집합 연관은 필요하지 않다.**
> 즉 개념적으로는 **양방향 M-N 연관**이 존재하지만, 실제 구현에서는 **상품 → 카테고리 단방향 M-N 연관**만 적용하면 된다.

```java
public class Product {
    private Set<CategoryId> categoryIds;
}
```

### 구현 — 조인 테이블 (그림 3.9)

```
   ┌──────────────┐     ┌──────────────────────┐     ┌──────────────┐
   │ product      │     │ product_category     │     │ category     │
   │  product_id ─┼────▶│  product_id          │     │  id          │
   │  name        │     │  category_id        ─┼────▶│  name        │
   └──────────────┘     └──────────────────────┘     └──────────────┘
                            (조인 테이블)
```

```java
@Entity
@Table(name = "product")
public class Product {
    @EmbeddedId
    private ProductId id;

    @ElementCollection
    @CollectionTable(name = "product_category",
                     joinColumns = @JoinColumn(name = "product_id"))
    private Set<CategoryId> categoryIds;
}
```

> [!note]
> 이 매핑은 카테고리 ID 목록을 보관하기 위해 **밸류 타입에 대한 컬렉션 매핑**을 이용했다.

### 조회 — `member of` 연산자

```java
@Repository
public class JpaProductRepository implements ProductRepository {
    @PersistenceContext
    private EntityManager entityManager;

    @Override
    public List<Product> findByCategoryId(CategoryId catId, int page, int size) {
        TypedQuery<Product> query = entityManager.createQuery(
            "select p from Product p " +
            "where :catId member of p.categoryIds order by p.id.id desc",
            Product.class);
        query.setParameter("catId", catId);
        query.setFirstResult((page - 1) * size);
        query.setMaxResults(size);
        return query.getResultList();
    }
}
```

> [!tip] `member of`
> `:catId member of p.categoryIds`는 `categoryIds` 컬렉션에 **`catId`로 지정한 값이 존재하는지를 검사**하기 위한 검색 조건이다.

## 정리

```
   개념 모델                         구현 모델
   Category 1 ──── N Product   ▶    Product ──N-1──▶ CategoryId
       (1-N 연관)                    (성능 때문에 뒤집는다)

   Product M ◀──▶ N Category   ▶    Product ──M-N 단방향──▶ Set<CategoryId>
      (양방향 M-N)                   (요구사항상 단방향으로 충분)
```

> [!warning] 조회 기능은 조회 전용 모델로
> 목록이나 상세 화면과 같은 **조회 기능은 조회 전용 모델을 이용해서 구현하는 것이 좋다.**
> → [[CQRS]] (11장)

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "애그리거트 간 1-N 연관을 구현에 반영?" | **하지 않는다** (성능 문제) |
| "1-N을 반영하면 생기는 문제" | 페이징 시 **전체 로딩** → 속도 급감 |
| "1-N 대신 쓰는 방법" | 상품 쪽에서 **N-1 연관** + 리포지터리 페이징 |
| "상품 ↔ 카테고리 M-N 구현" | **상품 → 카테고리 단방향 M-N**만 |
| "왜 단방향으로 충분한가" | 모든 카테고리가 필요한 화면은 **상품 상세 화면**뿐 |
| "M-N 구현 기술" | **조인 테이블** + `@ElementCollection` + `@CollectionTable` |
| "컬렉션에 값이 있는지 검사하는 JPQL" | **`member of`** |
