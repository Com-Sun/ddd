# 애그리거트와 트랜잭션 (★★★)

#ddd #transaction #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 문제 | 한 애그리거트를 **두 사용자가 동시에 변경**할 때 **일관성이 깨진다** |
| 원인 | **트랜잭션마다 리포지터리는 새로운 애그리거트 객체를 생성**한다 |
| 결과 | 개념적으로 동일한 애그리거트지만 **물리적으로 서로 다른 객체**를 사용 |
| 해법 ① | 한쪽이 작업하는 동안 **다른 쪽이 수정하지 못하게 막는다** → **선점 잠금** |
| 해법 ② | 조회 이후 값이 바뀌면 **다시 조회한 뒤 수정** → **비선점 잠금** |
| 필요성 | **DBMS가 지원하는 트랜잭션과 함께 애그리거트를 위한 추가적인 트랜잭션 처리 기법이 필요** |

## 문제 시나리오

> 한 주문 애그리거트에 대해 **운영자는 배송 상태로 변경**하고, 동시에 **사용자는 배송지 주소를 변경**하면 어떻게 될까?

```
 운영자 스레드                          고객 스레드
      │                                    │
   주문 애그리거트 구함              주문 애그리거트 구함
   (Order 객체 A)                     (Order 객체 B)     ← 서로 다른 객체!
      │                                    │
   배송 상태로 변경                    배송지 정보 변경
      │                                    │
   트랜잭션 커밋 → DB 반영            트랜잭션 커밋 → DB 반영
      │                                    │
      └──────────── ❌ ─────────────────────┘
   운영자는 "기존 배송지"로 배송 상태를 변경했는데
   그 사이 고객이 배송지를 바꿨다 → 애그리거트의 일관성이 깨진다
```

> [!important] 왜 서로 영향을 주지 않는가
> **트랜잭션마다 리포지터리는 새로운 애그리거트 객체를 생성**하므로,
> 운영자 스레드와 고객 스레드는 **같은 주문 애그리거트를 나타내는 다른 객체**를 구하게 된다.
>
> 두 스레드는 **개념적으로 동일한 애그리거트지만 물리적으로 서로 다른 애그리거트 객체를 사용**한다.
> 때문에 운영자 스레드가 배송 상태로 변경하더라도 **고객 스레드가 사용하는 객체에는 영향을 주지 않는다.**
> 고객 스레드 입장에서 주문은 아직 **배송 상태 전이므로 배송지 정보를 변경할 수 있다.**

> [!danger] 결과
> 두 스레드는 각각 트랜잭션을 커밋할 때 수정한 내용을 DB에 반영한다.
> 이 시점에 **배송 상태로 바뀌고 배송지 정보도 바뀐다.**
> 문제는 **운영자는 기존 배송지 정보를 이용해서 배송 상태로 변경했는데 그 사이 고객은 배송지 정보를 변경했다**는 점이다.
> 즉 **애그리거트의 일관성이 깨진다.**

## 두 가지 해법

> [!important] 일관성이 깨지지 않도록 하려면 다음 둘 중 하나를 해야 한다
> **①** 운영자가 배송지 정보를 조회하고 상태를 변경하는 동안, **고객이 애그리거트를 수정하지 못하게 막는다.**
> → **선점 잠금**
>
> **②** 운영자가 배송지 정보를 조회한 이후에 고객이 정보를 변경하면, **운영자가 애그리거트를 다시 조회한 뒤 수정하도록 한다.**
> → **비선점 잠금**

| 방식 | 다른 이름 | 저자의 용어 선택 이유 |
|------|-----------|----------------------|
| **선점 잠금** (Pessimistic Lock) | **비관적 잠금** | 영단어의 뉘앙스가 잘 전달되지 않아 **이해가 쉬운 용어**를 사용 |
| **비선점 잠금** (Optimistic Lock) | **낙관적 잠금** | 〃 |

> [!note]
> **DBMS가 지원하는 트랜잭션과 함께 애그리거트를 위한 추가적인 트랜잭션 처리 기법이 필요하다.**

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "동시 변경 시 왜 서로 영향이 없나" | **트랜잭션마다 리포지터리가 새 객체를 생성** |
| "개념적으로 같지만 물리적으로는?" | **서로 다른 애그리거트 객체** |
| "결과적으로 깨지는 것" | **애그리거트의 일관성** |
| "해법 두 가지" | **선점 잠금 / 비선점 잠금** |
| "Pessimistic Lock의 다른 이름" | **비관적 잠금 = 선점 잠금** |
| "Optimistic Lock의 다른 이름" | **낙관적 잠금 = 비선점 잠금** |
| "DBMS 트랜잭션만으로 충분한가?" | **부족하다.** 추가 기법 필요 |
