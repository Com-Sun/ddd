# 비선점 잠금 (Optimistic Lock) (★★★)

#ddd #transaction #optimistic-lock #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 언제 필요한가 | **선점 잠금으로는 해결할 수 없는** 상황 — 조회와 수정이 **서로 다른 트랜잭션**일 때 |
| 방식 | 잠그지 않고, **변경한 데이터를 실제 DBMS에 반영하는 시점에 충돌 여부를 검사** |
| 구현 | 애그리거트에 **버전으로 사용할 숫자 타입 프로퍼티** 추가 |
| 쿼리 | `UPDATE ... SET version = version + 1 ... WHERE ... AND version = 현재버전` |
| JPA | **`@Version`** 애너테이션 |
| 충돌 시 | 수정된 행이 **0개** → 트랜잭션 종료 시점에 **`OptimisticLockingFailureException`** |
| 응용 서비스 | **버전에 대해 알 필요가 없다** (JPA가 알아서 처리) |
| 확장 | 여러 트랜잭션에 걸쳐 적용하려면 **버전을 화면에 전달하고 되돌려 받는다** |

## 왜 필요한가 — 선점 잠금으로 못 푸는 문제

```
   1. 운영자가 배송을 위해 주문 정보를 조회       (트랜잭션 1)
   2. 고객이 배송지 변경을 요청                   (트랜잭션 2)
   3. 고객의 요청이 반영됨
   4. 운영자가 1번에서 조회한 정보를 기준으로
      배송 상태로 변경 요청                       (트랜잭션 3)
```

> [!danger] 문제
> **운영자가 배송지 정보를 조회하고 배송 상태로 변경하는 사이에 고객이 배송지를 변경한다.**
> 운영자는 **고객이 변경하기 전 배송지 정보를 이용하여 배송 준비를 한 뒤 배송 상태로 변경**하게 된다.
> 즉 운영자는 **다른 배송지로 물건을 발송**하게 되고, 고객은 **배송지를 변경했음에도 엉뚱한 곳으로 물건을 받게** 된다.
>
> **이 문제는 선점 잠금 방식으로는 해결할 수 없다.** 조회와 수정이 **서로 다른 트랜잭션**에서 일어나기 때문이다.

> [!important] 비선점 잠금의 발상
> **잠금을 걸지 않고**, **변경한 데이터를 실제 DBMS에 반영하는 시점에 변경 가능 여부를 확인**한다.

## 구현 — 버전 프로퍼티

```sql
UPDATE aggtable SET version = version + 1, colx = ?, coly = ?
WHERE aggid = ? AND version = 현재버전
```

> 이 쿼리는 **수정할 애그리거트와 매핑되는 테이블의 버전 값이 현재 애그리거트의 버전과 동일한 경우에만 데이터를 수정**한다.
> 수정에 성공하면 **버전 값을 1 증가**시킨다.
> **다른 트랜잭션이 먼저 데이터를 수정해서 버전 값이 바뀌면 데이터 수정에 실패**한다.

```
   스레드1                             스레드2
      │                                  │
   애그리거트 구함 (version=5)      애그리거트 구함 (version=5)
      │                                  │
   애그리거트 수정                    애그리거트 수정
      │                                  │
   커밋: SET version=6 WHERE version=5    │
      ▼ ✅ 성공 (version: 5 → 6)          │
                                     커밋: SET version=6 WHERE version=5
                                          ▼ ❌ 실패 (이미 version=6)
```

### JPA `@Version`

```java
@Entity
@Table(name = "purchase_order")
@Access(AccessType.FIELD)
public class Order {
    @EmbeddedId
    private OrderNo number;

    @Version
    private long version;
    ...
}
```

> JPA는 엔티티가 변경되어 `UPDATE` 쿼리를 실행할 때 **`@Version`에 명시한 필드를 이용해서 비선점 잠금 쿼리**를 실행한다.

```sql
UPDATE purchase_order SET ...생략, version = version + 1
WHERE number = ? AND version = 10
```

## 응용 서비스는 버전을 몰라도 된다

```java
public class ChangeShippingService {

    @Transactional
    public void changeShipping(ChangeShippingRequest changeReq) {
        Order order = orderRepository.findById(new OrderNo(changeReq.getNumber()));
        checkNoOrder(order);
        order.changeShippingInfo(changeReq.getShippingInfo());
    }
}
```

> [!tip]
> **응용 서비스는 버전에 대해 알 필요가 없다.**
> 리포지터리에서 애그리거트를 구하고 **알맞은 기능만 실행**하면 된다.
> 기능 실행 과정에서 데이터가 변경되면 **JPA는 트랜잭션 종료 시점에 비선점 잠금을 위한 쿼리를 실행**한다.

### 충돌 감지

> **비선점 잠금 쿼리 실행 결과 수정된 행의 개수가 0이면 이미 누군가 앞서 데이터를 수정한 것**이다.
> 이는 트랜잭션이 충돌한 것이므로 **트랜잭션 종료 시점에 익셉션이 발생**한다.
> 스프링의 `@Transactional`을 사용했다면 메서드가 리턴될 때 트랜잭션이 종료되고,
> 이 시점에 **`OptimisticLockingFailureException`** 이 발생한다.

```java
@Controller
public class OrderController {
    private ChangeShippingService changeShippingService;

    @PostMapping("/changeShipping")
    public String changeShipping(ChangeShippingRequest changeReq) {
        try {
            changeShippingService.changeShipping(changeReq);
            return "changeShippingSuccess";
        } catch (OptimisticLockingFailureException ex) {
            // 누군가 먼저 같은 주문 애그리거트를 수정했으므로
            // 트랜잭션이 충돌했다는 메시지를 보여준다.
            return "changeShippingTxConflict";
        }
    }
}
```

## ★ 여러 트랜잭션으로 확장하기

> [!important] 핵심 아이디어
> 시스템은 사용자에게 **수정 폼을 제공할 때 애그리거트 버전을 함께 제공**하고,
> **폼을 서버에 전송할 때 이 버전을 함께 전송**한다.
> **사용자가 전송한 버전과 애그리거트 버전이 동일한 경우에만 수정 기능을 수행**하도록 함으로써 충돌을 해소한다.

```
 운영자        표현/응용         DB
   │  1: 주문 데이터 요청 │
   │──────────────────▶│─1.1 애그리거트 로딩──▶│
   │◀─1.3 데이터 제공 (버전 A 포함)─────────────│
   │                     │
   │  2: 배송 상태 변경 요청 (버전 A 포함)
   │──────────────────▶│─2.1 애그리거트 로딩──▶│
   │                     │◀─2.1.1 데이터 (버전 B)│
   │                     │
   │              [버전 A ≠ 버전 B] → 2.1.2 에러 응답 ❌
   │              [버전 A == 버전 B] → 2.1.3 수정 → 2.1.4 쿼리 실행 ✅
```

### 응용 서비스 — 버전 일치 확인

```java
public class StartShippingService {

    @PreAuthorize("hasRole('ADMIN')")
    @Transactional
    public void startShipping(StartShippingRequest req) {
        Order order = orderRepository.findById(new OrderNo(req.getOrderNumber()));
        checkOrder(order);
        if (!order.matchVersion(req.getVersion())) {
            throw new VersionConflictException();
        }
        order.startShipping();
    }
}
```

> `matchVersion(long version)`은 **현재 애그리거트의 버전과 인자로 전달받은 버전이 일치하면 `true`** 를 리턴한다.
> `false`면 사용자가 **이전 버전의 애그리거트 정보를 바탕으로 상태 변경을 요청**한 것이므로 익셉션을 발생시킨다.

> [!danger] ⚠️ 예제 프로젝트에는 이 부분에 버그가 있다
> `ddd-start2/`의 `StartShippingService`는 **`!`가 빠져 있어 로직이 정확히 반대**다.
> ```java
> // order/command/application/StartShippingService.java — 실제 코드 (❌)
> if (order.matchVersion(req.getVersion())) {
>     throw new VersionConflictException();
> }
> ```
> | 상황 | 위 코드의 동작 | 올바른 동작 |
> |------|----------------|-------------|
> | 버전 **일치**(정상) | **예외 발생** ❌ | 배송 시작 |
> | 버전 **불일치**(충돌) | **그대로 진행** ❌ | 예외 발생 |
>
> **이 노트의 코드(`!` 포함)가 책 p.260 원문이며 올바르다.**
> 예제를 실행해 볼 때는 `!`를 추가해야 한다. → [[코드 대조 검증 보고서]], [[코드 리딩 연습문제]]

### 표현 계층 — 두 익셉션 처리

```java
@Controller
public class OrderAdminController {
    private StartShippingService startShippingService;

    @PostMapping("/startShipping")
    public String startShipping(StartShippingRequest startReq) {
        try {
            startShippingService.startShipping(startReq);
            return "shippingStarted";
        } catch (OptimisticLockingFailureException | VersionConflictException ex) {
            // 트랜잭션 충돌
            return "startShippingTxConflict";
        }
    }
}
```

## ★ 두 익셉션의 의미 차이

| 익셉션 | 발생 주체 | 의미 |
|--------|-----------|------|
| **`VersionConflictException`** | **응용 서비스 코드** | **이미 누군가가 애그리거트를 수정**했다 |
| **`OptimisticLockingFailureException`** | **스프링 프레임워크** | **누군가가 거의 동시에 애그리거트를 수정**했다 |

> [!tip]
> 이 두 익셉션은 **개발자 입장에서 트랜잭션 충돌이 발생한 시점을 명확하게 구분**해 준다.
> **버전 충돌 상황에 대한 구분이 명시적으로 필요 없다면**, 응용 서비스에서 프레임워크용 익셉션을 발생시키는 것도 고려할 수 있다.

```java
if (!order.matchVersion(req.getVersion())) {
    // 프레임워크가 제공하는 비선점 트랜잭션 충돌 관련 익셉션 사용
    throw new OptimisticLockingFailureException("version conflict");
}
```

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "선점 잠금으로 못 푸는 상황" | 조회와 수정이 **서로 다른 트랜잭션**일 때 |
| "비선점 잠금의 검사 시점" | **DBMS에 반영하는 시점** |
| "구현에 필요한 것" | **버전으로 사용할 숫자 타입 프로퍼티** |
| "JPA 애너테이션" | **`@Version`** |
| "충돌 시 수정된 행의 개수" | **0개** |
| "그때 발생하는 익셉션" | **`OptimisticLockingFailureException`** |
| "응용 서비스는 버전을 알아야 하나?" | **알 필요 없다** |
| "여러 트랜잭션 확장 방법" | 버전을 **화면(hidden)에 전달 → 되돌려 받아 비교** |
| "`VersionConflictException`의 의미" | **이미 누군가가 수정했다** |
| "`OptimisticLockingFailureException`의 의미" | **거의 동시에 수정했다** |
