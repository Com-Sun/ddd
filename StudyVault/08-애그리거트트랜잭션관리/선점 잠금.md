# 선점 잠금 (Pessimistic Lock) (★★★)

#ddd #transaction #pessimistic-lock #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 정의 | **먼저 애그리거트를 구한 스레드가 사용이 끝날 때까지 다른 스레드가 수정하지 못하게 막는 방식** |
| 대기 방식 | 다른 스레드는 **블로킹(blocking)** 된다 |
| 해제 시점 | 첫 스레드가 **수정하고 트랜잭션을 커밋**하면 잠금 해제 |
| 구현 | DBMS의 **행 단위 잠금** (`for update` 쿼리) |
| JPA | `EntityManager.find(..., LockModeType.PESSIMISTIC_WRITE)` |
| 스프링 데이터 JPA | **`@Lock`** 애너테이션 |
| ★ 위험 | **교착 상태(deadlock)** |
| 교착 상태 대비 | **최대 대기 시간 지정** (`javax.persistence.lock.timeout` 힌트 / `@QueryHints`) |

## 동작 방식

```
   스레드1                              스레드2
      │                                    │
   애그리거트 구함                    애그리거트 구함 시도
   [ 접근 잠금 ]  ─────────────────▶  [ 잠금으로 대기 ]  ← 블로킹
      │                                    ┊
   애그리거트 수정                          ┊
      │                                    ┊
   트랜잭션 커밋 → [ 잠금 해제 ] ──────▶  애그리거트 구함
                                            │  (스레드1이 수정한 내용을 본다)
```

> [!important]
> 한 스레드가 애그리거트를 구하고 수정하는 동안 **다른 스레드가 수정할 수 없으므로,
> 동시에 애그리거트를 수정할 때 발생하는 데이터 충돌 문제를 해소**할 수 있다.

## 문제 시나리오에 적용

```
 운영자 스레드                          고객 스레드
      │                                    │
   주문 애그리거트 구함              주문 애그리거트 구함 시도
   [ 접근 잠금 ]  ─────────────────▶  [ 잠금으로 대기 ]
      │                                    ┊
   배송 상태로 변경                          ┊
      │                                    ┊
   트랜잭션 커밋 → [ 잠금 해제 ] ──────▶  주문 애그리거트 구함
                                            │  ← 이미 배송 상태!
                                        배송지 변경 시도
                                            ▼
                                        ❌ 에러 발생 → 트랜잭션 실패
```

> 고객은 **"이미 배송이 시작되어 배송지를 변경할 수 없습니다"** 와 같은 안내 문구를 보게 된다.

## 구현

> 선점 잠금은 보통 **DBMS가 제공하는 행 단위 잠금**을 사용해서 구현한다.
> 오라클을 비롯한 다수의 DBMS가 **`for update`와 같은 쿼리**를 사용해서 특정 레코드에 **한 커넥션만 접근할 수 있는 잠금장치**를 제공한다.

### JPA `EntityManager`

```java
Order order = entityManager.find(
        Order.class, orderNo, LockModeType.PESSIMISTIC_WRITE);
```

> [!note]
> **JPA 프로바이더와 DBMS에 따라 잠금 모드 구현이 다르다.**
> 하이버네이트의 경우 `PESSIMISTIC_WRITE`를 잠금 모드로 사용하면 **`for update` 쿼리**를 이용해서 선점 잠금을 구현한다.

### 스프링 데이터 JPA — `@Lock`

```java
import org.springframework.data.jpa.repository.Lock;
import javax.persistence.LockModeType;

public interface MemberRepository extends Repository<Member, MemberId> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select m from Member m where m.id = :id")
    Optional<Member> findByIdForUpdate(@Param("id") MemberId memberId);
}
```

## ★ §8.2.1 선점 잠금과 교착 상태

> [!danger] 잠금 순서에 따른 교착 상태
> 선점 잠금 기능을 사용할 때는 **잠금 순서에 따른 교착 상태(deadlock)** 가 발생하지 않도록 주의해야 한다.

```
   1. 스레드1: A 애그리거트에 대한 선점 잠금 구함   ✅
   2. 스레드2: B 애그리거트에 대한 선점 잠금 구함   ✅
   3. 스레드1: B 애그리거트에 대한 선점 잠금 시도   ⏸ 대기 (스레드2가 점유)
   4. 스레드2: A 애그리거트에 대한 선점 잠금 시도   ⏸ 대기 (스레드1이 점유)
                        ▼
              두 스레드 모두 영원히 진행 불가 = 교착 상태
```

> [!warning] 사용자가 많을수록 위험하다
> **선점 잠금에 따른 교착 상태는 상대적으로 사용자 수가 많을 때 발생할 가능성이 높고,
> 사용자 수가 많아지면 교착 상태에 빠지는 스레드도 많아진다.**
> 교착 상태에 빠지는 스레드가 많아질수록 **시스템은 아무것도 할 수 없는 상태**가 된다.

### 해결 — 최대 대기 시간 지정

```java
Map<String, Object> hints = new HashMap<>();
hints.put("javax.persistence.lock.timeout", 2000);

Order order = entityManager.find(
        Order.class, orderNo, LockModeType.PESSIMISTIC_WRITE, hints);
```

> `javax.persistence.lock.timeout` 힌트는 **잠금을 구하는 대기 시간을 밀리초 단위**로 지정한다.
> **지정한 시간 이내에 잠금을 구하지 못하면 익셉션을 발생**시킨다.

### 스프링 데이터 JPA — `@QueryHints`

```java
import org.springframework.data.jpa.repository.QueryHints;
import javax.persistence.QueryHint;

public interface MemberRepository extends Repository<Member, MemberId> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints({
        @QueryHint(name = "javax.persistence.lock.timeout", value = "2000")
    })
    @Query("select m from Member m where m.id = :id")
    Optional<Member> findByIdForUpdate(@Param("id") MemberId memberId);
}
```

> [!danger] DBMS마다 다르다 (p.251~252)
> 이 힌트를 사용할 때 주의할 점은 **DBMS에 따라 힌트가 적용되지 않을 수도 있다**는 것이다.
> - **쿼리별로 대기 시간을 지정할 수 있는 DBMS**가 있고
> - **커넥션 단위로만 대기 시간을 지정할 수 있는 DBMS**도 있다.
>
> 따라서 선점 잠금을 사용하려면 **사용하는 DBMS가 어떤 식으로 대기 시간을 처리하는지 반드시 확인**해야 한다.

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "선점 잠금의 정의" | 먼저 구한 스레드가 **끝날 때까지 다른 스레드의 수정을 막는다** |
| "대기 중인 스레드 상태" | **블로킹(blocking)** |
| "잠금 해제 시점" | **트랜잭션 커밋** 시 |
| "DBMS 구현 수단" | **행 단위 잠금** (`for update`) |
| "하이버네이트 `PESSIMISTIC_WRITE`" | **`for update` 쿼리** 실행 |
| "스프링 데이터 JPA 잠금 지정" | **`@Lock`** |
| "선점 잠금의 대표 위험" | **교착 상태(deadlock)** |
| "교착 상태가 잘 생기는 조건" | **사용자 수가 많을 때** |
| "교착 상태 대비책" | **최대 대기 시간 지정** |
| "대기 시간 힌트 키" | **`javax.persistence.lock.timeout`** |
| "스프링에서 힌트 지정" | **`@QueryHints` / `@QueryHint`** |
| "힌트 사용 시 주의" | **DBMS에 따라 적용되지 않을 수 있다** |
