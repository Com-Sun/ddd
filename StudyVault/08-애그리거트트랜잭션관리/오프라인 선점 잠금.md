# 오프라인 선점 잠금 (★★★)

#ddd #transaction #offline-lock #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 목적 | **여러 트랜잭션에 걸쳐** 선점 잠금을 적용해 **충돌을 사전에 방지** |
| 비선점 잠금과의 차이 | 비선점은 **충돌을 나중에 감지**, 오프라인 선점은 **애초에 진입을 막는다** |
| 선점 잠금과의 차이 | 선점 잠금은 **한 트랜잭션 범위에서만** 적용된다 |
| 실제 사례 | **아틀라시안 컨플루언스(Confluence)** — "다른 사용자가 편집 중" 안내 |
| ★ 필수 요소 | **잠금 유효 시간** |
| 유효 시간이 필요한 이유 | 사용자가 **수정을 완료하지 않고 프로그램을 종료**하면 잠금이 영원히 해제되지 않는다 |
| 유효 시간 연장 | **일정 주기로 AJAX 호출**해서 유효 시간을 증가 |

## 컨플루언스 사례

> 아틀라시안의 **컨플루언스**는 문서를 편집할 때 **누군가 먼저 편집을 하는 중이면
> "다른 사용자가 문서를 수정하고 있다"는 안내 문구**를 보여준다.
> 이런 안내를 통해 **여러 사용자가 동시에 한 문서를 수정할 때 발생하는 충돌을 사전에 방지**할 수 있게 해준다.

> [!important] 더 엄격하게 막으려면
> 컨플루언스는 **사전에 충돌 여부를 알려주지만 동시에 수정하는 것을 막지는 않는다.**
> **더 엄격하게 데이터 충돌을 막고 싶다면 누군가 수정 화면을 보고 있을 때 수정 화면 자체를 실행하지 못하도록** 해야 한다.
> 이것이 **오프라인 선점 잠금 방식**이다.

## 세 방식 비교

| 방식 | 적용 범위 | 충돌 처리 시점 | 특징 |
|------|-----------|----------------|------|
| **선점 잠금** | **한 트랜잭션** 안 | 대기(블로킹) | DBMS 행 잠금 |
| **비선점 잠금** | 여러 트랜잭션 가능 | **커밋 시점에 감지** | 버전 비교, 사후 실패 |
| **오프라인 선점 잠금** | **여러 트랜잭션에 걸쳐** | **진입 시점에 차단** | 별도 잠금 저장소 + 유효 시간 |

```
   [ 오프라인 선점 잠금의 흐름 ]

   사용자 A                             사용자 B
      │                                   │
   1. 수정 폼 요청                          │
      → 잠금 선점 (LockId 발급)             │
      │                                    │
      │                          2. 수정 폼 요청
      │                             → 잠금 시도 → ❌ 실패
      │                             "다른 사용자가 수정 중입니다"
      │                                    │
   3. 수정 요청 (LockId 전송)                │
      → 잠금 확인 → 기능 실행 → 잠금 해제      │
      │                                    │
      │                          4. 이제 잠금 선점 가능 ⭕
```

## ★ 잠금 유효 시간이 반드시 필요하다

> [!danger] 유효 시간이 없으면
> 사용자 A가 **3번의 수정 요청을 수행하지 않고 프로그램을 종료**하면 어떻게 될까?
> **잠금을 해제하지 않으므로 다른 사용자는 영원히 잠금을 구할 수 없는 상황**이 발생한다.

> [!important] 해법
> 이런 상태를 방지하기 위해 오프라인 선점 방식은 **잠금 유효 시간**을 가져야 한다.
> **유효 시간이 지나면 자동으로 잠금을 해제**해서 다른 사용자가 잠금을 다시 구할 수 있도록 해야 한다.

### 부작용 — 정상 사용자가 실패할 수 있다

> [!warning]
> 사용자 A가 **잠금 유효 시간이 지난 후에 수정을 수행**했다고 가정하자.
> **잠금이 해제되어 사용자 A는 수정에 실패**하게 된다.

**해결**: **일정 주기로 유효 시간을 증가시키는 방식**이 필요하다.
예를 들어 **수정 폼에서 1분 단위로 AJAX 호출을 해서 잠금 유효 시간을 1분씩 증가**시키는 방법이 있다.

```
   수정 폼 진입
        │
        ├─ 1분마다 AJAX → extendLockExpiration()  ← 유효 시간 갱신
        │
   수정 완료 → 잠금 해제
```

## 필요한 네 가지 기능

> 오프라인 선점 잠금은 크게 **네 가지 기능**이 필요하다.

| # | 기능 |
|---|------|
| ① | **잠금 선점 시도** (`tryLock`) |
| ② | **잠금 확인** (`checkLock`) |
| ③ | **잠금 해제** (`releaseLock`) |
| ④ | **잠금 유효 시간 연장** (`extendLockExpiration`) |

→ 구현은 [[LockManager 구현]] 참고.
