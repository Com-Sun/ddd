# 응용 서비스의 인터페이스와 클래스 (★★)

#ddd #application-service #concept

## Overview Table (한눈에 비교)

| 질문 | 답 |
|------|-----|
| 응용 서비스에 인터페이스가 필요한가? | **명확하게 필요하기 전까지는 좋은 선택이 아니다** |
| 인터페이스가 유용한 상황 | ① **구현 클래스가 여러 개**인 경우 ② **런타임에 구현 객체를 교체**해야 할 때 |
| 응용 서비스의 실상 | 런타임 교체가 **거의 없고**, 구현 클래스가 두 개인 경우도 **드물다** |
| 무리하게 만들면 | 소스 파일 증가 + **간접 참조 증가** → 전체 구조가 복잡해진다 |
| TDD + 표현 영역부터 개발 | 인터페이스가 **필요해질 수 있다** |
| 반론 | **Mockito** 같은 도구는 **클래스에 대해서도 대역 객체 생성 가능** |

## 인터페이스가 필요한 상황

> [!important]
> 인터페이스가 필요한 몇 가지 상황이 있는데 그중 하나는 **구현 클래스가 여러 개인 경우**다.
> **구현 클래스가 다수 존재하거나 런타임에 구현 객체를 교체해야 할 때** 인터페이스를 유용하게 사용할 수 있다.
>
> **그런데 응용 서비스는 런타임에 교체하는 경우가 거의 없고, 한 응용 서비스의 구현 클래스가 두 개인 경우도 드물다.**

> [!warning] 무리하게 만들 때의 비용
> 이런 이유로 인터페이스와 클래스를 따로 구현하면
> - **소스 파일만 많아지고**
> - **구현 클래스에 대한 간접 참조가 증가해서 전체 구조가 복잡해진다.**
>
> 따라서 **인터페이스가 명확하게 필요하기 전까지는 응용 서비스에 대한 인터페이스를 작성하는 것이 좋은 선택이라고 볼 수는 없다.**

```
   인터페이스 추가
        ├─▶ 파일 수 ↑
        └─▶ 간접 참조 ↑  →  구조 복잡도 ↑
                 ▲
        얻는 것이 없다면 순손실
```

## TDD와 개발 순서에 따른 예외

| 개발 순서 | 결과 |
|-----------|------|
| **표현 영역부터 개발**(TDD) | 응용 서비스 구현이 아직 없으므로 **인터페이스부터 작성**하게 된다. 예: 스프링 MVC 컨트롤러를 TDD로 먼저 개발하면 응용 서비스 인터페이스로 컨트롤러 구현을 완성해 나갈 수 있다 |
| **도메인/응용 영역부터 개발** | **응용 서비스 클래스가 먼저 만들어진다.** 표현 영역 단위 테스트를 위해 가짜 객체가 필요해 인터페이스를 추가할 수도 있다 |

### ★ 하지만 — Mockito가 있다

> [!tip] 인터페이스 필요성을 약화시키는 결정적 요인
> **Mockito 같은 테스트 도구는 클래스에 대해서도 테스트용 대역 객체를 만들 수 있기 때문에,
> 응용 서비스에 대한 인터페이스가 없어도 표현 영역을 테스트할 수 있다.**
> 이는 결과적으로 **응용 서비스에 대한 인터페이스 필요성을 약화**시킨다.

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "응용 서비스 인터페이스는 필요한가?" | **명확히 필요하기 전까지는 아니다** |
| "인터페이스가 유용한 두 상황" | **구현 클래스 다수** / **런타임 교체** |
| "응용 서비스의 실제 상황" | 런타임 교체 **거의 없음**, 구현 2개도 **드묾** |
| "무리하게 만들면 생기는 문제" | **파일 증가 + 간접 참조 증가** → 복잡도 ↑ |
| "TDD로 표현 영역부터 개발하면?" | 인터페이스부터 작성하게 된다 |
| "그래도 인터페이스가 불필요한 이유" | **Mockito가 클래스도 대역 객체로 만들 수 있다** |
