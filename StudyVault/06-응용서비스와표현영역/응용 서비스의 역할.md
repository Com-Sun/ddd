| 역할 | 설명 |
|------|------|

| **② 도메인 객체 간 흐름 제어** | 도메인 영역과 표현 영역을 연결하는 **창구 역할** |
| **③ 트랜잭션 처리** | 도메인의 상태 변경을 **트랜잭션으로 처리** |

## 응용 서비스의 전형적인 구조

> 응용 서비스는 주로 **도메인 객체 간의 흐름을 제어**하기 때문에 다음과 같이 **단순한 형태**를 갖는다.

### 기존 애그리거트 사용

```java
public Result doSomeFunc(SomeReq req) {
    // 1. 리포지터리에서 애그리거트를 구한다.
    SomeAgg agg = someAggRepository.findById(req.getId());
    checkNull(agg);

    // 2. 애그리거트의 도메인 기능을 실행한다.
    agg.doFunc(req.getValue());

    // 3. 결과를 리턴한다.
    return createSuccessResult(agg);
}
```

### 새로운 애그리거트 생성

```java
public Result doSomeCreation(CreateSomeReq req) {
    // 1. 데이터 중복 등 데이터가 유효한지 검사한다.
    validate(req);

    // 2. 애그리거트를 생성한다.
    SomeAgg newAgg = createSome(req);

    // 3. 리포지터리에 애그리거트를 저장한다.
    someAggRepository.save(newAgg);

    // 4. 결과를 리턴한다.
    return createSuccessResult(newAgg);
}
```

> [!warning] 복잡하다면 신호다
> **응용 서비스가 복잡하다면 응용 서비스에서 도메인 로직의 일부를 구현하고 있을 가능성이 높다.**
> 응용 서비스가 도메인 로직을 일부 구현하면 **코드 중복, 로직 분산** 등 코드 품질에 안 좋은 영향을 준다.

## 트랜잭션 처리

```java
public void blockMembers(String[] blockingIds) {
    if (blockingIds == null || blockingIds.length == 0) return;
    List<Member> members = memberRepository.findByIdIn(blockingIds);
    for (Member mem : members) {
        mem.block();
    }
}
```

> [!danger] 트랜잭션이 없으면
> `blockMembers()`가 **트랜잭션 범위에서 실행되지 않는다고 가정**해 보자.
> `Member` 객체의 `block()`을 실행해 상태를 변경했는데 **DB에 반영하는 도중 문제가 발생하면
> 일부 `Member`만 차단 상태가 되어 데이터 일관성이 깨진다.**
>
> → 이런 상황이 발생하지 않으려면 **트랜잭션 범위에서 응용 서비스를 실행**해야 한다.

## ★ §6.2.1 도메인 로직 넣지 않기

> [!important] 원칙
> **도메인 로직은 도메인 영역에 위치하고 응용 서비스는 도메인 로직을 구현하지 않는다.**

### ⭕ 올바른 예 — 도메인이 검증한다

```java
public class ChangePasswordService {

    public void changePassword(String memberId, String curPw, String newPw) {
        Member member = memberRepository.findById(memberId);
        checkMemberExists(member);
        member.changePassword(curPw, newPw);      // 도메인에 위임
    }
}
```

```java
public class Member {

    public void changePassword(String curPw, String newPw) {
        if (!matchPassword(curPw)) throw new BadPasswordException();
        setPassword(newPw);
    }

    // 현재 암호와 일치하는지 검사하는 도메인 로직
    public boolean matchPassword(String pwd) {
        return passwordEncoder.matches(pwd);
    }

    private void setPassword(String newPw) {
        if (isEmpty(newPw)) throw new IllegalArgumentException("no new password");
        this.password = newPw;
    }
}
```

### ❌ 잘못된 예 — 응용 서비스가 검증한다

```java
public class ChangePasswordService {

    public void changePassword(String memberId, String curPw, String newPw) {
        Member member = memberRepository.findById(memberId);
        checkMemberExists(member);

        // ❌ 도메인의 핵심 로직을 응용 서비스에서 구현
        if (!passwordEncoder.matches(curPw, member.getPassword())) {
            throw new BadPasswordException();
        }
        member.setPassword(newPw);
    }
}
```

## 도메인 로직이 분산되면 생기는 두 가지 문제

| 문제 | 설명 |
|------|------|
| **① 코드의 응집성이 떨어진다** | 도메인 데이터와 **그 데이터를 조작하는 도메인 로직이 서로 다른 영역에 위치**하면, 도메인 로직을 파악하기 위해 **여러 영역을 분석**해야 한다 |
| **② 여러 응용 서비스에서 동일한 도메인 로직을 중복 구현**할 가능성이 높아진다 | — |

### 중복 사례 — 계정 정지 기능

비정상적인 계정 정지를 막기 위해 암호를 확인한다고 하면, 계정 정지 서비스에도 **같은 암호 확인 코드**가 필요해진다.

```java
// ❌ 중복
public class DeactivationService {
    public void deactivate(String memberId, String pwd) {
        Member member = memberRepository.findById(memberId);
        checkMemberExists(member);
        if (!passwordEncoder.matches(pwd, member.getPassword())) {   // 중복!
            throw new BadPasswordException();
        }
        member.deactivate();
    }
}
```

> [!tip] 도메인에 두면 중복이 사라진다
> 애초에 도메인 영역에 암호 확인 기능을 구현했으면, 응용 서비스는 **도메인이 제공하는 기능을 사용하면 되므로 중복 문제가 발생하지 않는다.**

```java
// ⭕ 중복 없음
public class DeactivationService {
    public void deactivate(String memberId, String pwd) {
        Member member = memberRepository.findById(memberId);
        checkMemberExists(member);
        if (!member.matchPassword(pwd)) {      // 도메인 기능 사용
            throw new BadPasswordException();
        }
        member.deactivate();
    }
}
```

> [!important] 결론
> 응집도가 떨어지고 코드 중복이 발생하는 두 문제는 결과적으로 **코드 변경을 어렵게 만든다.**
> 소프트웨어의 중요한 경쟁 요소 중 하나는 **변경 용이성**인데, **변경이 어렵다는 것은 그만큼 소프트웨어의 가치가 떨어진다**는 것을 의미한다.
> → **도메인 로직을 도메인 영역에 모아서 코드 중복을 줄이고 응집도를 높여야 한다.**

```
   도메인 로직이 응용 서비스로 샘
          ▼
   응집도 ↓ + 코드 중복 ↑
          ▼
   변경이 어려워짐
          ▼
   소프트웨어의 가치 ↓
```

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "응용 서비스의 주요 역할" | 도메인 객체로 **사용자 요청 처리** + **흐름 제어** |
| "도메인과 표현 영역을 잇는 역할" | **창구(파사드) 역할** |
| "응용 서비스가 복잡하다면?" | **도메인 로직을 구현하고 있을 가능성** |
| "트랜잭션 없이 다수 회원 차단 시" | **일부만 차단되어 데이터 일관성이 깨진다** |
| "도메인 로직 분산의 두 문제" | **응집성 저하 + 코드 중복** |
| "암호 일치 확인은 어디에?" | **도메인(`member.matchPassword()`)** |
| "궁극적 폐해" | **변경 용이성 저하 → 소프트웨어 가치 하락** |
