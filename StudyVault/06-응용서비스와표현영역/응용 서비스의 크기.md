# 응용 서비스의 크기 (★★★)

#ddd #application-service #service-granularity #concept

## Overview Table (두 가지 방식 비교)

| 방식 | ① 한 클래스에 모든 기능 | ② 구분되는 기능별로 분리 |
|------|------------------------|--------------------------|
| 구성 | `MemberService` 하나 | `ChangePasswordService`, `JoinService`, … (한 클래스에 **1~3개 기능**) |
| **장점** | 각 기능의 **동일 로직 코드 중복 제거가 쉽다** | 클래스 크기가 작고 **관련 없는 코드에 영향받지 않는다** |
| **단점** | **클래스 크기가 커진다** → 연관성 적은 코드가 섞여 이해를 방해 | 기능마다 **동일 로직을 중복 구현**할 가능성 |
| 중복 해결 | `private` 메서드로 추출 | **별도 헬퍼 클래스**로 추출 |

> [!note] 파사드(facade) 역할
> 응용 서비스는 표현 영역과 도메인 영역을 연결하는 매개체 역할을 하는데,
> 이는 디자인 패턴에서 **파사드(facade)와 같은 역할**이다.
> 응용 서비스 자체는 복잡한 로직을 수행하지 않기 때문에 **구현은 어렵지 않다.**

## ① 한 클래스에 모든 기능

```java
public class MemberService {
    // 각 기능을 구현하는 데 필요한 리포지터리, 도메인 서비스 필드 추가
    private MemberRepository memberRepository;
    private Notifier notifier;

    public void join(MemberJoinRequest joinRequest) { ... }
    public void changePassword(String memberId, String curPw, String newPw) { ... }
    public void initializePassword(String memberId) { ... }
    public void leave(String memberId, String curPw) { ... }
}
```

### 장점 — 중복 로직 제거가 쉽다

```java
public class MemberService {
    private MemberRepository memberRepository;
    private Notifier notifier;

    public void changePassword(String memberId, String currentPw, String newPw) {
        Member member = findExistingMember(memberId);
        member.changePassword(currentPw, newPw);
    }

    public void initializePassword(String memberId) {
        Member member = findExistingMember(memberId);
        String newPassword = member.initializePassword();
        notifier.notifyNewPassword(member, newPassword);
    }

    public void leave(String memberId, String curPw) {
        Member member = findExistingMember(memberId);
        member.leave();
    }

    // 각 기능의 동일 로직에 대한 구현 코드 중복을 쉽게 제거
    private Member findExistingMember(String memberId) {
        Member member = memberRepository.findById(memberId);
        if (member == null)
            throw new NoMemberException(memberId);
        return member;
    }
}
```

### ★ 단점 — 관련 없는 코드가 섞인다

> [!danger] 구체적 예 (p.209)
> 암호 초기화를 구현한 `initializePassword()`는 **신규 암호를 사용자에게 통지하기 위해 `Notifier`를 사용**하는데,
> 이 `Notifier`는 **암호 변경 기능(`changePassword()`)에서는 필요하지 않은 기능**이다.
> 하지만 **`Notifier`가 필드로 존재하기 때문에, 이 `Notifier`가 어떤 기능 때문에 필요한지 확인하려면 각 기능을 구현한 코드를 뒤져야 한다.**

```
   MemberService
   ├ memberRepository   ← 모든 기능이 사용
   └ notifier           ← initializePassword()만 사용
                          ▲ 어느 기능이 쓰는지 알려면 전부 읽어야 함
```

> [!warning] 더 나쁜 결과
> 한 클래스에 코드가 모이기 시작하면 **엄연히 분리하는 것이 좋은 상황임에도 습관적으로 기존에 존재하는 클래스에 억지로 끼워 넣게 된다.**
> 이는 결과적으로 **코드 품질을 낮추는 결과**를 초래한다.

## ② 구분되는 기능별로 분리

```java
public class ChangePasswordService {
    private MemberRepository memberRepository;

    public void changePassword(String memberId, String curPw, String newPw) {
        Member member = memberRepository.findById(memberId);
        if (member == null) throw new NoMemberException(memberId);
        member.changePassword(curPw, newPw);
    }
}
```

> [!tip] 장점
> 클래스 개수는 많아지지만 **한 클래스에 관련 기능을 모두 구현하는 것과 비교해서 코드 품질을 유지하는 데 도움**이 된다.
> 이 방식을 사용하면 **각 클래스마다 필요한 의존 객체만 포함하므로 다른 기능을 구현한 코드에 영향을 받지 않는다.**

### 중복은 별도 클래스로 해결

```java
// 각 응용 서비스에서 공통되는 로직을 별도 클래스로 구현
public final class MemberServiceHelper {
    public static Member findExistingMember(MemberRepository repo, String memberId) {
        Member member = repo.findById(memberId);
        if (member == null)
            throw new NoMemberException(memberId);
        return member;
    }
}
```

```java
// 공통 로직을 제공하는 메서드를 응용 서비스에서 사용
import static com.myshop.member.application.MemberServiceHelper.*;

public class ChangePasswordService {
    private MemberRepository memberRepository;

    public void changePassword(String memberId, String curPw, String newPw) {
        Member member = findExistingMember(memberRepository, memberId);
        member.changePassword(curPw, newPw);
    }
}
```

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "응용 서비스는 어떤 디자인 패턴 역할?" | **파사드(facade)** |
| "한 클래스에 모두 구현의 장점" | **동일 로직 코드 중복 제거가 쉽다** |
| "한 클래스에 모두 구현의 단점" | **클래스가 커지고 관련 없는 코드가 섞인다** |
| "`Notifier` 필드 문제" | 어느 기능이 쓰는지 알려면 **전체 코드를 뒤져야 함** |
| "기능별 분리의 장점" | **필요한 의존 객체만 포함** → 다른 기능에 영향 없음 |
| "기능별 분리 시 클래스당 기능 수" | **1개 내지 2~3개** |
| "기능별 분리 시 중복 해결법" | **별도 헬퍼 클래스** (정적 메서드) |
