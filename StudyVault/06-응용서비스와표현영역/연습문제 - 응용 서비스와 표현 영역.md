## Question 1 - 두 영역의 역할 [recall]
> 표현 영역과 응용 영역의 역할을 각각 설명하고, 표현 영역의 변환 책임을 서술하라.

> [!answer]- 정답 보기
> - **표현 영역**: 사용자의 **요청을 해석**한다. HTTP 요청 파라미터·쿠키·헤더로 실행할 기능을 판별하고 해당 응용 서비스를 실행한다.
> - **응용 영역**: 요청한 **기능을 실제로 제공**한다. 필요한 입력 값을 **메서드 인자로 받고 실행 결과를 리턴**한다.
> - **변환 책임**: 두 쪽의 데이터 형식이 일치하지 않으므로 **표현 영역이 응용 서비스가 요구하는 형식으로 사용자 요청을 변환**하고, 결과를 다시 응답 형식으로 변환한다.

## Question 2 - 의존 방향 [recall]
> 응용 서비스는 사용자가 웹 브라우저를 쓰는지, REST API를 호출하는지 알아야 하는가?

> [!answer]- 정답 보기
> **알 필요가 없다.** 사용자와의 상호작용은 표현 영역이 처리하므로 **응용 서비스는 표현 영역에 의존하지 않는다.** 단지 기능 실행에 필요한 **입력 값을 받고 실행 결과만 리턴**하면 된다.

## Question 4 - 도메인 로직 분산의 문제 [recall]
> 도메인 로직을 응용 서비스에 구현하면 발생하는 두 가지 문제와 최종적인 폐해는?

> [!answer]- 정답 보기
> ① **코드의 응집성이 떨어진다** — 도메인 데이터와 그 데이터를 조작하는 로직이 서로 다른 영역에 위치해, 로직 파악에 **여러 영역을 분석**해야 한다.
> ② **여러 응용 서비스에서 동일한 도메인 로직을 중복 구현**할 가능성이 높아진다.
> **최종 폐해**: 두 문제는 결과적으로 **코드 변경을 어렵게** 만든다. 변경 용이성은 소프트웨어의 중요한 경쟁 요소이므로, **변경이 어렵다는 것은 소프트웨어의 가치가 떨어진다**는 뜻이다.

## Question 5 - 응용 서비스 크기 [recall]
> 응용 서비스를 구현하는 두 가지 방식과 각각의 장단점은?

> [!answer]- 정답 보기
> **① 한 클래스에 모든 기능**: 장점은 **동일 로직의 코드 중복 제거가 쉽다**(private 메서드). 단점은 **클래스가 커져 연관성 적은 코드가 섞이고**, 기존 클래스에 억지로 끼워 넣게 되어 품질이 낮아진다.
> **② 구분되는 기능별로 분리**(클래스당 1~3개): 장점은 **필요한 의존 객체만 포함**해 다른 기능의 영향을 받지 않는다. 단점은 **동일 로직 중복 가능성**이며, **별도 헬퍼 클래스**로 해결한다.

## Question 6 - 인터페이스 필요성 [recall]
> 응용 서비스에 인터페이스가 필요한 상황은? 그리고 대체로 불필요한 이유는?

> [!answer]- 정답 보기
> **필요한 상황**: ① 구현 클래스가 여러 개인 경우 ② 런타임에 구현 객체를 교체해야 할 때.
> **불필요한 이유**: 응용 서비스는 **런타임 교체가 거의 없고 구현 클래스가 두 개인 경우도 드물다.** 무리하게 만들면 **소스 파일이 늘고 간접 참조가 증가해 구조가 복잡**해진다. 또한 **Mockito 같은 도구는 클래스에 대해서도 대역 객체를 만들 수 있어** 테스트를 위한 인터페이스도 불필요하다.

## Question 7 - 트랜잭션 롤백 [recall]
> 스프링에서 `@Transactional`이 적용된 메서드는 어떤 조건에서 롤백되는가?

> [!answer]- 정답 보기
> **`RuntimeException`을 발생시키면 트랜잭션을 롤백**하고, 그렇지 않으면 커밋한다. 프레임워크가 제공하는 규칙을 따르면 **간단한 설정만으로 트랜잭션을 시작·커밋·롤백**할 수 있어 코드를 간결하게 유지할 수 있다.

## Question 9 - 리턴 값 설계 [application]
> 아래 코드의 문제를 지적하고 고쳐라.
> ```java
> public Order placeOrder(OrderRequest req) { ... return order; }
> ```
> ```html
> <a th:href="@{/orders/{id}(id=${order.number})}">주문 내용 보기</a>
> ```

> [!answer]- 정답 보기
> **문제**: 응용 서비스가 **애그리거트 자체를 리턴**하고 있다. 코딩은 편하지만 **도메인의 로직 실행을 응용 서비스와 표현 영역 두 곳에서 할 수 있게 되어**, 기능 실행 로직이 분산되고 **코드의 응집도가 낮아진다.**
> **고침**: 표현 영역에서 필요한 데이터만 리턴한다.
> ```java
> public OrderNo placeOrder(OrderRequest req) { ...; return orderNo; }
> ```
> "뷰에서 애그리거트 기능을 실행하지 말자"는 **규칙을 정하는 것보다, 필요한 데이터만 리턴하는 것이 응집도를 높이는 확실한 방법**이다.

## Question 10 - 표현 영역 의존 제거 [application]
> 아래 코드의 문제 세 가지를 지적하고 올바른 방향을 제시하라.
> ```java
> public class AuthenticationService {
>     public void authenticate(HttpServletRequest request) {
>         String id = request.getParameter("id");
>         String password = request.getParameter("password");
>         if (checkIdPasswordMatching(id, password)) {
>             HttpSession session = request.getSession();
>             session.setAttribute("auth", new Authentication(id));
>         }
>     }
> }
> ```

> [!answer]- 정답 보기
> **문제 ①** 응용 서비스만 **단독으로 테스트하기 어려워진다.**
> **문제 ②** **표현 영역의 구현이 변경되면 응용 서비스도 함께 변경**해야 한다.
> **문제 ③ (가장 심각)** 응용 서비스가 **표현 영역의 역할까지 대신**한다. `HttpSession`과 쿠키는 **표현 영역의 상태**인데 이를 응용 서비스가 변경하면, **표현 영역 코드만으로 상태 변화를 추적할 수 없어 표현 영역의 응집도가 깨진다.**
> **방향**: **서비스 메서드의 파라미터와 리턴 타입으로 표현 영역의 구현 기술을 사용하지 않는다.** ID/암호는 값으로 받고, 세션 설정은 컨트롤러에서 한다.

## Question 11 - 도메인 로직 회수 [application]
> 아래 응용 서비스에서 도메인 로직을 도메인으로 옮기고, 그렇게 했을 때 계정 정지 서비스에서 무엇이 달라지는지 설명하라.
> ```java
> if (!passwordEncoder.matches(curPw, member.getPassword())) {
>     throw new BadPasswordException();
> }
> member.setPassword(newPw);
> ```

> [!answer]- 정답 보기
> **도메인으로 이동**
> ```java
> public class Member {
>     public void changePassword(String curPw, String newPw) {
>         if (!matchPassword(curPw)) throw new BadPasswordException();
>         setPassword(newPw);
>     }
>     public boolean matchPassword(String pwd) {
>         return passwordEncoder.matches(pwd);
>     }
> }
> ```
> 응용 서비스는 `member.changePassword(curPw, newPw)` 한 줄이 된다.
> **계정 정지 서비스의 변화**: 비정상 정지를 막기 위해 암호를 확인해야 하는데, 도메인에 기능이 있으므로 **`member.matchPassword(pwd)`를 호출하기만 하면 된다.** 응용 서비스마다 `passwordEncoder.matches(...)`를 **중복 구현할 필요가 없어진다.**

## Question 12 - 값 검증 UX [application]
> 응용 서비스에서 값을 검증할 때 잘못된 값을 만나는 즉시 익셉션을 던지면 어떤 UX 문제가 생기는가? 두 가지 해법을 제시하라.

> [!answer]- 정답 보기
> **문제**: 첫 번째 값이 올바르지 않아 익셉션을 발생시키면 **나머지 항목은 검사하지 않는다.** 사용자는 **첫 번째 오류 메시지만 보게 되어** 같은 폼에 **값을 여러 번 입력**하게 된다.
> **해법 A**: 응용 서비스가 잘못된 값을 `ValidationError` 목록으로 모아두었다가, 검증이 끝난 뒤 **하나의 익셉션(`ValidationErrorException`)으로 발생**시킨다. 표현 영역은 그 목록을 `BindingResult` 형태로 변환한다.
> **해법 B**: **표현 영역에서 필수 값과 형식을 모두 검증**하고(`Errors`, `Validator`), 응용 서비스는 **ID 중복 같은 논리적 오류만** 검사한다.

## Question 13 - 응용 서비스 생략 판단 [application]
> 아래 서비스를 그대로 두어야 하는가? 판단 근거를 제시하고 대안을 보여라.
> ```java
> public class OrderListService {
>     public List<OrderView> getOrderList(String ordererId) {
>         return orderViewDao.selectByOrderer(ordererId);
>     }
> }
> ```

> [!answer]- 정답 보기
> **생략해도 된다.**
> **근거**: ① 서비스에서 수행하는 **추가적인 로직이 없다** ② **단일 쿼리만 실행하는 조회 기능이라 트랜잭션도 필요 없다.**
> **대안**: 표현 영역에서 조회 전용 기능을 직접 사용한다.
> ```java
> @RequestMapping("/myorders")
> public String list(ModelMap model) {
>     String ordererId = SecurityContext.getAuthentication().getId();
>     List<OrderView> orders = orderViewDao.selectByOrderer(ordererId);
>     model.addAttribute("orders", orders);
>     return "order/list";
> }
> ```
> **일반 원칙**: 응용 서비스가 **사용자 요청 기능을 실행하는 데 별다른 기여를 하지 못한다면 굳이 만들지 않아도 된다.**

## Question 14 - 권한 검사 수준 선택 [analysis]
> "게시글 삭제는 본인 또는 관리자만 가능하다"는 요구사항을 구현하려 한다. 세 가지 권한 검사 위치 중 어디가 적합한지 각각 검토하고, 프레임워크 사용 여부에 대한 판단 기준도 제시하라.

> [!answer]- 정답 보기
> - **표현 영역(URL 기반)**: ❌ 인증 여부는 걸러낼 수 있으나 **게시글 작성자가 본인인지 판단할 수 없다.**
> - **응용 서비스(메서드 단위 AOP)**: ❌ `@PreAuthorize("hasRole('ADMIN')")` 같은 방식은 역할 기반이라 **"본인" 조건을 표현할 수 없다.** 본인 확인은 **게시글 애그리거트를 먼저 로딩해야** 가능하므로 메서드 수준에서 검사할 수 없다.
> - **도메인 객체 단위**: ⭕ 애그리거트를 로딩한 뒤 직접 검사한다.
> ```java
> Article article = articleRepository.findById(articleId);
> checkArticleExistence(article);
> permissionService.checkDeletePermission(userId, article);
> article.markDeleted();
> ```
> **프레임워크 판단 기준**: 스프링 시큐리티를 확장해 도메인 객체 수준 검사를 통합할 수도 있지만, **도메인 객체 수준의 권한 로직은 도메인별로 다르므로 프레임워크에 대한 높은 이해가 필요**하다. **이해도가 높지 않아 원하는 수준으로 확장할 수 없다면, 도메인에 맞는 권한 검사 기능을 직접 구현하는 것이 유지 보수에 유리하다.**

## Question 15 - 값 검증 책임 배분 [analysis]
> 값 검증을 표현 영역과 응용 서비스 중 어디서 얼마나 할 것인가에 대해, 저자의 입장 변화와 그 트레이드오프를 분석하고 자신의 판단 기준을 세워보라.

> [!answer]- 정답 보기
> **원칙**: 원칙적으로 **모든 값에 대한 검증은 응용 서비스에서 처리**한다.
> **저자의 입장 변화**
> - **예전**: 표현 영역에서 **필수 값을 검증**하고, 응용 서비스에서는 **논리적 오류(ID 중복 등)만** 검증해도 괜찮다고 생각했다.
> - **요즘**: 가능하면 **응용 서비스에서 필수 값 검증과 논리적 오류를 모두** 한다.
>
> **트레이드오프**
> | 응용 서비스에서 모두 검증 | 평가 |
> |---|---|
> | 단점 | 프레임워크 검증 기능(`Errors`, `Validator`)을 쓸 때보다 **작성할 코드가 늘어난다** |
> | 장점 | **응용 서비스의 완성도가 높아진다** (표현 영역을 신뢰하지 않아도 안전) |
>
> **판단 기준(예시)**: 응용 서비스를 사용하는 **표현 영역이 여러 개**(웹 + REST API + 배치)라면 응용 서비스에서 모두 검증하는 것이 안전하다. 표현 영역이 **한 곳뿐이고 UX가 중요**하다면, 형식 검증을 표현 영역에 두고 응용 서비스는 논리적 오류에 집중해 코드량을 줄이는 편이 실용적이다. 어느 쪽이든 **UX를 위해 오류를 모아서 한 번에 알려주는 구조**는 유지해야 한다.

## Question 16 - 표현 영역의 세 책임 [recall]
> 표현 영역의 세 가지 책임을 나열하라.

> [!answer]- 정답 보기
> ① **사용자가 시스템을 사용할 수 있도록 알맞은 흐름을 제공**한다 (다음 화면 링크, 입력 폼 등)
> ② **사용자의 요청에 맞게 응용 서비스에 기능 실행을 요청**한다. 이 과정에서 **요청 데이터를 응용 서비스가 요구하는 형식으로**, **결과를 사용자에게 응답할 수 있는 형식으로 변환**한다
> ③ **사용자의 연결 상태인 세션을 관리**한다 (쿠키/서버 세션). 세션 관리는 **권한 검사와도 연결**된다

## Question 17 - 응용 서비스의 전형적 구조 [recall]
> 응용 서비스의 두 가지 전형적인 구조(기존 애그리거트 사용 / 신규 생성)를 단계별로 서술하라.

> [!answer]- 정답 보기
> **기존 애그리거트 사용**
> ① 리포지터리에서 **애그리거트를 구한다** ② **애그리거트의 도메인 기능을 실행**한다 ③ **결과를 리턴**한다
> **새로운 애그리거트 생성**
> ① **데이터 중복 등 데이터가 유효한지 검사**한다 ② **애그리거트를 생성**한다 ③ **리포지터리에 저장**한다 ④ **결과를 리턴**한다
> 응용 서비스는 주로 **도메인 객체 간의 흐름을 제어**하므로 이렇게 단순한 형태를 갖는다.

## Question 18 - 복잡한 응용 서비스의 신호 [recall]
> 응용 서비스가 복잡하다면 무엇을 의심해야 하는가?

> [!answer]- 정답 보기
> **응용 서비스에서 도메인 로직의 일부를 구현하고 있을 가능성이 높다.**
> 응용 서비스가 도메인 로직을 일부 구현하면 **코드 중복, 로직 분산** 등 코드 품질에 안 좋은 영향을 준다.
