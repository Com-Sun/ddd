# 조회 전용 기능과 응용 서비스 (★★★)

#ddd #application-service #query #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 상황 | 서비스 코드가 **단순히 조회 전용 기능을 호출하는 형태로만** 끝날 때 |
| 특징 ① | 서비스에서 수행하는 **추가적인 로직이 없다** |
| 특징 ② | 단일 쿼리만 실행하는 조회 기능은 **트랜잭션이 필요하지도 않다** |

| 판단 기준 | 응용 서비스가 **사용자 요청 기능을 실행하는 데 별다른 기여를 하지 못한다면** 생략 |

## 문제 — 의미 없는 응용 서비스

5장에서는 조회 화면을 위한 **조회 전용 모델과 DAO**를 만드는 내용을 다뤘다.
서비스에서 이들 조회 전용 기능을 사용하면 서비스 코드가 **단순히 조회 전용 기능을 호출하는 형태로 끝날 수 있다.**

```java
public class OrderListService {

    public List<OrderView> getOrderList(String ordererId) {
        return orderViewDao.selectByOrderer(ordererId);
    }
}
```

> [!warning]
> 서비스에서 수행하는 **추가적인 로직이 없을뿐더러**,
> 단일 쿼리만 실행하는 조회 기능이어서 **트랜잭션이 필요하지도 않다.**

## ⭕ 해법 — 표현 영역에서 바로 사용

```java
public class OrderController {

    private OrderViewDao orderViewDao;

    @RequestMapping("/myorders")
    public String list(ModelMap model) {
        String ordererId = SecurityContext.getAuthentication().getId();
        List<OrderView> orders = orderViewDao.selectByOrderer(ordererId);
        model.addAttribute("orders", orders);
        return "order/list";
    }
}
```

```
   [ 일반적인 구조 ]
   표현 영역 ──▶ 응용 서비스 ──▶ 조회 전용 기능 (DAO/리포지터리)

   [ 조회 전용의 경우 ]
   표현 영역 ─────────────────▶ 조회 전용 기능 (DAO/리포지터리)
                  ▲
          응용 서비스가 아무 기여도 하지 않으면 생략
```

## 판단 기준

> [!important] (p.232)
> **응용 서비스를 항상 만들었던 개발자는 표현 영역에서 응용 서비스 없이 조회 기능을 사용하는 것이 어색하게 느껴질 수 있다.**
> **하지만 응용 서비스가 사용자 요청 기능을 실행하는 데 별다른 기여를 하지 못한다면
> 굳이 서비스를 만들지 않아도 된다.**

| 응용 서비스를 만들어야 하는가 | 판단 |
|-------------------------------|------|
| 추가 로직이 있는가? | 있으면 **만든다** |
| 트랜잭션이 필요한가? | 필요하면 **만든다** |
| 여러 도메인 객체를 조합하는가? | 조합하면 **만든다** |
| **단순히 조회 전용 기능 호출만 하는가?** | **생략 가능** |

> [!note] 이어지는 논의
> 조회 전용 기능에 대한 내용은 **11장 CQRS**에서 다시 살펴본다. → [[CQRS]]
