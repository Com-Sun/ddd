# 메서드 파라미터와 값 리턴 (★★★)

#ddd #application-service #concept

## Overview Table (한눈에 비교)

| 주제 | 권장 |
|------|------|
| **파라미터** | 개별 값 전달 ⭕ / **파라미터가 두 개 이상이면 별도 데이터 클래스** ⭕ |
| 이유 | 스프링 MVC 같은 웹 프레임워크가 **요청 파라미터를 자바 객체로 변환**해 주므로 편리 |
| **리턴 값** | **표현 영역에서 필요한 데이터만 리턴** ⭕ |
| ❌ 금지 | **애그리거트 자체를 리턴**하는 것 |
| 금지 이유 | 도메인 로직 실행을 **응용 서비스와 표현 영역 두 곳에서 할 수 있게 되어 응집도 저하** |

## 파라미터 — 개별 값 vs 데이터 클래스

### 개별 값

```java
public class ChangePasswordService {
    // 암호 변경 기능 구현에 필요한 값을 파라미터로 전달받음
    public void changePassword(String memberId, String curPw, String newPw) {
        ...
    }
}
```

### 별도 데이터 클래스

```java
public class ChangePasswordRequest {
    private String memberId;
    private String currentPassword;
    private String newPassword;

    ... // get 메서드 등 생략
}
```

```java
public class ChangePasswordService {
    public void changePassword(ChangePasswordRequest req) {
        Member member = findExistingMember(req.getMemberId());
        member.changePassword(req.getCurrentPassword(), req.getNewPassword());
    }
}
```

> [!tip] 언제 데이터 클래스를 쓰나
> **스프링 MVC 같은 웹 프레임워크는 웹 요청 파라미터를 자바 객체로 변환하는 기능을 제공**하므로,
> 응용 서비스에 데이터로 전달할 **요청 파라미터가 두 개 이상 존재하면 별도 클래스를 사용하는 것이 편리**하다.

```java
@Controller
@RequestMapping("/member/changePassword")
public class MemberPasswordController {

    // 클래스를 이용해서 응용 서비스에 데이터를 전달하면
    // 프레임워크가 제공하는 기능을 활용하기에 좋음
    @PostMapping
    public String submit(ChangePasswordRequest changePwdReq) {
        Authentication auth = SecurityContext.getAuthentication();
        changePwdReq.setMemberId(auth.getId());
        try {
            changePasswordService.changePassword(changePwdReq);
        } catch (NoMemberException ex) {
            // 알맞은 익셉션 처리 및 응답
        }
    }
}
```

## 리턴 값 — 필요한 데이터만

주문 후 **주문 상세 내역 링크**를 바로 보여주려면 **주문번호**를 알아야 한다.

```java
public class OrderService {

    @Transactional
    public OrderNo placeOrder(OrderRequest orderRequest) {
        OrderNo orderNo = orderRepository.nextId();
        Order order = createOrder(orderNo, orderRequest);
        orderRepository.save(order);

        // 응용 서비스 실행 후 표현 영역에서 필요한 값 리턴
        return orderNo;
    }
}
```

```java
@Controller
public class OrderController {

    @PostMapping("/order/place")
    public String order(OrderRequest orderReq, ModelMap model) {
        setOrderer(orderReq);
        OrderNo orderNo = orderService.placeOrder(orderReq);
        modelMap.setAttribute("orderNo", orderNo.toString());
        return "order/success";
    }
}
```

## ★ 애그리거트 자체를 리턴하지 마라

```java
// ❌ 애그리거트를 그대로 리턴
public Order placeOrder(OrderRequest req) {
    ...
    return order;
}
```

```java
@Controller
public class OrderController {

    @RequestMapping(value = "/order/place", method = RequestMethod.POST)
    public String order(OrderRequest orderReq, ModelMap model) {
        setOrderer(orderReq);
        Order order = orderService.placeOrder(orderReq);
        modelMap.setAttribute("order", order);
        return "order/success";
    }
}
```

```html
<!-- 뷰 코드 -->
<a th:href="@{/orders/{id}(id=${order.number})}">주문 내용 보기</a>
```

> [!danger] 왜 문제인가 (p.215)
> 응용 서비스에서 애그리거트 자체를 리턴하면 **코딩은 편할 수 있지만
> 도메인의 로직 실행을 응용 서비스와 표현 영역 두 곳에서 할 수 있게 된다.**
>
> 이것은 **기능 실행 로직을 응용 서비스와 표현 영역에 분산시켜 코드의 응집도를 낮추는 원인**이 된다.

> [!tip] 규칙보다 확실한 방법
> "애그리거트를 리턴해도 애그리거트가 제공하는 기능을 컨트롤러나 뷰 코드에서 실행하면 안 된다"는 **규칙을 정할 수도 있겠지만**,
> 그보다는 **응용 서비스는 표현 영역에서 필요한 데이터만 리턴하는 것이
> 기능 실행 로직의 응집도를 높이는 확실한 방법**이다.

```
   ❌ return order;              →  뷰에서 order.cancel()도 가능해짐
   ⭕ return orderNo;            →  필요한 데이터만, 로직 실행 불가
```

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "파라미터가 두 개 이상이면?" | **별도 데이터 클래스**가 편리 |
| "별도 클래스가 편리한 이유" | 웹 프레임워크가 **요청 파라미터를 객체로 변환** |
| "응용 서비스가 리턴해야 할 것" | **표현 영역에서 필요한 데이터만** |
| "애그리거트를 리턴하면?" | 도메인 로직을 **표현 영역에서도 실행 가능** → **응집도 저하** |
| "규칙으로 막는 것 vs 데이터만 리턴" | **데이터만 리턴하는 것이 확실한 방법** |
