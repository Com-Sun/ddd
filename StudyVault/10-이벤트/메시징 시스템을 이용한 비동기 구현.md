# 메시징 시스템을 이용한 비동기 구현 (★★★)

#ddd #event #async #message-queue #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 방식 | 이벤트 디스패처가 이벤트를 **메시지 큐에 전송** → **메시지 리스너**가 읽어와 핸들러로 처리 |
| 대표 시스템 | **카프카(Kafka)**, **래빗MQ(RabbitMQ)** |
| 실행 단위 | 큐 저장 과정과 읽기 과정은 **별도 스레드나 프로세스**로 처리 |
| **글로벌 트랜잭션** | 이벤트 발생 기능 + 큐 저장을 **한 트랜잭션으로 묶을 수 있다** |
| 글로벌 트랜잭션의 대가 | **전체 성능이 떨어진다** |
| ★ 전제 | 보통 이벤트 **발생 주체와 핸들러가 별도 프로세스(JVM)** 에서 동작 |
| ★ 주의 | **동일 JVM에서 비동기 처리를 위해 메시지 큐를 쓰는 것은 시스템을 복잡하게 만들 뿐** |

## 동작 흐름 (그림 10.8)

```
   [ 트랜잭션 범위 ]                          [ 별도 프로세스 ]
   ┌────────────────────────────┐            ┌──────────────────┐
   │ 도메인                      │            │  메시지 리스너    │
   │   │                        │            │      │           │
   │ Events.raise()             │            │  이벤트 핸들러    │
   │   │                        │            └──────────────────┘
   │ 이벤트 디스패처              │                    ▲
   └───┼────────────────────────┘                    │
       │ 메시지 전송                                   │ 메시지 수신
       ▼                                              │
   ┌──────────────────────────────────────────────────┘
   │            메시징 시스템 (Kafka / RabbitMQ)
   └──────────────────────────────────────────────────
```

| 단계 | 내용 |
|------|------|
| 1 | 이벤트가 발생하면 **이벤트 디스패처가 이벤트를 메시지 큐에 보낸다** |
| 2 | **메시지 큐는 이벤트를 메시지 리스너에 전달**한다 |
| 3 | **메시지 리스너는 알맞은 이벤트 핸들러를 이용해서 이벤트를 처리**한다 |

> [!important]
> 이때 **이벤트를 메시지 큐에 저장하는 과정과 메시지 큐에서 이벤트를 읽어와 처리하는 과정은 별도 스레드나 프로세스로 처리**된다.

## 글로벌 트랜잭션

> [!important]
> **필요하다면 이벤트를 발생시키는 도메인 기능과 이벤트를 메시지 큐에 저장하는 절차를 한 트랜잭션으로 묶어야 한다.**
> 이를 위해서는 **글로벌 트랜잭션**이 필요하다.

| 관점 | 평가 |
|------|------|
| **장점** | **안전하게 이벤트를 메시지 큐에 전달**할 수 있다 |
| **단점** | **전체 성능이 떨어진다** |
| **제약** | **글로벌 트랜잭션을 지원하지 않는 메시징 시스템도 있다** |

## ★ 프로세스 분리를 전제로 한다

> [!warning] (p.322)
> **메시지 큐를 사용하면 보통 이벤트를 발생시키는 주체와 이벤트 핸들러가 별도 프로세스에서 동작한다.**
> 이것은 **이벤트 발생 JVM과 이벤트 처리 JVM이 다르다**는 것을 의미한다.
>
> 물론 한 JVM에서 이벤트 발생 주체와 핸들러가 메시지 큐를 이용해 이벤트를 주고받을 수 있지만,
> **동일 JVM에서 비동기 처리를 위해 메시지 큐를 사용하는 것은 시스템을 복잡하게 만들 뿐이다.**

```
   [ JVM A ]  ──이벤트──▶  [ 메시지 큐 ]  ──이벤트──▶  [ JVM B ]
   발생 주체                                            핸들러
        ▲                                                ▲
        └────────── 별도 프로세스여야 의미가 있다 ─────────┘
```

## 카프카 vs 래빗MQ

| 항목 | **래빗MQ(RabbitMQ)** | **카프카(Kafka)** |
|------|----------------------|-------------------|
| 글로벌 트랜잭션 | **지원** | **지원하지 않음** |
| 클러스터·고가용성 | **지원** | — |
| 성능 | — | **다른 메시징 시스템에 비해 높은 성능** |
| 기타 | **다양한 개발 언어와 통신 프로토콜 지원** | — |

> 래빗MQ는 **글로벌 트랜잭션 지원과 함께 클러스터와 고가용성을 지원**하기 때문에 **안정적으로 메시지를 전달**할 수 있다.
> 카프카는 **글로벌 트랜잭션을 지원하지 않지만 높은 성능**을 보여준다.

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "메시지 큐 방식의 흐름" | 디스패처 → **메시지 큐** → 메시지 리스너 → 이벤트 핸들러 |
| "큐 저장/읽기 처리 단위" | **별도 스레드나 프로세스** |
| "이벤트 발생과 큐 저장을 한 트랜잭션으로" | **글로벌 트랜잭션** 필요 |
| "글로벌 트랜잭션의 대가" | **전체 성능 저하** |
| "메시지 큐 방식의 전제" | 발생 주체와 핸들러가 **별도 프로세스(JVM)** |
| "동일 JVM에서 메시지 큐를 쓰면?" | **시스템을 복잡하게 만들 뿐** |
| "글로벌 트랜잭션 지원 여부" | **래빗MQ = 지원 / 카프카 = 미지원** |
| "카프카의 강점" | **높은 성능** |
