## Question 1 - 강결합의 네 문제 [recall]
> 주문 취소 시 외부 환불 서비스를 직접 호출할 때 발생하는 네 가지 문제와 근본 원인은?

> [!answer]- 정답 보기
> ① **트랜잭션 처리가 애매하다** (롤백? 커밋?) ② **성능에 직접 영향**(환불이 30초면 취소도 30초) ③ **도메인 로직이 섞인다**(`Order`에 결제 로직) ④ **기능 추가 시 더 복잡**(통지까지 추가하면 파라미터·트랜잭션이 더 복잡)
> **근본 원인**: **바운디드 컨텍스트 간의 강결합(high coupling)**

## Question 2 - 이벤트의 정의와 네이밍 [recall]
> 이벤트란 무엇이며, 이벤트 클래스 이름을 지을 때의 규칙은?

> [!answer]- 정답 보기
> 이벤트는 **'과거에 벌어진 어떤 것'** 을 의미하며, **이벤트가 발생한다는 것은 상태가 변경됐다**는 뜻이다.
> 이벤트는 과거에 벌어진 것을 표현하므로 **이름에 과거 시제를 사용**한다. (`OrderCanceledEvent` 또는 간결하게 `OrderCanceled`)
> 이벤트를 위한 **상위 타입은 존재하지 않으며 원하는 클래스를 이벤트로 사용**하면 된다.

## Question 3 - 네 가지 구성요소 [recall]
> 이벤트 관련 네 가지 구성요소를 나열하고 각각의 역할을 설명하라.

> [!answer]- 정답 보기
> ① **이벤트** — 발생한 사건에 대한 정보
> ② **이벤트 생성 주체** — **엔티티, 밸류, 도메인 서비스** 같은 도메인 객체. 상태가 바뀌면 이벤트를 발생시킨다
> ③ **이벤트 디스패처(퍼블리셔)** — 생성 주체와 핸들러를 **연결**. 이벤트를 처리할 수 있는 핸들러에 전파
> ④ **이벤트 핸들러(구독자)** — 이벤트에 반응하여 원하는 기능을 실행
> **디스패처의 구현 방식에 따라 동기/비동기가 결정**된다.

## Question 4 - 이벤트의 용도와 장점 [recall]
> 이벤트의 두 가지 용도와 두 가지 장점을 각각 설명하라.

> [!answer]- 정답 보기
> **용도**: ① **트리거** — 상태가 바뀔 때 후처리 실행 (주문 취소 → 환불, 예매 완료 → SMS) ② **서로 다른 시스템 간의 데이터 동기화** (배송지 변경 → 외부 배송 서비스 동기화)
> **장점**: ① **서로 다른 도메인 로직이 섞이는 것을 방지** (`Order`에서 환불 로직과 파라미터가 사라짐 → 결제 도메인으로의 의존 제거) ② **기능 확장이 용이** (이메일 통지를 추가해도 **구매 취소 로직은 수정 불필요**)

## Question 7 - 멱등성 [recall]
> 멱등성(idempotent)이란 무엇이며, 이벤트 처리에서 왜 중요한가?

> [!answer]- 정답 보기
> **연산을 여러 번 적용해도 결과가 달라지지 않는 성질**이다. 수학의 **절댓값 함수 `abs()`** 가 대표적이다.
> 이벤트 핸들러가 멱등성을 가지면 **시스템 장애로 같은 이벤트가 중복 발생해도 결과적으로 동일 상태**가 되므로, **이벤트 중복 발생이나 중복 처리에 대한 부담을 줄여준다.**
> 예: **배송지 정보 변경 이벤트**는 한 번 처리하나 여러 번 처리하나 동일 주소가 된다.

## Question 8 - 이벤트가 담을 데이터 [application]
> 아래 핸들러 코드의 문제를 지적하고, 이벤트 설계 관점에서 어떻게 고쳐야 하는지 답하라. 또한 반대 방향의 주의점도 언급하라.
> ```java
> @EventListener(ShippingInfoChangedEvent.class)
> public void handle(ShippingInfoChangedEvent evt) {
>     Order order = orderRepository.findById(evt.getOrderNo());
>     shippingInfoSynchronizer.sync(order.getNumber().getValue(),
>                                   order.getShippingInfo());
> }
> ```

> [!answer]- 정답 보기
> **문제**: 이벤트가 **핸들러가 필요로 하는 데이터를 담고 있지 않아서**, 핸들러가 **리포지터리·조회 API·직접 DB 접근**으로 데이터를 다시 조회해야 한다.
> **고침**: 이벤트에 **바뀐 배송지 정보를 포함**시킨다.
> ```java
> public class ShippingInfoChangedEvent {
>     private String orderNumber;
>     private long timestamp;
>     private ShippingInfo newShippingInfo;   // ★ 필요한 데이터 포함
> }
> ```
> **반대 방향의 주의점**: **이벤트 자체와 관련 없는 데이터를 포함할 필요는 없다.** 배송지 변경 이벤트에 **주문 상품 번호와 개수를 담을 필요는 없다.**

## Question 9 - 비동기 전환 [application]
> 동기 이벤트 처리의 두 문제를 해결하기 위해 로컬 핸들러를 비동기로 전환하려 한다. 필요한 코드 변경을 보이고, 이 방식의 약점을 지적하라.

> [!answer]- 정답 보기
> **1단계 — 비동기 활성화**
> ```java
> @SpringBootApplication
> @EnableAsync
> public class ShopApplication { ... }
> ```
> **2단계 — 핸들러에 `@Async`**
> ```java
> @Async
> @EventListener(OrderCanceledEvent.class)
> public void handle(OrderCanceledEvent event) {
>     refundService.refund(event.getOrderNumber());
> }
> ```
> **해결되는 것**: 외부 환불 서비스가 느려져도 `cancel()`이 느려지지 않고, 외부 실패가 주문 취소 트랜잭션을 롤백시키지 않는다.
> **약점**: **이벤트 처리에 실패하면 이벤트를 유실**한다. (재처리 보장이 없다)

## Question 10 - offset 계산 [application]
> API 방식으로 이벤트를 가져가는 클라이언트가 1분 주기로 `limit=5`로 조회한다. 1분에 5개, 2분에 3개, 3분에 0개를 받았다면 각 시점의 `offset`은? 그리고 `lastOffset`을 저장하는 이유는?

> [!answer]- 정답 보기
> | 시점 | 요청 offset | 받은 개수 | 다음 offset |
> |---|---|---|---|
> | 1분 | **0** (저장값 없으면 0) | 5 | **5** |
> | 2분 | **5** | 3 | **8** (5+3) |
> | 3분 | **8** | 0 | **8** (그대로) |
> | 4분 | **8** | … | … |
>
> **`lastOffset`을 저장하는 이유**: **같은 이벤트를 중복해서 처리하지 않기 위해서**다.
> 덕분에 **처리에 실패하면 실패한 이벤트부터 다시 읽어와 재처리**할 수 있고, **API 서버 장애 후에도 재시도로 복구**할 수 있다.

## Question 11 - 트랜잭션 연계 [application]
> 주문 취소 트랜잭션은 롤백됐는데 환불 이벤트 핸들러는 실행되는 상황을 막으려면 어떻게 해야 하는가? 두 가지 방법을 제시하라.

> [!answer]- 정답 보기
> **방법 ① — `@TransactionalEventListener`**
> ```java
> @TransactionalEventListener(
>     classes = OrderCanceledEvent.class,
>     phase = TransactionPhase.AFTER_COMMIT
> )
> public void handle(OrderCanceledEvent event) {
>     refundService.refund(event.getOrderNumber());
> }
> ```
> `AFTER_COMMIT`을 지정하면 **트랜잭션 커밋에 성공한 뒤에만 핸들러를 실행**하고, 롤백되면 실행하지 않는다.
> **방법 ② — DB 이벤트 저장소**
> **이벤트 발생 코드와 이벤트 저장 처리를 한 트랜잭션**으로 처리한다. 트랜잭션이 성공할 때만 이벤트가 DB에 저장되므로 같은 효과를 얻는다.
> **근본 목적**: 트랜잭션 실패와 이벤트 처리 실패를 모두 고려하면 복잡하므로 **경우의 수를 줄이는 것**이다.

## Question 12 - 비동기 방식 선택 [analysis]
> 로컬 핸들러 비동기, 메시지 큐, 이벤트 저장소 세 가지를 이벤트 손실·순서 보장·구현 복잡도·프로세스 구조 관점에서 비교하고 선택 기준을 제시하라.

> [!answer]- 정답 보기
> | 관점 | 로컬 핸들러(`@Async`) | 메시지 큐 | 이벤트 저장소 |
> |---|---|---|---|
> | **이벤트 손실** | **유실 가능** | 글로벌 트랜잭션 시 안전 | **손실 없음** (발생+저장이 한 트랜잭션) |
> | **순서 보장** | — | **기술에 따라 순서가 다를 수 있다** | **발생 순서대로 저장·제공** |
> | **구현 복잡도** | **가장 단순** (애너테이션 2개) | 중간 (인프라 필요) | 높음 (저장소·포워더/API·offset) |
> | **프로세스 구조** | 동일 JVM | **별도 프로세스(JVM) 전제** | 별도 프로그램 |
> | **재처리** | 불가 | 시스템에 따라 다름 | **실패 지점부터 재처리 가능** |
>
> **선택 기준**
> - 이벤트 유실을 감수할 수 있고 **가장 빠르게 적용**하고 싶다면 → **로컬 핸들러 비동기**
> - **이미 별도 프로세스로 분리**되어 있고 인프라가 있다면 → **메시지 큐** (래빗MQ=글로벌 트랜잭션·고가용성, 카프카=고성능)
> - **유실이 허용되지 않거나 순서가 중요하고 재처리가 필요**하면 → **이벤트 저장소 + 포워더/API**
> - **동일 JVM에서 비동기 처리를 위해 메시지 큐를 쓰는 것은 시스템을 복잡하게 만들 뿐**이므로 피한다.

## Question 13 - 포워더 설계 결함 [analysis]
> 포워더를 구현했는데 특정 이벤트가 계속 전송에 실패한다. 어떤 문제가 발생하며 어떻게 설계해야 하는가? 또한 offset으로 DB 자동 증가 칼럼을 쓸 때의 함정도 설명하라.

> [!answer]- 정답 보기
> **문제**: 포워더는 실패하면 **실패한 이벤트부터 다시 읽어와 전송을 시도**하므로, 특정 이벤트가 계속 실패하면 **그 이벤트 때문에 나머지 이벤트를 전송할 수 없게 된다**(전체 정체).
> **설계**: **실패한 이벤트의 재전송 횟수 제한**을 둔다. 예를 들어 **동일 이벤트 3회 실패 시 생략하고 다음 이벤트로 넘어간다**는 정책을 정한다. 생략된 이벤트는 **별도 실패용 DB나 메시지 큐에 저장**해 두면 이후 **실패 이유 분석이나 후처리**에 도움이 된다.
> **자동 증가 칼럼의 함정**: 자동 증가 칼럼은 **`INSERT` 시점에 값이 증가하지만 실제 데이터는 커밋 시점에 반영**된다. 마지막 값이 10인 상태에서 A가 11을, B가 12를 획득했는데 **B가 먼저 커밋되면 그 사이 조회 시 11은 빠지고 12만 조회**된다. 그러면 offset이 12를 넘어가 **11번 이벤트가 영원히 누락**된다.
> **해법**: **ID를 기준으로 데이터를 지연 조회하는 방식**을 사용해야 한다.

## Question 14 - 이벤트 도입의 효과 종합 [analysis]
> 주문 취소 → 환불 시나리오에서 ① 직접 호출 ② 동기 이벤트 ③ 비동기 이벤트로 발전시킬 때 각 단계에서 무엇이 해결되고 무엇이 남는지 분석하라.

> [!answer]- 정답 보기
> **① 직접 호출**
> 문제: 트랜잭션 애매 / 성능 직접 영향 / **주문 도메인에 결제 로직 오염** / 기능 추가 시 복잡도 폭증. 근본 원인은 **강결합**.
>
> **② 동기 이벤트 (`@EventListener`)**
> **해결됨**: **강결합 제거**. `Order.cancel()`에서 `RefundService` 파라미터와 환불 로직이 사라지고, **주문 → 결제 도메인 의존이 제거**된다. 이메일 통지를 추가해도 **핸들러만 추가**하면 되어 **구매 취소 로직은 수정 불필요**.
> **남은 문제**: 스프링 기본 `@EventListener`는 **동기**이므로 **같은 스레드·같은 트랜잭션**에서 실행된다. 따라서 **외부 환불이 느려지면 `cancel()`도 느려지고**, 환불 실패 시 **롤백하면 구매 취소 자체가 실패**한다.
>
> **③ 비동기 이벤트 (`@Async` 등)**
> **해결됨**: **성능 분리**(외부 지연이 내 시스템에 전파되지 않음)와 **트랜잭션 분리**(구매 취소는 성공시키고 환불만 재처리).
> **새로 생기는 고려사항**: **이벤트 손실**(로컬 핸들러), **순서**, **재처리**(순번 기억/멱등성), **재전송 제한**, 그리고 **트랜잭션이 롤백됐는데 핸들러가 실행되는 상황** → `@TransactionalEventListener(AFTER_COMMIT)` 또는 **DB 이벤트 저장소**로 해결한다.
>
> **정리**: 이벤트는 **결합도 문제를 먼저 풀고**, 비동기는 **성능·트랜잭션 문제를 푼다**. 대신 **분산 시스템의 고려사항(손실·순서·중복)** 을 떠안게 되므로 이를 설계로 보완해야 한다.

> [!answer]- 정답 보기

## Question 16 - 포워더 vs API [recall]
> 이벤트 저장소를 사용하는 두 방식(포워더 / API)의 차이를 전달 방향과 offset 추적 주체 관점에서 설명하라.

> [!answer]- 정답 보기
> **전달 방식에 차이**가 있다.
> - **포워더 방식**: 포워더가 **이벤트를 외부에 전달**(push)한다. **이벤트를 어디까지 처리했는지 추적하는 역할이 포워더에 있다.**
> - **API 방식**: **외부 핸들러가 API 서버를 통해 이벤트 목록을 가져간다**(pull). **이벤트 목록을 요구하는 외부 핸들러가 자신이 어디까지 처리했는지 기억해야 한다.**

## Question 17 - 메시징 시스템 비교 [recall]
> 래빗MQ와 카프카를 글로벌 트랜잭션 지원 여부와 특징 관점에서 비교하라.

> [!answer]- 정답 보기
> - **래빗MQ(RabbitMQ)**: **글로벌 트랜잭션을 지원**하고 **클러스터와 고가용성**도 지원해 **안정적으로 메시지를 전달**할 수 있다. **다양한 개발 언어와 통신 프로토콜**을 지원한다.
> - **카프카(Kafka)**: **글로벌 트랜잭션을 지원하지 않지만** 다른 메시징 시스템에 비해 **높은 성능**을 보여준다.

## Question 18 - 메시지 큐 방식의 전제 [recall]
> 메시지 큐를 이용한 비동기 처리는 어떤 구조를 전제로 하는가? 동일 JVM에서 사용하면 어떻게 되는가?

> [!answer]- 정답 보기
> **보통 이벤트를 발생시키는 주체와 이벤트 핸들러가 별도 프로세스에서 동작**한다. 즉 **이벤트 발생 JVM과 이벤트 처리 JVM이 다르다.**
> 한 JVM에서도 메시지 큐로 이벤트를 주고받을 수는 있지만, **동일 JVM에서 비동기 처리를 위해 메시지 큐를 사용하는 것은 시스템을 복잡하게 만들 뿐이다.**
