# 이벤트 저장소를 이용한 비동기 처리 (★★★)

#ddd #event #async #event-store #event-forwarder #concept

## Overview Table (두 가지 방식)

| 방식 | 전달 주체 | 어디까지 처리했는지 추적하는 쪽 |
|------|-----------|--------------------------------|
| **① 포워더(Forwarder)** | **포워더가 이벤트를 외부에 전달** (push) | **포워더** |
| **② API** | **외부 핸들러가 API 서버를 통해 이벤트 목록을 가져감** (pull) | **외부 핸들러** |

| 공통 | 내용 |
|------|------|
| 전제 | 이벤트를 **일단 DB에 저장**한 뒤 별도 프로그램으로 전달 |
| ★ 최대 강점 | **이벤트 유실이 없다** — 발생과 저장을 **한 트랜잭션**으로 처리 |
| ★ 두 번째 강점 | **재처리 가능** — 실패한 이벤트부터 다시 읽어와 재시도 |
| 필요한 요소 | `EventEntry`, `EventStore`, `EventApi` / `EventForwarder`, `OffsetStore` |

## 방식 ① — 포워더 (그림 10.9)

```
   [ 트랜잭션 범위 ]
   도메인 → Events.raise() → 이벤트 디스패처 → 로컬 핸들러
                                                    │
                                            ┌───────▼────────┐
                                            │  이벤트 저장소  │ (DB)
                                            └───────┬────────┘
                                                    │ 주기적으로 읽음
                                            ┌───────▼────────┐
                                            │    포워더       │
                                            └───────┬────────┘
                                                    ▼
                                              이벤트 핸들러
```

## 방식 ② — API (그림 10.10)

```
   도메인 → 이벤트 저장소(DB)
                  │
           ┌──────▼──────┐          ┌──────────────┐
           │  API 서버   │◀─조회────│ 외부 핸들러   │
           └─────────────┘          └──────────────┘
                                    (자신이 어디까지 처리했는지 기억)
```

> [!important] 두 방식의 차이 (p.324)
> **이벤트를 전달하는 방식에 차이**가 있다.
> - **포워더 방식**: 포워더를 이용해서 **이벤트를 외부에 전달**한다. **이벤트를 어디까지 처리했는지 추적하는 역할이 포워더에 있다.**
> - **API 방식**: **외부 핸들러가 API 서버를 통해 이벤트 목록을 가져간다.** **이벤트 목록을 요구하는 외부 핸들러가 자신이 어디까지 처리했는지 기억해야 한다.**

## 이벤트 저장소 구현 (그림 10.11)

| 클래스 | 역할 |
|--------|------|
| **`EventEntry`** | 이벤트 저장소에 보관할 데이터 |
| **`EventStore`** | 이벤트를 **저장하고 조회하는 인터페이스** |
| **`JdbcEventStore`** | **JDBC를 이용한 `EventStore` 구현 클래스** |
| **`EventApi`** | **REST API로 이벤트 목록을 제공**하는 컨트롤러 |

### `EventEntry` (리스트 10.4)

```java
package com.myshop.eventstore.api;

public class EventEntry {
    private Long id;
    private String type;
    private String contentType;
    private String payload;
    private long timestamp;
    ...
}
```

| 필드 | 의미 |
|------|------|
| **`id`** | 이벤트를 **식별하기 위한 ID** |
| **`type`** | **이벤트 타입** |
| **`contentType`** | **직렬화한 데이터 형식** |
| **`payload`** | **이벤트 데이터 자체** |
| **`timestamp`** | **이벤트 시간** |

### `EventApi` 컨트롤러 (리스트 10.5)

```java
@RestController
public class EventApi {
    private EventStore eventStore;

    public EventApi(EventStore eventStore) {
        this.eventStore = eventStore;
    }

    @GetMapping("/api/events")
    public List<EventEntry> list(
            @RequestParam("offset") Long offset,
            @RequestParam("limit") Long limit) {
        return eventStore.get(offset, limit);
    }
}
```

> [!note]
> **이벤트를 수정하는 기능이 없으므로 `EventApi`도 단순 조회 기능만 존재**한다.

## ★ API 클라이언트의 offset 처리 (그림 10.13)

> API를 사용하는 클라이언트는 **일정 간격으로 다음 과정을 실행**한다.

| 단계 | 내용 |
|------|------|
| 1 | 가장 마지막에 처리한 데이터의 **offset인 `lastOffset`을 구한다.** 저장한 값이 없으면 **0**을 사용 |
| 2 | 마지막에 처리한 `lastOffset`을 **`offset`으로 사용해서 API를 실행**한다 |
| 3 | API 결과로 받은 **데이터를 처리**한다 |
| 4 | **`offset + 데이터 개수`를 `lastOffset`으로 저장**한다 |

> [!important] 왜 `lastOffset`을 저장하는가
> **같은 이벤트를 중복해서 처리하지 않기 위해서**다.

```
   1분 시점: /api/events?offset=0&limit=5  →  5개 제공  →  다음 offset = 5
   2분 시점: /api/events?offset=5&limit=5  →  3개 제공  →  다음 offset = 8  (5+3)
   3분 시점: /api/events?offset=8&limit=5  →  0개 제공  →  다음 offset = 8  (그대로)
   4분 시점: /api/events?offset=8&limit=5  →  5개 제공  →  다음 offset = 13
```

> [!tip] 장애 복구
> **클라이언트 API를 이용해서 언제든지 원하는 이벤트를 가져올 수 있기 때문에
> 이벤트 처리에 실패하면 다시 실패한 이벤트부터 읽어와 재처리할 수 있다.**
> **API 서버에 장애가 발생한 경우에도 주기적으로 재시도를 해서 API 서버가 살아나면 이벤트를 처리**할 수 있다.

## 포워더 구현 (리스트 10.10)

```java
@Component
public class EventForwarder {
    private static final int DEFAULT_LIMIT_SIZE = 100;

    private EventStore eventStore;
    private OffsetStore offsetStore;
    private EventSender eventSender;
    private int limitSize = DEFAULT_LIMIT_SIZE;

    public EventForwarder(EventStore eventStore,
                          OffsetStore offsetStore,
                          EventSender eventSender) {
        this.eventStore = eventStore;
        this.offsetStore = offsetStore;
        this.eventSender = eventSender;
    }

    @Scheduled(initialDelay = 1000L, fixedDelay = 1000L)
    public void getAndSend() {
        long nextOffset = getNextOffset();                       // ① 다음 offset
        List<EventEntry> events = eventStore.get(nextOffset, limitSize);  // ② 조회
        if (!events.isEmpty()) {                                 // ③ 존재 검사
            int processedCount = sendEvent(events);              // ④ 전송
            if (processedCount > 0) {
                saveNextOffset(nextOffset + processedCount);     // ⑤ offset 저장
            }
        }
    }

    private long getNextOffset() {
        return offsetStore.get();
    }

    private int sendEvent(List<EventEntry> events) {
        int processedCount = 0;
        try {
            for (EventEntry entry : events) {
                eventSender.send(entry);
                processedCount++;
            }
        } catch (Exception ex) {
            // 로깅 처리
        }
        return processedCount;
    }

    private void saveNextOffset(long nextOffset) {
        offsetStore.update(nextOffset);
    }
}
```

> [!important] 핵심 로직
> `sendEvent()`는 이벤트를 차례대로 발송하다가 **익셉션이 발생하면 전송을 멈추고 성공한 이벤트 개수를 리턴**한다.
> 따라서 저장하는 offset은 **최종적으로 전송에 성공한 이벤트를 기준으로 다음 이벤트에 대한 offset**이다.
> → **다음번 실행 시 마지막으로 전송에 성공한 이벤트의 다음 이벤트부터 읽어와 전송을 시도**한다.

### `OffsetStore` / `EventSender` 인터페이스

```java
public interface OffsetStore {
    long get();
    void update(long nextOffset);
}
```

> `OffsetStore` 구현 클래스는 offset 값을 **DB 테이블에 저장하거나 로컬 파일에 보관**해서 마지막 offset을 물리적 저장소에 보관한다.

```java
public interface EventSender {
    void send(EventEntry event);
}
```

> 이 인터페이스를 구현한 클래스는 `send()`에서 **외부 메시징 시스템에 이벤트를 전송**하거나 **원하는 핸들러에 이벤트를 전달**한다.
> **처리 중 익셉션이 발생하면 그대로 전파해서 다음 주기에 재처리**할 수 있도록 한다.

## ★ 자동 증가 칼럼을 offset으로 쓸 때의 함정 (p.337)

> [!danger] 반드시 알아야 할 문제
> **자동 증가 칼럼은 `INSERT` 쿼리를 실행하는 시점에 값이 증가하지만,
> 실제 데이터는 트랜잭션을 커밋하는 시점에 DB에 반영된다.**
> 즉 `INSERT`로 값이 증가했더라도 **커밋 전에 조회하면 그 레코드는 조회되지 않는다.**
> 또한 **커밋 시점에 따라 DB에 반영되는 시점이 달라질 수도 있다.**

```
   마지막 값 10인 상태
   A 트랜잭션: INSERT → 11 획득
   B 트랜잭션: INSERT → 12 획득
   B 커밋      → 12가 먼저 반영
   [ 이 사이에 조회하면 ]  →  11은 조회되지 않고 12만 조회된다  ❌
   A 커밋      → 11 반영 (하지만 이미 offset이 12를 넘어감)
```

> [!important] 해법
> **ID를 기준으로 데이터를 지연 조회하는 방식**을 사용해야 한다.

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "이벤트 저장소 방식의 두 가지" | **포워더 / API** |
| "포워더 vs API의 차이" | **전달 방식**(push/pull)과 **offset 추적 주체** |
| "포워더 방식의 추적 주체" | **포워더** |
| "API 방식의 추적 주체" | **외부 핸들러** |
| "`EventEntry`의 다섯 필드" | **id / type / contentType / payload / timestamp** |
| "`lastOffset`을 저장하는 이유" | **같은 이벤트를 중복 처리하지 않기 위해** |
| "5개 받았으면 다음 offset은?" | **이전 offset + 5** |
| "0개 받았으면?" | **offset을 그대로 유지** |
| "포워더 주기 실행 애너테이션" | **`@Scheduled`** |
| "전송 실패 시 offset 처리" | **성공한 개수만큼만** 증가 |
| "자동 증가 칼럼 offset의 함정" | **커밋 순서에 따라 중간 ID가 누락**될 수 있다 |
| "그 해법" | **ID 기준 지연 조회** |
| "이 방식의 최대 강점" | **이벤트 유실 없음 + 재처리 가능** |
