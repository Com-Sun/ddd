## Question 1 - 단일 모델의 함정 [recall]
> 처음 도메인 모델을 만들 때 빠지기 쉬운 함정은 무엇이며, 그 결과는?

> [!answer]- 정답 보기
> **도메인을 완벽하게 표현하는 단일 모델을 만들려는 시도**다.
> 한 도메인은 여러 하위 도메인으로 구분되므로, 한 개의 모델로 모두 표현하려 하면 **오히려 모든 하위 도메인에 맞지 않는 모델**을 만들게 된다.

## Question 2 - 용어의 차이 [recall]
> 하위 도메인에 따라 용어와 의미가 어떻게 달라지는지 '상품'과 '사람'을 예로 설명하라.

> [!answer]- 정답 보기
> **같은 용어, 다른 의미**: 카탈로그의 '상품'은 **이미지·가격·옵션·상세 설명 등 상품 정보 위주**지만, 재고 관리의 '상품'은 **실존하는 개별 객체를 추적**하기 위한 것이다. 따라서 **카탈로그에서 물리적으로 한 개인 상품이 재고 관리에서는 여러 개 존재할 수 있다.**
> **같은 대상, 다른 용어**: 카탈로그의 '상품'은 검색에서는 **문서**로 불리고, 사람은 회원 도메인에서 **회원**, 주문에서 **주문자**, 배송에서 **보내는 사람**으로 불린다.

## Question 3 - 바운디드 컨텍스트의 정의 [recall]
> 바운디드 컨텍스트의 정의와 구분 기준, 그리고 물리적 실체는?

> [!answer]- 정답 보기
> **모델의 경계를 결정**하며 **한 개의 바운디드 컨텍스트는 논리적으로 한 개의 모델**을 갖는다.
> **구분 기준은 용어**다.
> 또한 바운디드 컨텍스트는 **실제로 사용자에게 기능을 제공하는 물리적 시스템**이며, 도메인 모델은 이 안에서 도메인을 구현한다.

## Question 4 - 컨텍스트에 포함되는 것 [recall]
> 바운디드 컨텍스트는 도메인 모델만 포함하는가?

> [!answer]- 정답 보기
> **아니다.** 도메인 기능을 사용자에게 제공하는 데 필요한 **표현 영역, 응용 서비스, 인프라스트럭처 영역을 모두 포함**한다.
> 또한 **도메인 모델의 데이터 구조가 바뀌면 DB 테이블 스키마도 함께 변경해야 하므로 테이블도 포함**된다.

## Question 5 - 상류와 하류 [recall]
> 상류(Upstream)와 하류(Downstream)를 정의하고, 의존의 방향과 협업이 필요한 이유를 설명하라.

> [!answer]- 정답 보기
> **상류**는 API를 제공하는 쪽으로 **서비스 공급자** 역할, **하류**는 API를 호출하는 쪽으로 **고객** 역할이다.
> **하류가 상류에 의존**하며, 상류의 API 인터페이스가 바뀌면 하류 코드도 바뀐다.
> **협업이 필요한 이유**: 상류가 마음대로 바꾸면 하류는 **우선순위 높은 다른 기능을 개발하지 못할 수 있고**, 반대로 상류가 매번 승낙을 받아야 하면 **새로운 개발 시도 자체를 하지 않을 수 있다.** 따라서 **개발 계획을 공유하고 일정을 협의**해야 한다.

## Question 6 - 다섯 가지 관계 [recall]
> 바운디드 컨텍스트 간 다섯 가지 관계를 나열하고 각각 한 줄로 설명하라.

> [!answer]- 정답 보기
> ① **고객/공급자** — 상류가 API를 제공하고 하류가 사용 (가장 흔함)
> ② **공개 호스트 서비스(OHS)** — 여러 하류의 요구를 수용하는 **단일 API를 공개** (예: 검색 시스템)
> ③ **안티코럽션 계층(ACL)** — 외부 모델이 **내 도메인 모델을 침범하지 못하게 막는 완충 지대**
> ④ **공유 커널(Shared Kernel)** — 두 팀이 **같은 모델을 공유**
> ⑤ **독립 방식(Separate Way)** — **통합하지 않는다** (수동 통합)

## Question 7 - 여러 하위 도메인, 한 컨텍스트 [application]
> 소규모 쇼핑몰을 하나의 웹 애플리케이션으로 개발한다. 회원·카탈로그·재고·구매·결제를 모두 담당해야 할 때 무엇을 주의해야 하며, 어떻게 구현해야 하는가?

> [!answer]- 정답 보기
> **주의점**: 한 프로젝트에 각 하위 도메인의 모델이 모이면 **전체를 위한 단일 모델을 만들고 싶은 유혹**에 빠지기 쉽다. 그러면 도메인 모델이 개별 하위 도메인을 제대로 반영하지 못해 **하위 도메인별 기능 확장이 어려워지고 서비스 경쟁력이 떨어진다.**
> **구현**: 한 개의 바운디드 컨텍스트가 여러 하위 도메인을 포함하더라도 **하위 도메인마다 구분되는 패키지를 갖도록 구현**한다. 그러면 모델이 뒤섞이지 않고 **하위 도메인마다 바운디드 컨텍스트를 갖는 효과**를 낼 수 있다.

## Question 8 - 통합 인터페이스 설계 [application]
> 카탈로그 컨텍스트에서 추천 시스템의 REST API를 호출해 유사 상품 목록을 보여줘야 한다. 인터페이스와 구현을 설계하고, 각각의 위치와 책임을 답하라.

> [!answer]- 정답 보기
> **도메인 영역** — 카탈로그 도메인 언어로 인터페이스 정의
> ```java
> public interface ProductRecommendationService {
>     List<Product> getRecommendationsOf(ProductId id);
> }
> ```
> **인프라스트럭처 영역** — 구현 클래스가 **외부 연동 + 모델 변환**을 책임진다.
> ```java
> public class RecSystemClient implements ProductRecommendationService {
>     @Override
>     public List<Product> getRecommendationsOf(ProductId id) {
>         List<RecommendationItem> items = getRecItems(id.getValue());
>         return toProducts(items);   // 추천 모델 → 카탈로그 Product로 변환
>     }
> }
> ```
> 추천 API는 `{"itemId": "PROD-1000", "rank": 100}` 형태의 **추천 시스템 모델**을 주므로, 이 클래스가 **카탈로그 도메인 모델로 변환**한다. 변환이 복잡하면 **별도 변환기 클래스**를 둔다.

## Question 9 - 메시지 큐 데이터 구조 [application]
> 카탈로그와 추천 컨텍스트를 메시지 큐로 통합한다. 메시지 데이터 구조는 누가 결정하며, 카탈로그가 큐를 제공하는 경우와 추천이 제공하는 경우 코드가 어떻게 달라지는가?

> [!answer]- 정답 보기
> **큐를 제공하는 쪽의 도메인**이 데이터 구조를 결정한다. 두 팀은 **주고받을 데이터 형식을 협의**해야 한다.
> **카탈로그가 큐를 제공** → 카탈로그 도메인 그대로 전송, **추천 시스템이 자기 모델로 변환**해서 처리
> ```java
> messageClient.send(new ViewLog(memberId, productId, time));
> ```
> **추천이 큐를 제공** → 카탈로그가 추천 모델에 맞춰 전송
> ```java
> messageClient.send(new ActivityLog(productId, memberId, ActivityType.VIEW, time));
> ```
> 이 방식은 **한쪽이 출판하고 다른 쪽이 구독하는 출판/구독(pub/sub) 모델**을 따른다.

## Question 10 - 통합 방식 선택 [analysis]
> REST API 직접 통합과 메시지 큐 간접 통합을 비교하고, 각각 어떤 상황에 적합한지 판단 기준을 제시하라.

> [!answer]- 정답 보기
> | 관점 | REST API (직접) | 메시지 큐 (간접) |
> |---|---|---|
> | 동기성 | **동기** — 응답을 기다린다 | **비동기** — 큐에 넣고 바로 자기 처리를 계속 |
> | 결합도 | 하류가 상류 API에 **직접 의존** | **느슨한 결합** (출판/구독) |
> | 장애 전파 | 상류 장애가 **하류에 즉시 영향** | 큐가 완충 역할 |
> | 데이터 구조 | **상류 도메인**을 따름 | **큐 제공자 도메인**을 따름 |
>
> **판단 기준**
> - **즉시 응답이 필요**한 조회(예: 상품 상세 페이지의 추천 목록)는 **REST API**가 적합하다.
> - **이력·이벤트 전달처럼 즉시 응답이 필요 없고 처리량이 많은** 경우(예: 사용자 활동 이력 전달)는 **메시지 큐**가 적합하다. 상대 시스템의 처리 속도나 장애에 영향을 덜 받는다.
> - 어느 쪽이든 **자신의 도메인 언어로 된 인터페이스**를 두고 **인프라스트럭처에서 모델 변환**(안티코럽션 계층)을 처리하는 원칙은 동일하다.

## Question 11 - 공유 커널의 트레이드오프 [analysis]
> 운영자용 주문 관리 도구 팀과 고객용 주문 서비스 팀이 주문 모델을 공유하려 한다. 이 결정의 장단점과 성립 조건을 분석하고, 조건이 충족되지 않으면 어떻게 되는지 설명하라.

> [!answer]- 정답 보기
> 이것이 **공유 커널(Shared Kernel)** 관계다.
> **장점**: **중복을 줄여준다.** 두 팀이 하나의 모델을 개발해서 공유하므로 **동일한 모델을 두 번 개발하는 중복**을 없앨 수 있다.
> **단점 / 조건**: 두 팀이 한 모델을 공유하므로 **한 팀에서 임의로 모델을 변경하면 안 되며, 두 팀이 밀접한 관계를 유지해야 한다.**
> **조건이 충족되지 않으면**: 두 팀이 밀접한 관계를 형성할 수 없다면 **공유 커널의 장점보다 공유 커널로 인해 개발이 지연되고 정체되는 문제가 더 커진다.** 이 경우에는 모델을 분리하고 통합 관계(고객/공급자 + ACL)로 가는 편이 낫다.

## Question 12 - 컨텍스트 맵의 가치 [analysis]
> 컨텍스트 맵은 무엇이며 왜 필요한가? 무엇을 표시하고, 이를 통해 어떤 의사결정을 할 수 있는지 서술하라. 또한 컨텍스트 맵의 성질 하나를 지적하라.

> [!answer]- 정답 보기
> **정의/필요성**: **바운디드 컨텍스트 간의 관계를 표시한 지도**다. **개별 바운디드 컨텍스트에 매몰되면 전체를 보지 못하므로**("나무만 보고 숲을 못 봄") 전체를 조망할 지도가 필요하다.
> **표시하는 것**: 각 컨텍스트의 **경계와 관계**(OHS, ACL 등). **주요 애그리거트**를 함께 표시하면 모델 관계가 더 명확해지고, **하위 도메인이나 조직 구조**를 표시하면 전체 관계 이해에 도움이 된다.
> **가능한 의사결정**: ① **하위 도메인과 일치하지 않는 바운디드 컨텍스트를 찾아** 도메인에 맞게 **경계를 조절**하고 ② 사업의 **핵심 도메인을 위해 조직 역량을 어떤 컨텍스트에 집중할지** 파악한다.
> **성질**: **컨텍스트 맵은 시스템의 전체 이해 수준을 보여준다.** 즉 **시스템을 더 잘 이해하거나 컨텍스트 간 관계가 바뀌면 컨텍스트 맵도 함께 바뀐다** — 고정된 산출물이 아니라 **살아 있는 문서**다. (그리는 규칙은 따로 없고, 화이트보드나 파워포인트로 충분하다.)

## Question 13 - 바운디드 컨텍스트와 UI [recall]
> 바운디드 컨텍스트는 반드시 사용자에게 보여지는 UI를 가져야 하는가? UI 서버를 두는 구조에서 UI 서버의 역할은?

> [!answer]- 정답 보기
> **가질 필요가 없다.** 브라우저가 **카탈로그 컨텍스트에서 HTML을 받고, 리뷰 컨텍스트의 REST API를 직접 호출**해 JSON을 가공해 보여줄 수도 있다.
> **UI 서버를 두는 구조**에서 **UI 서버는 각 바운디드 컨텍스트를 위한 파사드 역할**을 수행한다. 브라우저 요청을 받아 **카탈로그와 리뷰 컨텍스트로부터 필요한 정보를 읽어와 조합한 뒤** 응답을 제공한다.

## Question 14 - 마이크로서비스와의 관계 [recall]
> 마이크로서비스 아키텍처가 바운디드 컨텍스트와 잘 어울리는 이유는?

> [!answer]- 정답 보기
> **바운디드 컨텍스트는 모델의 경계를 만드는데, 바운디드 컨텍스트를 마이크로서비스로 구현하면 자연스럽게 컨텍스트별로 모델이 분리**된다.
> 코드로 보면 **마이크로서비스마다 프로젝트를 생성**하므로 **바운디드 컨텍스트마다 프로젝트를 만들게 되어, 코드 수준에서 두 컨텍스트의 모델이 섞이지 않는다.**
> 또한 별도 프로세스로 개발한 컨텍스트는 **독립적으로 배포·모니터링·확장**되는데 이 역시 마이크로서비스의 특징과 일치한다.

## Question 15 - 컨텍스트 맵 작성 [recall]
> 컨텍스트 맵을 그리는 규칙과 사용하는 도구는? 맵에 흔히 표기하는 두 약어는 무엇인가?

> [!answer]- 정답 보기
> **그리는 규칙은 따로 없다.** **간단한 도형과 선으로 각 컨텍스트의 관계를 이해할 수 있는 수준**이면 되며, **화이트보드나 파워포인트** 같은 도구로 쉽게 그릴 수 있다.
> 흔히 표기하는 약어는 **OHS(공개 호스트 서비스)** 와 **ACL(안티코럽션 계층)** 이다. **주요 애그리거트**를 함께 표시하면 모델 관계가 더 명확해지고, **하위 도메인이나 조직 구조**를 표시하면 전체 관계 이해에 도움이 된다.
