# 바운디드 컨텍스트 간 통합 (★★★)

#ddd #bounded-context #context-integration #concept

## Overview Table (두 가지 통합 방식)

| 방식 | 특징 | 데이터 구조 결정 |
|------|------|------------------|
| **① 직접 통합 — REST API 호출** | 동기, 즉시 응답 | 상류(제공자) 도메인 모델을 따름 |
| **② 간접 통합 — 메시지 큐** | **비동기**, 대기하지 않음 | **큐를 제공하는 쪽**의 도메인 모델을 따름 |

| ★ 공통 핵심 | 내용 |
|-------------|------|
| **도메인 서비스로 표현** | 통합을 **자신의 도메인 언어로 된 인터페이스**로 정의 |
| **모델 변환 책임** | 구현 클래스(인프라스트럭처)가 **외부 모델 ↔ 내 도메인 모델** 변환 |
| 변환이 복잡하면 | **별도 변환기 클래스**를 둔다 |

## 통합이 필요해지는 상황

> 온라인 쇼핑 사이트에서 매출 증대를 위해 카탈로그 하위 도메인에 **개인화 추천 기능**을 도입하기로 했다.
> 기존 카탈로그 팀과 별도로 **추천 시스템을 담당하는 팀**이 생겼다.
> → 카탈로그 하위 도메인에 **카탈로그 컨텍스트 + 추천 컨텍스트**가 생기고, 자연스럽게 **통합**이 발생한다.

> 통합이 필요한 기능: **사용자가 제품 상세 페이지를 볼 때, 보고 있는 상품과 유사한 상품 목록을 하단에 보여준다.**

> [!important] 두 컨텍스트의 모델이 다르다
> - **카탈로그**: 제품을 중심으로 도메인 모델을 구현
> - **추천**: 추천 연산을 위한 모델을 구현. **상품의 상세 정보를 포함하지 않으며, 상품 번호 대신 '아이템 ID'라는 용어**를 사용하고 **추천 순위** 같은 데이터를 담는다

## ① 직접 통합 — REST API

### 1단계 — 도메인 언어로 인터페이스 정의

> 카탈로그 시스템에서는 **추천의 도메인 모델을 사용하기보다 카탈로그 도메인 모델을 사용해서 추천 상품을 표현**해야 한다.

```java
// 상품 추천 기능을 표현하는 도메인 서비스
public interface ProductRecommendationService {
    List<Product> getRecommendationsOf(ProductId id);
}
```

### 2단계 — 인프라스트럭처에서 구현 + 모델 변환

> [!important]
> **도메인 서비스를 구현한 클래스는 인프라스트럭처 영역에 위치한다.**
> 이 클래스는 **외부 시스템과의 연동을 처리하고 외부 시스템의 모델과 현재 도메인 모델 간의 변환을 책임진다.**

**외부 API 응답 (추천 시스템의 모델)**

```json
[
    {"itemId": "PROD-1000", "type": "PRODUCT", "rank": 100},
    {"itemId": "PROD-1001", "type": "PRODUCT", "rank": 54}
]
```

**변환 구현**

```java
public class RecSystemClient implements ProductRecommendationService {
    private ProductRepository productRepository;

    @Override
    public List<Product> getRecommendationsOf(ProductId id) {
        List<RecommendationItem> items = getRecItems(id.getValue());
        return toProducts(items);
    }

    private List<RecommendationItem> getRecItems(String itemId) {
        // externalRecClient는 외부 추천 시스템을 위한 클라이언트라고 가정
        return externalRecClient.getRecs(itemId);
    }

    private List<Product> toProducts(List<RecommendationItem> items) {
        return items.stream()
                .map(item -> toProductId(item.getItemId()))
                .map(prodId -> productRepository.findById(prodId))
                .collect(toList());
    }

    private ProductId toProductId(String itemId) {
        return new ProductId(itemId);
    }
}
```

```
   [ 도메인 영역 ]
   «interface» ProductRecommendationService     ← 도메인 관점에서 인터페이스 정의
        +getRecommendationsOf(ProductId) : List<Product>
                    △
   ─ ─ ─ ─ ─ ─ ─ ─ ─╎─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
   [ 인프라스트럭처 ]╎
        RecSystemClient ──REST API 호출──▶  외부 추천 시스템
              ▲
     도메인 모델과 외부 시스템 간의 모델 변환 처리
```

> [!tip] 변환이 복잡하면
> 두 모델 간의 **변환 과정이 복잡하면 변환 처리를 위한 별도 클래스(Translator)를 만들고 그 클래스에서 변환을 처리**해도 된다.
> ```java
> public class RecTranslator {
>     public Product toProduct(RecommendationItem item) { ... }
>     public String toItemId(ProductId productId) { ... }
> }
> ```

## ② 간접 통합 — 메시지 큐

> **대표적인 간접 통합 방식이 메시지 큐를 사용하는 것**이다.
> 추천 시스템은 **사용자가 조회한 상품 이력이나 구매 이력** 같은 사용자 활동 이력을 필요로 하는데, 이 내역을 전달할 때 메시지 큐를 사용할 수 있다.

```
   [ 카탈로그 컨텍스트 ]           [ 메시지 큐 ]        [ 추천 컨텍스트 ]
   활동 이력을 큐에 추가  ──────▶   메시지    ──────▶  큐에서 가져옴
        │                                              │
        └─ 기다리지 않고 바로 자신의 처리를 계속         └─ 추천 계산에 사용
```

> [!important] 비동기의 이점
> **메시지 큐는 비동기로 메시지를 처리하기 때문에**,
> 카탈로그 바운디드 컨텍스트는 **메시지를 큐에 추가한 뒤 추천 컨텍스트가 메시지를 처리할 때까지 기다리지 않고 바로 이어서 자신의 처리를 계속**한다.

> [!warning] 협의가 필요하다
> 두 바운디드 컨텍스트를 개발하는 팀은 **메시지의 데이터 구조를 맞춰야** 한다.
> 각각의 팀은 서로 만나서 **주고받을 데이터 형식에 대해 협의**해야 한다.

## ★ 큐의 소유자가 데이터 구조를 결정한다

| 큐 제공자 | 메시지 데이터 구조 | 변환 책임 |
|-----------|--------------------|-----------|
| **카탈로그 시스템** | **카탈로그 도메인**을 따름 (`ViewLog`, `OrderLog`, `ProductLog`) | **추천 시스템**이 자신의 모델에 맞게 변환 |
| **추천 시스템** | **추천 도메인**을 따름 (`ActivityLog`) | **카탈로그 시스템**이 맞춰서 전송 |

### 카탈로그 기준으로 저장하는 경우

```java
// 상품 조회 관련 로그 기록 코드
public class ViewLogService {
    private MessageClient messageClient;

    public void appendViewLog(String memberId, String productId, Date time) {
        messageClient.send(new ViewLog(memberId, productId, time));
    }
}

// MessageClient
public class RabbitMQClient implements MessageClient {
    private RabbitTemplate rabbitTemplate;

    @Override
    public void send(ViewLog viewLog) {
        // 카탈로그 기준으로 작성한 데이터를 큐에 그대로 보관
        rabbitTemplate.convertAndSend(logQueueName, viewLog);
    }
}
```

### 추천 기준으로 저장하는 경우

```java
public class ViewLogService {
    private MessageClient messageClient;

    public void appendViewLog(String memberId, String productId, Date time) {
        messageClient.send(
                new ActivityLog(productId, memberId, ActivityType.VIEW, time));
    }
}

public class RabbitMQClient implements MessageClient {
    private RabbitTemplate rabbitTemplate;

    @Override
    public void send(ActivityLog activityLog) {
        rabbitTemplate.convertAndSend(logQueueName, activityLog);
    }
}
```

> [!important] 출판/구독 모델
> 예를 들어 **카탈로그 시스템에서 큐를 제공한다면 큐에 담기는 내용은 카탈로그 도메인을 따른다.**
> 카탈로그 도메인은 메시징 큐에 카탈로그와 관련된 메시지를 저장하고,
> **다른 바운디드 컨텍스트는 이 큐로부터 필요한 메시지를 수신**한다.
> 즉 이 방식은 **한쪽에서 메시지를 출판하고 다른 쪽에서 메시지를 구독하는 출판/구독(pub/sub) 모델**을 따른다.

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "직접 통합의 대표 방식" | **REST API 호출** |
| "간접 통합의 대표 방식" | **메시지 큐** |
| "통합을 표현하는 방법" | **자신의 도메인 언어로 된 도메인 서비스 인터페이스** |
| "인터페이스/구현의 위치" | **도메인 영역 / 인프라스트럭처 영역** |
| "구현 클래스의 책임" | 외부 연동 + **외부 모델 ↔ 내 도메인 모델 변환** |
| "변환이 복잡하면?" | **별도 변환기(Translator) 클래스** |
| "메시지 큐의 이점" | **비동기** — 기다리지 않고 자신의 처리를 계속 |
| "메시지 데이터 구조는 누가 결정?" | **큐를 제공하는 쪽**의 도메인 |
| "이 방식이 따르는 모델" | **출판/구독(pub/sub) 모델** |
