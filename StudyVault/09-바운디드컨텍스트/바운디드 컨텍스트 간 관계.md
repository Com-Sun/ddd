# 바운디드 컨텍스트 간 관계 (★★★)

#ddd #bounded-context #context-relationship #concept

## Overview Table (다섯 가지 관계)

| 관계 | 영문 | 핵심 |
|------|------|------|
| **① 고객/공급자** | Customer / Supplier | **상류(Upstream)** = 공급자, **하류(Downstream)** = 고객. 가장 흔한 관계 |
| **② 공개 호스트 서비스** | **Open Host Service (OHS)** | 상류가 여러 하류의 요구를 수용하는 **단일 API를 서비스 형태로 공개** |
| **③ 안티코럽션 계층** | **Anticorruption Layer (ACL)** | 하류가 **상류 모델이 자기 모델을 침범하지 못하게 막는 완충 지대** |
| **④ 공유 커널** | **Shared Kernel** | 두 팀이 **같은 모델을 공유** |
| **⑤ 독립 방식** | **Separate Way** | 서로 **통합하지 않는다** |

## ① 상류(Upstream)와 하류(Downstream)

> 두 바운디드 컨텍스트 간 관계 중 **가장 흔한 관계는 한쪽에서 API를 제공하고 다른 한쪽에서 그 API를 호출하는 관계**다. REST API가 대표적이다.

```
   [ 카탈로그 컨텍스트 ]           [ 추천 컨텍스트 ]
        하류 (Downstream)  ─────▶   상류 (Upstream)
        고객 역할                    서비스 공급자 역할
        │                                  │
        └── 상류가 제공하는 데이터와 기능에 의존 ──┘
```

| 역할 | 설명 |
|------|------|
| **상류(Upstream)** | 일종의 **서비스 공급자** 역할 |
| **하류(Downstream)** | 그 서비스를 사용하는 **고객** 역할 |

> [!warning] 의존의 방향
> **API를 사용하는 바운디드 컨텍스트(하류)는 API를 제공하는 바운디드 컨텍스트(상류)에 의존**하게 된다.
> **추천 시스템이 제공하는 REST API의 인터페이스가 바뀌면 카탈로그 시스템의 코드도 바뀌게 된다.**

### 협업이 필요하다

> [!important] 두 팀의 딜레마
> **고객과 공급자 관계에 있는 두 팀은 상호 협력이 필수적**이다.
>
> | 상황 | 문제 |
> |------|------|
> | 상류 팀이 **마음대로 API를 변경**하면 | 하류 팀은 변경된 API에 맞추느라 **우선순위가 높은 다른 기능을 개발하지 못할 수도** 있다 |
> | 상류 팀이 변경할 때마다 **하류 팀의 승낙을 받아야** 한다면 | 상류 팀은 **새로운 개발 시도 자체를 하지 않을 수도** 있다 |
>
> 따라서 **상류 팀과 하류 팀은 개발 계획을 서로 공유하고 일정을 협의**해야 한다.

> 상류 컴포넌트는 보통 **하류 컴포넌트가 사용할 수 있는 통신 프로토콜을 정의하고 이를 공개**한다.
> (REST API, **프로토콜 버퍼(Protocol Buffers)** 등)

## ② 공개 호스트 서비스 (Open Host Service)

> [!important]
> 상류 팀의 고객인 **하류 팀이 다수 존재하면**, 상류 팀은 **여러 하류 팀의 요구사항을 수용할 수 있는 API를 만들고
> 이를 서비스 형태로 공개해서 서비스의 일관성을 유지**할 수 있다.
> 이런 서비스를 가리켜 **공개 호스트 서비스(Open Host Service)** 라고 한다.

### 대표 예 — 검색

```
                    [ 검색 바운디드 컨텍스트 ]  ← 상류
                       공개 호스트 서비스 (OHS)
                              △
              ┌───────────────┼───────────────┐
        [ 블로그 ]        [ 카페 ]        [ 게시판 ]   ← 하류들
```

> 블로그, 카페, 게시판과 같은 서비스를 제공하는 회사가 **각 서비스마다 검색 기능을 구현하기보다
> 검색을 위한 전용 시스템을 구축**하고 검색 시스템과 각 서비스를 통합한다.
> 이때 **검색 시스템은 상류 컴포넌트**가 되고 블로그·카페·게시판은 **하류 컴포넌트**가 된다.
> 상류 팀은 **각 하류 컴포넌트의 요구사항을 수용하는 단일 API를 만들어 공개**하고, 각 하류 팀은 공개된 API로 검색 기능을 구현한다.

## ③ 안티코럽션 계층 (Anticorruption Layer)

> [!important] 왜 필요한가
> **상류 컴포넌트의 서비스는 상류 바운디드 컨텍스트의 도메인 모델을 따른다.**
> 따라서 하류 컴포넌트는 **상류 서비스의 모델이 자신의 도메인 모델에 영향을 주지 않도록 보호해 주는 완충 지대**를 만들어야 한다.

```
   [ 카탈로그 도메인 ]
   «interface» ProductRecommendationService     ← 도메인 관점 인터페이스
                    △
   ─ ─ ─ ─ ─ ─ ─ ─ ─╎─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
   [ 인프라스트럭처 ]╎
        RecSystemClient ────REST API 호출────▶  외부 추천 시스템
              ▲
        ★ 안티코럽션 계층 (ACL) ★
        도메인 모델과 외부 시스템 간의 모델 변환 처리
```

> [!tip]
> `RecSystemClient`는 외부 시스템과의 연동을 처리하는데,
> **외부 시스템의 도메인 모델이 내 도메인 모델을 침범하지 않도록 막아주는 역할**을 한다.
> 즉 **내 모델이 깨지는 것을 막아주는 안티코럽션 계층**이 된다.
> 이 계층에서 **두 바운디드 컨텍스트 간의 모델 변환을 처리**해 주기 때문에,
> **다른 바운디드 컨텍스트의 모델에 영향을 받지 않고 내 도메인 모델을 유지**할 수 있다.

## ④ 공유 커널 (Shared Kernel)

> **두 바운디드 컨텍스트가 같은 모델을 공유하는 경우**도 있다.
> 예: **운영자를 위한 주문 관리 도구를 개발하는 팀**과 **고객을 위한 주문 서비스를 개발하는 팀**이 다를 때,
> 두 팀은 **주문을 표현하는 모델을 공유**함으로써 주문과 관련된 **중복 설계를 막을 수 있다.**
> 이렇게 **두 팀이 공유하는 모델을 공유 커널**이라고 부른다.

| 장점 | 단점 / 조건 |
|------|-------------|
| **중복을 줄여준다** — 두 팀이 동일한 모델을 두 번 개발하는 중복 제거 | **한 팀에서 임의로 모델을 변경하면 안 된다** |
| | **두 팀이 밀접한 관계를 유지해야 한다** |

> [!danger] 밀접한 관계가 없다면
> 두 팀이 밀접한 관계를 형성할 수 없다면,
> **공유 커널을 사용할 때의 장점보다 공유 커널로 인해 개발이 지연되고 정체되는 문제가 더 커진다.**

## ⑤ 독립 방식 (Separate Way)

> **그냥 서로 통합하지 않는 방식**이다. 두 컨텍스트 간에 통합하지 않으므로 **서로 독립적으로 모델을 발전**시킨다.

```
   [ 쇼핑몰 솔루션 ]  ──판매 정보를 보고 수동 입력──▶  [ 외부 ERP ]
     바운디드 컨텍스트                                바운디드 컨텍스트
```

> 온라인 쇼핑몰 솔루션이 외부 ERP 서비스와의 연동을 지원하지 않으므로,
> 판매가 발생하면 **쇼핑몰 운영자가 판매 정보를 보고 ERP 시스템에 직접 입력**해야 한다.

> [!warning] 규모의 한계
> **수동으로 통합하는 방식이 나쁜 것은 아니지만 규모가 커질수록 한계가 있으므로,
> 규모가 커지기 시작하면 두 바운디드 컨텍스트를 통합해야 한다.**
> 이때 이미 구매한 솔루션과 ERP를 완전히 대체할 수 없다면,
> **두 바운디드 컨텍스트를 통합해 주는 별도의 시스템을 만들어야 할 수도 있다.**

```
   [ 쇼핑몰 솔루션 ] ──판매 정보 로딩──▶ [ 통합 시스템 ] ──ERP에 입력──▶ [ 외부 ERP ]
```

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "API를 제공하는 쪽 / 호출하는 쪽" | **상류(Upstream) / 하류(Downstream)** |
| "누가 누구에게 의존하나" | **하류가 상류에 의존** |
| "상류/하류의 역할 비유" | **서비스 공급자 / 고객** |
| "상류가 마음대로 API를 바꾸면" | 하류가 **다른 기능 개발을 못 할 수 있다** |
| "여러 하류의 요구를 수용한 단일 공개 API" | **공개 호스트 서비스(OHS)** |
| "OHS의 대표 예" | **검색 시스템** |
| "외부 모델이 내 모델을 침범하지 못하게 막는 계층" | **안티코럽션 계층(ACL)** |
| "두 팀이 모델을 공유하는 관계" | **공유 커널(Shared Kernel)** |
| "공유 커널의 장점 / 조건" | **중복 감소** / **밀접한 관계 유지 필수** |
| "밀접한 관계가 없으면 공유 커널은?" | **개발이 지연·정체되는 문제가 더 커진다** |
| "서로 통합하지 않는 관계" | **독립 방식(Separate Way)** |
| "독립 방식의 한계" | **규모가 커지면 수동 통합 불가** → 별도 통합 시스템 필요 |
