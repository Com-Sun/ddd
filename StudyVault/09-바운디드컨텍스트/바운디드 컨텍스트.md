# 바운디드 컨텍스트 (★★★)

#ddd #bounded-context #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 정의 | **모델의 경계를 결정**하며, 한 개의 바운디드 컨텍스트는 **논리적으로 한 개의 모델**을 갖는다 |
| 구분 기준 | **용어** |

| **현실** | 그렇지 않을 때가 많다 |

| 현실 요인 ② | 용어를 명확히 구분하지 못해 **두 하위 도메인을 한 컨텍스트에서** 구현하기도 한다 |
| 현실 요인 ③ | 소규모 기업은 **여러 하위 도메인을 한 컨텍스트에서** 구현한다 |

## 정의

> [!important]
> **바운디드 컨텍스트는 모델의 경계를 결정하며, 한 개의 바운디드 컨텍스트는 논리적으로 한 개의 모델을 갖는다.**
> **바운디드 컨텍스트는 용어를 기준으로 구분한다.**
> 카탈로그 컨텍스트와 재고 컨텍스트는 서로 다른 용어를 사용하므로 이 용어를 기준으로 분리할 수 있다.
>
> 또한 바운디드 컨텍스트는 **실제로 사용자에게 기능을 제공하는 물리적 시스템**으로,
> **도메인 모델은 이 바운디드 컨텍스트 안에서 도메인을 구현한다.**

## 현실 ① — 팀 조직 구조가 경계를 결정한다

> 이상적으로 하위 도메인과 바운디드 컨텍스트가 **일대일 관계**를 가지면 좋겠지만 **현실은 그렇지 않을 때가 많다.**

```
   [ 주문 하위 도메인 ]              [ 카탈로그 ]  [ 재고 ]
   ┌────────────────────┐          ┌──────────────────────┐
   │ 주문                │          │ 상품                  │
   │ 바운디드 컨텍스트    │          │ 바운디드 컨텍스트      │
   ├────────────────────┤          │ (두 하위 도메인을      │
   │ 결제 금액 계산       │          │  하나로 구현)          │
   │ 바운디드 컨텍스트    │          └──────────────────────┘
   └────────────────────┘
   ▲ 팀이 나뉘어 있어                ▲ 용어 구분이 명확하지 않아
     컨텍스트가 2개                     컨텍스트가 1개
```

| 상황 | 결과 |
|------|------|
| 주문을 처리하는 팀과 **복잡한 결제 금액 계산 로직을 구현하는 팀이 따로** 있다 | 주문 하위 도메인 안에 **주문 컨텍스트 + 결제 금액 계산 컨텍스트** |
| **카탈로그와 재고 관리가 아직 명확하게 구분되지 않은** 경우 | 두 하위 도메인을 **하나의 바운디드 컨텍스트**에서 구현 |

## 현실 ② — 소규모 기업

> 규모가 작은 기업은 전체 시스템을 한 개 팀에서 구현할 때도 있다.
> 소규모 쇼핑몰은 **한 개의 웹 애플리케이션**으로 온라인 쇼핑을 서비스하며,
> 하나의 시스템에서 **회원, 카탈로그, 재고, 구매, 결제**와 관련된 모든 기능을 제공한다.
> 즉 **여러 하위 도메인을 한 개의 바운디드 컨텍스트에서 구현**한다.

### ★ 이때 반드시 주의할 점

> [!danger] 유혹에 빠지기 쉽다
> 한 프로젝트에 각 하위 도메인의 모델이 위치하면 아무래도 **전체 하위 도메인을 위한 단일 모델을 만들고 싶은 유혹**에 빠지기 쉽다.
> 이 유혹에 걸려들면:
> - 도메인 모델이 **개별 하위 도메인을 제대로 반영하지 못해서**
> - **하위 도메인별로 기능을 확장하기 어렵게** 되고
> - 이는 **서비스 경쟁력을 떨어뜨리는 원인**이 된다

> [!important] 해법 — 패키지로 논리적 경계를 만든다
> 비록 한 개의 바운디드 컨텍스트가 여러 하위 도메인을 포함하더라도
> **하위 도메인마다 구분되는 패키지를 갖도록 구현해야 한다.**
> 이렇게 함으로써 **하위 도메인을 위한 모델이 서로 뒤섞이지 않고
> 하위 도메인마다 바운디드 컨텍스트를 갖는 효과**를 낼 수 있다.

```
   온라인 쇼핑 바운디드 컨텍스트 (물리적으로 하나)
   ┌──────────────────────────────────────────┐
   │  ┌────────┐  ┌──────────┐  ┌────────┐   │
   │  │  주문  │  │ 카탈로그 │  │  회원  │   │
   │  │ 패키지 │  │  패키지  │  │ 패키지 │   │
   │  └────────┘  └──────────┘  └────────┘   │
   │   논리적 바운디드 컨텍스트                 │
   └──────────────────────────────────────────┘
```

## 컨텍스트마다 다른 모델

> 각 바운디드 컨텍스트는 **구현하는 하위 도메인에 알맞은 모델**을 포함한다.

| 예 | 모델의 차이 |
|----|-------------|
| 사용자 | 주문 컨텍스트에서는 **`Orderer`**, 회원 컨텍스트에서는 **`Member`** |
| 상품 | **카탈로그의 `Product`** 는 상품이 속할 `Category`와 연관을 갖지만, **재고의 `Product`** 는 `Category`와 연관을 맺지 않는다 |

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "바운디드 컨텍스트의 정의" | **모델의 경계**를 결정, 논리적으로 **한 개의 모델** |
| "구분 기준" | **용어** |
| "물리적 실체" | 사용자에게 **기능을 제공하는 물리적 시스템** |
| "하위 도메인과 1:1인가?" | **이상적으로는 그렇지만 현실은 다르다** |
| "무엇이 경계를 결정하기도 하나" | **기업의 팀 조직 구조** |
| "여러 하위 도메인을 한 컨텍스트에?" | **가능하다** (소규모 기업) |
| "그때 반드시 할 일" | **하위 도메인마다 구분되는 패키지** |
| "단일 모델의 유혹에 빠지면?" | 하위 도메인별 **기능 확장 곤란 → 서비스 경쟁력 저하** |
| "카탈로그의 Product vs 재고의 Product" | 카탈로그는 **Category와 연관**, 재고는 **연관 없음** |
