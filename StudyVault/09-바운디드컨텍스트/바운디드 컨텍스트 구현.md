# 바운디드 컨텍스트 구현 (★★★)

#ddd #bounded-context #architecture #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 포함 범위 | 도메인 모델 **+ 표현 영역 + 응용 서비스 + 인프라스트럭처 + DB 테이블** |
| ★ 필수 아님 ① | **반드시 도메인 주도로 개발할 필요는 없다** — 단순하면 **CRUD(서비스-DAO) 방식**도 OK |
| ★ 필수 아님 ② | 한 컨텍스트에서 **두 방식을 혼합**할 수 있다 (대표 예: **CQRS**) |
| ★ 필수 아님 ③ | 각 컨텍스트는 **서로 다른 구현 기술**을 사용할 수 있다 |

| UI 통합 방식 | 브라우저가 **직접 호출** / **UI 서버가 파사드 역할** |

## 바운디드 컨텍스트가 포함하는 것

> [!important]
> **바운디드 컨텍스트가 도메인 모델만 포함하는 것은 아니다.**
> 도메인 기능을 사용자에게 제공하는 데 필요한 **표현 영역, 응용 서비스, 인프라스트럭처 영역을 모두 포함**한다.
> **도메인 모델의 데이터 구조가 바뀌면 DB 테이블 스키마도 함께 변경해야 하므로 테이블도 바운디드 컨텍스트에 포함**된다.

```
   [ 바운디드 컨텍스트 ]
   ┌──────────────────────────┐
   │  표현 영역                │  ← HTML 페이지 또는 REST API
   ├──────────────────────────┤
   │  응용 서비스              │
   ├──────────────────────────┤
   │  도메인 모델              │
   ├──────────────────────────┤
   │  인프라스트럭처            │
   ├──────────────────────────┤
   │  DB 테이블                │  ← 테이블도 포함!
   └──────────────────────────┘
```

> 표현 영역은 **인간 사용자를 위해 HTML 페이지를 생성**할 수도 있고,
> **다른 바운디드 컨텍스트를 위해 REST API를 제공**할 수도 있다.

## ★ 모든 컨텍스트를 DDD로 만들 필요는 없다

> [!important] (p.282)
> **모든 바운디드 컨텍스트를 반드시 도메인 주도로 개발할 필요는 없다.**
> **상품의 리뷰는 복잡한 도메인 로직을 갖지 않기 때문에 CRUD 방식으로 구현해도 된다.**
> 즉 **DAO와 데이터 중심의 밸류 객체**를 이용해서 리뷰 기능을 구현해도 기능을 유지 보수하는 데 큰 문제가 없다.

| 컨텍스트 성격 | 권장 구현 |
|---------------|-----------|
| 복잡한 도메인 로직 | **도메인 모델 기반 (DDD)** |
| 단순한 기능 (예: 리뷰) | **서비스-DAO (CRUD)** |

> [!tip] 저자의 판단
> **서비스-DAO 구조를 사용하면 도메인 기능이 서비스에 흩어지게 되지만,
> 도메인 기능 자체가 단순하면 서비스-DAO로 구성된 CRUD 방식을 사용해도 코드를 유지 보수하는 데 문제되지 않는다**고 생각한다.

## ★ 한 컨텍스트에서 두 방식 혼합 — CQRS

> **한 바운디드 컨텍스트에서 두 방식을 혼합해서 사용할 수도 있다. 대표적인 예가 CQRS 패턴이다.**
> CQRS는 **Command Query Responsibility Segregation**의 약자로,
> **상태를 변경하는 명령 기능과 내용을 조회하는 쿼리 기능을 구분하는 패턴**이다.

```
   [ 한 바운디드 컨텍스트 ]
   ┌──────────────────────────────────────┐
   │  [명령]                [조회]         │
   │  컨트롤러              컨트롤러        │
   │     │                    │           │
   │  응용 서비스            서비스         │
   │     │                    │           │
   │  도메인 모델            DAO           │
   │     │                    │           │
   │  리포지터리        조회 전용 데이터 모델 │
   └──────────────────────────────────────┘
    ▲ 도메인 모델 기반      ▲ 서비스-DAO 기반
```

## ★ 컨텍스트마다 다른 구현 기술

> 각 바운디드 컨텍스트는 **서로 다른 구현 기술을 사용할 수도 있다.**

| 컨텍스트 예 | 기술 조합 |
|-------------|-----------|
| A | 웹 MVC는 **스프링 MVC**, 리포지터리는 **JPA/하이버네이트** |
| B | **Netty**로 REST API 제공, 리포지터리는 **마이바티스** |
| C | RDBMS 대신 **몽고DB 같은 NoSQL** |

## ★ UI가 없을 수도 있다

### 방식 ① — 브라우저가 직접 호출 (그림 9.8)

```
             1. 제품 상세 정보 요청     ┌─────────────────┐
   브라우저 ──────────────────────────▶│ 카탈로그         │
        ◀──── 2. HTML 응답 ───────────│ 바운디드 컨텍스트 │
             3. 리뷰 목록 JSON 요청     └─────────────────┘
        ──────────────────────────────▶┌─────────────────┐
        ◀──── 4. JSON 응답 ────────────│ 리뷰             │
                                       │ 바운디드 컨텍스트 │
                                       └─────────────────┘
```

### 방식 ② — UI 서버가 파사드 역할 (그림 9.9)

```
                          ┌──────────┐   ┌─────────────────┐
   브라우저 ──1. 요청───▶ │ UI 서버   │──▶│ 카탈로그 컨텍스트 │
          ◀──4. 응답───  │ (파사드)  │──▶│ 리뷰 컨텍스트     │
                          └──────────┘   └─────────────────┘
```

> [!important]
> 이 구조에서 **UI 서버는 각 바운디드 컨텍스트를 위한 파사드 역할**을 수행한다.
> 브라우저가 UI 서버에 요청을 보내면 UI 서버는 **카탈로그와 리뷰 바운디드 컨텍스트로부터 필요한 정보를 읽어와 조합한 뒤** 브라우저에 응답을 제공한다.

## 마이크로서비스와 바운디드 컨텍스트 (p.292)

> [!tip] 왜 잘 어울리는가
> **마이크로서비스**는 애플리케이션을 **작은 서비스로 나누어 개발하는 아키텍처 스타일**로,
> 개별 서비스를 **독립된 프로세스로 실행**하고 각 서비스가 **REST API나 메시징**을 이용해서 통신하는 구조를 갖는다.
>
> **바운디드 컨텍스트는 모델의 경계를 만드는데, 바운디드 컨텍스트를 마이크로서비스로 구현하면 자연스럽게 컨텍스트별로 모델이 분리된다.**
> 코드로 생각하면 **마이크로서비스마다 프로젝트를 생성**하므로 **바운디드 컨텍스트마다 프로젝트를 만들게 된다.**
> → 이는 **코드 수준에서 모델을 분리하여 두 컨텍스트의 모델이 섞이지 않도록** 해준다.
>
> 별도 프로세스로 개발한 바운디드 컨텍스트는 **독립적으로 배포하고 모니터링하며 확장**되는데, 이 역시 마이크로서비스의 특징과 일치한다.

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "바운디드 컨텍스트에 포함되는 것" | 도메인 모델 + 표현 + 응용 + 인프라 + **DB 테이블** |
| "모든 컨텍스트를 DDD로?" | **아니다.** 단순하면 **CRUD(서비스-DAO)** |
| "CRUD로 해도 되는 예" | **상품 리뷰** (복잡한 도메인 로직 없음) |
| "한 컨텍스트에서 두 방식 혼합의 대표 예" | **CQRS** |
| "CQRS의 뜻" | **Command Query Responsibility Segregation** |
| "컨텍스트마다 다른 기술을 써도 되나?" | **된다** |
| "바운디드 컨텍스트에 UI가 필수인가?" | **아니다** |
| "UI 서버의 역할" | **파사드** — 여러 컨텍스트의 정보를 조합 |
| "마이크로서비스와 잘 맞는 이유" | 서비스마다 프로젝트 → **코드 수준에서 모델 분리** |
