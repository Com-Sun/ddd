### 오답 메모

**엔티티/밸류 판단 기준 (식별자 필요 여부)** — 🟢 해결 (2라운드에서 정답)
- 1라운드: 개념 미학습. 2라운드: 호텔 예약 문제에서 예약=엔티티, 기간/투숙객=밸류 **정답**
- 단, 근거가 "table 컬럼이면 밸류, 테이블이면 엔티티"였고 이는 틀린 논리 → 별도 개념으로 분리 기록
- 확립된 3단계 판단 절차:
  1. **지목해서 조회/변경/삭제/추적할 요구사항이 있는가?** 있으면 엔티티
  2. **속성이 전부 같은 두 개를 서로 다른 것으로 구분해야 하는가?** 구분 필요하면 엔티티
  3. (밸류면) 관련 규칙·계산 로직을 안에 모을 수 있는가? → `DateRange.overlaps()`, `Money.multiply()`, `Password.match()`
- 반례로 확인: 홍길동이 같은 날짜·같은 금액으로 방 2개 예약 → 속성 동일해도 **다른 예약**(하나만 취소 가능) → 엔티티 / `DateRange(8/10~8/12)` 두 개는 **완전히 같음** → 밸류
- ⚠️ 필드 개수는 기준이 아니다: `Money`는 필드 1개인데 밸류(의미 명확화 + 계산 로직)
- ⚠️ 요구사항에 따라 바뀐다: `Guest`가 "예약서에 적힌 정보"면 밸류, "로그인하고 등급·누적숙박일이 쌓이는 회원"이면 엔티티 → ID 참조(`GuestId`)로 전환

**equals() 구현 규칙** — 🟢 해결 (2라운드에서 3개 모두 정답)
- 규칙 자체는 정확히 답했다: 엔티티=식별자, 밸류=모든 속성
- 사용자 질문 "JPA는 PK가 있는데 왜 equals()를 오버라이드해야 하나?" → **부분적으로 맞는 직관**
  - 같은 트랜잭션(영속성 컨텍스트) 안에서는 JPA 1차 캐시가 **같은 인스턴스**를 주므로 오버라이드 없이도 `==`로 통과
  - 깨지는 경우: ① **준영속/트랜잭션 경계를 넘어** 비교(다른 인스턴스 → false) ② **`Set`/`Map`의 키**로 쓸 때(`hashCode()` 필수, 쌍으로 구현) ③ **auto_increment 저장 전 id가 null**인 구간
- 연결: auto_increment는 **INSERT 후에야 식별자를 알 수 있어** 생성 시 전달 불가 → 이 책은 규칙 기반/UUID 식별자를 선호
- 밸류에 `protected` 기본 생성자가 필요한 이유: **JPA가 DB에서 읽어와 객체를 생성할 때 사용**. 다른 코드가 쓰면 온전하지 못한 객체가 되므로 `public`이 아니라 `protected`
- ★ 시험 답 vs 실무 답: "엔티티의 equals는 무엇을 기준으로?" → **식별자**(개념) / "엔티티에 equals를 만들어야 하나?" → **대개 불필요**(실무). 아래 항목 참고

**equals()/hashCode()를 실제로 언제 구현하나 (ddd-start2 전수 조사 결과)** — 🟢 사용자 직관이 맞았음
- 사용자 질문: "DDD에서 반드시 오버라이드해야 하나? 실무에서 써본 적이 거의 없다" → **직관이 정확했다**
- **실증**: `ddd-start2/` 도메인 클래스 24개 중 `equals()` 구현은 **7개뿐**. 애그리거트 루트 5개(`Order`, `Member`, `Product`, `Article`, `Category`) **전부 equals() 없음**
- 구현한 7개와 각각의 이유:
  - `OrderNo`/`MemberId`/`ProductId`/`CategoryId` → **JPA가 강제한다.** `@EmbeddedId`로 쓰이므로 스펙이 `Serializable` + `equals()` + `hashCode()`를 요구(하이버네이트가 1차 캐시 키로 사용). 선택이 아니라 의무
    - ★ 반전: PK를 밸류 타입으로 만들었기 때문에 **식별자 타입 쪽**에 equals()가 필요해진 것이다. `Article`처럼 `private Long id`면 `Long`에 이미 있으니 불필요
  - `Money`/`Email` → **값 비교를 실제로 한다.** `Money`는 불변이라 `multiply()`마다 새 인스턴스가 생기므로 `new Money(2000) == new Money(2000)`이 false. 값 비교가 밸류의 존재 이유
  - `Orderer` → 내부에 `MemberId`(equals 구현체)를 품고 있어 **일관성을 위해** 필요
- 구현하지 **않은** 밸류와 이유:
  - `Address`, `Receiver`, `ShippingInfo`, `OrderLine`, `Image`, `Option`, `ArticleContent` → **비교할 요구사항이 없다.** 저장·조회만 된다
  - `Password` → equals() 대신 **`match(String password)`** 도메인 메서드를 만들었다. "암호가 일치하는가"는 객체 동등성이 아니라 도메인 행위이므로 의미가 드러나는 이름을 쓴다
- 실제 코드의 도메인 비교 지점은 2곳뿐이고 둘 다 **엔티티끼리가 아니라 ID(String) 비교**(권한 검사): `MyOrderController:38`, `SecurityCancelPolicy:23`
- **IntelliJ 자동 생성 vs 도메인 정의**: 실제 코드는 IDE 템플릿 그대로다(`Objects.equals`, `Objects.hash`, `getClass() != o.getClass()`). 도구는 IDE를 쓰고 **판단만 도메인 정의로** 한다 — IntelliJ가 "어떤 필드를 포함할까요?"라고 물을 때 엔티티는 **식별자만**, 밸류는 **전부** 선택
  - ⚠️ 함정: 엔티티에 대해 IDE가 모든 필드를 체크한 채 생성하면 **배송지만 바꿔도 다른 주문**이 되는 버그
- 판단 표: `@EmbeddedId` 식별자 밸류 = **필수** / 연산으로 새 인스턴스가 생기는 밸류(`Money`) = **필수** / 테스트에서 값 비교 = 필요 / `Set`·`Map` 키 = 필요 / 저장·조회만 되는 밸류 = **불필요** / 애그리거트 루트 = **대개 불필요**
- 원칙: **필요할 때 만든다.** "DDD니까 다 만든다"가 아니다. 1장의 `Order.equals()` 예제는 "엔티티의 동등성은 식별자로 판단한다"는 **개념 교육용 코드**다

**DB 스키마 ≠ 도메인 모델 (테이블/PK 유무는 판단 기준이 아니다)** — 🔴 신규 발견
- 혼동: "기간과 투숙객은 table의 컬럼에 해당돼" → **DB 스키마를 먼저 보고 도메인 모델을 판단**하고 있다. DDD는 반대 순서다
- 반례 ①: **`OrderLine`은 자기 테이블 + PK가 있는데 밸류다**
- 반례 ②: **`ArticleContent`도 `article_content` 테이블 + `id` 칼럼이 있는데 밸류다**
- 원칙: **매핑되는 테이블의 식별자를 구성요소의 식별자와 동일시하면 안 된다.** 그 PK는 부모 테이블과 **연결하기 위한 것**이고, RDB가 밸류를 표현하지 못하는 **기술적 부산물**이다
- 결론: 테이블 구조는 **저장 방식**, 엔티티/밸류는 **도메인 모델의 개념**. `Address`가 컬럼으로 들어가든 별도 테이블로 빠지든 **양쪽 다 밸류**다 — 저장 방식이 바뀐다고 도메인 개념이 바뀌지 않는다
- 이것은 저자도 초년 시절 했던 실수로 책에 명시된 흔한 함정("도메인 모델의 엔티티 = DB 모델의 엔티티")

**set 메서드 안티패턴** — 🟢 해결
- 사용자가 정확히 지적한 것: setter 전면 개방 문제 / id 변경 불가 / 변경은 의미 있는 메서드로 / 기본 생성자 대신 필수값 생성자 / `modifyContent()` 네이밍
- 보충된 "왜" ①: **가장 큰 문제는 도메인 지식이 코드에서 사라지는 것**이다. `setState(PUBLISHED)`는 필드 대입 후 무엇을 더 할지 애매하지만, `publish()`는 "게시 조건 검사 + 게시일 기록 + 상태 변경"을 담는 것이 자연스럽다. setter로 두면 이 규칙들이 서비스·컨트롤러로 흩어지고 **여러 곳에서 중복**된다
- 보충된 "왜" ②: `new Article()` + setter는 **온전하지 않은 객체**를 만든다. `writer`가 null인 채로 PUBLISHED 상태가 되고, 예외 없이 통과해 먼 곳에서 NPE로 터진다. `setState()`에 null 검사를 넣는 것도 **책임이 뒤섞여** 답이 아니다 → 해법은 **생성자에서 모두 받고 검증**
- 부수 교정: JPA에서는 **`final` 필드를 쓸 수 없다**(리플렉션·프록시 필요). `final` 대신 **"setter를 만들지 않는 것"**으로 불변성을 확보한다
- 후보 개선: `String content` → `ArticleContent` 밸류(content + contentType이 개념적으로 하나)

**밸류 추출 신호 3가지 (왜/언제 밸류로 빼나)** — 🟢 해결
- 4라운드: "왜 밸류로 빼야하는지 모르겠음. **밸류는 '왜', '언제' 빼는 것이 좋은지에 대한 개념이 내게 아직 없다**" (미학습)
- 5라운드: `Instructor`, `Money` 후보를 **정확히 찾아냄**. 단 신호 적용 근거는 서술하지 않음 → 재테스트 필요
- 📐 **출처 표시 (2026-08-14 검증)**: 아래 3신호는 **어시스턴트가 만든 프레임**이다. 원서 PDF는 스캔 이미지라 대조 불가하여 사용자 원본 노트와 대조했다.
  - ②"이름이 붙는다" ← `01-도메인모델/밸류 타입.md`(§1.6.3 p.046~052) **"개념적으로 완전한 하나를 표현할 때"** ✅
  - ③"로직이 붙는다" ← 같은 파일 **"밸류 타입을 위한 기능(계산 로직)을 추가할 수 있다"** ✅
  - ①"함께 변한다" ← **대응 서술 없음. 어시스턴트가 추가한 것** ❌
  - → 시험 답으로는 쓰지 말 것. 실무 판단 도구로만 쓴다.
- ★ **추출 신호 3가지 — 셋 다 걸리면 뺀다**
  1. **항상 함께 변한다** — 하나만 따로 바꾸는 일이 없다 (`zip_code`만 바꾸고 `address1`은 그대로? 불가) / 반례: 호텔 `name`은 혼자 바뀐다 → 안 뺀다
  2. **그 묶음을 부르는 도메인 용어가 있다** — "주소", "받는 사람" ⭕ / 이름이 안 나오면 억지로 묶는 것
  3. **붙일 로직이 있다** — 검증·계산·비교 (`isSameRegion()`, `isRemoteArea()`, `multiply()`)
- 얻는 것 4가지(**일반론 — 이 코드베이스가 다 보여주는 것은 아님**): **검증이 한 곳** / **로직이 모인다** / **재사용** / **불변 = 안전**
  - ⚠️ 실제 `common/model/Address.java`는 **검증도 도메인 메서드도 없는 단순 홀더**이고(필드 3개 + `public` 기본 생성자 + getter), 검증은 응용 계층 `OrderRequestValidator`가 한다. `Address`는 `common/model/`에 있지만 실사용처는 **`ShippingInfo` 하나뿐**이라 "재사용"도 관찰된 사실이 아니라 배치 의도에 대한 추정이다
  - 이 코드베이스에서 **실제로 로직을 가진 밸류**는 `Money.multiply()`, `Password.match()`, `Image.getUrl()/hasThumbnail()`
- Before/After 핵심: 필드 3개로 흩어두면 `Member`·`ShippingInfo`에 **검증 코드를 복붙**하게 되고, 우편번호 규칙이 바뀌면 **전부 수정**해야 하며 하나 빠뜨리면 버그
- 실물 증거: `Address`는 `common/model/`에 있고, `ShippingInfo`에서 `@AttributeOverrides`로 **`shipping_zip_code`, `shipping_addr1`, `shipping_addr2`** 라는 **다른 이름의 칼럼**에 매핑된다 → **컬럼 이름은 상황마다 다른데 도메인 개념은 하나**
- `Receiver`(name + phone)가 "두 필드가 개념적으로 하나"의 표준 사례

**두 축 분리 (애그리거트 경계 판정 vs 엔티티/밸류 판정)** — 🟢 해결
- 4라운드 오류: `HotelAmenity`를 **"호텔과 라이프사이클이 같다"**는 근거로 **밸류**라고 판정 → **축 1의 기준으로 축 2의 결론**을 냈다
- 5라운드: `Lecture`에 대해 축 1(같은 애그리거트, 라이프사이클 근거)과 축 2(엔티티, "지목해서 추적할 요구사항 존재") **분리 성공**
- ★ 두 축은 **독립**이다

  | | **축 1 — 애그리거트 경계** | **축 2 — 엔티티 vs 밸류** |
  |---|---|---|
  | 묻는 것 | 어느 울타리에 속하는가 | 식별자가 필요한가 |
  | 기준 | 함께 생성/변경, 변경 주체, 라이프사이클 | **지목해서 조회·변경·추적**하는가 |

- 2×2 조합 (루트는 반드시 엔티티, 내부는 둘 다 가능):

  | | 엔티티 | 밸류 |
  |---|---|---|
  | 애그리거트 루트 | `Order`, `Member`, `Product` | ❌ 불가능 |
  | 애그리거트 내부 | 가능 (드물다) — `Lecture` | `OrderLine`, `Address`, `Receiver` |

- 책 경험칙: "다수의 애그리거트가 한 개의 엔티티 객체만 갖는다. **두 개 이상의 엔티티로 구성되는 애그리거트는 드물었다**" → **"드물다"는 0이 아니다**
- "호텔 없으면 어메니티도 없다"는 **축 1만 증명**할 뿐 축 2를 증명하지 않는다

**cardinality(1:N)는 어떤 판정에도 기준이 아니다** — 🔴 반복 오류 (2회)
- 1라운드: "상품은 하나인데 리뷰가 여러개일수도 있고"
- 5라운드: "강의:강의회차 = **1:N**", "저장되는게 **1:n 이니** 당연히 엔티티로"
- ★ 같은 1:N인데 판정이 전부 다르다:

  | 쌍 | 관계 | 애그리거트 | 엔티티/밸류 |
  |---|---|---|---|
  | `Order`/`OrderLine` | 1:N | 같음 | **밸류** |
  | `Product`/`Image` | 1:N | 같음 | **밸류** |
  | `Product`/`Review` | 1:N | **다름** | 엔티티(루트) |
  | `Course`/`Lecture` | 1:N | 같음 | **엔티티** |

- **1:N을 보면 판정에 아무 정보가 없다고 생각할 것**

**밸류 "추출" vs 엔티티 "추적" — 방향이 반대다** — 🔴 신규 발견
- 혼동(사용자 원문): "회차별 통계 / 개별 비공개 / 수강 완료 표시 — 이건 나는 밸류라고 생각했던 거거든? **밸류도 '추적해야 할 요구사항'이 있을 때 컬럼에서 밸류로 빠지는 거잖아?**"
- 핵심 교정: **밸류 추출 3신호에 "추적"은 없다.** ① 함께 변한다 ② 이름이 붙는다 ③ 로직이 붙는다 — **셋 다 "묶는" 이유**다
  ```
  밸류 추출     zipCode, address1, address2  →  Address     ← 합친다 (필드 여러 개 → 개념 하나)
  엔티티 판정   Lecture 목록 [A, B, C]       →  A? B? C?    ← 나눈다 (덩어리 → 개별 지목)
  ```
- 📐 **출처 표시 (2026-08-14 검증)**: 아래 판별 질문 3개는 **어시스턴트가 만든 조작적 정의**다. 노트가 제시하는 책의 기준은 `01-도메인모델/엔티티와 식별자.md`의 **"식별자를 가진다"** 하나뿐이다.
  - 시험 답 = **"식별자가 필요한가"** / 아래 3개 = 그 판단을 코드에 적용할 때 쓰는 도구
  - 단, 3개 안의 **관찰 사실**(`order_line` 테이블에 PK 없음, `changeImages()`가 `clear()`+`addAll()`)은 실제 코드에서 확인된 것이다
- ★ **판별 질문 3개** (`OrderLine`과 `Lecture`가 둘 다 1:N인데 갈리는 지점)

  | | ① 통째 교체 OK? | ② 다른 데이터가 참조? | ③ 원소마다 다른 상태? | 판정 |
  |---|---|---|---|---|
  | `Lecture` | ❌ | ⭕ | ⭕ | **엔티티** |
  | `OrderLine` | ⭕ | ❌ | ❌ | **밸류** |
  | `Image` | ⭕ | ❌ | ❌ | **밸류** (PK 있어도) |

- **결정타 ① 통째로 교체 가능한가**: `OrderLine`은 `this.orderLines = newLines`로 갈아끼워도 무해하다(아무도 예전 줄을 기억 안 함). `Lecture`를 갈아끼우면 `LectureProgress(studentId, lectureId, completedAt)` 기록이 **전부 고아가 되어 학습 이력이 증발**한다 → 통째로 교체하면 안 되는 것 = 엔티티
- **결정타 ② 다른 곳에서 참조되는가** (가장 기계적): 가리키려면 안정적 식별자가 필요하고, 식별자가 있으면 엔티티. `order_line` 테이블에 **PK가 아예 없는 이유** = 참조당할 일이 없어서
- **결정타 ③ 원소마다 서로 다른 상태**: 주문 3줄은 전부 "그냥 데이터" / 강의 3회차는 "3회차만 `hidden=true`"
- `Image`가 PK를 갖고도 밸류인 근거: **상태 변경 메서드가 아예 없고**, `changeImages()`가 `clear()` + `addAll()`로 통째 교체한다

**private setter는 안티패턴이 아니다 (금지 대상은 public)** — 🔴 신규 발견
- 혼동: "set도 닫혀야하고"라고만 답해 private setter의 정당한 용도를 인지하지 못했다
- 핵심: **금지 대상은 공개(public) set 메서드**다. `private` setter는 **생성자와 도메인 메서드 안에서 검증 로직을 한곳에 모으기 위해** 사용한다
- `public setter` → 외부 어디서든 상태를 깨뜨린다 ❌ / `private setter` → 생성자·도메인 메서드 안에서만 사용 ⭕
- 시험 함정: "private set 메서드도 안티패턴인가?" → **아니다**
