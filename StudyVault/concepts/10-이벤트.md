### 오답 메모

**포워더(Forwarder)의 역할과 offset 처리**
- 혼동: "포워더가 뭔지도 모르겠다" — 개념 미학습
- 선행 개념: 이벤트는 **강결합 문제를 해결**할 뿐이고 성능·트랜잭션 문제를 해결하지 않는다. 스프링 기본 `@EventListener`는 **동기 = 같은 스레드·같은 트랜잭션**. 성능·트랜잭션 문제는 **비동기 처리**로 푼다
- 핵심: 포워더 = 이벤트를 일단 DB(이벤트 저장소)에 저장한 뒤, **`@Scheduled`로 주기적으로 읽어서 외부로 push**하는 별도 컴포넌트
- 강점 2개: ① **이벤트 유실 없음**(발생과 저장을 한 트랜잭션으로) ② **재처리 가능**
- 포워더 vs API: 전달 방향(push/pull) + **offset 추적 주체**(포워더 / 외부 핸들러)
- offset 로직: 순서대로 보내다 익셉션이 나면 **멈추고 성공 개수만 리턴** → offset은 **성공한 만큼만** 전진 → 다음 주기에 실패한 이벤트부터 재시도. offset 저장 이유 = **중복 처리 방지**
- 함께 알 것: ① 재전송 횟수 제한이 없으면 실패 이벤트에 막혀 **뒤의 모든 이벤트가 정체** → 3회 실패 시 생략 + 별도 실패용 DB/큐 보관 ② 롤백 시 핸들러 실행 방지 → `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`

**자동 증가 칼럼을 offset으로 쓸 때의 이벤트 누락**
- 혼동: 미학습
- 핵심 원인: 자동 증가 칼럼은 **INSERT 시점에 값이 증가**하지만 데이터는 **커밋 시점에 반영**된다 → 커밋 순서가 ID 순서와 다를 수 있다
- 누락 시나리오: A가 11 획득, B가 12 획득 → **B가 먼저 커밋** → 그 사이 조회하면 11은 안 보이고 12만 조회 → offset이 13으로 전진 → A가 나중에 커밋해도 **11은 영구 누락**
- 해법: **ID 기준 지연 조회**(진행 중 트랜잭션이 커밋될 만큼 시간이 지난 ID까지만 읽는다)
