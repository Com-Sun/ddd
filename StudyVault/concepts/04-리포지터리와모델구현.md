### 오답 메모

**밸류 컬렉션 매핑 — 밸류도 별도 테이블에 1:N으로 저장된다** — 🔴 사용자 질문에서 발견
- 사용자 질문: **"Value인데 저장만 1:N으로 고유한 PK를 갖고 관리되는건가?"** → **그렇다. 그리고 PK가 아예 없을 수도 있다**
- ★ 실제 DDL 3개 비교 — **셋 다 도메인상 밸류인데 PK 형태가 전부 다르다**

  | 테이블 | PK | JPA 매핑 | 도메인 개념 |
  |---|---|---|---|
  | `order_line` | **없음** (인덱스만: `order_number, line_idx`) | `@ElementCollection` | **밸류** |
  | `article_content` | 있음 (부모 `article`의 id 공유) | `@SecondaryTable` | **밸류** |
  | `image` | **고유 auto_increment** | `@Entity` + `@OneToMany` | **밸류** ⚠️ |

  → **PK와 엔티티/밸류의 상관관계는 0이다**

- 밸류 컬렉션 매핑 방식:
  ```java
  @ElementCollection(fetch = FetchType.LAZY)
  @CollectionTable(name = "order_line", joinColumns = @JoinColumn(name = "order_number"))
  @OrderColumn(name = "line_idx")
  private List<OrderLine> orderLines;      // OrderLine은 @Embeddable, 식별자 필드 없음
  ```
  | 애너테이션 | 역할 |
  |---|---|
  | `@ElementCollection` | 밸류 컬렉션임을 지정 |
  | `@CollectionTable` | `name` = 저장 테이블, `joinColumns` = FK 칼럼 |
  | `@OrderColumn` | 지정 칼럼에 **리스트 인덱스** 저장 |
  - `OrderLine`에 인덱스 프로퍼티가 없는 이유: **`List` 타입 자체가 인덱스를 갖기 때문**
  - 행을 특정하는 건 `(order_number, line_idx)` = **"몇 번 주문의 몇 번째 줄"**이지 `OrderLine` 자신의 정체성이 아니다

- ★ `Image`가 고유 PK를 갖는 이유 — **개념은 밸류인데 기술 한계로 `@Entity` 매핑**
  - **JPA는 `@Embeddable` 타입의 클래스 상속 매핑을 지원하지 않는다.** `Image`는 `InternalImage`/`ExternalImage` 상속 구조가 필요해서 `@Entity` + discriminator로 갈 수밖에 없었다
  - 책이 못 박음: **"`Image`를 `@Entity`로 매핑했지만 모델에서 `Image`는 밸류이므로 상태를 변경하는 기능은 추가하지 않는다."**
  - 행동으로 확인: `product.changeImages(newImages)`는 `images.clear()` 후 `addAll()` — **"image #17을 수정"이 아니라 "목록을 통째로 교체"**. 이게 밸류의 행동 방식

- ⚠️ 그 대가 — `clear()` 성능 (미테스트, 다음 드릴 대상)

  | 매핑 | `clear()` 시 쿼리 |
  |---|---|
  | `@Entity` + `@OneToMany` | **SELECT 1번 + DELETE N번** |
  | `@Embeddable` + `@ElementCollection` | **DELETE 1번** |

  이미지 4개면 5번의 쿼리. 변경 빈도가 높으면 **상속을 포기하고 `@Embeddable` 단일 클래스 + if-else**로 가는 것이 책의 결론

- ★ **판정의 3단계 (혼동의 근원을 정리)**
  ```
  1) 도메인 요구사항:  식별자로 지목해서 추적·변경하는가?      ← 진짜 기준
  2) 도메인 모델:      그 결과로 식별자 필드를 둔다 (또는 안 둔다)
  3) JPA 매핑:         기술 제약(상속·성능)에 따라 별개로 결정
                       @Embeddable / @Entity / @SecondaryTable
                       PK 유무는 여기서 정해진다 ← 도메인과 무관
  ```
  `Image`가 3단계에서 PK를 얻었다고 1단계 판정이 바뀌지 않는다. **PK는 저장 계층의 사정이다**

- 관련: [[concepts/01-도메인모델]]의 "DB 스키마 ≠ 도메인 모델", "cardinality는 기준이 아니다"

**객체 모델 ↔ 관계형 모델 대응 (밸류 저장 4패턴)** — 🔴 사용자 질문에서 발견
- 사용자 질문: "엔티티 내부의 밸류를 한 테이블에서 관리한다거나, 밸류로 빼서 다른 테이블로 관리되는 개념이 부족하다. **Object Relation과 Entity Relation의 차이**를 아직 완벽히 이해 못 함"
- ★ 근본 원인: **RDB에는 "밸류"라는 개념이 없다.** 모든 행이 PK로 식별되므로 "식별자 없는 것"을 담을 자리가 없다

  | | 객체 모델 | 관계형 모델 |
  |---|---|---|
  | 중첩 | 무한히 가능 (`Order→ShippingInfo→Address→zipCode`) | **불가능. 평평하다** |
  | 식별 | **엔티티만** 식별자를 갖는다 | **모든 행이 식별된다** |
  | 소유 | 포함/참조 구분 | **FK 하나뿐.** 구분 안 됨 |
  | 행동 | 데이터 **+ 기능** | 데이터만 |

- 책 원문: RDBMS는 밸류를 제대로 표현하지 못해 **한 테이블에 넣으면 개념이 드러나지 않고, 별도 테이블로 빼면 테이블 엔티티처럼** 되어버린다 → **둘 다 손해. 헷갈리는 게 정상**
- **실물 ① 테이블 1행 = 객체 8개**: `purchase_order`의 평평한 컬럼 13개에 `Order` + `OrderNo` + `Orderer` + `MemberId` + `Money` + `ShippingInfo` + `Address` + `Receiver`가 **3단계 중첩된 채로 눌려 들어간다**
  - `@Embeddable`의 의미 = **"자기 테이블을 갖지 않는다. 부모 테이블에 컬럼으로 녹아든다"**
  - 착시 주의: 테이블만 보면 "주소는 그냥 컬럼"이지만 객체 쪽 `Address`는 **독립된 클래스**이고 `ShippingInfo` 안에 중첩되어 있다
  - ⚠️ **실제 `common/model/Address.java`는 검증 로직도 도메인 메서드도 없다** — 필드 3개 + `public` 기본 생성자 + getter 3개뿐이고, 검증은 응용 계층 `OrderRequestValidator`가 한다. "밸류에 로직을 붙일 수 있다"는 **가능성**이지 이 코드가 실제로 그렇다는 뜻이 아니다. 실제로 로직을 가진 밸류는 **`Money.multiply()`**, **`Password.match()`**다
- **실물 ② 엔티티 1개 = 테이블 2개**: `Article`이 `@SecondaryTable`로 `article` + `article_content`에 걸쳐 있다
  - `article_content.id`는 `ArticleContent`의 식별자가 아니라 **`article`과 연결하기 위한 것**(부모 id 공유). 클래스에는 식별자 필드가 아예 없다
  - ❌ **2026-08-14 정정**: 이전 서술 "나눈 이유는 본문이 크고 목록 조회 때 필요 없어서 → 목록은 `article`만 읽는다"는 **틀렸다.** 원본 노트 `밸류를 이용한 ID 매핑과 별도 테이블 매핑.md`(§4.3.8)는 **`@SecondaryTable`이 목록 조회에서도 항상 조인하는 것을 이 매핑의 한계**로 명시한다 — **"목록 화면에 보여줄 `Article`을 조회할 때 `article_content` 테이블까지 조인해서 읽어오는데 이것은 원하는 결과가 아니다."**
  - 책의 해법: `ArticleContent`를 `@Entity`+지연로딩 ❌("밸류인 모델을 엔티티로 만드는 것이라 좋은 방법이 아니다") / **조회 전용 기능 구현 ⭕**(5장·11장) → 이 주제는 4장에서 안 끝난다
- ★ **책이 명시한 밸류/엔티티 판단 절차 (p.152~153)** — 어시스턴트 프레임이 아니라 원본 노트에 있는 3단계
  > ① 애그리거트에서 **루트 엔티티를 뺀 나머지 구성요소는 대부분 밸류**다. 루트 외에 또 다른 엔티티가 있다면 진짜 엔티티인지 의심해 봐야 한다
  > ② **단지 별도 테이블에 저장한다고 해서 엔티티인 것은 아니다** (`OrderLine`이 반례)
  > ③ 엔티티가 확실하다면 **다른 애그리거트는 아닌지** 확인 — 특히 **자신만의 독자적 라이프 사이클**을 가지면 별도 애그리거트일 가능성이 높다
- ★ **밸류 저장 4패턴**

  | 패턴 | 애너테이션 | 실제 예 |
  |---|---|---|
  | ① 부모 테이블에 컬럼으로 펼치기 | `@Embeddable` + `@Embedded` | `Orderer`, `ShippingInfo`, `Address`, `Receiver`, `Password` |
  | ② 한 칼럼에 몰아넣기 | `AttributeConverter` + `@Convert` | `Money`→`int`, `EmailSet`→콤마 문자열 |
  > ⚠️ **필드 개수는 ①/②를 가르지 않는다** (2026-08-14 정정). `Password`(필드 1개) = ①, `Money`(필드 1개) = ②.
  > 노트 `AttributeConverter를 이용한 밸류 매핑.md`(§4.3.4 p.145~147)의 컨버터 사유는 **"두 개 이상의 프로퍼티를 한 개 칼럼에"**(`Length{value,unit}`→`"1000mm"`)이고 `Money`는 해당하지 않는다.
  > 관찰되는 실제 차이는 **`Money`가 JPA 애너테이션을 전혀 안 단 순수 도메인 클래스**라는 점. 책의 명시적 이유는 확인 불가(PDF가 스캔 이미지). → [[내 질문 노트#Q10]]
  | ③ 별도 테이블 1:1 | `@SecondaryTable` (부모 PK 공유) | `ArticleContent` |
  | ④ 별도 테이블 1:N | `@ElementCollection` + `@CollectionTable` | `OrderLine` |
  | (예외) 상속 필요 | `@Entity` + `@OneToMany` (고유 PK 생김) | `Image` |

  - ②의 극단적 예: `member.emails varchar(200)` — **컬렉션인데 칼럼 하나**(`"a@x.com,b@y.com"`). 도메인에서는 여전히 `Set<Email>`
- **결론**: 같은 개념이 4가지로 저장될 수 있으므로 **판별은 항상 객체 쪽에서** 한다. 테이블은 4가지 답을 주는데 도메인은 하나다
  - "테이블 컬럼이니까 밸류" ❌ 저장 방식 ①일 뿐
  - "자기 테이블 + PK 있으니까 엔티티" ❌ 저장 방식 ③④일 뿐
  - "1:N으로 저장되니까 엔티티" ❌ 저장 방식 ④일 뿐
- 한 줄 요약: **테이블은 "어떻게 저장할까"의 답, 엔티티/밸류는 "이게 무엇인가"의 답.** `ShippingInfo`가 오늘은 `purchase_order` 컬럼이고 내일 별도 테이블로 빠져도 **계속 밸류**다

**`@AttributeOverride`가 필요한 이유 (컬럼 이름의 소유권)** — ⬜ 설명만 함, **미테스트**
- 사용자 질문(Q10): "`@AttributeOverride`는 왜 필요해?"
- ★ 원인: **컬럼 이름은 밸류 클래스가 자기 안에 선언하는데, 밸류는 자기가 어느 부모 테이블에 펼쳐질지 모른다** → 부모마다 다른 이름이 필요하면 부모 쪽에서 덮어쓴다
- **결정적 증거 — `MemberId` 한 클래스가 두 테이블에서 다른 컬럼 이름**

  | 부모 | 코드 | 결과 컬럼 |
  |---|---|---|
  | `Member` | `@EmbeddedId private MemberId id;` (오버라이드 없음) | `member.member_id` |
  | `Orderer` | `@AttributeOverride(name="id", column=@Column(name="orderer_id"))` | `purchase_order.orderer_id` |

  `MemberId` 자신의 선언은 `@Column(name = "member_id")`. DDL 양쪽 다 확인함
- ★ **대조가 핵심 — 같은 `ShippingInfo` 안에서 `Address`는 덮어쓰고 `Receiver`는 안 덮어쓴다**

  | | `Address` | `Receiver` |
  |---|---|---|
  | 위치 | `common/model/` | `order/command/domain/` |
  | 자기 컬럼 이름 | `zip_code`, `address1`, `address2` | `receiver_name`, `receiver_phone` |
  | 오버라이드 | **필요** (→ `shipping_*`) | **불필요** (이미 맞음) |

  ⚠️ 위 표는 코드에서 확인한 사실. 단 "`Address`가 범용이라 이름이 중립적"이라는 **인과 설명은 추론**이다 — 실사용처는 `ShippingInfo` 하나뿐이라 재사용이 관찰된 것은 아니다
- **오버라이드가 하는 일 3층**: ① 이름 모호 해소(`member_id`→`orderer_id`) ② 맥락 표시(`zip_code`→`shipping_zip_code`) ③ **대상 테이블 지정**(`@Column(table="article_content", ...)`)
  - `Article`의 경우 `ArticleContent` 클래스에 `@Column`이 **하나도 없고** 매핑 정보가 전부 `Article` 쪽에 있다
- ⚠️ 일반론(**이 코드베이스에 사례 없음**): 한 부모에 같은 밸류를 두 번 넣으면(청구지+배송지 주소) 컬럼 이름이 충돌하므로 오버라이드가 필수가 된다

**컬럼 개수 = 밸류의 필드 개수 (`Password`)** — ⬜ 설명만 함, **미테스트**
- 사용자 질문(Q10): "`Password`는 밸류인데 왜 컬럼이 하나야?"
- ★ 답: **`@Embeddable`은 "필드 하나당 컬럼 하나"로 펼친다.** `Password`는 필드가 `String value` 하나 → 컬럼도 `member.password` 하나. 특별한 일이 아니다

  | 밸류 | 필드 수 | 컬럼 수 |
  |---|---|---|
  | `Address` | 3 | 3 |
  | `Receiver` | 2 | 2 |
  | `Orderer` | 2 | 2 |
  | `Password` | **1** | **1** |

- 착시의 원인: `Address`·`Receiver`·`Orderer`만 보면 "밸류 = 컬럼 여러 개"로 보인다
- **필드 1개인데 왜 밸류로 뺐나** — `밸류 타입.md`(§1.6.3): "데이터 개수는 꼭 2개 이상일 필요 없다. **1개여도 의미 명확화를 위해 사용**". 실제 이득이 코드에 있다:
  ```java
  public void changePassword(String oldPw, String newPw) {
      if (!password.match(oldPw)) throw new IdPasswordNotMatchingException();
      this.password = new Password(newPw);      // 통째 교체 (불변)
  }
  ```
  `String`이면 해시 비교로 바뀔 때 **호출한 모든 곳**을 고쳐야 한다. `match()`면 그 안만 고친다
- `Password`에 `equals()`가 **없고** `match()`만 있는 이유: "암호가 일치하는가"는 객체 동등성이 아니라 **도메인 행위** → [[concepts/01-도메인모델]]의 equals 항목

**4패턴을 무엇이 결정하나 (①이 기본, ③은 스키마가 정한다)** — ⬜ 설명만 함, **미테스트**
- 사용자 질문(Q11): "밸류는 객체에서 PK가 없으니 결국 1:1인데, **1:1인 걸 왜 굳이 다른 테이블로 빼?** `@Embeddable`로 같은 테이블 쓰는 거와 같지 않아?"
- ★ **직관이 맞다 — 도메인 관점에서는 완전히 같다.** `Address`(①)와 `ArticleContent`(③)는 `@Embeddable` / 식별자 필드 없음 / 통째 교체 / **밸류** 까지 전부 동일하고 **다른 줄은 "저장 테이블" 하나뿐**이다
- **왜 나누나 — 세 겹**
  1. **책은 정당화하지 않는다.** §4.3.8 원문이 *"게시글 데이터를 `ARTICLE`과 `ARTICLE_CONTENT`로 **나눠 저장한다고 하자**"* — 나뉜 스키마는 **주어진 전제**다. 책의 질문은 "왜 나누나"가 아니라 **"이미 나뉘어 있을 때 엔티티로 볼 것인가"**(답: 아니다)
  2. ★ **이 스키마가 "본문이 커서"를 반박한다**: `article_content.content`는 **`varchar(255)`인데 별도 테이블**, `product.detail`은 **`text`인데 같은 테이블**. **큰 쪽이 안 나뉘고 작은 쪽이 나뉘었다**
  3. **책은 이 매핑을 사실상 권장하지 않는다** — 항상 조인이라는 한계 + 해법은 조회 전용 기능(5장·11장)
- ⚠️ 현실에서 나누는 이유(**어시스턴트 일반 지식, 책·코드 근거 없음**): 레거시 스키마 / BLOB·TEXT 분리 / 테이블 단위 접근권한·암호화 / 아카이빙 주기 → 전부 **운영 사정**이라 판정은 안 바뀐다
- ★ **결정 로직 (정정판)**
  ```
  0. 기본값은 ① @Embedded. 아래에 안 걸리면 ①.
  1. 상속이 필요한가?          YES → (예외) @Entity + @OneToMany   [Image]
  2. 원소가 여러 개인가?       YES ─┬ 칼럼 1개로 뭉쳐도 되나? → ② Converter          [EmailSet]
                                    └ 아니면                  → ④ @ElementCollection [OrderLine, CategoryId]
  3. 여러 필드를 칼럼 1개에?   YES → ② Converter                  [Length{value,unit}]
  4. 스키마가 이미 나뉘었나?   YES → ③ @SecondaryTable            [ArticleContent]
                               NO  → ① @Embedded                  ← 기본
  ```
  **③은 골라잡는 옵션이 아니라 스키마가 이미 나뉘어 있을 때 쓰는 것이다.**
- **② 가장 헷갈리는 사례**: `EmailSet`은 **컬렉션인데 칼럼 1개**(`EmailSetConverter`가 `Collectors.joining(",")`), `OrderLine`은 컬렉션인데 ④ → **"컬렉션이니까 별도 테이블"이 아니다**. ⚠️ 대가(일반 지식): 콤마 문자열은 **검색·인덱싱 불가**
- **④ 같은 애너테이션인데 PK가 갈린다**: `order_line`은 **PK 없음**(인덱스만) / `product_category`는 **복합 PK**(`product_id, category_id`). `List`는 `@OrderColumn` 필요, `Set`은 불필요
- **(예외) `Image`의 밸류 근거가 코드에 있다**: `abstract` + `@Inheritance(SINGLE_TABLE)` + `@DiscriminatorColumn(image_type)` → 상속 때문에 `@Entity`. **상태 변경 메서드 0개**(getter와 abstract 조회 메서드뿐), `changeImages()`가 `clear()`+`addAll()`, `orphanRemoval = true`
- ★ **착시 정리 — 관찰은 전부 근거가 안 된다**

  | 관찰 | 반례 |
  |---|---|
  | "별도 테이블이니까 엔티티" | `ArticleContent`, `OrderLine` |
  | "PK 있으니까 엔티티" | `article_content.id`(부모 것) · `product_category`(복합) · `image.image_id`(상속) |
  | "1:N이니까 별도 테이블" | `EmailSet` — 컬렉션인데 칼럼 1개 |
  | "1:1이니까 같은 테이블" | `ArticleContent` — 1:1인데 별도 테이블 |
  | "크니까 나눈다" | `product.detail`은 `text`인데 안 나눔 |

**★ 행을 특정하는 것의 출처 (부모 파생 = 밸류 / 자기 자신 = 엔티티)** — ⬜ 설명만 함, **미테스트**
- 사용자 질문(Q12)에서 웹 조사 중 도출. **기존 "밸류는 식별자가 없다"를 대체하는 프레임**이다
- 문제: "밸류는 식별자가 없다"로 말하면 `image_id`·`article_content.id`가 보일 때마다 **매번 예외 설명**이 필요하다
- ★ **바꿔 쓰면 예외가 사라진다**
  > **저장 계층은 반드시 행을 특정할 방법이 필요하다.**
  > **그 방법이 부모에서 파생되면 밸류, 자기 자신에서 나오면 엔티티.**

  | 대상 | 행을 특정하는 것 | 출처 | 판정 |
  |---|---|---|---|
  | `Orderer`, `ShippingInfo`, `Password` | 부모 행 자체 | **부모** | 밸류 |
  | `ArticleContent` | `article_content.id` = 부모 PK | **부모** | 밸류 |
  | `OrderLine` | `(order_number, line_idx)` | **부모 + 인덱스** | 밸류 |
  | `CategoryId` (Set) | `(product_id, category_id)` | **부모 + 값 자체** | 밸류 |
  | `Image` | `image_id` auto_increment | ⚠️ **자기 자신** | **밸류** (기술 타협) |

  `Image`만 어긋나고 그 이유가 코드에 있다 — `@Inheritance(SINGLE_TABLE)` 때문이며, 대가로 **상태 변경 메서드 0개**를 유지해 밸류처럼 다룬다
- **A등급 근거 — Microsoft 공식 문서(.NET Microservices Architecture) 원문**
  > *"under the covers, **owned types do have the identity, but the owner navigation property is part of this identity**. The identity of instances of owned types **is not completely their own**. It consists of three components: The identity of the owner / The navigation property pointing to them / In the case of collections of owned types, an independent component."*

  `order_line`의 `(order_number, line_idx)`가 **component 1 + component 3** 그대로다
- ⚠️ 이 프레임은 **어시스턴트가 MS 문서를 근거로 재구성한 것**이다. 최범균 책의 표현이 아니다. **시험 답은 여전히 "식별자를 가지는가"**로 쓴다 → [[concepts/01-도메인모델]]

**업계 convention — Fowler PoEAA 패턴명과 4패턴의 대응** — ⬜ 설명만 함, **미테스트**
- 사용자 질문(Q12): "best practice·convention의 개념을 명확히 하고 싶다"
- **A등급 — Fowler 카탈로그 원문 인용**

  | Fowler 패턴명 | 원문 정의 | 대응 |
  |---|---|---|
  | **Embedded Value** | *"Maps an object into several fields of another object's table."* | **①** — 정확히 일치 |
  | **Serialized LOB** | *"Saves a graph of objects by serializing them into a single large object (LOB), which it stores in a database field."* | ② `EmailSet` (**어시스턴트 판단**) |
  | **Dependent Mapping** | *"Has one class perform the database mapping for a child class."* | ④ (**어시스턴트 판단**) |
  | **Single Table Inheritance** | *"Represents an inheritance hierarchy of classes as a single table..."* | (예외) `Image` — 일치 |

  ⚠️ **③ `@SecondaryTable`에 대응하는 Fowler 패턴은 카탈로그에 없다**
- ★ **①이 기본값인 이유의 업계 표현 (Fowler 원문)**
  > *"Although the default thinking is to save an object as a table, **no sane person would want a table of money values**."*
  > 예시로 든 것이 **`Money`와 `DateRange`** — 둘 다 이 학습에 등장한 것들이다
- ★ **저장 위치는 선택 사항이라는 스펙 근거 (MS 문서 원문)**
  > *"Table splitting is optional, that is, they can **optionally be mapped to a separate table and still be owned types**."*
  → 같은 테이블이든 별도 테이블이든 **여전히 밸류**다
- **EF Core 1.x도 JPA와 같은 타협을 했다** (MS 문서 원문): *"you needed to store your value object as an EF entity with an ID field... you could **hide its ID**"* → `Image` 케이스가 JPA만의 문제가 아님을 확인
- **"왜 나누나"는 DDD 밖의 질문이다**

  | 질문 | 분야 |
  |---|---|
  | 왜 나누나 | **DB 물리 설계** (vertical partitioning) |
  | 나뉘었을 때 뭐라 부르나 | **DDD / O-R 매핑** ← 책이 다루는 것 |

- ⚠️ **B/C등급 — 나누는 게 이득인 조건** (DB 설계 아티클 통용 기준, 1차 출처 아님): 핫 컬럼이 평균 행 크기의 **10~20%** / 콜드 컬럼이 **KB 단위** / 읽기의 **5~10% 미만**만 콜드 컬럼 필요
  - ★ **이 기준으로 `article_content` 분리는 정당화되지 않는다** — `content`가 `varchar(255)`다. `product.detail`은 `text`인데 안 나눴다 → **교육용 예시 확정**
  - **실무에서 가장 흔한 이유는 크기가 아니라 레거시**: Thorben Janssen의 `@SecondaryTable` 사용 동기는 *"I'm working with a **legacy database**"* 하나뿐이었고, 그 글은 단점을 언급조차 안 한다
- ★ **best practice 4줄**
  ```
  1. 도메인 판정이 먼저다.      "지목해서 조회·변경·추적할 요구사항이 있는가" ← DB를 보지 않고 결정
  2. 기본 저장 방식은 ① Embedded Value.
  3. ③ 별도 테이블은 이유가 이미 있을 때만. 레거시(가장 흔함) / 크기 기준 충족
                                 → DB 설계 결정이지 DDD 결정이 아니다
  4. 저장 방식이 무엇이든 도메인 판정은 안 바뀐다.
  ```
