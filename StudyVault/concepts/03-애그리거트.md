### 오답 메모

**애그리거트 경계 판단 4체크리스트 (특히 변경 주체)** — 🟢 해결 (3라운드 8개 기준 전부 정답)
- 1라운드: Product/Review 결론은 맞았으나 **변경 주체**를 놓치고 1-N 관계를 기준으로 잘못 사용
- 3라운드: Survey/SurveyItem = 같은 애그리거트, Member/Coupon = 다른 애그리거트 — **4기준 × 2쌍 = 8개 전부 정확**
- 체크리스트: ① 함께 생성 ② 함께 변경 ③ **변경 주체가 같은가** ④ 한쪽 변경이 다른 쪽에 영향
- 근본 이유: 애그리거트는 **일관성 관리 단위**다. 바꾸는 사람이 다르면 지켜야 할 정합성이 없다

**애그리거트 라이프 사이클** — 🟢 해결
- 정의: 생성 → 변경 → 삭제의 타이밍. 한 애그리거트 객체들은 **함께 태어나고 함께 죽는다**
- 확인 사살 기법: **쿠폰은 유효기간이 지나면 회원과 무관하게 혼자 만료된다** → 라이프 사이클 독립 → 다른 애그리거트. `OrderLine`이 `Order` 없이 혼자 만료되는 일은 없다

**"함께 생성"의 정밀한 기준 (도메인 필연 vs 정책 트리거)** — 🟢 해결
- 함정: "회원가입 시 웰컴 쿠폰 자동 발급"이 1번 기준을 ⭕처럼 보이게 만든다. 여기서 대부분 "같은 애그리거트"로 오판한다
- 사용자가 정확히 처리함: "함께 생성되지 않음 **(이벤트라던가 이거로 연결만 시켜놓음)**" → **이 책의 해법 그대로**. `MemberRegisteredEvent`를 발행하고 쿠폰 발급 핸들러가 받는다. 10장 이벤트가 존재하는 이유가 바로 이 문제(강결합 없이 다른 애그리거트 잇기)
- ★ 기준: **"동시에 만들어진다"가 아니라 "하나가 없으면 다른 하나가 성립하지 않는가"**
  - `Order`/`Orderer`: 주문자 없는 주문은 **성립 자체가 불가** → 도메인 규칙상 **필연** → 같은 애그리거트
  - `Member`/`Coupon`: 쿠폰 없는 회원은 **완전히 정상**. 웰컴 쿠폰 정책을 폐지해도 회원은 멀쩡 → **정책상 트리거** → 다른 애그리거트

**판정 결과의 코드 반영 (컬렉션 보유 vs ID 참조)** — 🔴 미테스트 (설명만 제공)
- **같은 애그리거트 → 루트가 컬렉션을 직접 보유하고 일관성을 보장**
  ```java
  public class Survey {                      // 루트
      private List<SurveyItem> items;        // 컬렉션 보유 OK
      public void addItem(SurveyItem item) {
          verifyNotStarted(); verifyItemLimit();
          this.items.add(item);
          reorderItems();                    // 일관성 유지
      }
  }
  ```
  - ⚠️ 외부에서 `survey.getItems().add(...)`로 추가하면 `reorderItems()`와 검증을 건너뛴다 → `Order`가 `OrderLines`를 그대로 리턴하면 안 되는 것과 같은 문제. 방어: **① 불변 구현 ② 패키지/`protected` 범위 제한**
- **다른 애그리거트 → ID 참조 + 조회는 별도 경로**
  ```java
  public class Coupon {                      // 독립 루트
      private MemberId memberId;             // Member 객체가 아니라 ID
  }
  ```
  - `Member`에 `List<Coupon>`을 두면 안 되는 이유: **개념적으로 1-N이라고 코드에도 컬렉션을 두면 안 된다.** `member.getCoupons(page, size)`는 그 회원의 쿠폰을 **전부 조회**하게 되어 헤비 유저에서 성능이 무너진다
  - 대안: **쿠폰 쪽에서 N-1**(`Coupon.memberId`) + 리포지터리에서 **DB가 페이징** → `couponRepository.findByMemberId(memberId, pageable)`
- 한 줄 정리: **(가) 컬렉션 OK, (나) 컬렉션 금지** — 경계 판정의 실전 결과

**애그리거트 내부 엔티티 (구성요소도 엔티티일 수 있다)** — 🟢 해결
- 5라운드 `Course`/`Lecture`: 축 1 = 같은 애그리거트, 축 2 = **엔티티** — 둘 다 정답
- 근거(사용자가 정확히 씀): **"지목해서 추적해야 할 요구사항 존재 (시청률 통계, 비공개)"**
- 내부 엔티티여도 애그리거트 규칙은 그대로 적용된다:
  ```java
  @Entity
  public class Lecture {
      @Id @GeneratedValue private Long id;       // 식별자 필드가 있다
      void hide() { this.hidden = true; }        // 패키지 범위 — 루트만 호출
  }

  @Entity
  public class Course {                          // 루트
      @OneToMany(cascade = {PERSIST, REMOVE}, orphanRemoval = true)
      @JoinColumn(name = "course_id")
      @OrderColumn(name = "order_no")
      private List<Lecture> lectures;

      public void hideLecture(Long lectureId) { findLecture(lectureId).hide(); }
  }
  ```
  - 외부에서 `lectureRepository.findById()`로 꺼내 변경하면 ❌ — **리포지터리는 애그리거트 루트 단위**로만 존재
  - `cascade` + `orphanRemoval`로 **라이프사이클은 여전히 루트에 종속**
  - 변경은 반드시 **루트를 통해서**(`course.hideLecture(id)`)

**변경 주체 = 역할이지 코드 진입점이 아니다** — 🔴 신규 발견
- 혼동: "회차 추가·삭제는 강사가 하지만, **결국 이 행동 자체는 `course.addLecture()` 이런식으로 주체가 `Course`가 될 것 같은데?**"
- 설계로서는 정확하다(루트가 유일한 진입점). 하지만 **판정 기준으로는 순환 논리**다
  - ❌ `course.addLecture()`로 접근하니까 → 같은 애그리거트다
  - ⭕ 같은 애그리거트라고 판정했으니 → `course.addLecture()`로 접근한다 **(결과)**
- **"변경 주체"는 코드 진입점이 아니라 "어떤 역할의 사람이 바꾸는가"** (상품 담당자 vs 고객)
- ★ 4기준은 **하나라도 어긋나면 탈락이 아니라 종합 판단**이다. 5라운드 문제의 함정:

  | 행위 | 주체 | Lecture를 변경하나 |
  |---|---|---|
  | 회차 추가·삭제·순서변경 | 강사 | ⭕ |
  | 특정 회차 임시 비공개 | 운영자 | ⭕ |
  | **수강 완료 표시** | 수강생 | ❌ 별도 애그리거트(`Enrollment`) |
  | **회차별 시청률 통계** | 시스템 | ❌ **조회 전용 모델**(5장) |

  → 실제로 `Lecture`를 변경하는 건 강사·운영자뿐이고 둘 다 "강의를 운영하는 쪽" → 같은 애그리거트
