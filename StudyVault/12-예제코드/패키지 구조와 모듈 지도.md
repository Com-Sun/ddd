## ★ 최상위 구조가 곧 책의 구조다

```
com.myshop
├── catalog/        하위 도메인 — 카탈로그
│   ├── command/domain/{category,product}     3·4장 애그리거트·매핑
│   ├── query/{category,product}              5·11장 조회 모델
│   └── ui/
├── member/         하위 도메인 — 회원
│   ├── command/{application,domain}
│   ├── query/                                5장 스펙·페이징
│   └── infra/
├── order/          하위 도메인 — 주문  ★ 가장 완전한 예제
│   ├── command/{application,domain}          1·3·6·8장
│   ├── query/{application,dao,dto}           5·11장
│   ├── infra/{,domain,paygate}               2장 DIP
│   └── ui/
├── board/domain/                             4장 @SecondaryTable 전용 예제
│
├── common/         공통
│   ├── event/                                10장 이벤트 인프라
│   ├── jpa/                                  4·5장 컨버터·스펙 빌더
│   ├── model/                                1장 밸류 (Money·Address·Email)
│   └── ui/
├── eventstore/{api,infra,ui}                 10장 이벤트 저장소
├── integration/{,infra}                      9·10장 통합·포워더
├── lock/                                     8장 오프라인 선점 잠금
└── springconfig/{security,web}
```

> [!important] ★ 가장 중요한 관찰 — CQRS가 패키지에 있다
> `order`, `catalog`, `member` 모두 **`command/`와 `query/`로 먼저 나뉜다.**
> 이것은 11장 [[CQRS]]의 **"명령 모델과 조회 모델을 분리한다"** 를 **패키지 구조로 강제**한 것이다.
>
> | 패키지 | 성격 | 대응 장 |
> |--------|------|---------|
> | `order/command/domain/Order.java` | **명령 모델** — 애그리거트, 도메인 로직 | 1·3장 |
> | `order/query/dto/OrderSummary.java` | **조회 모델** — `@Subselect` 전용 엔티티 | 5·11장 |
>
> 두 `Order`는 **같은 데이터를 보지만 완전히 다른 클래스**다. 책에서 글로 읽은 분리가 **파일 시스템에 물리적으로 존재**한다.

## 하위 도메인 = 바운디드 컨텍스트의 패키지 표현

> 9장 [[바운디드 컨텍스트]]에서 "**한 개의 바운디드 컨텍스트가 여러 하위 도메인을 포함하더라도 하위 도메인마다 구분되는 패키지를 갖도록 구현해야 한다**"고 했다.
> 이 프로젝트가 정확히 그 형태다 — **물리적으로는 하나의 스프링 부트 애플리케이션이지만, 패키지로 논리적 경계**를 만든다.

```
   [ 하나의 웹 애플리케이션 (ShopApplication.java) ]
   ┌─────────────────────────────────────────────────┐
   │  catalog    │   member    │   order   │  board  │
   │  (논리적     │  (논리적     │  (논리적   │        │
   │   컨텍스트)  │   컨텍스트)  │  컨텍스트) │        │
   └─────────────────────────────────────────────────┘
```

### 컨텍스트 간 통합 지점

| 통합 | 코드 | 방식 |
|------|------|------|
| **order → member** | `order/infra/OrdererServiceImpl.java` → `MemberQueryService` | 도메인 서비스 인터페이스 경유 |
| **order → catalog** | `order/command/application/PlaceOrderService.java` → `ProductRepository` | 직접 참조 (같은 앱) |
| **order → 외부 결제** | `order/infra/paygate/ExternalRefundService.java` | 이벤트 핸들러 경유 |

> [!tip] `OrdererService`가 핵심이다
> `order/command/domain/OrdererService.java`는 **인터페이스만 도메인에** 두고,
> 구현(`OrdererServiceImpl`)은 **`order/infra/`** 에 두어 `member` 컨텍스트를 호출한다.
> → 2장 [[DIP]] + 7장 [[외부 시스템 연동과 도메인 서비스]] + 9장 [[바운디드 컨텍스트 간 관계]]의 **ACL(안티코럽션 계층)** 이 한 클래스에 모두 구현되어 있다.

## 계층 배치 규칙 확인

2장 [[모듈 구성]]의 규칙이 실제로 지켜지는지 대조했다.

| 책의 규칙 | 실제 코드 | 판정 |
|-----------|-----------|------|
| 영역별 별도 패키지 | `domain` / `application` / `infra` / `ui` | ⭕ |
| 도메인이 크면 하위 도메인별 패키지 | `catalog` / `member` / `order` | ⭕ |
| 하위 도메인이 크면 애그리거트 기준 | `catalog/command/domain/{product,category}` | ⭕ |
| **애그리거트·모델·리포지터리는 같은 패키지** | `order/command/domain/`에 `Order`, `OrderLine`, `Orderer`, `OrderRepository` 전부 | ⭕ |
| 리포지터리 인터페이스는 도메인, 구현은 인프라 | `OrderRepository`(domain) — 구현체는 **스프링 데이터 JPA가 자동 생성** | ⭕(변형) |
| 한 패키지 10~15개 미만 | `order/command/domain` = **17개** | ⚠️ 살짝 초과 |

> [!note] 리포지터리 구현 클래스가 안 보이는 이유
> `JpaOrderRepository` 같은 구현 클래스가 없다. 4장 [[스프링 데이터 JPA 리포지터리]]에서 말한 대로
> **`Repository<Order, OrderNo>`를 상속하면 스프링 데이터 JPA가 구현 객체를 자동 생성**하기 때문이다.
> 즉 **"구현 클래스를 직접 작성할 일은 거의 없다"** 가 실제로 지켜진 것이다.
>
> 예외적으로 직접 구현한 것은 **JPA로 안 되는 것들**뿐이다:
> `lock/SpringLockManager`(JdbcTemplate), `eventstore/infra/JdbcEventStore`(JdbcTemplate), `common/jpa/RangeableRepositoryImpl`(COUNT 회피).

## 기술 스택 (`pom.xml`)

| 분류 | 라이브러리 |
|------|-----------|
| 코어 | `spring-boot-starter-web`, `spring-boot-starter-data-jpa` |
| 보안 | `spring-boot-starter-security`, `thymeleaf-extras-springsecurity5` |
| 뷰 | `spring-boot-starter-thymeleaf` |
| **조회 보조** | **`mybatis-spring-boot-starter`** ← 11장 "조회 모델은 마이바티스" |
| DB | `mysql-connector-java`, `h2`(테스트) |
| 기타 | `spring-boot-starter-validation`, `spring-boot-starter-mail` |

> [!important] 마이바티스가 들어 있다는 사실
> 11장 [[CQRS]]에서 **"명령 모델은 JPA, 조회 모델은 마이바티스"** 라고 했는데,
> `pom.xml`에 **실제로 마이바티스 의존성이 포함**되어 있다. 조회 측에 다른 기술을 쓸 수 있도록 열어 둔 것이다.

## 주요 설정 (`src/main/resources/application.properties`)

```properties
spring.jpa.show-sql=true            # 발생하는 SQL 확인 → 학습에 필수
spring.jpa.open-in-view=false       # ★ OSIV 비활성화
logging.level.com.myshop=DEBUG
```

> [!tip] `open-in-view=false`가 중요한 이유
> OSIV를 끄면 **트랜잭션 밖에서 지연 로딩이 동작하지 않는다.**
> 이는 4장 [[애그리거트 로딩 전략]]의 **"JPA는 트랜잭션 범위 내에서 지연 로딩을 허용한다"** 를
> **강제로 지키게 만드는 설정**이다. 뷰에서 실수로 지연 로딩을 건드리면 바로 예외가 난다.

| "`pom.xml`에 마이바티스가 있는 이유" | **조회 모델용** (CQRS) |
| "`open-in-view=false`의 효과" | 트랜잭션 밖 **지연 로딩 차단** |
