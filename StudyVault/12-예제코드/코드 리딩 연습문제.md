## Question 3 - private setter 확인 [code-reading]
> `Order.java`의 `setXxx` 메서드들의 접근 범위는? 그리고 그 안에서 무엇을 하는가?

> [!answer]- 정답 보기
> **전부 `private`** 이다.
> ```java
> private void setNumber(OrderNo number) {
>     if (number == null) throw new IllegalArgumentException("no number");
>     this.number = number;

>     verifyAtLeastOneOrMoreOrderLines(orderLines);   // 제약 검증

## Question 5 - @Subselect 실물 확인 [code-reading]
> `OrderSummary`에 붙은 하이버네이트 애너테이션 3개와 각각의 역할은? `@Synchronize`에 지정된 테이블은 무엇이며 왜 그것들인가?

> [!answer]- 정답 보기
> `order/query/dto/OrderSummary.java`
> ```java
> @Entity
> @Immutable
> @Subselect("""select o.order_number as number, ... from purchase_order o
>              inner join order_line ol ... cross join product p ...""")
> @Synchronize({"purchase_order", "order_line", "product"})
> ```
> - **`@Subselect`** — 쿼리 결과를 매핑할 테이블처럼 사용 (뷰와 유사)
> - **`@Immutable`** — 수정해도 DB에 반영하지 않음 (매핑 테이블이 없어 UPDATE 시 에러 방지)
> - **`@Synchronize`** — **`@Subselect` 쿼리가 읽는 세 테이블**을 지정. 로딩 전에 이 테이블들에 변경이 있으면 **먼저 플러시**해서 **이전 값(stale)이 조회되는 것을 방지**한다.
> → [[하이버네이트 Subselect 사용]]

## Question 6 - 설정 추적 [configuration]
> `application.properties`에서 `spring.jpa.open-in-view=false`는 무엇을 의미하며, 이 프로젝트의 어떤 설계 결정과 맞물리는가?

> [!answer]- 정답 보기
> OSIV(Open Session In View)를 **끈다** — **트랜잭션 밖에서는 지연 로딩이 동작하지 않는다.**
> 이 프로젝트는 **모든 컬렉션을 `LAZY`로** 설정했으므로(`Order.orderLines`, `Product.images`, `Product.categoryIds`),
> 뷰에서 실수로 지연 로딩을 건드리면 **즉시 예외**가 난다.
> 즉 4장 [[애그리거트 로딩 전략]]의 **"JPA는 트랜잭션 범위 내에서 지연 로딩을 허용한다"** 를 **설정으로 강제**한 것이다.
> 조회 화면은 지연 로딩 대신 **조회 전용 모델**(`OrderSummary`/`OrderView`)로 해결한다.

## Question 7 - 커스텀 리포지터리 추적 [code-reading]
> `MemberDataDao.getRange()`는 스프링 데이터 JPA의 기본 메서드가 아니다. 어떻게 동작하는지 관련 파일 3개를 찾아 설명하라.

> [!answer]- 정답 보기
> | 파일 | 역할 |
> |------|------|
> | `common/jpa/Rangeable.java` | `start`/`limit`/`sort`를 담는 파라미터 객체 |
> | `common/jpa/RangeableRepository.java` | `getRange(spec, rangeable)` 선언 |
> | `common/jpa/RangeableRepositoryImpl.java` | `SimpleJpaRepository`를 **상속**해 구현 |
>
> 활성화는 진입점에서 한다.
> ```java
> // ShopApplication.java
> @EnableJpaRepositories(repositoryBaseClass = RangeableRepositoryImpl.class)
> ```
> **왜 만들었나**: 5장 [[페이징 처리하기]]에서 **"스펙을 사용하는 `findAll`은 리턴 타입이 `List`여도 COUNT 쿼리를 실행한다"** 고 했다.
> `getRange()`는 `TypedQuery`에 `setFirstResult`/`setMaxResults`만 적용해 **COUNT 쿼리 없이** 페이징한다.
> 책이 "커스텀 리포지터리 기능으로 직접 구현해야 한다"고 한 것의 **실물**이다.

## Question 8 - 이벤트 핸들러 세기 [code-reading]
> `OrderCanceledEvent` 하나가 발생하면 몇 개의 핸들러가 반응하는가? 각각의 실행 시점이 다른 이유는?

> [!answer]- 정답 보기
> **2개**다.
> | 핸들러 | 애너테이션 | 실행 시점 |
> |--------|-----------|-----------|
> | `common/event/EventStoreHandler` | `@EventListener(Event.class)` | **동기, 같은 트랜잭션** |

## Question 9 - 🔴 버그 찾기 [debugging]
> `StartShippingService.startShipping()`을 열어 책 p.260과 비교하라. 무엇이 다른가? 어떤 증상이 나타나며 어떻게 고치는가?

> [!answer]- 정답 보기
> **`!`가 빠져 있다.**
> ```java
> // 실제 코드 (❌)
> if (order.matchVersion(req.getVersion())) {
>     throw new VersionConflictException();
> }
> // 책 p.260 (⭕)
> if (!order.matchVersion(req.getVersion())) {
>     throw new VersionConflictException();
> }
> ```
> `matchVersion()`은 **일치하면 `true`** 를 리턴하므로 로직이 **정확히 반대**가 된다.
>
> **증상**
> | 상황 | 실제 동작 |
> |------|-----------|
> | 정상 요청(버전 일치) | **`VersionConflictException` 발생 → 배송 시작 불가** |
> | 실제 충돌(버전 불일치) | **검사를 통과해 그대로 배송 시작** |
>
> **수정**: `if` 조건 앞에 **`!` 추가**.
> → [[코드 대조 검증 보고서]], [[비선점 잠금]]

## Question 11 - 도메인 서비스의 삼중 역할 [analysis]
> `OrdererService`와 `OrdererServiceImpl`을 열어보라. 이 한 쌍이 동시에 구현하고 있는 **세 가지 개념**은 무엇인가?

> [!answer]- 정답 보기
> ```java
> // order/command/domain/OrdererService.java  ← 도메인 영역
> public interface OrdererService {
>     Orderer createOrderer(MemberId ordererMemberId);
> }
> // order/infra/OrdererServiceImpl.java        ← 인프라 영역
> public Orderer createOrderer(MemberId ordererMemberId) {
>     MemberData memberData = memberQueryService.getMemberData(ordererMemberId.getId());
>     return new Orderer(MemberId.of(memberData.getId()), memberData.getName());
> }
> ```
> ① **[[DIP]]** — 인터페이스가 **고수준(도메인)** 에, 구현이 **저수준(인프라)** 에 위치
> ② **[[도메인 서비스]]** — **상태 없이 로직만**, 이름이 도메인 개념(`createOrderer`)
> ③ **[[바운디드 컨텍스트 간 관계]]의 ACL** — `member` 컨텍스트의 **`MemberData`를 `order` 컨텍스트의 `Orderer`로 변환**
>
> 핵심은 **`order` 도메인이 `MemberData`를 전혀 모른다**는 것이다. 변환은 인프라에서만 일어난다.

## Question 12 - 권한 검사 위치 판단 [analysis]
> 주문 취소 권한 검사가 왜 URL이나 메서드 수준이 아닌 **도메인 객체 수준**에서 이뤄지는지, `SecurityCancelPolicy`를 근거로 설명하라.

> [!answer]- 정답 보기
> ```java
> // order/infra/domain/SecurityCancelPolicy.java
> public boolean hasCancellationPermission(Order order, Canceller canceller) {
>     return isCancellerOrderer(order, canceller) || isCurrentUserAdminRole();
> }
> private boolean isCancellerOrderer(Order order, Canceller canceller) {
>     return order.getOrderer().getMemberId().getId().equals(canceller.getMemberId());
> }
> ```
> **"본인이거나 ADMIN"** 조건 중 **"본인"** 을 판단하려면 **`Order` 애그리거트를 로딩해서 주문자를 확인**해야 한다.
> - **URL 기반**(서블릿 필터) → 어떤 주문인지 모른 채 판단해야 하므로 **불가능**
> - **메서드 수준**(`@PreAuthorize("hasRole('ADMIN')")`) → **역할만** 판단 가능, "본인" 표현 불가
> - **도메인 객체 수준** → 애그리거트를 로딩한 뒤 검사 ⭕
>
> 6장 [[권한 검사]]의 **"게시글 삭제는 본인 또는 관리자만"** 예시와 구조가 동일하다.
> 인터페이스(`CancelPolicy`)는 **도메인**에, 스프링 시큐리티에 의존하는 구현은 **인프라**에 둔 것도 주목하라.

## Question 13 - 기능 확장 [extension]
> 주문이 취소될 때 **환불에 더해 이메일로 취소 안내를 보내는 기능**을 추가하려 한다. 어떤 파일을 만들고, 기존 파일 중 무엇을 수정해야 하는가?

> [!answer]- 정답 보기
> **새 파일 1개만 만들고, 기존 파일은 하나도 수정하지 않는다.**
> ```java
> // order/infra/OrderCanceledMailHandler.java  (신규)
> @Service
> public class OrderCanceledMailHandler {
>     private MailService mailService;
>
>     @Async
>     @TransactionalEventListener(
>             classes = OrderCanceledEvent.class,
>             phase = TransactionPhase.AFTER_COMMIT)
>     public void handle(OrderCanceledEvent event) {
>         mailService.sendCancelNotice(event.getOrderNumber());
>     }
> }
> ```
> **수정 불필요한 것**: `Order.cancel()`, `CancelOrderService`, `CancelOrderController` — **전부 그대로**.
>
> 이것이 10장 [[이벤트 개요]]의 **장점 ②(기능 확장 용이)** 다.
> 만약 이벤트 없이 `Order.cancel(refundService, mailService)`처럼 구현했다면
> **도메인 객체의 시그니처와 트랜잭션 처리가 모두 복잡해졌을 것**이다. → [[시스템 간 강결합 문제]]
>
> ⚠️ 다만 `OrderCanceledEvent`가 **이메일 주소를 담고 있지 않다**면 핸들러가 회원을 조회해야 한다.
> 이벤트에 담을 데이터를 결정하는 것이 [[이벤트 개요]]의 **"부족해도 과해도 안 된다"** 원칙이다.

## Question 14 - 설계 의도 종합 [analysis]
> 이 프로젝트에서 **책에 나오지만 구현하지 않은 것**들을 찾아, 저자가 왜 넣지 않았을지 추론하라.

> [!answer]- 정답 보기
> **구현되지 않은 것들**
> | 항목 | 책 위치 |
> |------|---------|
> | **선점 잠금**(`PESSIMISTIC_WRITE`) | 8.2 [[선점 잠금]] |
> | **강제 버전 증가**(`OPTIMISTIC_FORCE_INCREMENT`) | 8.3.1 [[강제 버전 증가]] |
> | **메시징 시스템**(카프카/래빗MQ) | 10.5.2 [[메시징 시스템을 이용한 비동기 구현]] |
> | **애그리거트 팩토리 메서드**(`Store.createProduct`) | 3.6 [[애그리거트를 팩토리로 사용하기]] |
> | **할인 계산 도메인 서비스** | 7.2.1 [[도메인 서비스]] |
>
> **추론되는 이유**
> ① **필요할 때 도입하라는 태도** — 8장은 "**선점 잠금은 교착 상태 위험이 있다**"고 경고했고, 이 예제 규모에서는 **비선점 잠금(`@Version`)으로 충분**하다.
> ② **인프라 부담 회피** — 카프카/래빗MQ를 넣으면 예제를 돌리기 위해 **미들웨어를 띄워야 한다.** `SysoutEventSender`로 대체해 **핵심 구조(포워더·offset·저장소)만 보여준다.**
> ③ **설명용 예시와 실제 도메인의 구분** — `Store`/`Product` 팩토리, 할인 계산은 **개념을 설명하기 위해 지어낸 상황**이지 이 쇼핑몰의 요구사항이 아니다. **억지로 넣으면 오히려 도메인이 왜곡**된다.
>
> **교훈**: DDD 패턴은 **카탈로그가 아니라 도구상자**다. 2장 [[DIP와 아키텍처]]의 **"DIP를 항상 적용할 필요는 없다"**, 11장 [[CQRS 장단점]]의 **"도메인이 복잡하지 않은데 도입하면 비용만 높아진다"** 와 같은 태도가 코드 전반에 일관되게 나타난다.
