# 밸류 컬렉션 매핑 (★★★)

#ddd #repository #jpa-mapping #value-collection #concept

## Overview Table (세 가지 매핑 방식)

| 방식 | 사용 애너테이션 | 언제 |
|------|-----------------|------|
| **① 별도 테이블 매핑** (§4.3.5) | `@ElementCollection` + `@CollectionTable` (+ `@OrderColumn`) | 일반적인 밸류 컬렉션 |
| **② 한 개 칼럼 매핑** (§4.3.6) | `AttributeConverter` + 컬렉션 전용 밸류 타입 | 콤마 구분 등 한 칼럼 저장 |
| **③ `@Entity`로 매핑** (§4.3.9) | `@Entity` 상속 매핑 + `@OneToMany` | **밸류에 상속 구조**가 필요할 때 |

## ① 별도 테이블 매핑 (§4.3.5)

```
   ┌─────────────────────┐        ┌──────────────────────────────┐
   │ purchase_order      │        │ order_line                   │
   │  order_number  (PK) │◀───────┤  order_number  (FK)          │
   │  ...                │        │  line_idx      ← 인덱스 칼럼 │
   └─────────────────────┘        │  product_id                  │
                                  │  price / quantity / amounts  │
                                  └──────────────────────────────┘
```

> [!important]
> 밸류 컬렉션을 저장하는 테이블은 **외부키를 이용해서 엔티티에 해당하는 테이블을 참조**한다. 이 외부키는 **컬렉션이 속할 엔티티**를 의미한다.
> `List` 타입의 컬렉션은 **인덱스 값이 필요**하므로 **인덱스 값을 저장하기 위한 칼럼(`line_idx`)** 도 존재한다.

```java
@Entity
@Table(name = "purchase_order")
public class Order {

    @EmbeddedId
    private OrderNo number;

    @ElementCollection(fetch = FetchType.LAZY)
    @CollectionTable(name = "order_line",
                     joinColumns = @JoinColumn(name = "order_number"))
    @OrderColumn(name = "line_idx")
    private List<OrderLine> orderLines;
}
```

> [!note] `fetch` 전략은 `LAZY`가 실제 코드다
> 책 4.3.5의 초기 예제는 `EAGER`로 표기하지만, **실제 `ddd-start2/`는 모든 컬렉션이 `LAZY`** 다
> (`Order.orderLines`, `Product.images`, `Product.categoryIds`).
> 이는 4.4 [[애그리거트 로딩 전략]]의 결론 — **"무조건 즉시 로딩으로 설정할 필요는 없다"** — 을 따른 것이다.
> `application.properties`의 **`spring.jpa.open-in-view=false`** 와 함께 보면,
> 지연 로딩을 **트랜잭션 안에서만** 쓰겠다는 의도가 분명하다.

```java
@Embeddable
public class OrderLine {

    @Embedded
    private ProductId productId;

    @Column(name = "price")
    private Money price;

    @Column(name = "quantity")
    private int quantity;

    @Column(name = "amounts")
    private Money amounts;
}
```

| 애너테이션 | 역할 |
|-----------|------|
| **`@ElementCollection`** | 밸류 컬렉션임을 지정 |
| **`@CollectionTable`** | `name` = 밸류를 저장할 **테이블 이름**, `joinColumns` = **외부키로 사용할 칼럼** |
| **`@OrderColumn`** | 지정한 칼럼에 **리스트의 인덱스 값**을 저장 |

> [!tip] `OrderLine`에 인덱스 프로퍼티가 없는 이유
> **`List` 타입 자체가 인덱스를 갖고 있기 때문**이다. JPA는 `@OrderColumn`으로 지정한 칼럼에 인덱스를 저장한다.

> [!note] 외부키가 두 개 이상이면
> `joinColumns`에 **`@JoinColumn`의 배열**을 이용해서 외부키 목록을 지정한다.

## ② 한 개 칼럼 매핑 (§4.3.6)

> 도메인 모델에는 이메일 주소 목록을 `Set`으로 보관하고, DB에는 **한 개 칼럼에 콤마로 구분해서 저장**해야 할 때가 있다.

> [!important] 전제 조건
> `AttributeConverter`를 사용하려면 **밸류 컬렉션을 표현하는 새로운 밸류 타입을 추가**해야 한다.

### 1단계 — 컬렉션 전용 밸류 타입 추가

```java
public class EmailSet {
    private Set<Email> emails = new HashSet<>();

    public EmailSet(Set<Email> emails) {
        this.emails.addAll(emails);
    }

    public Set<Email> getEmails() {
        return Collections.unmodifiableSet(emails);
    }
}
```

### 2단계 — AttributeConverter 구현

```java
public class EmailSetConverter implements AttributeConverter<EmailSet, String> {

    @Override
    public String convertToDatabaseColumn(EmailSet attribute) {
        if (attribute == null) return null;
        return attribute.getEmails().stream()
                .map(email -> email.getAddress())
                .collect(Collectors.joining(","));
    }

    @Override
    public EmailSet convertToEntityAttribute(String dbData) {
        if (dbData == null) return null;
        String[] emails = dbData.split(",");
        Set<Email> emailSet = Arrays.stream(emails)
                .map(value -> new Email(value))
                .collect(toSet());
        return new EmailSet(emailSet);
    }
}
```

### 3단계 — 프로퍼티에 지정

```java
@Column(name = "emails")
@Convert(converter = EmailSetConverter.class)
private EmailSet emailSet;
```

## ③ `@Entity`로 매핑하기 (§4.3.9)

> [!warning] 왜 이런 상황이 생기나
> **개념적으로 밸류인데 구현 기술의 한계나 팀 표준 때문에 `@Entity`를 사용해야 할 때**도 있다.
> **JPA는 `@Embeddable` 타입의 클래스 상속 매핑을 지원하지 않는다.**
> 상속 구조를 갖는 밸류 타입을 사용하려면 `@Embeddable` 대신 **`@Entity`를 이용해서 상속 매핑**으로 처리해야 한다.

```
                    Image (추상)
                  ├─ getURL()
                  ├─ hasThumbnail()
                  └─ getThumbnailURL()
                        △
            ┌───────────┴───────────┐
    InternalImage              ExternalImage
```

**필요한 추가 작업**

| 작업 | 이유 |
|------|------|
| **식별자 매핑용 필드 추가** | `@Entity`이므로 |
| **타입 식별(discriminator) 칼럼 추가** | 구현 클래스를 구분하기 위해 |
| `@Inheritance(strategy = SINGLE_TABLE)` | 한 테이블에 상속 계층을 매핑 |
| `@DiscriminatorColumn` | 타입 구분용 칼럼 지정 |

```java
@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "image_type")
@Table(name = "image")
public abstract class Image {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "image_id")
    private Long id;

    @Column(name = "image_path")
    private String path;

    @Column(name = "upload_time")
    private LocalDateTime uploadTime;

    protected Image() {}
    public Image(String path) {
        this.path = path;
        this.uploadTime = LocalDateTime.now();
    }

    protected String getPath() { return path; }
    public LocalDateTime getUploadTime() { return uploadTime; }

    public abstract String getUrl();
    public abstract boolean hasThumbnail();
    public abstract String getThumbnailUrl();
}
```

> [!note] 실제 예제 코드 기준으로 정정
> 책 본문(리스트 4.7)은 `@Temporal(TemporalType.TIMESTAMP) Date uploadTime`으로 표기하지만,
> **실제 `ddd-start2/`는 `LocalDateTime`을 쓰고 `@Temporal`이 없다.**
> JPA 2.2부터 `LocalDateTime`을 기본 지원하므로 **`@Temporal`이 불필요**하다.
> 메서드명도 `getURL()`이 아니라 **`getUrl()`** 이다. → `catalog/command/domain/product/Image.java`

```java
@Entity
@DiscriminatorValue("II")
public class InternalImage extends Image { ... }

@Entity
@DiscriminatorValue("EI")
public class ExternalImage extends Image { ... }
```

> [!important]
> `Image`를 `@Entity`로 매핑했지만 **모델에서 `Image`는 밸류이므로 상태를 변경하는 기능은 추가하지 않는다.**

### 컬렉션 매핑 — `@OneToMany` (리스트 4.8)

```java
@Entity
@Table(name = "product")
public class Product {
    @EmbeddedId
    private ProductId id;
    private String name;

    @Convert(converter = MoneyConverter.class)
    private Money price;
    private String detail;

    @OneToMany(
            cascade = {CascadeType.PERSIST, CascadeType.REMOVE},
            orphanRemoval = true)
    @JoinColumn(name = "product_id")
    @OrderColumn(name = "list_idx")
    private List<Image> images = new ArrayList<>();

    public void changeImages(List<Image> newImages) {
        images.clear();
        images.addAll(newImages);
    }
}
```

> [!tip] `cascade`와 `orphanRemoval`이 필요한 이유
> `Image`는 밸류이므로 **독자적인 라이프 사이클을 갖지 않고 `Product`에 완전히 의존**한다.
> - `Product`를 저장할 때 함께 저장, 삭제할 때 함께 삭제 → **`cascade` 지정**
> - 리스트에서 `Image` 객체를 제거하면 DB에서 함께 삭제 → **`orphanRemoval = true`**

## ★ `@Entity` 컬렉션의 성능 함정

> [!danger] `clear()` 성능 문제 (p.159)
> `@Entity`에 대한 `@OneToMany` 매핑에서 컬렉션의 **`clear()` 메서드를 호출하면 삭제 과정이 효율적이지 않다.**
>
> 하이버네이트는 `@Entity`를 위한 컬렉션 객체의 `clear()`를 호출하면
> **`select` 쿼리로 대상 엔티티를 로딩하고, 각 개별 엔티티에 대해 `delete` 쿼리를 실행**한다.

```
   Product에 Image가 4개일 때 changeImages() 실행:

   ① SELECT ... FROM image WHERE product_id = ?      ← 1번
   ② DELETE FROM image WHERE image_id = ?            ← 4번
                                              총 5번의 쿼리
```

> **변경 빈도가 낮으면 괜찮지만 빈도가 높으면 전체 서비스 성능에 문제가 될 수 있다.**

### 대조 — `@Embeddable`은 한 번에 삭제한다

> [!important]
> 하이버네이트는 **`@Embeddable` 타입에 대한 컬렉션의 `clear()`를 호출하면
> 컬렉션에 속한 객체를 로딩하지 않고 한 번의 `delete` 쿼리로 삭제 처리**를 수행한다.

| 매핑 | `clear()` 시 쿼리 |
|------|-------------------|
| `@Entity` + `@OneToMany` | **`select` 1번 + `delete` N번** |
| `@Embeddable` + `@ElementCollection` | **`delete` 1번** |

### 해결 — 상속을 포기하고 if-else

> 애그리거트 특성을 유지하면서 이 문제를 해소하려면 결국 **상속을 포기하고 `@Embeddable`로 매핑된 단일 클래스로 구현**해야 한다.

```java
@Embeddable
public class Image {
    @Column(name = "image_type")
    private String imageType;
    @Column(name = "image_path")
    private String path;

    @Temporal(TemporalType.TIMESTAMP)
    @Column(name = "upload_time")
    private Date uploadTime;

    public boolean hasThumbnail() {
        // 성능을 위해 다형을 포기하고 if-else로 구현
        if (imageType.equals("II")) {
            return true;
        } else {
            return false;
        }
    }
}
```

> [!important] 결론
> **코드 유지 보수와 성능의 두 가지 측면을 고려해서 구현 방식을 선택해야 한다.**

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "밸류 컬렉션 별도 테이블 매핑" | **`@ElementCollection` + `@CollectionTable`** |
| "리스트 인덱스 저장" | **`@OrderColumn`** |
| "`OrderLine`에 인덱스 필드가 없는 이유" | **`List` 타입 자체가 인덱스를 가짐** |
| "컬렉션을 한 칼럼에 저장" | **컬렉션 전용 밸류 타입 + `AttributeConverter`** |
| "JPA가 지원하지 않는 것" | **`@Embeddable`의 클래스 상속 매핑** |
| "상속 구조 밸류를 매핑하려면" | **`@Entity` + 상속 매핑** (+ 식별자, discriminator 칼럼) |
| "`@Entity` 밸류에 상태 변경 메서드를?" | **추가하지 않는다** |
| "밸류의 라이프 사이클" | 루트에 완전히 의존 → **`cascade` + `orphanRemoval`** |
| "`@Entity` 컬렉션 `clear()`의 쿼리 수" | **select 1 + delete N** |
| "`@Embeddable` 컬렉션 `clear()`의 쿼리 수" | **delete 1** |
| "성능 문제 최종 해법" | **상속 포기 + `@Embeddable` 단일 클래스 + if-else** |
