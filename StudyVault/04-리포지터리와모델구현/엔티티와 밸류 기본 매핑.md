# 엔티티와 밸류 기본 매핑 (★★★)

#ddd #repository #jpa-mapping #concept

## Overview Table (기본 규칙 4가지)

| 대상 | 애너테이션 |
|------|-----------|
| **애그리거트 루트** (엔티티) | **`@Entity`** |
| **밸류** | **`@Embeddable`** |
| **밸류 타입 프로퍼티** | **`@Embedded`** |
| 칼럼 이름이 다를 때 | **`@AttributeOverrides` / `@AttributeOverride`** |

| 추가 규칙 | 이유 |
|-----------|------|
| **기본 생성자 필수** (`protected`) | JPA가 DB에서 읽어와 객체를 생성할 때 사용 |
| **필드 접근 방식**(`@Access(AccessType.FIELD)`) | 불필요한 **get/set 메서드를 만들지 않기 위해** |

> [!important] 한 테이블 매핑
> 한 테이블에 엔티티와 밸류 데이터가 같이 있다면, **루트 엔티티와 루트 엔티티에 속한 밸류는 한 테이블에 매핑할 때가 많다.**

## §4.3.1 기본 매핑

### 루트 엔티티 — `@Entity`

```java
import javax.persistence.Entity;

@Entity
@Table(name = "purchase_order")
public class Order {
    ...
}
```

### 밸류 — `@Embeddable`

```java
import javax.persistence.Embeddable;

@Embeddable
public class Orderer {

    // MemberId에 정의된 칼럼 이름을 변경하기 위해
    // @AttributeOverride 애너테이션 사용
    @Embedded
    @AttributeOverrides(
        @AttributeOverride(name = "id",
                           column = @Column(name = "orderer_id"))
    )
    private MemberId memberId;

    @Column(name = "orderer_name")
    private String name;
}
```

```java
@Embeddable
public class MemberId implements Serializable {
    @Column(name = "member_id")
    private String id;
}
```

> [!tip] `@AttributeOverride`가 필요한 이유
> `Orderer`의 `memberId` 프로퍼티와 매핑되는 칼럼 이름은 **`orderer_id`** 인데,
> `MemberId`에 설정된 칼럼 이름은 **`member_id`** 로 서로 다르다.
> **`@Embeddable` 타입에 설정한 칼럼 이름과 실제 칼럼 이름이 다르므로** `@AttributeOverride`로 매핑할 칼럼 이름을 변경한다.

### 중첩 밸류

```java
@Embeddable
public class ShippingInfo {

    @Embedded
    @AttributeOverrides({
        @AttributeOverride(name = "zipCode",
                           column = @Column(name = "shipping_zip_code")),
        @AttributeOverride(name = "address1",
                           column = @Column(name = "shipping_addr1")),
        @AttributeOverride(name = "address2",
                           column = @Column(name = "shipping_addr2"))
    })
    private Address address;

    @Column(name = "shipping_message")
    private String message;

    @Embedded
    private Receiver receiver;
}
```

> [!note] 실제 예제 코드와 대조 (`ddd-start2/`)
> - 칼럼명은 **`shipping_zip_code`** 다(밑줄 3개). → `order/command/domain/ShippingInfo.java`
> - `Orderer`의 `MemberId` 필드에는 **`@Embedded`가 없다.** `@AttributeOverrides`만 붙어 있어도 JPA가 `@Embeddable` 타입을 인식한다.
> ```java
> // order/command/domain/Orderer.java — 실제 코드
> @AttributeOverrides(
>         @AttributeOverride(name = "id", column = @Column(name = "orderer_id"))
> )
> private MemberId memberId;
> ```
> → [[코드 대조 검증 보고서]]

### 루트 엔티티에서 밸류 프로퍼티 — `@Embedded`

```java
@Entity
public class Order {

    @Embedded
    private Orderer orderer;

    @Embedded
    private ShippingInfo shippingInfo;
}
```

## §4.3.2 기본 생성자

> [!important] 왜 필요한가
> `Receiver`가 **불변 타입이면 생성 시점에 필요한 값을 모두 전달받으므로 set 메서드를 제공하지 않는다.**
> 이는 기본 생성자(파라미터가 없는)를 추가할 필요가 없다는 뜻이다.
>
> **하지만** JPA에서 `@Entity`와 `@Embeddable`로 클래스를 매핑하려면 **기본 생성자를 제공해야 한다.**
> **DB에서 데이터를 읽어와 매핑된 객체를 생성할 때 기본 생성자를 사용**하기 때문이다.

```java
@Embeddable
public class Receiver {
    @Column(name = "receiver_name")
    private String name;
    @Column(name = "receiver_phone")
    private String phone;

    protected Receiver() {}        // ★ JPA를 적용하기 위해 기본 생성자 추가

    public Receiver(String name, String phone) {
        this.name = name;
        this.phone = phone;
    }
    // get 메서드 생략
}
```

> [!warning] 왜 `protected`인가
> 기본 생성자는 **JPA 프로바이더가 객체를 생성할 때만 사용**한다.
> 기본 생성자를 다른 코드에서 사용하면 **값이 없는 온전하지 못한 객체를 만들게 된다.**
> 이런 이유로 다른 코드에서 사용하지 못하도록 **`protected`로 선언**한다.

> [!note] 실제 예제 코드에서는 일관되지 않다
> `ddd-start2/`를 보면 **`protected`와 `public`이 섞여 있다.**
>
> | 클래스 | 기본 생성자 |
> |--------|-------------|
> | `Order`, `OrderLine`, `OrderNo`, `MemberId`, `Product`, `Image`, `Article`, `ArticleContent`, `OrderSummary` | **`protected`** ⭕ |
> | `Receiver`, `ShippingInfo`, `Address` | **`public`** ⚠️ |
>
> 원칙은 `protected`가 맞다. `public`인 것들은 폼 바인딩 편의 때문으로 보이며,
> **원칙을 알고 예외를 두는 것**과 **모르고 쓰는 것**은 다르다.
> → [[코드 대조 검증 보고서]]

```
   public  기본 생성자  →  아무 데서나 빈 객체 생성 가능   ❌
   protected 기본 생성자 →  JPA 프로바이더만 사용         ⭕
```

## §4.3.3 필드 접근 방식 사용

JPA는 **필드**와 **메서드**의 두 가지 방식으로 매핑을 처리할 수 있다.

### ❌ 메서드(프로퍼티) 접근 방식

```java
@Entity
@Access(AccessType.PROPERTY)
public class Order {

    @Column(name = "state")
    @Enumerated(EnumType.STRING)
    public OrderState getState() {
        return state;
    }

    public void setState(OrderState state) {
        this.state = state;
    }
}
```

> [!danger] 문제
> - 엔티티에 프로퍼티를 위한 **공개 get/set 메서드를 추가하면 도메인의 의도가 사라지고**, 객체가 아닌 **데이터 기반으로 엔티티를 구현할 가능성**이 높아진다.
> - 특히 **set 메서드는 내부 데이터를 외부에서 변경할 수 있는 수단**이 되므로 **캡슐화를 깨는 원인**이 될 수 있다.
> - 밸류 타입을 **불변으로 구현하려면 set 메서드 자체가 필요 없는데**, JPA 구현 방식 때문에 공개 set 메서드를 추가하는 것도 좋지 않다.

**의도가 드러나는 이름 비교**

| ❌ set 메서드 | ⭕ 도메인 메서드 |
|---------------|------------------|
| `setState()` | **`cancel()`** — 주문 취소 |
| `setShippingInfo()` | **`changeShippingInfo()`** — 배송지 변경 |

### ⭕ 필드 접근 방식

```java
@Entity
@Access(AccessType.FIELD)
public class Order {

    @EmbeddedId
    private OrderNo number;

    @Column(name = "state")
    @Enumerated(EnumType.STRING)
    private OrderState state;

    ... // cancel(), changeShippingInfo() 등 도메인 기능 구현
    ... // 필요한 get 메서드 제공
}
```

> [!important]
> 객체가 제공할 **기능 중심으로 엔티티를 구현하게끔 유도**하려면
> JPA 매핑 처리를 **프로퍼티 방식이 아닌 필드 방식**으로 선택해서 **불필요한 get/set 메서드를 구현하지 말아야 한다.**

> [!note] 하이버네이트의 기본 동작
> 하이버네이트는 `@Access`로 명시적으로 접근 방식을 지정하지 않으면
> **`@Id`나 `@EmbeddedId`가 어디에 위치했느냐에 따라** 접근 방식을 결정한다.
> - **필드**에 위치하면 → **필드 접근 방식**
> - **get 메서드**에 위치하면 → **메서드 접근 방식**

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "애그리거트 루트 매핑" | **`@Entity`** |
| "밸류 매핑" | **`@Embeddable`** |
| "밸류 타입 프로퍼티 매핑" | **`@Embedded`** |
| "칼럼 이름이 다를 때" | **`@AttributeOverride(s)`** |
| "불변 밸류에 기본 생성자가 필요한 이유" | JPA가 **DB에서 읽어와 객체 생성**할 때 사용 |
| "기본 생성자의 접근 범위" | **`protected`** |
| "필드 접근 방식을 쓰는 이유" | **불필요한 get/set 방지** → 캡슐화·도메인 의도 보존 |
| "`@Access` 미지정 시 결정 기준" | **`@Id`/`@EmbeddedId`의 위치** |
