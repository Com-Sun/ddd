# 애그리거트 로딩 전략 (★★★)

#ddd #repository #jpa-mapping #loading-strategy #concept

## Overview Table (한눈에 비교)

| 항목 | 즉시 로딩(EAGER) | 지연 로딩(LAZY) |
|------|------------------|-----------------|
| 로딩 시점 | 루트 조회 시 **모두 함께** | **실제 접근할 때** |
| 장점 | 한 번에 완전한 애그리거트 | **동작 방식이 항상 동일**해서 경우의 수를 따질 필요 없음 |
| 단점 | **카타시안 조인**으로 중복 행 폭증 | 쿼리 실행 **횟수가 많아질 가능성** |
| 컬렉션에 적용 시 | ⚠️ **오히려 문제**가 될 수 있다 |
| 결론 | **무조건 한쪽으로 설정하지 말고 애그리거트에 맞게 선택** |

## 전제 — 애그리거트는 완전해야 한다

> JPA 매핑을 설정할 때 항상 기억해야 할 점은 **애그리거트에 속한 객체가 모두 모여야 완전한 하나가 된다**는 것이다.

```java
// product는 완전한 하나여야 한다.
Product product = productRepository.findById(id);
```

조회 시점에서 애그리거트를 완전한 상태로 만들려면 **연관 매핑의 조회 방식을 즉시 로딩으로 설정**하면 된다.

```java
// @Entity 컬렉션에 대한 즉시 로딩 설정
@OneToMany(cascade = {CascadeType.PERSIST, CascadeType.REMOVE},
           orphanRemoval = true, fetch = FetchType.EAGER)
@JoinColumn(name = "product_id")
@OrderColumn(name = "list_idx")
private List<Image> images = new ArrayList<>();

// @Embeddable 컬렉션에 대한 즉시 로딩 설정
@ElementCollection(fetch = FetchType.EAGER)
@CollectionTable(name = "order_line",
                 joinColumns = @JoinColumn(name = "order_number"))
@OrderColumn(name = "line_idx")
private List<OrderLine> orderLines;
```

## ★ 즉시 로딩의 함정 — 카타시안 조인

> [!danger] 컬렉션에 EAGER를 설정하면 오히려 문제가 된다
> `Product`가 `@Entity`로 구현한 `Image` 목록과 `@Embeddable`로 구현한 `Option` 목록을 **둘 다** 갖고 있다고 하자.

```sql
select
    p.product_id, ..., img.product_id, img.image_id, img.list_idx, img.image_type,
    opt.product_id, opt.option_title, opt.option_value, opt.list_idx
from
    product p
    left outer join image img on p.product_id = img.product_id
    left outer join product_option opt on p.product_id = opt.product_id
where p.product_id = ?
```

> [!warning] 카타시안(Cartesian) 조인
> 이 쿼리는 **카타시안 조인**을 사용하고, 이는 **쿼리 결과에 중복을 발생**시킨다.

**중복 계산**

| 이미지 수 | 옵션 수 | 결과 행 수 | 실제 필요한 행 수 |
|-----------|---------|------------|-------------------|
| 2 | 2 | **4행** (product 4번, image·option 각 2번 중복) | 5 (1+2+2) |
| **20** | **15** | **300행** | **36** (1+20+15) |

```
   실제 필요 행: 36
   실제 조회 행: 300     ← 과도하게 많다
```

> [!note]
> 물론 하이버네이트가 **중복된 데이터를 알맞게 제거해서** 메모리에는 1개 `Product`, 20개 `Image`, 15개 `Option` 객체로 변환해 준다.
> **하지만 애그리거트가 커지면 문제가 된다.**
>
> 보통 조회 성능 때문에 즉시 로딩을 사용하지만, **이렇게 조회되는 데이터 개수가 많아지면
> 성능(실행 빈도, 트래픽, 지연 로딩 시 실행 속도 등)을 검토해 봐야 한다.**

## ★ 애그리거트가 완전해야 하는 두 가지 이유

> [!important] (p.164)
> 애그리거트는 개념적으로 하나여야 한다. **하지만 루트 엔티티를 로딩하는 시점에 애그리거트에 속한 객체를 모두 로딩해야 하는 것은 아니다.**
>
> | 이유 | 설명 | 더 나은 해법 |
> |------|------|--------------|
> | ① | **상태를 변경하는 기능**을 실행할 때 애그리거트 상태가 완전해야 하기 때문 | 트랜잭션 범위 내 **지연 로딩**으로 충분 |
> | ② | **표현 영역에서 애그리거트의 상태 정보를 보여줄 때** 필요하기 때문 | **별도의 조회 전용 기능과 모델**이 더 유리 |
>
> 두 번째는 조회 전용 기능이 유리하므로, **완전한 로딩 문제는 결국 ①상태 변경과 더 관련이 있다.**

### 지연 로딩으로 충분한 이유

**JPA는 트랜잭션 범위 내에서 지연 로딩을 허용**하기 때문에, 실제 상태를 변경하는 시점에 필요한 구성요소만 로딩해도 문제가 되지 않는다.

```java
@Transactional
public void removeOptions(ProductId id, int optIdxToBeDeleted) {
    // Product를 로딩. 컬렉션은 지연 로딩으로 설정했다면, Option은 로딩하지 않음
    Product product = productRepository.findById(id);
    // 트랜잭션 범위이므로 지연 로딩으로 설정한 연관 로딩 가능
    product.removeOption(optIdxToBeDeleted);
}
```

```java
@Entity
public class Product {

    @ElementCollection(fetch = FetchType.LAZY)
    @CollectionTable(name = "product_option",
                     joinColumns = @JoinColumn(name = "product_id"))
    @OrderColumn(name = "list_idx")
    private List<Option> options = new ArrayList<>();

    public void removeOption(int optIdx) {
        // 실제 컬렉션에 접근할 때 로딩
        this.options.remove(optIdx);
    }
}
```

> [!tip] 결정적 근거
> 일반적인 애플리케이션은 **상태 변경 기능을 실행하는 빈도보다 조회 기능을 실행하는 빈도가 훨씬 높다.**
> 따라서 **상태 변경을 위해 지연 로딩을 사용할 때 발생하는 추가 쿼리로 인한 성능 저하는 크지 않다.**

## 결론 — 무조건 하나로 정하지 마라

> [!important]
> - **애그리거트 내의 모든 연관을 즉시 로딩으로 설정할 필요는 없다.**
> - **지연 로딩은 동작 방식이 항상 동일**하기 때문에 즉시 로딩처럼 **경우의 수를 따질 필요가 없는 장점**이 있다.
>   (즉시 로딩 설정은 `@Entity`나 `@Embeddable`에 대해 **다르게 동작**하고, **JPA 프로바이더에 따라 구현 방식이 다를 수도** 있다.)
> - 물론 지연 로딩은 즉시 로딩보다 **쿼리 실행 횟수가 많아질 가능성**이 더 높다.
> - **따라서 무조건 즉시 로딩이나 지연 로딩으로만 설정하기보다는 애그리거트에 맞게 선택해야 한다.**

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "컬렉션 두 개에 EAGER 설정 시" | **카타시안 조인** → 중복 행 폭증 |
| "이미지 20 + 옵션 15일 때 결과 행" | **300행** (실제 필요 36행) |
| "애그리거트가 완전해야 하는 두 이유" | **① 상태 변경 시 ② 표현 영역 조회 시** |
| "②는 어떻게 푸는 게 유리한가" | **별도 조회 전용 기능/모델** |
| "그럼 완전 로딩은 무엇과 관련?" | **상태 변경** |
| "지연 로딩으로 충분한 이유" | JPA가 **트랜잭션 범위 내 지연 로딩 허용** |
| "지연 로딩의 성능 저하가 작은 이유" | **조회 빈도 ≫ 상태 변경 빈도** |
| "지연 로딩의 장점" | **동작 방식이 항상 동일** (경우의 수 없음) |
| "최종 권장" | **애그리거트에 맞게 즉시/지연을 선택** |
