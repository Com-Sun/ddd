# 여러 애그리거트가 필요한 기능 (★★★)

#ddd #domain-service #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 상황 | **한 애그리거트로 기능을 구현할 수 없을 때** |
| 대표 예 | **결제 금액 계산 로직** |
| 관여 애그리거트 | **상품 / 주문 / 할인 쿠폰 / 회원** — 4개 |
| ❌ 안티패턴 | 한 애그리거트(주문)에 **억지로 넣기** |
| 부작용 4가지 | 코드가 **길어짐** / **외부 의존 증가** / 코드 복잡·**수정 어려움** / **도메인 개념이 숨어 명시적으로 드러나지 않음** |
| ⭕ 해법 | **도메인 기능을 별도 서비스(도메인 서비스)로 구현** |

## 결제 금액 계산에 필요한 것들

| 애그리거트 | 필요한 정보 |
|-----------|-------------|
| **상품** | 구매하는 상품의 **가격**. 상품에 따라 **배송비**가 추가되기도 한다 |
| **주문** | 상품별 **구매 개수** |
| **할인 쿠폰** | 쿠폰별 **할인 금액이나 비율**. 쿠폰을 **조건에 따라 중복 적용**하거나 **우선순위**를 정할 수 있으면 로직이 복잡해진다 |
| **회원** | **회원 등급**에 따라 추가 할인 가능 |

## 누구의 책임인가?

```
   총 주문 금액 계산     →  주문 애그리거트가 할 수 있다  ⭕
   실제 결제 금액 계산   →  ???
        │
        ├─ 할인 금액은 누가?
        │     └─ "할인 쿠폰이 갖고 있으니 할인 쿠폰 애그리거트?"
        │           ▼
        │        ❌ 쿠폰을 두 개 이상 적용할 수 있다면
        │           단일 할인 쿠폰 애그리거트로는 계산 불가
        ▼
   어느 애그리거트도 온전히 책임질 수 없다
```

## ★ 무엇이 문제인가 — 변경 시나리오

> [!danger] 결정적 반례 (p.235)
> **특별 감사 세일로 전 품목에 대해 한 달간 2% 추가 할인**을 하기로 했다고 해보자.
> 이 할인 정책은 **주문 애그리거트가 갖고 있는 구성요소와는 관련이 없음에도 불구하고**,
> **결제 금액 계산 책임이 주문 애그리거트에 있다는 이유로 주문 애그리거트의 코드를 수정해야 한다.**

> [!important] 억지로 구현하면 생기는 네 가지 문제
> 한 애그리거트에 넣기 애매한 도메인 기능을 억지로 특정 애그리거트에 구현하면:
> ① 애그리거트가 **자신의 책임 범위를 넘어서는 기능**을 구현하므로 **코드가 길어진다**
> ② **외부에 대한 의존이 높아진다**
> ③ 코드를 복잡하게 만들어 **수정을 어렵게** 만든다
> ④ **애그리거트의 범위를 넘어서는 도메인 개념이 애그리거트에 숨어들어 명시적으로 드러나지 않게 된다**

```
   할인 정책 변경
        ▼
   주문 애그리거트 코드 수정  ← 관련 없는데도!
        ▼
   변경 파급 범위가 잘못 설계됨
```

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "한 애그리거트로 구현할 수 없는 대표 예" | **결제 금액 계산** |
| "결제 금액 계산에 필요한 애그리거트" | **상품 / 주문 / 할인 쿠폰 / 회원** |
| "할인 쿠폰 애그리거트가 계산하면 안 되는 이유" | **쿠폰을 두 개 이상 적용**하면 단일 애그리거트로 불가 |
| "억지로 넣었을 때의 결정적 반례" | **전 품목 2% 추가 할인** → 관련 없는데 주문 코드 수정 |
