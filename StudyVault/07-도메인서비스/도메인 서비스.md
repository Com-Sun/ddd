## 도메인 서비스를 사용하는 두 상황

| 상황 | 설명 |
|------|------|
| **① 계산 로직** | 여러 애그리거트가 필요한 계산 로직이나, **한 애그리거트에 넣기에는 다소 복잡한 계산 로직** |
| **② 외부 시스템 연동** | 구현하기 위해 **타 시스템을 사용해야 하는 도메인 로직** → [[외부 시스템 연동과 도메인 서비스]] |

## ★ 상태 없이 로직만 구현한다

> [!important] 핵심 구분
> 도메인 영역의 **애그리거트나 밸류와 같은 구성요소와 도메인 서비스를 비교할 때 다른 점은,
> 도메인 서비스는 상태 없이 로직만 구현한다는 점**이다.
> **도메인 서비스를 구현하는 데 필요한 상태는 다른 방법으로 전달받는다.**

| 구성요소 | 상태 | 로직 |
|----------|------|------|
| 엔티티 / 밸류 | ⭕ 갖는다 | ⭕ 갖는다 |
| **도메인 서비스** | ❌ **없다** | ⭕ 갖는다 |

## §7.2.1 계산 로직과 도메인 서비스

> 할인 금액 규칙 계산처럼 한 애그리거트에 넣기 애매한 도메인 개념은,
> **애그리거트에 억지로 넣기보다 도메인 서비스를 이용해서 도메인 개념을 명시적으로 드러내면 된다.**

```java
public class DiscountCalculationService {

    public Money calculateDiscountAmounts(
            List<OrderLine> orderLines,
            List<Coupon> coupons,
            MemberGrade grade) {

        Money couponDiscount = coupons.stream()
                .map(coupon -> calculateDiscount(coupon))
                .reduce(Money(0), (v1, v2) -> v1.add(v2));

        Money membershipDiscount =
                calculateDiscount(orderer.getMember().getGrade());

        return couponDiscount.add(membershipDiscount);
    }

    private Money calculateDiscount(Coupon coupon) { ... }

    private Money calculateDiscount(MemberGrade grade) { ... }
}
```

> [!tip] 이름이 곧 도메인 개념이다
> 도메인 서비스는 **도메인의 의미가 드러나는 용어를 타입과 메서드 이름으로 갖는다.**
> `DiscountCalculationService.calculateDiscountAmounts(...)`

## 전달 방향 A — 애그리거트에 도메인 서비스를 전달

```java
public class Order {

    public void calculateAmounts(
            DiscountCalculationService disCalSvc, MemberGrade grade) {
        Money totalAmounts = getTotalAmounts();
        Money discountAmounts =
                disCalSvc.calculateDiscountAmounts(this.orderLines, this.coupons, grade);
        this.paymentAmounts = totalAmounts.minus(discountAmounts);
    }
}
```

> [!important]
> **애그리거트 객체에 도메인 서비스를 전달하는 것은 응용 서비스 책임이다.**

```java
public class OrderService {

    private DiscountCalculationService discountCalculationService;

    @Transactional
    public OrderNo placeOrder(OrderRequest orderRequest) {
        OrderNo orderNo = orderRepository.nextId();
        Order order = createOrder(orderNo, orderRequest);
        orderRepository.save(order);
        return orderNo;
    }

    private Order createOrder(OrderNo orderNo, OrderRequest orderReq) {
        Member member = findMember(orderReq.getOrdererId());
        Order order = new Order(orderNo, orderReq.getOrderLines(),
                orderReq.getCoupons(), createOrderer(member),
                orderReq.getShippingInfo());
        order.calculateAmounts(this.discountCalculationService, member.getGrade());
        return order;
    }
}
```

## ★ 안티패턴 — 도메인 서비스를 애그리거트에 주입하지 마라

```java
// ❌ 나쁜 예
public class Order {
    @Autowired
    private DiscountCalculationService discountCalculationService;
    ...
}
```

> [!danger] 왜 나쁜가 (p.239~240)
> 스프링 DI와 AOP를 공부하다 보면 **프레임워크가 제공하는 의존 주입 기능으로 도메인 서비스를 애그리거트에 주입해야
> 기술적으로 나은 것 같은 착각**을 하게 된다. **하지만 좋은 방법이 아니다.**
>
> | 이유 | 설명 |
> |------|------|
> | **① 데이터가 아니다** | 도메인 객체는 **필드(프로퍼티)로 구성된 데이터와 메서드**로 개념적으로 하나를 표현한다. **모델의 데이터를 담는 필드는 모델에서 중요한 구성요소**인데, `discountCalculationService` 필드는 **데이터 자체와는 관련이 없다.** |
> | **② 저장 대상이 아니다** | `Order` 객체를 DB에 보관할 때 다른 필드와는 달리 **저장 대상도 아니다.** |
> | **③ 일부 기능만 필요로 한다** | `Order`가 제공하는 **모든 기능에서 도메인 서비스를 필요로 하는 것도 아니다.** 일부 기능을 위해 굳이 의존 주입할 이유가 없다 |

## 전달 방향 B — 도메인 서비스에 애그리거트를 전달

> 애그리거트 메서드를 실행할 때 도메인 서비스를 인자로 전달하지 않고, **반대로 도메인 서비스의 기능을 실행할 때 애그리거트를 전달**하기도 한다.
> 대표적인 예가 **계좌 이체 기능**이다.

```java
public class TransferService {

    public void transfer(Account fromAcc, Account toAcc, Money amounts) {
        fromAcc.withdraw(amounts);
        toAcc.credit(amounts);
    }
}
```

> 응용 서비스는 두 `Account` 애그리거트를 구한 뒤 `TransferService`를 이용해서 계좌 이체 도메인 기능을 실행한다.

> [!warning] 도메인 서비스는 응용 로직을 수행하지 않는다
> **도메인 서비스는 도메인 로직을 수행하지 응용 로직을 수행하지 않는다.**
> **트랜잭션 처리와 같은 로직은 응용 로직이므로 도메인 서비스가 아닌 응용 서비스에서 처리해야 한다.**

## ★ 응용 서비스인가 도메인 서비스인가 — 판별법

> [!tip] 감을 잡기 어려울 때 (p.240)
> 해당 로직이 **애그리거트의 상태를 변경하거나 애그리거트의 상태 값을 계산하는지** 검사해 보면 된다.

| 로직 | 하는 일 | 판정 |
|------|---------|------|
| **계좌 이체** | 계좌 애그리거트의 **상태를 변경** | 도메인 로직 → **도메인 서비스** |
| **결제 금액 계산** | 주문 애그리거트의 **주문 금액을 계산** | 도메인 로직 → **도메인 서비스** |
| 트랜잭션 처리 | 애그리거트 상태와 무관 | 응용 로직 → **응용 서비스** |

```
   애그리거트의 상태를 변경하는가?
   또는 애그리거트의 상태 값을 계산하는가?
        │ 예                          │ 아니오
        ▼                             ▼
   도메인 로직                     응용 로직
        │                             ▼
        ├─ 한 애그리거트에 적합? ──▶ 애그리거트에 구현
        └─ 넣기에 적합하지 않음 ──▶ 도메인 서비스
```

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "도메인 서비스가 다루는 것" | **도메인 로직** (응용 서비스는 응용 로직) |
| "애그리거트·밸류와의 결정적 차이" | **상태 없이 로직만 구현** |
| "필요한 상태는?" | **파라미터로 전달**받는다 |
| "도메인 서비스를 쓰는 두 상황" | **계산 로직 / 외부 시스템 연동** |
| "애그리거트에 도메인 서비스를 전달하는 주체" | **응용 서비스** |
| "도메인 서비스를 애그리거트에 `@Autowired`?" | ❌ 데이터가 아니고, 저장 대상도 아니며, 일부 기능만 사용 |
| "계좌 이체는 어느 방향?" | **도메인 서비스에 애그리거트를 전달** |
| "트랜잭션 처리는 어디서?" | **응용 서비스** (응용 로직) |
| "응용/도메인 서비스 판별법" | **애그리거트의 상태를 변경하거나 상태 값을 계산하는가** |
