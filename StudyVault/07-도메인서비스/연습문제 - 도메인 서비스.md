## Question 1 - 결제 금액 계산의 난점 [recall]
> 실제 결제 금액 계산에 필요한 네 개의 애그리거트와 각각 제공하는 정보는?

> [!answer]- 정답 보기
> - **상품**: 구매하는 상품의 **가격**, 상품에 따라 **배송비**
> - **주문**: 상품별 **구매 개수**
> - **할인 쿠폰**: 쿠폰별 **할인 금액이나 비율** (중복 적용/우선순위가 있으면 더 복잡)
> - **회원**: **회원 등급**에 따른 추가 할인

## Question 2 - 억지 구현의 문제 [recall]
> 한 애그리거트에 넣기 애매한 도메인 기능을 억지로 특정 애그리거트에 구현하면 생기는 네 가지 문제는?

> [!answer]- 정답 보기
> ① 애그리거트가 **자신의 책임 범위를 넘어서는 기능**을 구현하므로 **코드가 길어진다**
> ② **외부에 대한 의존이 높아진다**
> ③ 코드가 복잡해져 **수정이 어려워진다**
> ④ **애그리거트의 범위를 넘어서는 도메인 개념이 애그리거트에 숨어들어 명시적으로 드러나지 않는다**

## Question 3 - 도메인 서비스의 특징 [recall]
> 도메인 서비스가 애그리거트·밸류와 결정적으로 다른 점은 무엇이며, 필요한 상태는 어떻게 확보하는가?

> [!answer]- 정답 보기
> **상태 없이 로직만 구현한다**는 점이다. 엔티티·밸류는 상태와 로직을 모두 갖지만 도메인 서비스는 **상태가 없다.**
> 구현에 필요한 상태는 **다른 방법(주로 메서드 파라미터)으로 전달**받는다.

## Question 4 - 사용 상황 [recall]
> 도메인 서비스를 사용하는 두 가지 상황은?

> [!answer]- 정답 보기
> ① **계산 로직** — 여러 애그리거트가 필요한 계산 로직이나, 한 애그리거트에 넣기에는 다소 복잡한 계산 로직
> ② **외부 시스템 연동이 필요한 도메인 로직** — 구현하기 위해 타 시스템을 사용해야 하는 도메인 로직

## Question 5 - 패키지 위치와 인터페이스 [recall]
> 도메인 서비스는 어느 패키지에 두며, 인터페이스로 분리해야 하는 조건은?

> [!answer]- 정답 보기
> **다른 도메인 구성요소와 동일한 패키지**(애그리거트와 같은 패키지)에 둔다. 개수가 많거나 구분하고 싶으면 `domain.model`, `domain.service` 등 하위 패키지로 나눠도 된다.
> **인터페이스 조건**: **도메인 서비스의 로직이 고정되어 있지 않은 경우**, 특히 **외부 시스템이나 별도 엔진(룰 엔진)** 을 이용해 구현할 때. 이를 통해 **도메인이 특정 구현에 종속되는 것을 방지**하고 **테스트가 쉬워진다.**

## Question 6 - 변경 시나리오 판단 [application]
> 결제 금액 계산을 `Order` 애그리거트에 구현해 두었다. "전 품목 한 달간 2% 추가 할인" 정책이 추가될 때 무엇이 문제가 되는가?

> [!answer]- 정답 보기
> 이 할인 정책은 **주문 애그리거트가 갖고 있는 구성요소와는 아무 관련이 없다.** 그럼에도 **결제 금액 계산 책임이 주문 애그리거트에 있다는 이유만으로 주문 애그리거트의 코드를 수정**해야 한다.
> 즉 **변경의 파급 범위가 잘못 설계**되었다는 신호이며, 이 로직을 **도메인 서비스로 분리**해야 한다는 근거가 된다.

## Question 7 - 도메인 서비스 전달 [application]
> `Order` 애그리거트가 결제 금액을 계산할 때 `DiscountCalculationService`를 사용해야 한다. 코드를 작성하고, 도메인 서비스를 전달하는 주체가 누구인지 답하라.

> [!answer]- 정답 보기
> ```java
> public class Order {
>     public void calculateAmounts(
>             DiscountCalculationService disCalSvc, MemberGrade grade) {
>         Money totalAmounts = getTotalAmounts();
>         Money discountAmounts =
>                 disCalSvc.calculateDiscountAmounts(this.orderLines, this.coupons, grade);
>         this.paymentAmounts = totalAmounts.minus(discountAmounts);
>     }
> }
> ```
> **애그리거트 객체에 도메인 서비스를 전달하는 것은 응용 서비스의 책임**이다.
> ```java
> order.calculateAmounts(this.discountCalculationService, member.getGrade());
> ```

## Question 8 - 외부 연동 인터페이스 설계 [application]
> 설문 조사 생성 시 사용자 역할 관리 시스템과 연동해 권한을 확인해야 한다. 도메인 서비스 인터페이스를 설계하고, 인터페이스/구현의 위치를 답하라.

> [!answer]- 정답 보기
> ```java
> // 도메인 영역
> public interface SurveyPermissionChecker {
>     boolean hasUserCreationPermission(String userId);
> }
> ```
> ```java
> public class CreateSurveyService {
>     private SurveyPermissionChecker permissionChecker;
>
>     public Long createSurvey(CreateSurveyRequest req) {
>         validate(req);
>         if (!permissionChecker.hasUserCreationPermission(req.getRequestorId())) {
>             throw new NoPermissionException();
>         }
>         ...
>     }
> }
> ```
> **위치**: 인터페이스는 **도메인 영역**, 연동을 구현한 클래스는 **인프라스트럭처 영역**.
> **이름 짓기가 핵심**이다. `RoleSystemClient`가 아니라 `SurveyPermissionChecker`처럼 **도메인 개념을 표현**해야 한다.

## Question 9 - DI 안티패턴 분석 [analysis]
> 아래처럼 도메인 서비스를 애그리거트에 의존 주입하는 것을 세 가지 근거로 반박하라.
> ```java
> public class Order {
>     @Autowired
>     private DiscountCalculationService discountCalculationService;
> }
> ```

> [!answer]- 정답 보기
> ① **데이터가 아니다** — 도메인 객체는 **필드로 구성된 데이터와 메서드**로 개념적으로 하나를 표현하며 **모델의 데이터를 담는 필드는 중요한 구성요소**다. 그런데 `discountCalculationService` 필드는 **데이터 자체와는 관련이 없다.**
> ② **저장 대상이 아니다** — `Order`를 DB에 보관할 때 다른 필드와 달리 **저장 대상이 아니다.**
> ③ **일부 기능만 필요로 한다** — `Order`가 제공하는 **모든 기능이 도메인 서비스를 필요로 하지 않는다.** 일부 기능을 위해 굳이 애그리거트 전체에 의존 주입할 이유가 없다.
> **대안**: 도메인 서비스를 **필요한 메서드의 파라미터로 전달**하고, 전달은 **응용 서비스가 담당**한다.

## Question 10 - 응용 서비스 vs 도메인 서비스 판별 [analysis]
> 아래 세 로직이 응용 서비스인지 도메인 서비스인지 판별하고, 사용한 판단 기준을 설명하라.
> (a) 계좌 이체 (b) 결제 금액 계산 (c) 트랜잭션 커밋/롤백 처리

> [!answer]- 정답 보기
> **판단 기준**: 해당 로직이 **애그리거트의 상태를 변경하거나 애그리거트의 상태 값을 계산하는지** 검사한다. 그렇다면 도메인 로직이고, 그중 **한 애그리거트에 넣기에 적합하지 않으면 도메인 서비스**로 구현한다.
> - **(a) 계좌 이체** → **도메인 서비스**. 두 `Account` 애그리거트의 **상태를 변경**한다(`withdraw`/`credit`). 한 애그리거트에 넣기 부적합하다. 이 경우는 **도메인 서비스에 애그리거트를 전달**하는 방향이다.
> - **(b) 결제 금액 계산** → **도메인 서비스**. 주문 애그리거트의 **주문 금액을 계산**한다. 여러 애그리거트(상품·주문·쿠폰·회원)가 필요해 한 애그리거트에 넣기 부적합하다.
> - **(c) 트랜잭션 처리** → **응용 서비스**. 애그리거트의 상태를 변경하거나 계산하지 않는 **응용 로직**이다. **도메인 서비스는 도메인 로직을 수행하지 응용 로직을 수행하지 않는다.**

## Question 11 - 도메인 서비스의 이름 [recall]
> 도메인 서비스의 타입과 메서드 이름을 지을 때의 원칙은? 할인 금액 계산을 예로 들어라.

> [!answer]- 정답 보기
> **도메인의 의미가 드러나는 용어를 타입과 메서드 이름으로 갖는다.**
> 예: `DiscountCalculationService.calculateDiscountAmounts(orderLines, coupons, grade)`
> 이렇게 하면 **한 애그리거트에 넣기 애매한 도메인 개념을 명시적으로 드러낼 수 있다.**
> 응용 영역의 서비스가 **응용 로직**을 다룬다면 도메인 서비스는 **도메인 로직**을 다룬다.

## Question 12 - 두 가지 전달 방향 [recall]
> 애그리거트와 도메인 서비스가 협력하는 두 가지 방향을 각각 예를 들어 설명하라.

> [!answer]- 정답 보기
> **방향 A — 애그리거트 메서드에 도메인 서비스를 전달**
> `order.calculateAmounts(disCalSvc, grade)` — 결제 금액 계산. **전달하는 주체는 응용 서비스**다.
> **방향 B — 도메인 서비스에 애그리거트를 전달**
> `transferService.transfer(fromAcc, toAcc, amounts)` — **계좌 이체**. 두 계좌 애그리거트가 관여하며 한쪽은 출금, 한쪽은 입금한다.

## Question 13 - 외부 연동 인터페이스 네이밍 [recall]
> 외부 시스템 연동을 도메인 서비스로 표현할 때 인터페이스 이름은 무엇을 기준으로 지어야 하는가?

> [!answer]- 정답 보기
> **연동이라는 구현 관심사가 아니라 도메인 개념을 표현**하도록 짓는다.
> - ❌ `RoleSystemClient`, `HttpApiCaller`, `callRoleApi()` — 연동 기술 관점
> - ⭕ **`SurveyPermissionChecker`, `hasUserCreationPermission()`** — **"권한을 가졌는가"라는 도메인 개념**
> 인터페이스는 **도메인 영역**에, 연동을 구현한 클래스는 **인프라스트럭처 영역**에 둔다. 이는 2장 DIP의 "**인터페이스는 고수준 모듈 관점에서 도출한다**"는 원칙의 적용이다.
