# 도메인 서비스의 패키지 위치와 인터페이스 (★★)

#ddd #domain-service #module-structure #concept

## Overview Table (한눈에 비교)

| 주제 | 핵심 |
|------|------|
| **패키지 위치** | 다른 도메인 구성요소와 **동일한 패키지** (애그리거트와 같은 패키지) |
| 서비스가 많거나 구분하고 싶다면 | `domain.model`, `domain.service`, `domain.repository` 등 **하위 패키지 분리** |

| 대표 상황 | 도메인 로직을 **외부 시스템이나 별도 엔진**을 이용해 구현할 때 |

| 얻는 것 | ① 도메인 영역이 **특정 구현에 종속되는 것을 방지** ② 도메인 영역에 대한 **테스트가 쉬워진다** |

## §7.2.3 패키지 위치

> **도메인 서비스는 도메인 로직을 표현하므로 도메인 서비스의 위치는 다른 도메인 구성요소와 동일한 패키지에 위치**한다.

```
   com.myshop.order.domain
   ├── Order              (애그리거트 루트)
   ├── OrderLine
   ├── Orderer
   ├── OrderService       ← 도메인 서비스도 같은 패키지
   └── «interface» OrderRepository
```

### 서비스가 많다면 하위 패키지 분리

> 도메인 서비스의 **개수가 많거나** 엔티티나 밸류 같은 다른 구성요소와 **명시적으로 구분하고 싶다면**,
> `domain` 패키지 밑에 하위 패키지를 구분하여 위치시켜도 된다.

```
   com.myshop.order.domain
   ├── model/         (엔티티, 밸류)
   ├── service/       (도메인 서비스)
   └── repository/    (리포지터리)
```

> [!note] 2장과의 연결
> [[모듈 구성]]에서 본 `com.myshop.order.domain.order`(애그리거트) / `com.myshop.order.domain.service`(도메인 서비스) 분리와 같은 맥락이다.

## §7.2.4 인터페이스와 클래스

> [!important] 언제 인터페이스를 만드는가
> **도메인 서비스의 로직이 고정되어 있지 않은 경우** 도메인 서비스 자체를 인터페이스로 구현하고 이를 구현한 클래스를 둘 수도 있다.
> **특히 도메인 로직을 외부 시스템이나 별도 엔진을 이용해서 구현할 때 인터페이스와 클래스를 분리**하게 된다.

예: 할인 금액 계산 로직을 **룰 엔진**을 이용해서 구현한다면

```
   [ 도메인 영역 ]
   Order  ──▶  «interface» DiscountCalculationService
                            △
   ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─╎─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
   [ 인프라스트럭처 영역 ]    ╎
              RuleBasedDiscountCalculationService
```

> [!important] 두 가지 이점
> 도메인 서비스의 구현이 **특정 구현 기술에 의존하거나 외부 시스템의 API를 실행한다면**,
> 도메인 영역의 도메인 서비스는 **인터페이스로 추상화해야 한다.**
>
> 이를 통해:
> ① **도메인 영역이 특정 구현에 종속되는 것을 방지**할 수 있고
> ② **도메인 영역에 대한 테스트가 쉬워진다**

### 판단 기준

| 도메인 서비스의 성격 | 인터페이스 |
|----------------------|-----------|
| 로직이 **고정**되어 있고 순수 자바로 구현 | **불필요** (클래스 하나면 충분) |
| 로직이 **고정되어 있지 않음** | **필요** |
| **외부 시스템 / 별도 엔진(룰 엔진)** 사용 | **필요** |
| **특정 구현 기술에 의존** | **필요** |

> [!tip] 응용 서비스와의 대비
> [[응용 서비스의 인터페이스와 클래스]]에서는 "**명확하게 필요하기 전까지 인터페이스를 만들지 않는 게 좋다**"고 했다.
> 도메인 서비스는 **외부 시스템·엔진 의존이라는 명확한 이유가 있을 때** 인터페이스를 만든다.
> 즉 두 결론은 **"이유가 있을 때만 만든다"** 는 같은 원칙의 적용이다.

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "도메인 서비스의 패키지 위치" | **다른 도메인 구성요소와 동일한 패키지** |
| "서비스가 많으면?" | `domain.model` / `domain.service` 등 **하위 패키지 분리** |
| "인터페이스가 필요한 조건" | **로직이 고정되어 있지 않을 때** |
| "대표 상황" | **외부 시스템·별도 엔진(룰 엔진)** 사용 |
| "인터페이스/구현의 위치" | **도메인 영역 / 인프라스트럭처 영역** |
| "추상화로 얻는 두 이점" | **특정 구현 종속 방지 + 테스트 용이** |
