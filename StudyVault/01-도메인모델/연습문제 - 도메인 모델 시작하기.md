## Question 1 - 도메인의 정의 [recall]
> 온라인 서점 소프트웨어를 개발할 때, "온라인 서점"은 DDD 용어로 무엇에 해당하는가?

> [!answer]- 정답 보기
> **도메인(domain)** — 소프트웨어로 해결하고자 하는 **문제 영역**이다.
> 한 도메인은 다시 카탈로그·주문·결제·배송·혜택·회원 등 **하위 도메인(subdomain)** 으로 나눌 수 있다.

---

## Question 2 - 하위 도메인 구성 [recall]
> "모든 온라인 쇼핑몰은 카탈로그, 주문, 결제, 배송, 혜택, 회원 하위 도메인을 갖는다." 참인가 거짓인가?

> [!answer]- 정답 보기
> **거짓.** 정해진 하위 도메인 집합은 존재하지 않으며 **비즈니스 상황에 따라 달라진다.**
> 기업 고객 대상 대형 장비 판매는 카탈로그 + 주문서 접수 정도만 필요하고, 소규모 업체는 엑셀로 정산을 수작업 처리하기도 한다.

---

## Question 3 - 외부 시스템 연동 [recall]
> 쇼핑몰이 배송·결제 기능을 직접 구현하지 않고 외부 업체 시스템을 사용하는 것은 DDD 관점에서 잘못된 설계인가?

> [!answer]- 정답 보기
> **아니다. 오히려 일반적이다.** 특정 도메인을 위한 소프트웨어라고 해서 도메인의 **모든 기능을 직접 구현하지는 않는다.**
> 배송 도메인의 일부만 자체 구현하고 나머지는 외부 물류 업체 시스템을, 결제는 결제 대행업체(PG)를 이용하는 경우가 많다.

## Question 4 - GIGO [recall]
> 요구사항 맥락에서 "Garbage In, Garbage Out"이 뜻하는 바는?

> [!answer]- 정답 보기
> **잘못된 요구사항이 들어가면 잘못된 제품이 나온다**는 의미다.
> 이를 줄이는 가장 간단한 방법은 개발자와 도메인 전문가가 **직접 대화**하는 것이다. 전달자가 많을수록 정보가 왜곡되고 손실된다.

---

## Question 5 - 개념 모델과 구현 모델 [recall]
> 개념 모델과 구현 모델의 차이는 무엇이며, 둘의 바람직한 관계는?

> [!answer]- 정답 보기
> - **개념 모델**: 순수하게 문제를 분석한 결과물. DB·트랜잭션 성능·구현 기술을 **고려하지 않아** 그대로 코드로 쓸 수 없다.
> - **구현 모델**: 구현 기술에 맞게 전환한 모델.
> - 관계: **구현 모델이 개념 모델을 최대한 따르도록** 한다.

## Question 6 - 아키텍처 네 영역 [recall]
> "업무 로직을 직접 구현하지 않으며 도메인 계층을 조합해서 기능을 실행한다"는 어느 영역인가?

> [!answer]- 정답 보기
> **응용(Application) 영역.**
> 나머지: 표현(UI)=요청 처리·정보 표시(사용자에는 외부 시스템도 포함), 도메인=도메인 규칙 구현, 인프라스트럭처=DB·메시징 등 외부 연동.

## Question 7 - 엔티티의 특징 [recall]
> 엔티티의 가장 큰 특징과, 두 엔티티가 같은지 판단하는 기준은?

> [!answer]- 정답 보기
> 가장 큰 특징은 **식별자를 가진다**는 것이다. 식별자는 엔티티마다 고유하며 생성부터 삭제까지 **바뀌지 않는다.**
> 따라서 **두 엔티티 객체의 식별자가 같으면 두 엔티티는 같다**고 판단하며, `equals()`/`hashCode()`도 식별자를 기준으로 구현한다.

## Question 8 - 식별자 생성 방식 [recall]
> 엔티티 식별자를 생성하는 대표적인 네 가지 방식을 나열하라.

> [!answer]- 정답 보기
> ① **특정 규칙에 따라 생성**(주문번호·운송장번호) ② **UUID/Nano ID 같은 고유 식별자 생성기** ③ **값을 직접 입력**(회원 아이디·이메일) ④ **일련번호**(DB 시퀀스·자동 증가 칼럼)

---

## Question 9 - 밸류의 동등성 [recall]
> 밸류 객체 두 개를 비교할 때는 무엇을 비교하는가? 엔티티와 어떻게 다른가?

> [!answer]- 정답 보기
> 밸류는 **모든 속성이 같은지** 비교한다. 반면 엔티티는 **식별자 하나만** 비교한다.

---

## Question 10 - 자동 증가 칼럼 [application]
> 식별자를 MySQL 자동 증가 칼럼으로 생성하는 경우, 엔티티 객체를 생성하는 시점에 식별자를 생성자로 전달할 수 있는가? 그렇다면/아니라면 식별자는 언제 확보되는가?

> [!answer]- 정답 보기
> **전달할 수 없다.** 자동 증가 칼럼은 **DB 테이블에 데이터를 삽입해야 비로소 값을 알 수 있기** 때문이다.
> 따라서 `repository.save(article)` 이후에 `article.getId()`로 참조하며, **리포지터리가 DB가 생성한 식별자를 구해 엔티티 객체에 반영**한다.

## Question 11 - 불변 밸류의 필요성 [application]
> 아래 코드에서 `Money`가 `setValue()`를 제공한다면 어떤 문제가 생기는가?
> ```java
> Money price = new Money(1000);
> OrderLine line = new OrderLine(product, price, 2);  // amounts = 2000
> price.setValue(2000);
> ```

> [!answer]- 정답 보기
> `line`의 `price`는 2000으로 바뀌지만 **`amounts`는 2000 그대로 남아 데이터가 깨진다**(참조 투명성 문제, 그림 1.10).
> 해법은 `Money`를 **불변**으로 만드는 것이며, 불변이 아니라면 생성자에서 `this.price = new Money(price.getValue());` 처럼 **방어적 복사**를 해야 한다.

## Question 12 - set 메서드 제거 [application]
> 다음 코드의 문제 두 가지를 지적하고 고쳐라.
> ```java
> Order order = new Order();
> order.setOrderLine(lines);
> order.setShippingInfo(shippingInfo);
> order.setState(OrderState.PREPARING);
> ```

> [!answer]- 정답 보기
> ① **도메인 의도 상실** — `setState()`는 "결제 완료"라는 도메인 지식을 표현하지 못한다(`completePayment()`로).
> ② **온전하지 않은 상태** — `orderer`가 `null`인 채로 상품 준비 중이 된다.
> 해법: **생성자에서 필요한 데이터를 모두 받고 검증**한다.
> `Order order = new Order(orderer, lines, shippingInfo, OrderState.PREPARING);`
> (내부 set 메서드는 `private`으로 두어 검증 로직을 모은다.)

## Question 13 - 도메인 용어 반영 [application]
> 아래 코드를 유비쿼터스 언어 관점에서 리팩터링하고, 무엇이 개선되는지 설명하라.
> ```java
> public enum OrderState { STEP1, STEP2, STEP3, STEP4, STEP5, STEP6 }
> private void verifyStep1OrStep2() { ... }
> ```

> [!answer]- 정답 보기
> ```java
> public enum OrderState {
>     PAYMENT_WAITING, PREPARING, SHIPPED, DELIVERING, DELIVERY_COMPLETED;
> }
> private void verifyNotYetShipped() { ... }
> ```
> 개선점: '출고 전'이라는 **도메인 규칙이 이름에 드러나고**, 전문가의 말("출고 전")을 코드로 **번역할 필요가 없어진다.**
> → 가독성↑, 분석 시간↓, 의미 변환 과정에서 생기는 **버그↓**

## Question 14 - 규칙의 배치 결정 [analysis]
> 배송지 변경 가능 여부를 판단하는 로직을 `OrderState`(enum)에 둘 것인가, `Order`(애그리거트 루트)에 둘 것인가? 판단 기준을 설명하고, 어느 쪽이든 공통으로 지켜야 할 원칙은 무엇인가?

> [!answer]- 정답 보기
> **판단 기준**: 판단에 **주문 상태만** 필요하면 `OrderState`에 둘 수 있다. 판단에 **주문 상태 + 다른 정보**가 함께 필요하면 `OrderState`만으로는 불가능하므로 **`Order`에서 구현**해야 한다.
> **공통 원칙**: 어디에 두든 **주문과 관련된 중요 업무 규칙을 주문 도메인 모델(`Order`/`OrderState`) 안에서 구현한다**는 점이 핵심이다. 그래야 규칙이 바뀌거나 확장될 때 **다른 코드에 영향을 덜 주고** 변경을 모델에 반영할 수 있다.

## Question 15 - 하위 도메인별 모델 분리 [analysis]
> 카탈로그 도메인과 배송 도메인의 '상품'을 하나의 클래스 다이어그램에 함께 그리면 왜 문제가 되는가? 근본 원리는 무엇인가?

> [!answer]- 정답 보기
> 카탈로그의 상품은 **가격·상세 내용을 담은 정보**이고, 배송의 상품은 **실제 배송되는 물리적인 상품**이다. 한 다이어그램에 그리면 그 "상품"이 **두 의미를 함께 갖게 되어** 카탈로그 도메인의 상품을 제대로 이해하는 데 방해가 된다.
> **근본 원리**: 모델의 각 구성요소는 **특정 도메인으로 한정할 때 비로소 의미가 완전**해진다. 따라서 **하위 도메인마다 별도의 모델**을 만들어야 한다. (→ 9장 [[바운디드 컨텍스트]]로 이어지는 개념)
