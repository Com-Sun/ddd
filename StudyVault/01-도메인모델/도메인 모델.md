# 도메인 모델 (★★★)

#ddd #domain-model #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 정의 | 특정 도메인을 **개념적으로 표현**한 것 |
| 표현 방식 | 객체 모델, 상태 다이어그램, 그래프, 수학 공식… **무엇이든 가능** |
| 판단 기준 | **도메인을 이해하는 데 도움이 되는가** — 표기법 자체는 중요하지 않다 |
| 객체 모델이 유리한 이유 | **기능과 데이터를 함께** 보여주기 때문 |
| 개념 모델 | 순수하게 문제를 분석한 결과물. 구현 기술 고려 X |
| 구현 모델 | 구현 기술에 맞게 전환한 모델. 개념 모델을 **최대한 따르도록** 만든다 |
| 하위 도메인과 모델 | **하위 도메인마다 별도 모델**을 만들어야 한다 |

## 도메인 모델 = 도메인의 개념적 표현

주문 도메인을 객체 모델로 구성한 예 (그림 1.3 기준):

```
        Orderer                 Order                    OrderLine
  +name : String        +orderNumber : String      +product : Product
  +email : String    1  +totalAmounts : Money   1  +price : int
                     ─▶ +orderer : Orderer      ─▶ +quantity : int
                        +shippingInfo           *  +amounts : int
                        +state : OrderState
                        +changeShippingInfo(ShippingInfo)
                        +cancel()
                                │
                                ▼ 1
                         ShippingInfo
                    +receiverName : String
                    +receiverPhoneNumber : String
                    +address1 : String
                    +address2 : String
                    +zipCode : String
```

이 모델만 봐도 다음을 알 수 있다.

- 주문(`Order`)은 **주문번호**와 **지불할 총금액**을 갖는다.
- 배송정보(`ShippingInfo`)를 **변경**(`changeShippingInfo`)할 수 있다.
- 주문을 **취소**(`cancel`)할 수 있다.

> [!tip] 도메인 모델의 효용
> 여러 관계자들이 **동일한 모습으로 도메인을 이해**하고 **도메인 지식을 공유**하는 데 도움이 된다.

## 표현 방식은 자유다

> [!important] UML만 써야 하는 것이 아니다
> 도메인을 이해하는 데 도움이 된다면 **표현 방식이 무엇인지는 중요하지 않다.**

| 도메인 특성 | 적합한 표현 |
|-------------|-------------|
| 기능과 데이터가 함께 중요 | **객체 모델**(클래스 다이어그램) — 도메인 모델링에 특히 적합 |
| 상태에 따라 행동이 달라짐 | **상태 다이어그램** |
| 관계가 중요 | **그래프** |
| 계산 규칙이 중요 | **수학 공식** |

### 상태 다이어그램으로 표현한 주문 (그림 1.4)

```
   [주문전] ──주문함──▶ [결제 대기 중]
                              │ 결제함
                              ▼
                        [상품 준비 중] ──택배사에서 상품 수령함──▶ [출고/배송]
                              │
     주문 취소함 / 결제 취소    │  주문 취소함
   ◀──────────────────────────┘
              ▼
        [주문 취소됨]
```

이 다이어그램에서 **결제 대기 중 상태에서 주문을 취소하면 결제 취소가 함께 이루어진다**는 규칙을 읽어낼 수 있다.

## 개념 모델 vs 구현 모델

| 구분 | 개념 모델 | 구현 모델 |
|------|-----------|-----------|
| 성격 | 순수하게 **문제를 분석한 결과물** | 구현 가능한 형태로 전환한 모델 |
| 고려사항 | DB·트랜잭션 처리 성능·구현 기술을 **고려하지 않음** | 구현 기술을 반영 |
| 코드화 | 있는 그대로 코드로 쓸 수 **없다** | 코드로 옮길 수 있다 |
| 관계 | — | 구현 모델이 **개념 모델을 최대한 따르도록** 한다 |

- 객체 기반 모델 → **객체 지향 언어**로 개념 모델에 가깝게 구현
- 수학적 모델 → **함수**를 이용해 유사한 구현 모델 작성

> [!warning] 처음부터 완벽한 모델을 만들려 하지 마라
> 프로젝트 초기에 완벽한 개념 모델을 만드는 것은 **불가능하다.**
> - 개발하는 동안 개발자와 관계자들의 도메인 이해도가 계속 높아진다.
> - 초기에 이해한 도메인 지식이 시간이 지나 **완전히 다른 의미로 해석**되는 경우도 있다.
>
> → 처음에는 **전반적인 개요를 알 수 있는 수준**의 개념 모델로 전체 윤곽을 이해하는 데 집중하고,
> 구현하는 과정에서 **점진적으로 구현 모델로 발전**시켜 나간다.

## 하위 도메인과 모델 — 하나의 다이어그램에 담지 마라

같은 용어라도 하위 도메인마다 의미가 달라진다.

| 용어 | 카탈로그 도메인 | 배송 도메인 |
|------|-----------------|-------------|
| **상품** | 상품 가격, 상세 내용을 담고 있는 **정보** | 고객에게 실제 배송되는 **물리적인 상품** |

> [!danger] 여러 하위 도메인을 하나의 다이어그램에 모델링하면 안 된다
> 카탈로그와 배송을 구분하지 않고 한 다이어그램에 표시하면, 그 "상품"은 두 의미를 함께 갖게 되어
> **카탈로그 도메인의 상품을 제대로 이해하는 데 방해**가 된다.
>
> 모델의 각 구성요소는 **특정 도메인으로 한정할 때 비로소 의미가 완전**해지므로,
> **하위 도메인마다 별도의 모델**을 만들어야 한다.

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "도메인을 개념적으로 표현한 것" | **도메인 모델** |
| "도메인 모델은 UML로 그려야 한다?" | **거짓.** 그래프·수학 공식 등 무엇이든 가능 |
| "객체 모델이 도메인 모델링에 적합한 이유" | **기능과 데이터를 함께** 보여주기 때문 |
| "DB·성능을 고려하지 않은 분석 결과물" | **개념 모델** |
| "카탈로그의 상품 ≠ 배송의 상품" | 하위 도메인마다 **별도 모델**을 만들어야 함 |
| "초기에 완벽한 모델을 만들어야 한다?" | **거짓.** 개요 수준 → 점진적 발전 |
