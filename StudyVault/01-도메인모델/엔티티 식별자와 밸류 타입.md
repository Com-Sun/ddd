# 엔티티 식별자와 밸류 타입 (★★)

#ddd #domain-model #entity #value-type #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 문제 | 식별자의 실제 데이터는 대부분 **`String` 같은 문자열** |
| 하지만 | 그 식별자는 도메인에서 **특별한 의미**를 지니는 경우가 많다 |
| 해법 | 식별자를 위한 **밸류 타입**을 만들어 의미가 드러나게 한다 |
| 효과 | **타입 자체로 의미 전달**, 필드 이름이 `id`여도 무슨 id인지 알 수 있다 |

## 문제 — 문자열은 의미를 담지 못한다

엔티티 식별자의 실제 데이터는 문자열인 경우가 많다.

| 식별자 | 실제 타입 |
|--------|-----------|
| 주문번호 | 문자열 |
| 신용카드 번호 | 16개의 숫자로 구성된 문자열 |
| 회원 구분용 이메일 주소 | 문자열 |

> [!important] `Money`와 같은 논리
> `Money`가 단순 숫자가 아닌 도메인의 '**돈**'을 의미하는 것처럼,
> 이런 식별자도 단순한 문자열이 아니라 **도메인에서 특별한 의미를 지닌다.**

## 해법 — 식별자를 위한 밸류 타입

```java
public class Order {
    // OrderNo 타입 자체로 id가 주문번호임을 알 수 있다
    private OrderNo id;

    public OrderNo getId() {
        return id;
    }
}
```

**비교**

| 식별자 타입 | 필드 선언 | 의미 파악 |
|-------------|-----------|-----------|
| `String` | `private String id;` | `id`라는 이름만으로는 **주문번호인지 알 수 없다** → `orderNo`로 이름을 바꿔야 함 |
| `OrderNo` (밸류) | `private OrderNo id;` | **타입 자체로 주문번호임을 알 수 있다** → 필드 이름이 `id`여도 무방 |

> [!tip] 정리
> 식별자를 위해 `OrderNo` 타입을 만들면 **타입 자체로 주문번호라는 것을 알 수 있으므로**,
> 필드 이름이 `id`여도 실제 의미를 찾는 것은 어렵지 않다.

```
   String id            →   "이게 무슨 id지?"  (이름에 의존)
   OrderNo id           →   "주문번호구나"      (타입이 말해준다)
```

> [!warning] 밸류 식별자를 쓸 때 함께 고려할 점
> 식별자를 밸류 타입으로 만들면 JPA 매핑 시 별도 처리가 필요하다.
> 자세한 내용은 [[밸류를 이용한 ID 매핑과 별도 테이블 매핑]] 참고.

> [!note] 실제 예제 코드의 식별자 밸류 3종
> `ddd-start2/`에는 **`OrderNo`, `MemberId`, `ProductId`, `CategoryId`** 가 모두 식별자 밸류로 구현되어 있고,
> 네 개 모두 **동일한 형태**를 갖는다.
> ```java
> @Embeddable
> public class OrderNo implements Serializable {   // ① Serializable
>     @Column(name = "order_number")
>     private String number;
>
>     protected OrderNo() {}                        // ② protected 기본 생성자
>     public OrderNo(String number) { this.number = number; }
>
>     @Override public boolean equals(Object o) { ... }   // ③ equals/hashCode
>     @Override public int hashCode() { ... }
>
>     public static OrderNo of(String number) {     // ④ 정적 팩토리
>         return new OrderNo(number);
>     }
> }
> ```
> **책 p.152의 `is2ndGeneration()`은 실제 레포에 없다** — 식별자에 도메인 로직을 넣을 수 있다는 **설명용 예시**다.
> 대신 실제 코드는 **`static of()` 정적 팩토리**를 공통 관례로 채택했다. → [[코드 대조 검증 보고서]]

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "식별자를 `String` 대신 `OrderNo`로 만드는 이유" | **타입 자체로 의미 전달** |
| "필드 이름이 `id`인데 무슨 id인지 알 수 있나?" | 밸류 식별자 타입이면 **알 수 있다** |
| "식별자도 밸류 타입이 될 수 있나?" | **가능하다.** 도메인 의미를 지닐 때 권장 |
| "`Money`와 `OrderNo`의 공통점" | 단순 타입에 **도메인 의미**를 부여한 밸류 |
