## 아키텍처 네 영역 (표 1.1)

| 영역 | 설명 |
|------|------|
| **사용자 인터페이스(UI) / 표현(Presentation)** | 사용자의 요청을 처리하고 사용자에게 정보를 보여준다. 여기서 사용자는 **사람뿐 아니라 외부 시스템**일 수도 있다 |
| **응용(Application)** | 사용자가 요청한 기능을 실행한다. **업무 로직을 직접 구현하지 않으며** 도메인 계층을 조합해서 기능을 실행한다 |
| **도메인(Domain)** | 시스템이 제공할 **도메인 규칙을 구현**한다 |
| **인프라스트럭처(Infrastructure)** | 데이터베이스나 메시징 시스템 같은 **외부 시스템과의 연동**을 처리한다 |

```
  ┌───────────────────────────┐
  │  표현 (UI / Presentation) │  요청 처리 · 정보 표시
  ├───────────────────────────┤
  │  응용 (Application)       │  기능 실행 (로직 직접 구현 X, 조합만)
  ├───────────────────────────┤
  │  도메인 (Domain)          │  ★ 도메인 규칙 구현 ★
  ├───────────────────────────┤
  │  인프라스트럭처            │  DB · 메시징 · 외부 연동
  └───────────────────────────┘
```

## 규칙을 도메인 모델에 구현한다

### 상태 객체에 규칙을 두는 방식

```java
public class Order {
    private OrderState state;
    private ShippingInfo shippingInfo;

    public void changeShippingInfo(ShippingInfo newShippingInfo) {
        if (!state.isShippingChangeable()) {
            throw new IllegalStateException("can't change shipping in " + state);
        }
        this.shippingInfo = newShippingInfo;
    }
}

public enum OrderState {
    PAYMENT_WAITING {
        public boolean isShippingChangeable() { return true; }
    },
    PREPARING {
        public boolean isShippingChangeable() { return true; }
    },
    SHIPPED, DELIVERING, DELIVERY_COMPLETED;

    public boolean isShippingChangeable() { return false; }
}
```

- `OrderState`가 **배송지를 변경할 수 있는지 판단하는 기능**(`isShippingChangeable()`)을 제공한다.
- 주문 대기 중(`PAYMENT_WAITING`)과 상품 준비 중(`PREPARING`)에서만 `true` → **"이 두 상태에서만 배송지 변경 가능"이라는 도메인 규칙**을 구현한 것.

### 애그리거트 루트로 규칙을 옮기는 방식

큰 틀에서 보면 `OrderState`는 `Order`에 속한 데이터이므로, 판단 코드를 `Order`로 옮길 수도 있다.

```java
public class Order {
    private OrderState state;
    private ShippingInfo shippingInfo;

    public void changeShippingInfo(ShippingInfo newShippingInfo) {
        if (!isShippingChangeable()) {
            throw new IllegalStateException("can't change shipping in " + state);
        }
        this.shippingInfo = newShippingInfo;
    }

    private boolean isShippingChangeable() {
        return state == OrderState.PAYMENT_WAITING ||
               state == OrderState.PREPARING;
    }
}
```

> [!important] 어디에 두든 본질은 같다
> 배송지 변경 가능 여부를 판단하는 기능이 `Order`에 있든 `OrderState`에 있든 중요한 것은,
> **주문과 관련된 중요 업무 규칙을 주문 도메인 모델인 `Order`나 `OrderState`에서 구현한다**는 점이다.
>
> 핵심 규칙을 구현한 코드가 도메인 모델에만 위치하므로, 규칙이 바뀌거나 확장될 때
> **다른 코드에 영향을 덜 주고** 변경 내역을 모델에 반영할 수 있다.

### 어느 쪽을 선택할 것인가

| 상황 | 규칙의 위치 |
|------|-------------|
| 판단에 **주문 상태만** 필요 | `OrderState` (상태 enum)에 둘 수 있다 |
| 판단에 **주문 상태 + 다른 정보**가 함께 필요 | `OrderState`만으로는 판단 불가 → **`Order`에서 구현해야 한다** |

> [!warning] 용어 혼동 주의
> "도메인 모델"이란 용어는 **도메인 자체를 표현하는 개념적인 모델**을 의미하지만,
> **도메인 계층을 구현할 때 사용하는 객체 모델**을 언급할 때에도 똑같이 사용된다.
> 이 책도 도메인 계층의 객체 모델을 표현할 때 "도메인 모델"이라고 부른다.

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "마틴 파울러 / 엔터프라이즈 애플리케이션 아키텍처 패턴" | **도메인 모델 패턴** |
| "업무 로직을 직접 구현하지 않고 조합만 한다" | **응용(Application) 영역** |
| "DB·메시징 등 외부 연동 처리" | **인프라스트럭처 영역** |
| "사용자에는 외부 시스템도 포함된다" | **표현(UI) 영역** |
| "핵심 업무 규칙은 어디에 두는가" | **도메인 모델(엔티티/밸류) 안** |
| "상태 + 다른 정보로 판단해야 한다면" | 상태 enum이 아닌 **애그리거트 루트(Order)** 에 구현 |
| "규칙을 도메인 모델에 두면 좋은 점" | 규칙 변경 시 **다른 코드 영향 최소화** |
