# 도메인 모델 도출 (★★★)

#ddd #domain-model #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 출발점 | **요구사항** (기획서, 유스케이스, 사용자 스토리, 관계자와의 대화) |
| 모델링 기본 작업 | 모델을 구성하는 **핵심 구성요소 · 규칙 · 기능**을 찾는 것 |
| 전제 | 도메인 이해 없이는 코딩을 시작할 수 없다 |
| 도구 | 화이트보드, 종이와 연필, 모델링 툴 — **무엇이든 상관없다** |
| 제약/규칙 구현 위치 | **생성자**와 **도메인 메서드** 안에서 검증한다 |
| 이름 | 도메인 이해가 깊어지면 **메서드 이름도 바뀐다** |

## 요구사항 → 모델 도출 과정

```
 요구사항 수집 ──▶ 핵심 구성요소/규칙/기능 식별 ──▶ 초기 모델 ──▶ 공유·정련 ──▶ 구현
   (기획서·대화)         (명사=요소, 동사=기능)      (일부는 이름만)   (화이트보드/위키)
```

### 1단계 — 기능 도출

> 요구사항
> - 주문할 때 배송지 정보를 반드시 지정해야 한다.
> - 배송지 정보는 받는 사람 이름, 전화번호, 주소로 구성된다.

이 요구사항에서 주문은 **'출고 상태로 변경하기', '배송지 정보 변경하기', '주문 취소하기', '결제 완료하기'** 기능을 제공한다는 것을 알 수 있다. 아직 상세 구현 수준은 아니지만 메서드로 추가할 수 있다.

```java
public class Order {
    public void changeShipped() { ... }
    public void changeShippingInfo(ShippingInfo newShipping) { ... }
    public void cancel() { ... }
    public void completePayment() { ... }
}
```

### 2단계 — 데이터 구성 도출

> 요구사항
> - 각 상품의 구매 가격 합은 **상품 가격 × 구매 개수**이다.

`OrderLine`은 적어도 **주문할 상품, 상품의 가격, 구매 개수**를 포함해야 하고, 각 구매 항목의 **구매 가격**도 제공해야 한다.

```java
public class OrderLine {
    private Product product;
    private int price;
    private int quantity;
    private int amounts;

    public OrderLine(Product product, int price, int quantity) {
        this.product = product;
        this.price = price;
        this.quantity = quantity;
        this.amounts = calculateAmounts();
    }

    private int calculateAmounts() {
        return price * quantity;
    }

    public int getAmounts() { ... }
}
```

### 3단계 — 관계와 제약 도출

> 요구사항
> - 최소 한 종류 이상의 상품을 주문해야 한다.
> - 총 주문 금액은 각 상품의 구매 가격 합을 모두 더한 금액이다.

```java
public class Order {
    private List<OrderLine> orderLines;
    private Money totalAmounts;

    public Order(List<OrderLine> orderLines) {
        setOrderLines(orderLines);
    }

    private void setOrderLines(List<OrderLine> orderLines) {
        verifyAtLeastOneOrMoreOrderLines(orderLines);
        this.orderLines = orderLines;
        calculateTotalAmounts();
    }

    private void verifyAtLeastOneOrMoreOrderLines(List<OrderLine> orderLines) {
        if (orderLines == null || orderLines.isEmpty()) {
            throw new IllegalArgumentException("no OrderLine");
        }
    }

    private void calculateTotalAmounts() {
        int sum = orderLines.stream()
                            .mapToInt(x -> x.getAmounts())
                            .sum();
        this.totalAmounts = new Money(sum);
    }
}
```

> [!tip] 제약은 생성자에서 검사한다
> 생성자에서 호출하는 `setOrderLines()`가 요구사항에 정의한 제약 조건을 검사한다.
> **"최소 한 종류 이상"** → `verifyAtLeastOneOrMoreOrderLines()`
> **"총 주문 금액 = 구매 가격 합"** → `calculateTotalAmounts()`

### 4단계 — 필수 값 제약

> 요구사항
> - 주문할 때 **배송지 정보를 반드시 지정**해야 한다.

```java
public class ShippingInfo {
    private String receiverName;
    private String receiverPhoneNumber;
    private String shippingAddress1;
    private String shippingAddress2;
    private String shippingZipcode;
    // 생성자, getter
}

public class Order {
    private List<OrderLine> orderLines;
    private ShippingInfo shippingInfo;

    public Order(List<OrderLine> orderLines, ShippingInfo shippingInfo) {
        setOrderLines(orderLines);
        setShippingInfo(shippingInfo);
    }

    private void setShippingInfo(ShippingInfo shippingInfo) {
        if (shippingInfo == null) {
            throw new IllegalArgumentException("no ShippingInfo");
        }
        this.shippingInfo = shippingInfo;
    }
}
```

`setShippingInfo()`에서 `null`이면 익셉션을 발생시킴으로써 **"배송지 정보 필수"라는 도메인 규칙을 구현**한다.

### 5단계 — 상태에 따른 제약

> 요구사항
> - 출고를 하면 배송지를 변경할 수 없다.
> - 출고 전에 주문을 취소할 수 있다.
> - 고객이 결제를 완료하기 전에는 상품을 준비하지 않는다.

```java
public enum OrderState {
    PAYMENT_WAITING, PREPARING, SHIPPED, DELIVERING, DELIVERY_COMPLETED,
    CANCELED;
}

public class Order {
    private OrderState state;

    public void changeShippingInfo(ShippingInfo newShippingInfo) {
        verifyNotYetShipped();
        setShippingInfo(newShippingInfo);
    }

    public void cancel() {
        verifyNotYetShipped();
        this.state = OrderState.CANCELED;
    }

    private void verifyNotYetShipped() {
        if (state != OrderState.PAYMENT_WAITING && state != OrderState.PREPARING) {
            throw new IllegalStateException("already shipped");
        }
    }
}
```

> [!important] 이름이 바뀐 이유 — 도메인 이해가 깊어졌기 때문
> 앞선 [[도메인 모델 패턴]]에서는 `isShippingChangeable`이라는 이름으로 제약을 검사했는데 여기서는 `verifyNotYetShipped`로 바뀌었다.
>
> | 시점 | 파악한 도메인 | 이름 |
> |------|---------------|------|
> | 최초 | 배송지 정보 변경에 대한 제약만 파악 | `isShippingChangeable` (배송지 변경 가능 여부) |
> | 이후 | 배송지 변경 **과 주문 취소가 둘 다** '출고 전'에 가능함을 알게 됨 | `verifyNotYetShipped` ('출고 전'이라는 의미 반영) |
>
> 도메인을 더 잘 알게 되면 **이름도 함께 진화**한다.

## 모델은 점진적으로 만들어진다

- 일부는 **구현 수준까지**, 일부는 **이름 정도만** 결정한다.
- 이렇게 만든 모델은 요구사항 정련을 위해 **도메인 전문가나 다른 개발자와 논의하는 과정에서 공유**한다.
- 공유할 때는 **화이트보드나 위키** 같은 도구로 누구나 쉽게 접근할 수 있게 하면 좋다.

## 문서화 (p.041)

> [!note] 왜 문서를 만드는가
> 문서화의 주된 이유는 **지식을 공유하기 위함**이다.

| 관점 | 내용 |
|------|------|
| 코드만으로 충분한가 | 실제 구현은 코드에 있지만, 코드는 **상세한 모든 내용**을 담고 있어 전체 분석에 많은 시간이 든다 |
| 문서가 유리한 것 | 전반적인 **기능 목록, 모듈 구조, 빌드 과정** 등 **상위 수준** 정보 |
| 권장 흐름 | 문서로 전체 구조 파악 → 더 깊게 볼 부분만 **코드로 분석** |
| 코드도 문서다 | **도메인 지식이 잘 묻어나도록** 작성해야 문서로서 의미를 갖는다 |

단순히 코드를 보기 좋게 작성하는 것을 넘어, **도메인 관점에서 코드가 도메인을 잘 표현해야** 비로소 가독성이 높아진다.

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "모델링의 기본 작업은?" | 핵심 **구성요소 · 규칙 · 기능**을 찾는 것 |
| "최소 한 종류 이상 주문" 제약을 어디서 검사? | **생성자**(→ `setOrderLines` → `verifyAtLeastOneOrMoreOrderLines`) |
| "배송지 정보 필수" 구현 방법 | 생성자에서 `null` 검사 후 **익셉션 발생** |
| "출고 전에만 가능" 제약 | `verifyNotYetShipped()` 같은 **상태 검증 메서드** |
| "메서드 이름이 바뀐 이유" | **도메인을 더 잘 알게 되어** 의미를 더 정확히 반영 |
| "문서화를 하는 주된 이유" | **지식 공유** |
| "코드만 있으면 문서는 불필요한가?" | **거짓.** 상위 수준 파악에는 문서가 효율적 |
