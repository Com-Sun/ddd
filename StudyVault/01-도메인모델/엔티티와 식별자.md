# 엔티티와 식별자 (★★★)

#ddd #domain-model #entity #concept

## Overview Table (한눈에 비교)

| 항목 | 엔티티(Entity) |
|------|----------------|
| **가장 큰 특징** | **식별자를 가진다** |
| 식별자의 성질 | 엔티티 객체마다 **고유**하다 |
| 식별자의 생명주기 | 생성 → 속성 변경 → 삭제까지 **바뀌지 않는다** |
| 동등성 판단 | **식별자가 같으면 두 엔티티는 같다** |
| 구현 | `equals()` / `hashCode()`를 **식별자 기준**으로 구현 |

> [!important] 왜 엔티티와 밸류를 구분해야 하는가
> 엔티티와 밸류를 제대로 구분해야 도메인을 올바르게 설계하고 구현할 수 있다.
> 둘의 차이를 명확하게 이해하는 것은 도메인 구현에 있어 매우 중요하다.

## 엔티티의 특징

주문 도메인에서 각 주문은 **주문번호**를 갖고, 주문번호는 주문마다 서로 다르다. 따라서 **주문번호가 주문의 식별자**가 된다.

```
                Order  (엔티티)
        ┌──────────────────────────────┐
        │ -orderNumber : String  ◀── 식별자
        │ -orderLines  : List<OrderLine>
        │ -totalAmounts: Money
        │ -shippingInfo: ShippingInfo
        │ -state       : OrderState
        └──────────────────────────────┘
   배송지 주소가 바뀌어도, 상태가 바뀌어도 → orderNumber는 그대로
```

## 식별자 기준 equals / hashCode

```java
public class Order {
    private String orderNumber;

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;
        if (obj == null) return false;
        if (obj.getClass() != Order.class) return false;
        Order other = (Order) obj;
        if (this.orderNumber == null) return false;
        return this.orderNumber.equals(other.orderNumber);
    }

    @Override
    public int hashCode() {
        final int prime = 31;
        int result = 1;
        result = prime * result
                 + ((orderNumber == null) ? 0 : orderNumber.hashCode());
        return result;
    }
}
```

> [!tip] 핵심
> 엔티티의 식별자는 **바뀌지 않고 고유**하기 때문에, 두 엔티티 객체의 **식별자가 같으면 두 엔티티는 같다**고 판단할 수 있다.

## 엔티티의 식별자 생성 (§1.6.2)

식별자를 생성하는 **시점은 도메인의 특징과 사용하는 기술에 따라 달라진다.** 흔히 다음 네 가지 중 하나를 쓴다.

| 방식 | 설명 | 예 |
|------|------|-----|
| **특정 규칙에 따라 생성** | 도메인·회사마다 규칙이 다름 | 주문번호, 운송장번호, 카드번호 |
| **UUID / Nano ID 등 고유 식별자 생성기** | 마땅한 규칙이 없을 때 | `UUID.randomUUID()` |
| **값을 직접 입력** | 사용자가 입력 | 회원 아이디, 이메일 |
| **일련번호 사용** | DB 시퀀스 / 자동 증가 칼럼 | 게시글 번호 |

### ① 특정 규칙에 따라 생성

예: 주문번호 `20211128317280001` → 앞의 `20211128`은 2021년 11월 28일을 의미.

> [!warning] 날짜·시간 기반 식별자의 함정
> **같은 시간에 동시에 식별자를 생성해도 같은 식별자가 만들어지면 안 된다.**

### ② UUID / Nano ID

```java
UUID uuid = UUID.randomUUID();
// 예: 61572309-0374-4050-9420-21545943f151
String strUuid = uuid.toString();
```

- 다수의 개발 언어가 UUID 생성기를 제공하므로 **마땅한 규칙이 없다면 UUID를 식별자로 사용해도 된다.**
- 자바는 `java.util.UUID` 클래스를 사용한다.
- 최근에는 고유 식별자 생성을 위해 **Nano ID**를 사용하는 곳도 늘고 있다.

### ③ 값을 직접 입력

회원 아이디나 이메일처럼 **사용자가 직접 입력**하는 값.

> [!warning] 중복 방지가 핵심
> 사용자가 직접 입력하는 값이므로 **식별자를 중복해서 입력하지 않도록 사전에 방지**하는 것이 중요하다.

### ④ 일련번호 (자동 증가)

주로 **데이터베이스가 제공하는 자동 증가 기능**을 사용한다.

| DBMS | 방식 |
|------|------|
| 오라클 | **시퀀스**를 이용해 자동 증가 식별자를 구함 |
| MySQL | **자동 증가 칼럼**을 이용 |

> [!danger] 자동 증가 칼럼은 식별자 생성 시점이 다르다
> 자동 증가 칼럼은 **DB 테이블에 데이터를 삽입해야 비로소 값을 알 수 있다.**
> → 테이블에 데이터를 추가하기 **전에는 식별자를 알 수 없다.**
> → 즉 **엔티티 객체를 생성할 때 식별자를 전달할 수 없다.**

**비교: 미리 생성 vs 삽입 후 획득**

```java
// (A) 규칙/UUID — 엔티티를 생성하기 전에 식별자 생성
String orderNumber = orderRepository.generateOrderNumber();
Order order = new Order(orderNumber, ...);
orderRepository.save(order);

// (B) 자동 증가 칼럼 — DB에 저장한 뒤에야 식별자를 알 수 있다
Article article = new Article(author, title, ...);
articleRepository.save(article);        // DB에 저장한 뒤 구한 식별자를 엔티티에 반영
Long savedArticleId = article.getId();  // 저장한 후에야 식별자 참조 가능
```

> [!note] 리포지터리의 역할
> 리포지터리는 도메인 객체를 데이터베이스에 저장할 때 사용하는 구성요소다.
> 자동 증가 칼럼을 사용할 경우 **리포지터리가 DB가 생성한 식별자를 구해서 엔티티 객체에 반영**한다.
> 자세한 내용은 [[JPA 리포지터리 구현]], [[식별자 생성 기능]] 참고.

| "엔티티의 가장 큰 특징" | **식별자를 가진다** |
| "두 엔티티가 같은지 어떻게 판단?" | **식별자가 같으면** 같다 |
| "주소·상태가 바뀌면 식별자도 바뀐다?" | **거짓.** 식별자는 생성~삭제까지 유지 |
