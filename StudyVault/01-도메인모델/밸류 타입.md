# 밸류 타입 (★★★)

#ddd #domain-model #value-type #concept

## Overview Table (한눈에 비교)

| 항목 | 밸류 타입(Value Type) |
|------|------------------------|
| **사용 목적** | **개념적으로 완전한 하나**를 표현할 때 |
| 식별자 | **없다** |
| 동등성 판단 | **모든 속성이 같은지** 비교 |
| 데이터 개수 | 꼭 2개 이상일 필요 없다. **1개여도 의미 명확화를 위해 사용** |
| 변경 방식 | 기존 데이터 변경 ❌ → **변경한 데이터를 갖는 새 객체 생성** ⭕ |
| 권장 형태 | **불변(immutable)** |
| 부가 이점 | 밸류 타입을 위한 **기능(계산 로직)을 추가**할 수 있다 |

## 왜 밸류 타입인가 — 개념적으로 하나

```java
public class ShippingInfo {
    private String receiverName;          // ┐ 개념적으로
    private String receiverPhoneNumber;   // ┘ "받는 사람"
    private String shippingAddress1;      // ┐
    private String shippingAddress2;      // │ 개념적으로 "주소"
    private String shippingZipcode;       // ┘
    // 생성자, getter
}
```

`receiverName`과 `receiverPhoneNumber`는 서로 다른 두 데이터를 담고 있지만, **개념적으로는 하나("받는 사람")** 를 표현한다. 마찬가지로 주소 관련 세 필드도 **"주소"라는 하나의 개념**이다.

### 밸류 타입으로 추출

```java
public class Receiver {
    private String name;
    private String phoneNumber;

    public Receiver(String name, String phoneNumber) {
        this.name = name;
        this.phoneNumber = phoneNumber;
    }

    public String getName() { return name; }
    public String getPhoneNumber() { return phoneNumber; }
}

public class Address {
    private String address1;
    private String address2;
    private String zipCode;

    public Address(String address1, String address2, String zipCode) {
        this.address1 = address1;
        this.address2 = address2;
        this.zipCode = zipCode;
    }
    // getter
}

public class ShippingInfo {
    private Receiver receiver;
    private Address address;
    // 생성자, getter
}
```

> [!tip] 효과
> `receiverName` + `receiverPhoneNumber`는 이름으로 **유추**해야 하지만,
> `Receiver`는 **그 자체로 "받는 사람"을 뜻한다.**
> 배송정보가 **받는 사람과 주소로 구성된다**는 것도 한눈에 보인다.

## 데이터가 하나여도 밸류 타입을 쓴다

`OrderLine`의 `price`와 `amounts`는 `int` 숫자지만 실은 **'돈'을 의미하는 값**이다.

```java
public class Money {
    private int value;

    public Money(int value) {
        this.value = value;
    }

    public int getValue() {
        return this.value;
    }
}
```

**Before / After 비교**

| Before (`int`) | After (`Money`) |
|----------------|-----------------|
| `private int price;` | `private Money price;` |
| `private int amounts;` | `private Money amounts;` |
| 숫자인지 금액인지 이름으로 유추 | **타입 자체가 '돈'임을 표현** |
| `return price * quantity;` | `return price.multiply(quantity);` |
| "정수 타입 연산" | **"돈 계산"이라는 의미로 코드 작성** |

> [!important] 밸류 타입의 또 다른 장점
> 밸류 타입을 위한 **기능을 추가**할 수 있다. `Money`는 돈 계산을 위한 기능을 자연스럽게 갖는다.

```java
public class Money {
    private int value;

    public Money add(Money money) {
        return new Money(this.value + money.value);
    }

    public Money multiply(int multiplier) {
        return new Money(value * multiplier);
    }
}
```

> [!note] 실제 예제 코드에는 `multiply()`만 있다
> `ddd-start2/`의 `common/model/Money.java`에는 **`multiply()`만 존재**하고 `add()`는 없다.
> 총액 합산은 `Order`가 스트림으로 처리하기 때문이다.
> ```java
> // order/command/domain/Order.java
> private void calculateTotalAmounts() {
>     this.totalAmounts = new Money(orderLines.stream()
>             .mapToInt(x -> x.getAmounts().getValue()).sum());
> }
> ```
> 대신 `Money`는 **`equals()`/`hashCode()`/`toString()`을 구현**한다 — 밸류의 **모든 속성 비교** 원칙 그대로다.

## 불변(immutable)으로 만들어라

> [!important] 원칙
> 밸류 객체의 데이터를 변경할 때는 **기존 데이터를 변경하기보다, 변경한 데이터를 갖는 새로운 밸류 객체를 생성**하는 방식을 선호한다.
> `Money`처럼 데이터 변경 기능을 제공하지 않는 타입을 **불변(immutable)** 이라고 한다.

### 왜 불변인가 — 안전한 코드

가장 중요한 이유는 **안전한 코드를 작성할 수 있다**는 데 있다.

```java
Money price = new Money(1000);
OrderLine line = new OrderLine(product, price, 2);
// 만약 price.setValue(2000)로 값을 변경할 수 있다면?
```

**참조 투명성 문제 (그림 1.10)**

```
Money price = new Money(1000);
OrderLine line = new OrderLine(product, price, 2);
                          ──▶ [price=1000, quantity=2, amounts=2000]  ✅

price.setValue(2000);     ──▶ [price=2000, quantity=2, amounts=2000]  ❌
                                 ▲ price는 바뀌었는데 amounts는 그대로!
                                   OrderLine의 데이터가 깨진다
```

`Money`가 `setValue()` 같은 메서드를 제공하면, **`OrderLine`의 `price` 값이 잘못 반영되는 상황**이 발생한다.

### 밸류가 불변이 아니라면 방어적 복사가 필요하다

```java
public class OrderLine {
    private Money price;

    public OrderLine(Product product, Money price, int quantity) {
        this.product = product;
        // Money가 불변 객체가 아니라면,
        // price 파라미터가 변경될 때 발생하는 문제를 방지하기 위해
        // 데이터를 복사한 새로운 객체를 생성해야 한다.
        this.price = new Money(price.getValue());
        this.quantity = quantity;
        this.amounts = calculateAmounts();
    }
}
```

> [!note] 불변 객체의 특징
> 불변 객체는 **참조 투명성**과 **스레드 안전성**을 갖는다.

## 밸류의 동등성 — 모든 속성 비교

```java
public class Receiver {
    private String name;
    private String phoneNumber;

    @Override
    public boolean equals(Object other) {
        if (other == null) return false;
        if (this == other) return true;
        if (!(other instanceof Receiver)) return false;
        Receiver that = (Receiver) other;
        return this.name.equals(that.name) &&
               this.phoneNumber.equals(that.phoneNumber);
    }
}
```

> [!warning] 엔티티와의 결정적 차이
> - 엔티티: **식별자 하나만** 비교
> - 밸류: **모든 속성**을 비교

## 엔티티 vs 밸류 요약

| 기준 | 엔티티 | 밸류 |
|------|--------|------|
| 식별자 | **있음** | 없음 |
| 동등성 | 식별자 비교 | **모든 속성 비교** |
| 가변성 | 상태가 바뀔 수 있음 | **불변 권장** |
| 변경 방법 | 자신의 필드를 변경 | **새 객체 생성으로 교체** |
| 대표 예 | `Order`, `Member`, `Article` | `Money`, `Address`, `Receiver`, `ShippingInfo` |

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "개념적으로 완전한 하나를 표현" | **밸류 타입** |
| "밸류는 데이터가 2개 이상이어야 한다?" | **거짓.** `Money`처럼 1개도 가능 |
| "밸류 객체 값을 바꾸려면?" | **새로운 밸류 객체를 생성**해서 교체 |
| "불변으로 만드는 가장 중요한 이유" | **안전한 코드** (참조 투명성 문제 방지) |
| "밸류의 equals는?" | **모든 속성** 비교 |
| "int price → Money price로 바꾸는 이유" | 의미 명확화 + **계산 기능 추가** 가능 |
| "밸류가 가변이면 반드시 해야 할 것" | **방어적 복사**(새 객체 생성) |
| "불변 객체의 두 가지 특징" | 참조 투명성, **스레드 안전** |
