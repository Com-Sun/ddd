# 도메인 용어와 유비쿼터스 언어 (★★★)

#ddd #domain-model #ubiquitous-language #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 유비쿼터스 언어 | 전문가·관계자·개발자가 만든 **도메인 관련 공통의 언어** |
| 제안자 | **에릭 에반스**(『도메인 주도 설계』) |
| 사용 범위 | **대화, 문서, 도메인 모델, 코드, 테스트 등 모든 곳** |
| 도메인 용어를 안 쓰면 | 코드↔도메인 사이에 **불필요한 해석 과정**이 생긴다 |
| 효과 | 가독성 향상 · 분석 시간 단축 · **버그 감소** |
| 언어의 진화 | 새로 이해한 내용을 표현할 용어를 찾아 **다시 공통 언어로** 만든다 |
| 국내 개발자의 난점 | **영어** — 도메인 용어를 영어로 옮기는 노력이 필요 |

## 나쁜 예 — 도메인 용어를 쓰지 않은 코드

```java
// ❌ 개발자가 전체 상태를 6단계로 보고 기계적으로 표현
public enum OrderState {
    STEP1, STEP2, STEP3, STEP4, STEP5, STEP6
}

public class Order {
    public void changeShippingInfo(ShippingInfo newShippingInfo) {
        verifyStep1OrStep2();
        setShippingInfo(newShippingInfo);
    }

    private void verifyStep1OrStep2() {
        if (state != OrderState.STEP1 && state != OrderState.STEP2) {
            throw new IllegalStateException("already shipped");
        }
    }
}
```

실제 주문 상태는 **'결제 대기 중', '상품 준비 중', '출고 완료됨', '배송 중', '배송 완료됨', '주문 취소됨'** 인데, 코드는 이를 `STEP1~STEP6`로 뭉개버렸다.

> [!danger] 무엇이 문제인가
> - 배송지 변경은 **'출고 전'에 가능**한데, `verifyStep1OrStep2`라는 이름에는 **중요한 도메인 규칙이 드러나지 않는다.** 그저 STEP1과 STEP2인지 검사만 할 뿐이다.
> - 코드를 이해하려면 **STEP1 = '결제 대기 중', STEP2 = '상품 준비 중'** 임을 따로 알아야 한다.
> - 회의에서 전문가가 **'출고 전'** 이라고 말하면, 개발자는 머릿속으로 **"출고 전은 STEP1과 STEP2"** 라고 **번역**해야 한다.

```
   [ 나쁜 코드 ]
   도메인 전문가 ──"출고 전"──▶ 개발자 ──머릿속 번역──▶ STEP1, STEP2 ──▶ 코드
                                        ▲ 매번 발생하는 해석 비용 + 버그 위험

   [ 좋은 코드 ]
   도메인 전문가 ──"출고 전"──▶ 개발자 ──그대로──▶ PAYMENT_WAITING, PREPARING
                                        ▲ 해석 과정 없음
```

## 좋은 예 — 도메인 용어를 코드에 반영

```java
public enum OrderState {
    PAYMENT_WAITING, PREPARING, SHIPPED, DELIVERING, DELIVERY_COMPLETED;
}
```

`STEP1, STEP2, STEP3`이 아닌 `PAYMENT_WAITING`, `PREPARING`, `SHIPPED` 같이 **도메인에서 사용하는 용어를 최대한 코드에 반영**하면:

- **출고(SHIPPED) 전 = 결제 대기 중(PAYMENT_WAITING)이나 상품 준비 중(PREPARING)** 임을 바로 이해할 수 있다.
- 코드를 도메인 용어로 해석하거나, 도메인 용어를 코드로 해석하는 **과정이 줄어든다.**

> [!tip] 세 가지 효과
> 1. **가독성 향상** → 코드를 분석하고 이해하는 시간 단축
> 2. 최대한 도메인 용어로 도메인 규칙을 작성하게 됨
> 3. **(의미를 변환하는 과정에서 발생하는) 버그 감소**

## 유비쿼터스 언어 (Ubiquitous Language)

> [!important] 에릭 에반스의 정의
> 에릭 에반스는 『도메인 주도 설계』에서 **언어의 중요함을 강조하기 위해 '유비쿼터스 언어'** 라는 용어를 사용했다.
>
> 전문가, 관계자, 개발자가 **도메인과 관련된 공통의 언어를 만들고**
> 이를 **대화, 문서, 도메인 모델, 코드, 테스트 등 모든 곳에서 같은 용어로 사용**한다.

| 얻는 것 | 설명 |
|---------|------|
| 소통 명확화 | 소통 과정에서 발생하는 **용어의 모호함**을 줄인다 |
| 해석 비용 제거 | 개발자는 도메인과 코드 사이에서 **불필요한 해석 과정**을 줄인다 |

### 언어는 계속 진화한다

시간이 지날수록 도메인에 대한 이해가 높아진다.

```
  새로운 이해 ──▶ 잘 표현할 용어 발굴 ──▶ 공통 언어로 승격 ──▶ 코드·문서에 반영
        ▲                                                              │
        └──────────────────  최신 모델이 산출물에 유지됨  ◀─────────────┘
```

새로 발견한 용어는 **코드나 문서에도 반영**해서 산출물에 **최신 모델**을 적용한다.
(→ [[도메인 모델 도출]]에서 `isShippingChangeable` → `verifyNotYetShipped`로 이름이 바뀐 사례가 바로 이것이다.)

## 국내 개발자의 현실적 어려움 — 영어

> [!warning] 도메인 용어를 영어로 옮기는 비용
> 클래스·필드·메서드 이름은 알파벳과 숫자로 작성하게 되므로, **도메인 용어를 영어로 해석하는 노력**이 필요하다.

| 어려움 | 예시 |
|--------|------|
| 의미를 명확히 전달하는 영단어를 찾기 힘듦 | — |
| 비슷한 의미의 영단어가 많아 뉘앙스 차이로 선택이 어려움 | '상태' → `state` vs `status` |
| 〃 | '종류' → `kind` vs `type` |
| 타협 | 이해하기 쉽게 발음대로 `gubun`(구분) 같은 이름을 쓰기도 한다 |

| Scenario/Keyword | Answer |
|-------------------|--------|
| "전문가·관계자·개발자의 공통 언어" | **유비쿼터스 언어** |
| "유비쿼터스 언어를 제안한 사람" | **에릭 에반스** |
| "유비쿼터스 언어를 쓰는 범위" | 대화·문서·**도메인 모델·코드·테스트 모두** |

| "`verifyStep1OrStep2` → 어떻게 고칠까" | `verifyNotYetShipped` 등 **도메인 용어 반영** |
| "도메인 용어 사용의 효과 3가지" | 가독성↑, 해석 과정↓, **버그↓** |
| "도메인 이해가 깊어지면?" | 새 용어를 찾아 **공통 언어·코드·문서에 반영** |
