# CQRS 장단점 (★★★)

#ddd #cqrs #concept

## Overview Table (한눈에 비교)

| 구분 | 내용 |
|------|------|
| **장점 ①** | **도메인 모델을 단순하게 유지**할 수 있다 |
| **장점 ②** | **조회 성능을 향상시키는 데 유리**하다 |
| **단점 ①** | **구현해야 할 코드가 더 많다** |
| **단점 ②** | **더 많은 구현 기술이 필요**하다 |

## 장점 ① — 도메인 모델을 단순하게 유지

> [!important]
> **명령 모델과 조회 모델을 구분하면 조회 성능을 위한 코드가 명령 모델에 없으므로
> 도메인 로직을 구현하는 데 집중**할 수 있다.
> 또한 **명령 모델에서 조회 관련 로직이 사라져 복잡도가 낮아진다.**

```
   [ 단일 모델 ]                    [ CQRS ]
   Order                            Order (명령)
    ├─ 도메인 로직                    └─ 도메인 로직만  ⭕
    ├─ 즉시/지연 로딩 전략
    ├─ N+1 회피 매핑                 OrderSummary (조회)
    └─ 통계 조회용 성능 코드           └─ 조회 최적화만  ⭕
         ▲ 복잡도 폭증
```

## 장점 ② — 조회 성능 향상에 유리

> [!tip]
> - **조회 단위로 캐시 기술을 적용**할 수 있다
> - **조회에 특화된 쿼리를 마음대로 사용**할 수도 있다
> - 캐시뿐만 아니라 **조회 전용 저장소를 사용하면 조회 처리량을 대폭 늘릴 수도 있다**
> - **조회 전용 모델을 사용하기 때문에 조회 성능을 높이기 위한 코드가 명령 모델에 영향을 주지 않는다**

## 단점 ① — 구현해야 할 코드가 더 많다

> [!warning]
> **단일 모델을 사용할 때 발생하는 복잡함 때문에 발생하는 구현 비용과
> 조회 전용 모델을 만들 때 발생하는 구현 비용을 따져봐야 한다.**

| 상황 | 판단 |
|------|------|
| **도메인이 복잡하거나 대규모 트래픽**이 발생하는 서비스 | **조회 전용 모델을 만드는 것이 향후 유지 보수에 유리** |
| **도메인이 단순하거나 트래픽이 많지 않은** 서비스 | 조회 전용 모델을 따로 만들 때 **얻을 이점이 있는지 따져봐야** 한다 |

## 단점 ② — 더 많은 구현 기술이 필요

> [!warning]
> **명령 모델과 조회 모델을 다른 구현 기술을 이용해서 구현하기도 하고,
> 경우에 따라 다른 저장소를 사용하기도 한다.**
> 또한 **데이터 동기화를 위해 메시징 시스템을 도입해야 할 수도 있다.**

```
   CQRS 도입 시 필요할 수 있는 기술
   ├─ 명령 모델: JPA / 하이버네이트
   ├─ 조회 모델: 마이바티스 / 네이티브 SQL
   ├─ 저장소: RDBMS + NoSQL
   └─ 동기화: 메시징 시스템 (Kafka, RabbitMQ) + 이벤트
```

## ★ 도입 판단 기준

> [!important] (p.352)
> **이러한 장단점을 고려해서 CQRS 패턴을 도입할지 여부를 결정해야 한다.**
>
> - **도메인이 복잡하지 않은데 CQRS를 도입하면 두 모델을 유지하는 비용만 높아지고 얻을 수 있는 이점은 없다.**
> - 반면에 **트래픽이 높은 서비스인데 단일 모델을 고집하면 유지 보수 비용이 오히려 높아질 수 있으므로 CQRS 도입을 고려**하자.

```
                  트래픽 높음
                       │
      단일 모델 고집    │    CQRS 도입 ⭕
      → 유지 보수 비용 ↑│
   도메인 ──────────────┼────────────── 도메인
   단순                 │              복잡
      CQRS 불필요 ❌     │    CQRS 도입 ⭕
      → 유지 비용만 ↑    │
                  트래픽 낮음
```

| 조건 | 판단 |
|------|------|
| 도메인 단순 + 트래픽 낮음 | **CQRS 불필요** — 유지 비용만 증가 |
| 도메인 복잡 | **CQRS 유리** — 도메인 로직에 집중 가능 |
| 트래픽 높음 | **CQRS 유리** — 단일 모델은 유지 보수 비용이 오히려 높아진다 |

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "CQRS의 두 장점" | **도메인 모델 단순 유지 / 조회 성능 향상 유리** |
| "장점 ①의 구체적 효과" | 조회 성능 코드가 명령 모델에 없어 **도메인 로직에 집중** |
| "장점 ②의 구체적 수단" | **조회 단위 캐시, 특화 쿼리, 조회 전용 저장소** |
| "CQRS의 두 단점" | **코드가 더 많다 / 더 많은 구현 기술 필요** |
| "동기화를 위해 도입할 수도 있는 것" | **메시징 시스템** |
| "도메인이 단순한데 도입하면?" | **유지 비용만 높아지고 이점 없음** |
| "트래픽이 높은데 단일 모델을 고집하면?" | **유지 보수 비용이 오히려 높아진다** |
| "도입 판단 기준 두 가지" | **도메인 복잡도 / 트래픽 규모** |
