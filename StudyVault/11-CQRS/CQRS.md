# CQRS (★★★)

#ddd #cqrs #command-model #read-model #concept

## Overview Table (한눈에 비교)

| 항목 | 핵심 내용 |
|------|-----------|
| 이름 | **Command Query Responsibility Segregation** |
| 정의 | **상태를 변경하는 명령(Command)을 위한 모델**과 **상태를 제공하는 조회(Query)를 위한 모델**을 **분리**하는 패턴 |
| 적합 대상 | **복잡한 도메인** — 도메인이 복잡할수록 두 기능이 다루는 데이터 범위 차이가 크다 |
| 명령 모델의 범위 | 주로 **한 애그리거트**의 상태를 변경 |
| 조회 모델의 범위 | **두 개 이상의 애그리거트**가 필요할 때가 많다 |
| 이점 ① | 각 모델에 **맞는 구현 기술을 선택**할 수 있다 |
| 이점 ② | **서로 다른 데이터 저장소**를 사용할 수 있다 |
| 저장소 동기화 | **이벤트** 활용 (10장) |
| ★ 조회 모델 | **응용 서비스가 없어도 된다** |
| 필수 기술 | **따로 존재하지 않는다** |

## 명령과 조회

시스템이 제공하는 기능은 크게 두 가지로 나눌 수 있다.

| 구분 | 예 | 구현 방식 |
|------|-----|-----------|
| **상태를 변경하는 기능** | 새로운 주문 생성, 배송지 정보 변경, 회원 암호 변경 | **저장하고 있는 데이터를 변경** |
| **상태 정보를 조회하는 기능** | 주문 상세 내역 보기, 게시글 목록 보기, 회원 정보 보기, 판매 통계 보기 | **필요한 데이터를 읽어와 UI로 표시** |

> [!important] 범위의 불일치
> 도메인 모델 관점에서 **상태 변경 기능은 주로 한 애그리거트의 상태를 변경**한다.
> 반면에 **조회 기능에 필요한 데이터를 표시하려면 두 개 이상의 애그리거트가 필요할 때가 많다.**
>
> **상태를 변경하는 범위와 상태를 조회하는 범위가 정확하게 일치하지 않기 때문에 단일 모델로 두 기능을 구현하면 모델이 불필요하게 복잡해진다.**

## CQRS 패턴

```
                    사용자 인터페이스
                    ┌─────────────┐
                    │             │
        조회 ◀──────┤             ├──────▶ 명령
          │         └─────────────┘          │
          ▼                                   ▼
   ┌─────────────┐                    ┌─────────────┐
   │  조회 모델   │                    │  명령 모델   │
   │ (Query)     │                    │ (Command)   │
   │             │                    │ 도메인 로직  │
   └─────────────┘                    └─────────────┘
          │                                   │
          └────────────  DB  ─────────────────┘
```

> [!important]
> **CQRS는 Command Query Responsibility Segregation의 약자로,
> 상태를 변경하는 명령(Command)을 위한 모델과 상태를 제공하는 조회(Query)를 위한 모델을 분리하는 패턴**이다.

## 왜 복잡한 도메인에 적합한가

> **CQRS는 복잡한 도메인에 적합**하다. **도메인이 복잡할수록 명령 기능과 조회 기능이 다루는 데이터 범위에 차이가 난다.**
> 이 두 기능을 **단일 모델로 처리하면 조회 기능의 로딩 속도를 위해 모델 구현이 필요 이상으로 복잡해진다.**

**예: 온라인 쇼핑의 다양한 차원의 주문/판매 통계**

| 접근 | 결과 |
|------|------|
| **JPA 기반 단일 도메인 모델** | 통계 값을 빠르게 조회하기 위해 **JPA 관련 다양한 성능 기능을 모델에 적용**해야 한다 |
| **CQRS 적용** | **통계를 위한 조회 모델을 별도로 만들기 때문에 조회 기능 때문에 도메인 모델이 복잡해지는 것을 막는다** |

## 이점 ① — 모델별 구현 기술 선택

> **CQRS를 사용하면 각 모델에 맞는 구현 기술을 선택할 수 있다.**

```
   [ 표현 계층 ]
   컨트롤러                              컨트롤러
       │                                    │
   응용 서비스                          (DAO 직접 사용)
       │                                    │
   도메인 모델                            인프라
       │                              (MyBatis DAO 구현)
   인프라 (JPA 리포지터리 구현)                │
       │                                    │
       └──────────────  DB  ────────────────┘
```

| 모델 | 적합한 기술 | 이유 |
|------|-------------|------|
| **명령 모델** | **JPA** | 객체 지향에 기반해서 **도메인 모델을 구현하기에 적당** |
| **조회 모델** | **마이바티스(MyBatis)** | **DB 테이블에서 SQL로 데이터를 조회할 때 좋다** |

> [!important] ★ 조회 모델에는 응용 서비스가 없어도 된다
> **단순히 데이터를 읽어와 조회하는 기능은 응용 로직이 복잡하지 않기 때문에 컨트롤러에서 바로 DAO를 실행해도 무방**하다.
> 물론 **데이터를 표현 영역에 전달하는 과정에서 몇 가지 로직이 필요하다면 응용 서비스를 두면 된다.**
> (→ 6장 [[조회 전용 기능과 응용 서비스]]와 같은 결론)

## 모델 설계 차이 (그림 11.4)

| 명령 모델 | 조회 모델 |
|-----------|-----------|
| `Order`, `OrderLine`, `Orderer`, `ShippingInfo`, `Product`, `Receiver` … | **`OrderSummary`** (단일 데이터 타입) |
| **객체 지향에 기반해 도메인 모델을 구현** | **주문 목록을 제공할 때 필요한 정보를 담고 있는 데이터 타입** |
| **상태를 변경하는 도메인 로직 수행에 초점** | **화면에 보여줄 데이터를 조회하는 데 초점** |

> [!note] 이미 5장에서 다뤘다
> 명령 모델과 조회 모델이 **같은 구현 기술을 사용할 수도 있다.**
> 5장의 **동적 인스턴스로 사용할 클래스**와 **`@Subselect`를 적용한 클래스**가 바로 **조회 모델**에 해당한다.
> → [[동적 인스턴스를 이용한 조회]], [[하이버네이트 Subselect 사용]]

## 이점 ② — 서로 다른 데이터 저장소

> **명령 모델과 조회 모델이 서로 다른 데이터 저장소를 사용할 수도 있다.**
> 예: 명령 모델은 **트랜잭션을 지원하는 RDBMS**, 조회 모델은 **조회 성능이 좋은 NoSQL**

```
   [ 명령 모델 ]                    [ 조회 모델 ]
   JPA 리포지터리                    DAO
        │                              │
      RDBMS  ──── 이벤트로 동기화 ───▶  NoSQL
```

> [!important] 동기화는 이벤트로
> **두 데이터 저장소 간 데이터 동기화는 10장에서 배운 이벤트를 활용해서 처리**한다.
> **명령 모델에서 상태를 변경하면 이에 해당하는 이벤트가 발생하고,
> 그 이벤트를 조회 모델에 전달해서 데이터를 동기화**한다.

| 동기화 요구 | 방법 | 대가 |
|-------------|------|------|
| **데이터가 바뀌자마자 바로 반영**해야 한다 | **동기 이벤트 + 글로벌 트랜잭션** | **전반적인 성능(응답 속도) 저하** |
| 일정 지연을 허용한다 | **비동기 이벤트** | 최종 일관성 |

> [!tip] 필수 기술은 없다
> **CQRS 패턴을 적용하기 위해 사용해야 할 필수 기술이 따로 존재하는 것은 아니다.**
> **JPA만 사용해서** 명령 모델과 조회 모델을 구현할 수도 있고,
> **명령 모델은 JPA로 구현하고 조회 모델은 직접 SQL을 사용**해서 구현할 수도 있다.

## §11.2.1 웹과 CQRS

> **일반적인 웹 서비스는 상태를 변경하는 요청보다 상태를 조회하는 요청이 많다.**
> 온라인 쇼핑몰은 **주문 요청보다 카탈로그·상품 상세 조회 요청이 비교할 수 없을 정도로 많고**,
> 게시판도 **한번 등록한 게시글을 수십에서 수백만 번 조회**한다.

**조회 성능을 높이기 위해 흔히 쓰는 기법**

| 기법 | 설명 |
|------|------|
| **쿼리 최적화** | 쿼리 실행 속도 자체를 높인다 |
| **메모리 캐싱** | 조회 데이터를 캐싱해 응답 속도를 높인다 |
| **조회 전용 저장소** | 따로 사용한다 |

> [!important] ★ 사실 이미 CQRS를 하고 있다
> **이렇게 조회 성능을 높이기 위해 다양한 기법을 사용하는 것은 결과적으로 CQRS를 적용하는 것과 같은 효과**를 만든다.
>
> - 메모리에 캐싱하는 데이터는 DB 데이터를 그대로 저장하기보다 **화면에 맞는 모양으로 변환한 데이터를 캐싱할 때 성능에 더 유리**하다. 즉 **조회 전용 모델을 캐시하는 것**이다.
> - **쿼리를 최적화한다는 것은 조회 화면에 보여줄 데이터를 빠르게 읽어올 수 있도록 쿼리를 작성하는 것**이다.
>
> **대규모 트래픽이 발생하는 웹 서비스는 알게 모르게 CQRS를 적용하게 된다. 단지 명시적으로 명령 모델과 조회 모델을 구분하지 않을 뿐이다.**

> [!tip] 그렇다면 명시적으로 구분하라
> **조회 속도를 높이기 위해 별도 처리를 하고 있다면 명시적으로 명령 모델과 조회 모델을 구분하자.**
> 이를 통해:
> - **조회 기능 때문에 명령 모델이 복잡해지는 것을 막을 수 있고**
> - **명령 모델에 관계없이 조회 기능에 특화된 구현 기법을 보다 쉽게 적용**할 수 있다

## Exam/Test Patterns (시험 빈출 패턴)

| Scenario/Keyword | Answer |
|-------------------|--------|
| "CQRS의 풀네임" | **Command Query Responsibility Segregation** |
| "CQRS의 정의" | **명령 모델과 조회 모델을 분리**하는 패턴 |
| "CQRS가 적합한 도메인" | **복잡한 도메인** |
| "명령/조회의 데이터 범위" | 명령 = **한 애그리거트** / 조회 = **두 개 이상** |
| "명령 모델에 적합한 기술" | **JPA** (객체 지향 도메인 모델) |
| "조회 모델에 적합한 기술" | **마이바티스** (SQL 조회) |
| "조회 모델에 응용 서비스가 필요한가?" | **없어도 된다** (컨트롤러에서 바로 DAO) |
| "서로 다른 저장소 동기화 방법" | **이벤트** |
| "실시간 동기화의 대가" | **동기 이벤트 + 글로벌 트랜잭션 → 성능 저하** |
| "CQRS의 필수 기술" | **없다** |
| "웹 서비스의 요청 비율" | **조회 ≫ 변경** |
| "캐싱·쿼리 최적화는?" | **사실상 CQRS를 적용하는 것과 같은 효과** |
| "명시적으로 구분하면 얻는 것" | **명령 모델 복잡도 방지 + 조회 특화 기법 적용 용이** |
