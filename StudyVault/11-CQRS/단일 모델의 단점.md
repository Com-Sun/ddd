## 문제 상황 — 주문 상세 조회 화면

```
   [ 주문 상세 조회 화면 ]
   ┌────────────────────────────────┐
   │ 주문번호 / 주문일시 / 주문상태   │ ← Order 애그리거트
   │ 주문자: 홍길동 (user1)          │ ← Member 애그리거트
   │ 상품명: 스프링 부트 책           │ ← Product 애그리거트
   │ 배송지 / 총 결제 금액            │ ← Order 애그리거트
   └────────────────────────────────┘
```

> 조회 화면 특성상 **조회 속도가 빠를수록 좋은데 여러 애그리거트의 데이터가 필요하면 구현 방법을 고민해야 한다.**

## 두 가지 참조 방식 모두 고민이 생긴다

| 방식 | 고민 |
|------|------|
| **ID 참조** (3장 권장) | **JPA의 즉시 로딩·지연 로딩 방식 같은 쿼리 관련 최적화 기능을 사용할 수 없다.** 한 번의 DB 쿼리로 조회 화면에 필요한 데이터를 읽어올 수 없어 **조회 성능에 문제**가 생길 수 있다 |
| **직접 참조** | **조회 화면 특성에 따라 같은 연관도 즉시 로딩이나 지연 로딩으로 다르게 처리해야 한다** |
| 공통 | 조회 기능 구현 시 **DBMS가 제공하는 전용 기능이 필요하면 JPA의 네이티브 쿼리**를 사용해야 할 수도 있다 |

## ★ 근본 원인

> [!important] (p.345)
> **이런 고민이 발생하는 이유는 시스템 상태를 변경할 때와 조회할 때 단일 도메인 모델을 사용하기 때문**이다.
>
> 객체 지향으로 도메인 모델을 구현할 때 주로 사용하는 **ORM 기법은
> `Order#cancel()`이나 `Order#changeShippingInfo()` 기능처럼 도메인 상태를 변경하는 데는 적합**하지만,
> **주문 상세 조회 화면처럼 여러 애그리거트에서 데이터를 가져와 출력하는 기능을 구현하기에는
> 고려할 게 많아서 구현을 복잡하게 만드는 원인**이 된다.

```
   [ 단일 모델 ]
   Order 애그리거트
     ├─ cancel()                    ← 상태 변경에 적합  ⭕
     ├─ changeShippingInfo()        ← 상태 변경에 적합  ⭕
     └─ 조회 화면용 데이터 조합       ← 고려할 게 많다   ❌
             ├─ 로딩 전략 결정
             ├─ N+1 회피
             └─ 네이티브 쿼리 필요?
```

| Scenario/Keyword | Answer |
|-------------------|--------|
| "주문 상세 조회에 필요한 애그리거트" | **Order + Product + Member** |
